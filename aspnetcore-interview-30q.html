ASP.NET Core Interview – 30 Questions

1. Hosting, Startup, and the Host

This is where the interview usually opens – not to trick you, but to see whether you know what your own Program.cs actually does.

Q1. Walk me through what happens between CreateBuilder and app.Run()

Program.cs has two distinct phases, and the line builder.Build() is the boundary. Before it, you're configuring services: WebApplication.CreateBuilder(args) sets up configuration, logging, and the DI container, and you add your registrations to builder.Services. builder.Build() then locks that container and produces the WebApplication. After it, you're building the request pipeline: each app.UseSomething() appends middleware, and app.Run() starts Kestrel and blocks until shutdown.

The reason this matters: the two phases can't be interleaved. You can't register a service after Build(), and you can't add middleware before it. Knowing the boundary explains half the "why doesn't this work" bugs juniors hit.

Q2. Why does registering a service after builder.Build() throw?

Because Build() finalizes the service collection into an immutable service provider. Up to that point builder.Services is a mutable IServiceCollection – just a list of descriptors. Build() reads that list, validates it, and produces the root IServiceProvider that will resolve everything for the app's lifetime. Mutating registrations after the container is built would mean some consumers see a service and others don't, depending on timing, so the framework forbids it.

Practical takeaway: everything that needs to be injectable has to be registered before Build(). If you want to add a service later, that's usually a sign you need a factory or an options-configured registration instead.

Q3. Kestrel, IIS, and reverse proxies – how is your app actually served?

Kestrel is the built-in, cross-platform HTTP server that actually runs your ASP.NET Core app – it owns the sockets and turns raw HTTP into an HttpContext. It can run as an edge server facing the internet directly, or behind a reverse proxy like IIS, Nginx, or YARP that handles TLS termination, load balancing, and static content.

The detail interviewers want: behind a proxy, the proxy talks to Kestrel over localhost, and you need UseForwardedHeaders so the app sees the real client IP and scheme instead of the proxy's. On Windows/IIS, the ASP.NET Core Module forwards requests into Kestrel – IIS isn't running your app, it's fronting Kestrel. Getting this wrong is why "HTTP internally but HTTPS externally" redirect loops happen.

Q4. What is the Generic Host, and why does a web app use the same host as a Worker Service?

The Host is the object that owns your app's lifetime: the DI container, configuration, logging, and the set of IHostedServices that start and stop with the app. WebApplication is built on this same generic host – a web app is just a host that also runs Kestrel and a request pipeline. A Worker Service uses the identical host without the web server.

Why it matters: everything you know about DI, configuration, and hosted services transfers directly between a web API and a background worker. BackgroundService, options binding, logging – all host features, not web features.

2. The Middleware Pipeline

The single most reliable ASP.NET Core topic in any interview. Expect to explain order, and expect at least one "why is this broken" scenario.

Q5. What is middleware, and how does the pipeline execute a request?

Middleware is a component in the request pipeline that gets a RequestDelegate pointing at the next component. Each one runs some logic, then decides whether to call next() to pass control down the chain – or to short-circuit and return. On the way back, execution unwinds in reverse, so code after await next() runs as the response bubbles up. That's the onion model. 

app.Use(async (context, next) =>
{
    // runs on the way IN
    await next(context);
    // runs on the way OUT (response is coming back up)
});

Q6. Give me the correct middleware order, and explain why it matters

Order is behavior, not style. A typical correct sequence:

  1. Exception handler (wraps everything below)
  2. HSTS, HTTPS redirection
  3. Static files
  4. UseRouting
  5. UseCors
  6. UseAuthentication
  7. UseAuthorization
  8. Endpoints

The reasoning is what they're grading: authentication before authorization because you can't decide what a user may do until you know who they are. Routing before auth so the framework knows which endpoint – and which auth requirements – apply. CORS before auth so preflight OPTIONS requests get their headers before anything rejects them. Classic bug: CORS after auth → "missing CORS header" errors that look like a framework fault but are pure ordering.

Q7. Difference between Use, Run, and Map?

  • Use – adds middleware that can call next (the normal case).
  • Run – terminal middleware, never calls next; ends the pipeline.
  • Map – branches the pipeline by request path into a separate sub-pipeline. 
app.Map("/health", branch =>
    branch.Run(async ctx => await ctx.Response.WriteAsync("OK")));

Point to land: if you accidentally put a Run in the middle of your pipeline, everything after it silently never runs.

Q8. How do you short-circuit the pipeline, and what's the bug when you write to the response after next()?

Short-circuit by not calling next() – write a response (or set a status code) and return. That's how auth middleware rejects with a 401 without running the endpoint.

The bug: once downstream middleware has started writing the body, headers are already sent. Setting a status code or header in the unwind phase after await next() throws InvalidOperationException: response has already started. Response-mutating logic must happen before next (or via OnStarting), or you must buffer the response. 

app.Use(async (context, next) =>
{
    // Safe: set headers BEFORE next writes the body
    context.Response.OnStarting(() =>
    {
        context.Response.Headers["X-Trace-Id"] = trace;
        return Task.CompletedTask;
    });
    await next(context);
    // Unsafe here: context.Response.StatusCode = 500; // headers already sent
});

Q9. Where does exception-handling middleware go, and what changed in .NET 10?

First, or close to it – middleware only catches exceptions from components registered after it. Put UseExceptionHandler (or your IExceptionHandler pipeline) at the top so it wraps the entire request.

.NET 10: the exception handler middleware no longer writes diagnostic logs for exceptions an IExceptionHandler handled, and there's a new ExceptionHandlerOptions.SuppressDiagnosticsCallback to control that per exception. Before, a handled exception could still spam logs as if unhandled. 

app.UseExceptionHandler(new ExceptionHandlerOptions
{
    SuppressDiagnosticsCallback = ctx => ctx.Exception is MyKnownException
});

Q10. Your custom middleware needs a scoped service. Why can't you inject it in the constructor?

Convention-based middleware is instantiated once at startup and reused for every request – effectively a singleton. Injecting a scoped service (e.g. DbContext) into its constructor captures one instance for the app's whole lifetime: a captive dependency.

Fix: inject scoped services into InvokeAsync, where they're resolved from the current request's scope on every call. 

public class AuditMiddleware(RequestDelegate next)
{
    public async Task InvokeAsync(HttpContext context, IAuditService audit) // resolved per request
    {
        await audit.RecordAsync(context.Request.Path);
        await next(context);
    }
}

3. Dependency Injection Internals

DI is the framework feature candidates use most and understand least. These separate "I call AddScoped" from "I know what the container does with it."

Q11. Transient vs Scoped vs Singleton – what does each mean for state and concurrency?

  • Transient – new instance every resolve. Lightweight, stateless services.
  • Scoped – one per scope = one per HTTP request. Shared within a request, isolated between requests (e.g. DbContext).
  • Singleton – one for the app's lifetime, shared across all requests and threads. Stateless, thread-safe services and caches.

Concurrency angle: a singleton must be thread-safe; a scoped service must not be captured by a longer-lived one. Lifetime is a correctness decision, not style.

Q12. You inject a scoped service into a singleton. What happens, and how does the container catch it?

Captive dependency. The singleton holds the scoped service forever – one DbContext, one change tracker, shared across every request. Thread-safety violations, stale data, unbounded growth.

With scope validation on – default in Development – the container validates the graph at startup and throws if a singleton depends on a scoped service. In Production validation is off by default (startup performance), which is why this passes locally and blows up in prod. Fix: inject IServiceScopeFactory and create a scope per unit of work.

Q13. You register the same interface three times. What does resolving it give you?

Resolving INotifier gives the last one registered (last-wins). Resolving IEnumerable<INotifier> gives all of them, in registration order – the built-in pattern for "run every handler". 

builder.Services.AddScoped<INotifier, EmailNotifier>();
builder.Services.AddScoped<INotifier, SmsNotifier>();

public class Alerts(IEnumerable<INotifier> notifiers) { /* gets both */ }

Q14. What problem do keyed services solve?

Keyed services (.NET 8+) register multiple implementations of the same interface under distinct keys and resolve a specific one by key – instead of injecting IEnumerable<T> and filtering, or hand-writing a factory. 

builder.Services.AddKeyedScoped<IPaymentGateway, StripeGateway>("stripe");
builder.Services.AddKeyedScoped<IPaymentGateway, PayPalGateway>("paypal");

public class Checkout([FromKeyedServices("stripe")] IPaymentGateway gateway) { }

Trade-off: keys reintroduce stringly-typed coupling. Use them for genuine "pick one of N by name" cases (payment providers, cache backends); prefer distinct interfaces when implementations are really different roles.

Q15. Who disposes the services the container creates, and when?

The container disposes what it created, tied to the scope that created it:

  • Scoped disposables → disposed when the scope ends (end of request).
  • Transient disposables resolved from a scope → tracked and disposed with that scope (not immediately!).
  • Singletons → disposed when the root provider is disposed (app shutdown).

Catches: AddSingleton(myInstance) – the container does not dispose it; you own it. And a transient disposable resolved from the root provider lives until shutdown – a slow memory leak if you resolve many from a singleton.

4. Configuration and Options

Tests whether you've deployed across environments or only run on localhost.

Q16. Two sources set the same config key. Which wins, and why?

Configuration is layered; later providers override earlier ones. Default order from CreateBuilder:

  1. appsettings.json
  2. appsettings.{Environment}.json
  3. User secrets (Development only)
  4. Environment variables
  5. Command-line arguments (wins over everything)

Ship safe defaults in appsettings.json, override per environment without editing files – e.g. a container sets ConnectionStrings__Default as env var. "My setting isn't taking effect" = something later in the chain overrides it.

Q17. IOptions vs IOptionsSnapshot vs IOptionsMonitor – when do you use each?

  • IOptions<T> – singleton, computed once, never reloads.
  • IOptionsSnapshot<T> – scoped, recomputed per request; picks up changes between requests. Can't inject into a singleton.
  • IOptionsMonitor<T> – singleton with current value + change callback; reloads on the fly. Use inside singletons and background services.

Trap: injecting IOptionsSnapshot into a BackgroundService or singleton fails or captures a stale scope. For long-lived services needing fresh config → IOptionsMonitor.

Q18. How do you make a bad configuration fail at startup instead of at 3am?

Validate options and force validation at startup. Binding alone doesn't validate – a missing value binds to null and blows up on first use. 

builder.Services.AddOptions<SmtpOptions>()
    .Bind(builder.Configuration.GetSection("Smtp"))
    .ValidateDataAnnotations()
    .Validate(o => o.Port > 0, "SMTP port must be set")
    .ValidateOnStart();

Principle: fail fast and loud at deploy time when a human is watching. Turns a production incident into a failed deployment.

Q19. How does the app pick appsettings.Production.json, and where does the environment name come from?

From the ASPNETCORE_ENVIRONMENT (or DOTNET_ENVIRONMENT) environment variable. The host reads it at startup and layers appsettings.{Environment}.json on top of appsettings.json. If unset, default is Production.

Same value drives app.Environment.IsDevelopment() – one setting controls config files, error pages, and your own environment branches.

5. Filters and Model Binding

The layer above middleware – the part of the pipeline that understands actions, arguments, and results.

Q20. Middleware or a filter – how do you decide?

Middleware runs on every request and sees only raw HttpContext – no actions, model binding, or ModelState. Filters run inside the MVC/endpoint layer, after routing and model binding, with action-aware context: bound arguments, selected action, result about to be returned.

Rule: app-wide cross-cutting concerns that don't need action details (logging, compression, CORS, exception handling) → middleware. Concerns that inspect action arguments or short-circuit a specific endpoint's result (validation, action-level auth policies, response shaping) → filters.

Q21. What's the filter execution order, and where does short-circuiting happen?

  1. Authorization filters
  2. Resource filters
  3. Model binding
  4. Action filters (before / after the action)
  5. Exception filters
  6. Result filters (around result execution)

Any filter can short-circuit: an authorization filter that sets a result stops everything below – that's how [Authorize] blocks an action.

Nuance: filters of the same type run outer-to-inner on the way in and inner-to-outer on the way out; scope (global / controller / action) plus Order decides the sequence.

Q22. Action filters vs endpoint filters – what's the Minimal API equivalent?

Action filters belong to MVC/controllers. Endpoint filters (.NET 7+) are the Minimal API counterpart – they wrap the route handler, run after model binding, and can inspect/modify bound arguments and the result. 

app.MapPost("/orders", (Order o) => Results.Ok(o))
   .AddEndpointFilter(async (ctx, next) =>
   {
       // runs after binding, before the handler
       var result = await next(ctx);
       return result;
   });

Q23. How does model binding decide where to read a parameter from?

Simple types bind from route values, then query string. Complex types: with [ApiController] (and in minimal APIs) → request body as JSON; in a plain MVC controller → form fields. Explicit attributes: [FromRoute], [FromQuery], [FromBody], [FromHeader], [FromForm], [FromServices].

Gotcha: only one parameter can bind from the body – the body is a forward-only stream read once. Two [FromBody] params → the second gets nothing.

Q24. In .NET 10, how do you validate input in a Minimal API without FluentValidation?

.NET 10 added built-in validation: call AddValidation() and the framework wires an endpoint filter that validates using DataAnnotations attributes – which now also work on record types. 

builder.Services.AddValidation();

app.MapPost("/products",
    (Product p) => Results.Ok(p)); // validated automatically

public record Product([Required] string Name, [Range(1, 1000)] int Quantity);

On failure: 400 with problem details, customizable via IProblemDetailsService. For cross-field or complex conditional rules, FluentValidation is still the better tool.

6. Request Lifecycle and Background Work

The senior end of the round – threads, context, lifetime.

Q25. What is HttpContext, what's its lifetime, and why is capturing it a bug?

HttpContext is the per-request object holding headers, user, request-scoped service provider, body streams. Lifetime = exactly one request: created when Kestrel accepts the request, disposed when the response completes. Not thread-safe, not valid after the request ends.

Stashing it (or its User/Request) in a field, static, or closure that runs later (fire-and-forget, background continuation) → ObjectDisposedException or garbage. Copy the values you need while the request is alive, pass those instead.

Q26. Within one request, does everything run on one thread? What happens across an await?

No. On an await of real I/O, the thread is released to the pool, and the continuation may resume on a different thread. That's why async scales.

ASP.NET Core has no SynchronizationContext (unlike old ASP.NET): no "UI thread" to marshal back to, ConfigureAwait(false) isn't needed for correctness in app code, and anything assuming thread affinity ([ThreadStatic], same-thread locks) is broken. Request state lives in DI or HttpContext.Items, not on the thread.

Q27. You need the current user inside a singleton service. How, and what's the catch?

Inject IHttpContextAccessor and read .HttpContext when needed. Safe from a singleton because it doesn't capture the context – it resolves the current one on each access via an AsyncLocal.

Catches: returns null with no active request (background service, startup) – guard for it; small perf cost from AsyncLocal; must register with AddHttpContextAccessor(). Cleaner where possible: pass user info as a parameter from the request-scoped layer.

Q28. An unauthenticated API call returns 401 in .NET 10 where it used to redirect to login. What changed?

.NET 10 cookie authentication change: requests to known API endpoints now return 401/403 instead of a 302 to the login page.

How it decides: a new IApiEndpointMetadata marker, applied automatically to [ApiController] actions, minimal APIs that read/write JSON, endpoints using TypedResults, and SignalR. To get the old redirect, override OnRedirectToLogin.

Q29. Your BackgroundService needs a DbContext. Why is injecting it a trap, and how does shutdown work?

BackgroundService is a singleton; DbContext is scoped. Constructor injection = captive dependency: one context forever, change tracker growing unbounded. Inject IServiceScopeFactory and create a fresh scope per unit of work: 

public class Worker(IServiceScopeFactory scopeFactory) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            using var scope = scopeFactory.CreateScope();
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
            // fresh, short-lived context per iteration
            await Task.Delay(1000, stoppingToken);
        }
    }
}

Shutdown: the host signals stoppingToken; your loop should observe it and exit within the shutdown timeout (graceful shutdown). Ignore it and in-flight work is killed when the timeout expires.

Q30. Walk me through the full journey of a request, from the socket to your endpoint

  1. Kestrel accepts the TCP connection, parses HTTP into an HttpContext, allocates a request-scoped IServiceProvider.
  2. Request enters the middleware pipeline in registration order – exception handling, HTTPS, static files, …
  3. UseRouting matches an endpoint; UseAuthentication / UseAuthorization establish and check identity for it.
  4. At the endpoint, model binding fills your parameters; the filter / endpoint-filter pipeline runs around the handler.
  5. Your handler executes, resolving scoped services from the request's provider.
  6. Result is written, execution unwinds back up the middleware in reverse, and the request scope is disposed – releasing scoped services and the DbContext.

If you can narrate this, every earlier question has a home in the story.
