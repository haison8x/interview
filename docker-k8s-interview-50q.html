Docker & Kubernetes Interview – 50 Questions

1. Docker Fundamentals

Q1. What is the difference between a container and a virtual machine?

A VM virtualises hardware: each VM runs its own full guest kernel on a hypervisor. A container virtualises the operating system: it is just a process on the host, isolated with Linux namespaces (what it can see – PIDs, network, mounts, users) and constrained with cgroups (what it can use – CPU, memory, IO). All containers share the host kernel.

Consequences: containers start in milliseconds and are megabytes rather than gigabytes, but isolation is weaker – a kernel exploit affects every container on the host. That is why multi-tenant platforms sometimes add a sandbox layer (gVisor, Kata Containers, Firecracker microVMs). It also means a Linux container needs a Linux kernel; on Windows/macOS, Docker Desktop runs a small Linux VM underneath.

Q2. Image vs container – and what are layers?

An image is a read-only template: an ordered stack of filesystem layers plus metadata (entrypoint, env, exposed ports). A container is a running (or stopped) instance of an image, with a thin writable layer on top.

Each Dockerfile instruction that changes the filesystem (RUN, COPY, ADD) produces a layer. Layers are content-addressed and shared: ten containers from the same image share the same read-only layers on disk. Writes go to the container's layer via copy-on-write – modifying a file from a lower layer copies it up first. That is also why deleting a file in a later layer does not shrink the image: the bytes are still in the earlier layer.

Q3. What is the difference between CMD and ENTRYPOINT?

ENTRYPOINT defines the executable that always runs; CMD provides default arguments (or a default command if there is no ENTRYPOINT). Arguments to docker run image ... replace CMD, not ENTRYPOINT (that needs --entrypoint). 

ENTRYPOINT ["dotnet", "MyApi.dll"]
CMD ["--urls", "http://+:8080"]   # overridable defaults

The part that matters in production is exec form vs shell form. ENTRYPOINT ["app"] (exec form) runs your process as PID 1. ENTRYPOINT app (shell form) runs /bin/sh -c app, so the shell is PID 1 and your app never receives SIGTERM – see Q12.

Q4. Docker, containerd, runc, OCI – who does what? Do Docker images still work on Kubernetes?

  • OCI – the standards for image format and runtime, so images are portable across tools.
  • runc – low-level runtime that actually creates the namespaces/cgroups and starts the process.
  • containerd (or CRI-O) – high-level runtime: pulls images, manages snapshots, supervises containers.
  • Docker Engine – developer tooling (CLI, BuildKit, networks, compose) built on top of containerd.

Kubernetes talks to runtimes through the CRI. The dockershim adapter was removed in Kubernetes 1.24, so nodes run containerd or CRI-O directly. Images built with Docker are OCI images and run unchanged – what broke was only things that depended on the Docker socket on the node (e.g. Docker-in-Docker builds, some monitoring agents).

Q5. Why is using the latest tag in production a bad idea? Tags vs digests.

A tag is a mutable pointer; latest is just the default tag name, not "the newest". Two nodes pulling myapp:latest an hour apart can run different code, rollbacks become impossible to reason about, and with imagePullPolicy: IfNotPresent a node may keep an old cached copy.

Use immutable, meaningful tags (version or git SHA) and, for the strongest guarantee, pin by digest (myapp@sha256:...) – the digest is the hash of the content, so it can never point at different bytes. Many registries can also enforce tag immutability.

2. Dockerfile and Builds

Q6. What is a multi-stage build and why use it?

Multiple FROM stages in one Dockerfile: build in a stage with the full SDK and toolchain, then copy only the artefacts into a small runtime stage. Compilers, source code, package caches and build secrets never reach the final image. 

FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src
COPY *.csproj .
RUN dotnet restore
COPY . .
RUN dotnet publish -c Release -o /app

FROM mcr.microsoft.com/dotnet/aspnet:10.0
WORKDIR /app
COPY --from=build /app .
USER app
ENTRYPOINT ["dotnet", "MyApi.dll"]

Result: smaller image, faster pulls, smaller attack surface. BuildKit also builds independent stages in parallel and skips stages the target does not need.

Q7. Every build re-downloads all dependencies. Why, and how do you fix it?

Layer caching is sequential: once one instruction's inputs change, that layer and every layer after it is rebuilt. If you COPY . . before restoring packages, any source change invalidates the restore layer.

Order instructions from least to most frequently changing: copy only the dependency manifests (*.csproj, package.json + lock file, requirements.txt), restore, then copy the source. With BuildKit you can also use cache mounts so the package cache survives even when the layer is rebuilt: 

RUN --mount=type=cache,target=/root/.nuget/packages dotnet restore

In CI, where each runner starts empty, use a remote cache (--cache-from/--cache-to with a registry or the CI cache).

Q8. What is the build context, and why does .dockerignore matter? COPY vs ADD?

The build context is the directory sent to the builder. Without a .dockerignore, that includes .git, node_modules, bin/obj, local .env files – slow builds, needless cache busts, and secrets accidentally copied into the image by a COPY . ..

COPY copies local files. ADD additionally extracts local tar archives and can fetch URLs. Prefer COPY – it is explicit and predictable; use ADD only when you specifically want auto-extraction.

Q9. Your image is 1.5 GB. How do you shrink it?

  • Multi-stage build – the biggest win; drop the SDK and build tools.
  • Smaller base – -slim, Alpine (watch musl vs glibc differences), distroless or chiseled images with no shell or package manager.
  • Clean up in the same layer – apt-get install ... && rm -rf /var/lib/apt/lists/* in one RUN; deleting in a later layer saves nothing.
  • --no-install-recommends, no dev dependencies in the runtime stage.
  • .dockerignore to keep junk out of the context.

Inspect with docker history or dive to see which layer is actually large before guessing.

Q10. How do you use a secret (e.g. a private package token) during a build without leaking it?

Not with ARG or ENV – build args are recorded in the image history and ENV values ship inside the image. Copying a file in and deleting it later also leaks it through the earlier layer.

Use a BuildKit secret mount: the secret is available only during that single RUN and is never written to a layer. 

# Dockerfile
RUN --mount=type=secret,id=nuget_token \
    NUGET_TOKEN=$(cat /run/secrets/nuget_token) dotnet restore

# build
docker build --secret id=nuget_token,env=NUGET_TOKEN .

For SSH-based git access, RUN --mount=type=ssh works the same way. Runtime secrets are a separate matter – inject them at run time (env/orchestrator secrets/mounted files), never bake them in.

Q11. How do you secure the container supply chain?

  • Trusted, minimal bases – official or vendor images, pinned by digest, rebuilt regularly to pick up patches.
  • Scan images in CI and in the registry (Trivy, Grype, Docker Scout) and fail on critical CVEs with a fix available.
  • SBOM – generate a software bill of materials so you can answer "are we affected?" in minutes when the next big CVE drops.
  • Sign images (cosign / Sigstore) and verify signatures at admission time in the cluster, so only images built by your pipeline can run.
  • Restrict which registries the cluster may pull from.

3. Docker Runtime, Networking, Storage

Q12. docker stop takes 10 seconds and your app never shuts down gracefully. Why?

docker stop sends SIGTERM to PID 1, waits (10s by default), then sends SIGKILL. Two common causes:

  1. Shell form ENTRYPOINT/CMD or a wrapper script: /bin/sh is PID 1 and does not forward signals to your app. Fix: exec form, and in wrapper scripts end with exec "$@" so your app replaces the shell.
  2. PID 1 semantics: the kernel does not apply default signal handlers to PID 1, so a process that never registered a SIGTERM handler simply ignores it. PID 1 is also responsible for reaping zombie child processes. If your process spawns children, run a tiny init (docker run --init, tini, dumb-init).

Exit code 137 (128+9) after stop means it had to be SIGKILLed; 143 (128+15) means it exited on SIGTERM.

Q13. Why run containers as non-root, and what else hardens a container?

Root in a container is root on the host kernel, limited only by namespaces and dropped capabilities. If an attacker escapes the container (kernel bug, misconfigured mount, Docker socket mounted inside), running as root makes it a host compromise.

  • USER a non-root UID in the Dockerfile (many base images ship one, e.g. app in .NET images); listen on a port above 1024.
  • Read-only root filesystem (--read-only), with tmpfs for scratch space.
  • Drop all capabilities and add back only what is needed (--cap-drop ALL); no-new-privileges.
  • Never mount /var/run/docker.sock into an app container – it is root on the host.
  • Avoid --privileged; consider rootless Docker or user namespace remapping.

Q14. A container keeps dying with exit code 137. What's happening?

137 = killed by SIGKILL. The most common source is the kernel OOM killer because the container exceeded its cgroup memory limit (docker inspect shows OOMKilled: true). Other sources: a docker stop/orchestrator timeout, or a manual kill.

For OOM: check whether usage genuinely needs more memory or is a leak. Also make sure the runtime is container-aware – modern .NET and JVM read the cgroup limit and size their heaps from it, but old runtimes or hard-coded heap flags may assume the host's RAM and blow straight through the limit. Native memory and file cache in tmpfs also count against the limit.

Q15. A container exits immediately after starting. How do you debug it?

  1. docker ps -a for the exit code, docker logs <id> for output.
  2. Remember: a container lives exactly as long as its main process. A command that finishes (or a service that daemonises into the background) ends the container.
  3. Run interactively with the entrypoint overridden to look inside: docker run -it --entrypoint sh myimage, then run the command by hand.
  4. docker inspect to check the effective Entrypoint/Cmd, env and mounts.
  5. Distroless image with no shell? Use docker debug or attach a debug container sharing its namespaces.

Usual causes: wrong path or working directory, missing config/env variable, file permission problem after switching to a non-root user, or binary built for the wrong architecture (arm64 vs amd64 – "exec format error").

Q16. Explain Docker networking. Why can't my container reach a service on localhost?

  • bridge (default) – containers get private IPs on a virtual bridge; outbound via NAT; inbound only through published ports (-p 8080:80).
  • user-defined bridge – same, plus built-in DNS: containers resolve each other by name. The default bridge does not do name resolution – one reason Compose always creates its own network.
  • host – shares the host network stack; no isolation, no port mapping.
  • none – no networking.
  • overlay – multi-host networking (Swarm).

localhost inside a container is the container itself, not the host or another container. Call other containers by service name on a shared network; reach the host via host.docker.internal (Docker Desktop, or add it with --add-host=host.docker.internal:host-gateway on Linux).

Q17. Volumes vs bind mounts vs tmpfs – and why did my data disappear?

  • Named volume – managed by Docker, lives outside the container lifecycle, portable, the right default for persistent data (databases).
  • Bind mount – a specific host path mapped in. Great for development (live code reload), fragile in production (host path and permissions dependencies).
  • tmpfs – in memory only, gone on stop; good for scratch data and secrets you do not want on disk.

Data written to the container's writable layer is deleted when the container is removed (docker rm, compose down, recreating on a new image). If it must survive, it must be in a volume. Watch out also for docker compose down -v, which deletes named volumes.

Q18. In Docker Compose, the API starts before the database is ready and crashes. How do you fix it?

Plain depends_on only waits for the dependency container to start, not to be ready. Add a healthcheck and wait for it: 

services:
  db:
    image: postgres:17
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 10
  api:
    build: .
    depends_on:
      db:
        condition: service_healthy

The more robust fix is in the app itself: retry the connection with backoff at startup. In Kubernetes there is no depends_on at all, so the app has to tolerate dependencies being unavailable anyway.

4. Kubernetes Architecture and Workloads

Q19. What are the components of a Kubernetes cluster?

Control plane:

  • kube-apiserver – the only component that talks to etcd; every client and component goes through it (authn, authz, admission, validation).
  • etcd – consistent key-value store holding the entire cluster state. Back it up.
  • kube-scheduler – assigns unscheduled pods to nodes.
  • kube-controller-manager – runs the controllers (Deployment, ReplicaSet, Node, Job, EndpointSlice…).
  • cloud-controller-manager – cloud integrations (load balancers, node lifecycle, routes).

Every node: kubelet (makes the pods assigned to its node actually run, reports status), the container runtime (containerd/CRI-O), and usually kube-proxy (Service networking) plus a CNI plugin for pod networking.

The core idea: everything is a reconciliation loop – controllers continuously compare desired state (in etcd) with actual state and act to close the gap.

Q20. What happens, end to end, when you run kubectl apply on a Deployment?

  1. kubectl sends the manifest to the API server, which authenticates, authorises (RBAC), runs admission controllers/webhooks (mutation, validation, policy), and stores the Deployment in etcd.
  2. The Deployment controller notices it and creates a ReplicaSet.
  3. The ReplicaSet controller creates Pod objects – with no node assigned yet.
  4. The scheduler sees unscheduled pods, filters nodes that fit (resources, taints, affinity, volumes), scores them, and binds each pod to a node.
  5. The kubelet on that node sees the pod, asks the runtime to pull the image and start containers, the CNI plugin sets up networking, volumes are mounted.
  6. Probes run; when readiness passes, the pod's IP is added to the matching Service's EndpointSlices, and kube-proxy/the dataplane starts routing traffic to it.

No component calls another directly – they all watch the API server and react. That's why the system self-heals.

Q21. Why does Kubernetes schedule pods, not containers? Init containers vs sidecars?

A pod is a group of containers that share a network namespace (same IP, talk over localhost), can share volumes, and are always scheduled together on the same node. It's the unit for things that must live together: an app plus a log shipper, proxy, or config reloader.

  • Init containers run to completion, one after another, before app containers start – migrations, waiting for a dependency, fetching config.
  • Native sidecars are init containers with restartPolicy: Always (GA in 1.33): they start before the app containers, keep running alongside them, and are stopped after them. This fixed the old problems where a Job never finished because its proxy sidecar kept running, or a sidecar died before the app finished shutting down.

Q22. Deployment vs StatefulSet vs DaemonSet vs Job – when do you use each?

  • Deployment – stateless, interchangeable replicas; rolling updates; pods have random names and can be replaced anywhere.
  • StatefulSet – stable identity: ordered, predictable names (db-0, db-1), stable DNS via a headless Service, and a dedicated PersistentVolumeClaim per replica that follows the pod. Ordered startup/shutdown. For databases, Kafka, ZooKeeper-style clustered systems.
  • DaemonSet – exactly one pod per (matching) node: log collectors, node exporters, CNI and storage agents.
  • Job / CronJob – run to completion (with retries, parallelism, deadlines); CronJob on a schedule.

Running a database in a StatefulSet is possible, but the hard part is not Kubernetes – it is backups, failover, and upgrades. That is why operators (or managed databases) are usually the better answer.

Q23. ConfigMap vs Secret – and are Secrets actually secret?

Both inject configuration as env variables or mounted files. ConfigMap is for non-sensitive data; Secret is for credentials. But a Secret is only base64-encoded, not encrypted – anyone who can read it via the API, or read etcd, has the value.

What actually protects secrets:

  • Encryption at rest for etcd (EncryptionConfiguration, ideally with a KMS provider) – on by default on most managed clusters, verify it.
  • RBAC – tightly restrict get/list/watch on secrets; list returns the values too.
  • An external secret store (Vault, AWS Secrets Manager, Azure Key Vault) synced via External Secrets Operator or the Secrets Store CSI driver.
  • Never commit raw Secret manifests to git – use Sealed Secrets/SOPS or the external store.

Also: env-variable values are read once at start; mounted files are updated (eventually) when the Secret/ConfigMap changes, but the app still has to re-read them.

5. Resources, Probes, and Deployments

Q24. Requests vs limits – and what are QoS classes?

Requests are what the scheduler reserves: a pod only lands on a node with enough unreserved allocatable capacity. Limits are the hard ceiling enforced at runtime: exceeding the CPU limit means throttling; exceeding the memory limit means the container is OOM-killed.

QoS classes come from how you set them, and decide eviction order under node memory pressure:

  • Guaranteed – every container has CPU and memory requests = limits. Evicted last.
  • Burstable – some requests/limits set but not equal.
  • BestEffort – nothing set. Evicted first.

Requests that are too low cause overcommitted nodes and noisy neighbours; too high wastes money. Base them on observed usage.

Q25. Should you set CPU limits?

It is a real debate, and the senior answer explains the mechanism. CPU limits are enforced by CFS quota per time period: a multi-threaded app can burn its whole quota in the first part of the 100ms period and then be throttled for the rest – causing latency spikes even when the node has idle CPU and average usage looks well under the limit.

A common production stance: always set memory requests and limits (memory is not compressible – usually request = limit), set CPU requests accurately, and omit or set generous CPU limits for latency-sensitive services, since requests already guarantee each pod its share under contention. Keep CPU limits where you need hard isolation (multi-tenant, batch, cost control). Watch the container_cpu_cfs_throttled_periods_total metric either way.

Q26. Liveness vs readiness vs startup probes – and how can a probe cause an outage?

  • Readiness – "can I receive traffic now?" Failing removes the pod from Service endpoints; the container is not restarted.
  • Liveness – "am I stuck beyond recovery?" Failing restarts the container.
  • Startup – "have I finished starting?" Disables the other probes until it passes; for slow-starting apps.

The outage pattern: a liveness probe that checks a dependency (the database). The database blips, every pod fails liveness at once, Kubernetes restarts the whole fleet, the cold-starting pods hammer the recovering database – a self-inflicted outage. Rules: liveness checks only the process itself (cheap, local, no dependencies); dependencies belong in readiness if anywhere; give probes realistic timeouts and thresholds; use a startup probe instead of a huge initialDelaySeconds.

Q27. How does a rolling update work, and how do you roll back?

The Deployment creates a new ReplicaSet and shifts pods across gradually, controlled by:

  • maxSurge – how many extra pods above the desired count during the update.
  • maxUnavailable – how many may be unavailable. maxUnavailable: 0 + maxSurge: 1 = never drop below capacity.

Only pods that pass readiness count as available, so a broken version stalls rather than replacing everything – if readiness is meaningful. minReadySeconds adds a soak time.

Roll back with kubectl rollout undo deployment/x (old ReplicaSets are kept, per revisionHistoryLimit), or – in a GitOps setup – revert the commit. For canary or blue/green with automated analysis, use Argo Rollouts or Flagger; the built-in Deployment only does rolling and recreate.

Q28. Users get errors during every deployment even with a rolling update. Why?

Graceful shutdown is a race. When a pod is deleted, two things happen in parallel: the kubelet sends SIGTERM to the container, and the endpoint controller removes the pod from EndpointSlices, which then has to propagate to every node's kube-proxy and to ingress controllers/load balancers. If the app exits immediately on SIGTERM, traffic is still being routed to it for a few seconds → connection refused / 502s.

Fixes:

  • A preStop hook that sleeps a few seconds (newer versions have a built-in sleep action) so routing updates before shutdown starts.
  • The app handles SIGTERM: stop accepting new connections, finish in-flight requests, then exit.
  • terminationGracePeriodSeconds (default 30s) must cover preStop + drain time, or the pod is SIGKILLed.
  • Make sure the process actually receives SIGTERM (exec form, see Q12).

Q29. What is a PodDisruptionBudget?

A PDB limits how many pods of an application may be down at once due to voluntary disruptions – node drains, cluster upgrades, autoscaler scale-down. kubectl drain uses the eviction API, which refuses to evict if it would violate the PDB (minAvailable or maxUnavailable).

It does not protect against involuntary disruptions (node crash, OOM). And misconfigured PDBs can block operations: minAvailable equal to the replica count, or a PDB on a single-replica deployment, means a drain hangs forever and cluster upgrades stall.

6. Kubernetes Networking and Storage

Q30. What Service types are there?

  • ClusterIP (default) – stable virtual IP and DNS name reachable only inside the cluster.
  • NodePort – opens the same port (30000–32767) on every node, forwarding to the service.
  • LoadBalancer – asks the cloud provider for an external load balancer pointing at the service.
  • ExternalName – DNS CNAME to an external host; no proxying.
  • Headless (clusterIP: None) – no virtual IP; DNS returns the individual pod IPs. Used by StatefulSets and clients that do their own load balancing.

A Service selects pods by labels; a selector that matches nothing is the classic "service has no endpoints" bug.

Q31. How does a ClusterIP actually route traffic? Nothing listens on that IP.

Correct – the ClusterIP is virtual. The endpoint controller maintains EndpointSlices listing the IPs of ready pods behind each Service. kube-proxy on every node watches Services and EndpointSlices and programs the kernel – iptables, IPVS, or nftables rules (nftables mode is GA since 1.33) – to DNAT packets addressed to the ClusterIP:port to one of the backing pod IPs.

Some CNIs (e.g. Cilium) replace kube-proxy entirely with eBPF. Either way, the load balancing is per connection, not per request – which is why long-lived connections (gRPC, HTTP/2, keep-alive) can pile onto one pod and need client-side or L7 (mesh/gateway) balancing.

Q32. How does DNS work in Kubernetes, and why might lookups be slow?

CoreDNS serves records like my-svc.my-namespace.svc.cluster.local. Pods get a resolv.conf pointing at it, with search domains so you can just use my-svc within a namespace.

Gotcha: the default ndots:5. Any name with fewer than five dots (e.g. api.example.com) is first tried with every search domain appended – several failing lookups (times A and AAAA) before the real one. Under load that multiplies DNS traffic and adds latency, and conntrack races on UDP can cause occasional 5-second timeouts. Mitigations: use FQDNs with a trailing dot for external names, lower ndots in dnsConfig, NodeLocal DNSCache, and scale CoreDNS.

Q33. Ingress vs Gateway API – and what happened to ingress-nginx?

Ingress is the original L7 HTTP routing API (host/path → Service). It's minimal; anything advanced (rewrites, timeouts, canary) lives in controller-specific annotations, so configs aren't portable. The Ingress resource only works if an Ingress controller is installed.

Gateway API is its successor: role-oriented resources (GatewayClass for the infra provider, Gateway for the platform team, HTTPRoute/GRPCRoute for app teams), with header matching, traffic splitting, and cross-namespace routing in the spec instead of annotations.

2026 currency point: the community ingress-nginx controller was retired in March 2026 – no further releases or security fixes. The Kubernetes project recommends migrating to Gateway API or another controller. Note the distinction: the Ingress API itself is not removed, only that popular controller.

Q34. What is a NetworkPolicy, and why might yours do nothing?

By default every pod can talk to every other pod in the cluster. A NetworkPolicy selects pods by label and whitelists allowed ingress and/or egress (by pod selector, namespace selector, or IP block). Once any policy selects a pod for a direction, everything not explicitly allowed in that direction is denied.

Why it might do nothing: NetworkPolicy is enforced by the CNI plugin; if your CNI doesn't support it (e.g. plain flannel), the objects are accepted and silently ignored.

Common pattern: a default-deny policy per namespace, then explicit allows. And the classic mistake with egress default-deny: forgetting to allow DNS (UDP/TCP 53 to CoreDNS), so everything breaks with name-resolution errors.

Q35. Explain PV, PVC and StorageClass. Why is my pod Pending on a volume?

  • PersistentVolumeClaim – the app's request: "10 GiB, ReadWriteOnce, class fast-ssd".
  • PersistentVolume – the actual piece of storage bound to that claim.
  • StorageClass – how to provision PVs dynamically via a CSI driver (disk type, reclaim policy, binding mode).

Access modes: RWO (one node), ROX, RWX (many nodes – needs NFS/file storage, most block disks can't do it), RWOP (one pod).

Common Pending causes: no default StorageClass; a zonal disk in zone A while the pod can only schedule in zone B (fix with volumeBindingMode: WaitForFirstConsumer, so the disk is created where the pod lands); RWO volume still attached to the old node during a rollout (multi-attach error – use Recreate strategy or a StatefulSet). Check events on the PVC and pod, and the CSI driver's logs. Also check reclaimPolicy: Delete means deleting the PVC deletes the data.

7. Scaling and Scheduling

Q36. HPA, VPA, Cluster Autoscaler – how do they fit together? Traffic doubled but HPA didn't scale – why?

  • HPA – changes the number of replicas based on metrics (CPU/memory utilisation, custom or external metrics). KEDA extends this with event sources like queue length and scale-to-zero.
  • VPA – recommends or sets requests/limits per pod (size, not count).
  • Cluster Autoscaler / Karpenter – adds nodes when pods are Pending for lack of capacity, removes underused nodes.

Don't let HPA and VPA both act on CPU/memory for the same workload – they fight.

HPA didn't scale – usual reasons:

  • No metrics: metrics-server not installed, or kubectl get hpa shows <unknown>.
  • No CPU requests set – utilisation is a percentage of requests, so it can't be computed.
  • Already at maxReplicas.
  • Wrong signal: the service is I/O-bound or thread-pool-starved, so CPU stays low while latency explodes – scale on RPS, latency or queue depth instead.
  • It did scale, but new pods are Pending (no node capacity) or slow to become Ready.

Q37. What is in-place pod resize?

Historically, changing a pod's CPU or memory meant deleting and recreating it. Since Kubernetes 1.35 in-place pod resize is GA: you can change a running container's resources via the pod's resize subresource without recreating the pod. Each container's resizePolicy says whether a given resource can change live (NotRequired) or needs a container restart (RestartContainer) – memory changes often need a restart because the app sized itself at startup.

Why it matters: rightsizing without restarts, giving extra CPU during startup then shrinking it, and VPA's InPlaceOrRecreate mode, which uses it. The scheduler still has to fit the new size on the current node – if it doesn't fit, the resize stays pending.

Q38. How do you control where pods run? Taints, affinity, topology spread.

  • nodeSelector / node affinity – the pod is attracted to nodes with certain labels (GPU, zone, instance type); required or preferred.
  • Taints and tolerations – the node repels pods unless they tolerate the taint. Used to dedicate nodes (GPU pool, system pool). A toleration only allows; to force pods onto those nodes you also need affinity.
  • Pod (anti-)affinity – place pods near or away from other pods (e.g. not two replicas on one node).
  • Topology spread constraints – spread replicas evenly across zones/nodes with a max skew. The modern, more flexible way to get high availability across zones.

Too many hard (required) rules is the classic source of mysteriously Pending pods.

8. Troubleshooting Scenarios

Q39. A pod has been Pending for 20 minutes. Walk me through it.

Pending = not scheduled yet (or, after scheduling, waiting on volumes/images). Start with kubectl describe pod – the Events section almost always states the reason:

  • Insufficient cpu/memory – requests don't fit any node's allocatable (not raw capacity). Reduce requests or add nodes; check if the autoscaler is working and allowed to.
  • node(s) had untolerated taint – missing toleration.
  • didn't match Pod's node affinity/selector or topology spread – rules too strict.
  • unbound immediate PersistentVolumeClaims – storage problem (Q35).
  • Too many pods per node (max pods / IP exhaustion in the CNI).

If the pod doesn't exist at all, it's not a scheduling problem – look at the ReplicaSet events (often a ResourceQuota or admission webhook rejection).

Q40. A pod is in CrashLoopBackOff. What do you do?

CrashLoopBackOff means the container keeps starting and exiting, and the kubelet is backing off restarts (exponentially, up to 5 minutes). It's a symptom, not a cause.

  1. kubectl logs pod --previous – logs of the crashed instance, not the new one that's backing off.
  2. kubectl describe pod – Last State: exit code and reason. 1 = app error; 137 + OOMKilled = memory limit; 137 without OOM = killed (often failed liveness probe); 127 = command not found; 126 = permission.
  3. Check events for liveness probe failures – a too-aggressive liveness probe on a slow starter looks exactly like a crash loop.
  4. Check config: missing ConfigMap/Secret keys, wrong env, unreachable dependency the app treats as fatal at startup.
  5. To get inside: kubectl debug with an ephemeral container, or a copy of the pod with the command overridden to sleep.

Q41. Pods are Running but not Ready, or the Service returns intermittent 503s.

Running but not Ready: the readiness probe is failing. kubectl describe pod shows the probe failure messages. Typical causes: wrong port/path, probe timeout too short, readiness checking a dependency that is down, app listening on 127.0.0.1 instead of 0.0.0.0.

Intermittent 503s:

  • Some pods flapping between Ready and NotReady (probe on the edge of its timeout under load).
  • Errors only during deploys/scale-down → graceful shutdown race (Q28).
  • One bad pod behind the Service – check per-pod error rates; kubectl get endpointslices to see what's actually behind it.
  • Ingress/gateway timeouts or upstream connection limits.
  • Pods being CPU-throttled or OOM-restarting under load.

Q42. Pods restart during traffic spikes with OOMKilled. Or they get Evicted. What's the difference?

OOMKilled (exit 137): the container exceeded its own memory limit; the kernel kills it and the kubelet restarts it in place. Fix: right-size the limit, or find the leak/spike (large request bodies, unbounded caches, runtime not respecting the cgroup limit).

Evicted: the node is under pressure (memory, disk/ephemeral storage, PIDs). The kubelet evicts pods to protect the node – BestEffort first, then Burstable pods using the most above their requests. The pod is terminated and (if owned by a controller) recreated elsewhere. Fix: set realistic requests so the scheduler doesn't overpack nodes, set ephemeral-storage requests/limits, clean up log/temp file growth.

Q43. ImagePullBackOff / ErrImagePull – what's wrong?

  • Typo in image name or tag, or the tag was never pushed.
  • Private registry without credentials: missing imagePullSecrets, or the node identity lacks pull permission (ECR/ACR/GAR IAM).
  • Registry rate limiting (e.g. anonymous Docker Hub pulls) – use a pull-through cache or mirror.
  • Network: nodes can't reach the registry (private cluster without NAT or private endpoint).
  • Architecture mismatch: arm64 nodes with an amd64-only image – no matching manifest.

kubectl describe pod shows the exact registry error. Pre-building multi-arch images and mirroring critical images into your own registry removes most of these.

Q44. A Deployment rollout is stuck. How do you investigate and recover?

kubectl rollout status hangs; after progressDeadlineSeconds (default 600s) the Deployment gets the condition ProgressDeadlineExceeded – but Kubernetes does not roll back automatically.

  • Look at the new ReplicaSet's pods: CrashLoopBackOff, ImagePullBackOff, failing readiness, Pending for capacity (with maxUnavailable: 0 you need room for surge pods).
  • A PDB or quota blocking new pods (ResourceQuota exceeded shows on the ReplicaSet events).
  • An admission webhook rejecting the new pod spec.

Recover with kubectl rollout undo (or a git revert in GitOps), then fix. Long term: alert on ProgressDeadlineExceeded, or use progressive delivery (Argo Rollouts/Flagger) that aborts automatically on bad metrics.

Q45. A node becomes NotReady. What happens to its pods?

The kubelet stops reporting; the node controller marks the node NotReady/Unknown and adds a NoExecute taint (node.kubernetes.io/unreachable or not-ready). Pods have a default toleration of 300 seconds for these taints, so after ~5 minutes they are marked for deletion and controllers create replacements on healthy nodes. Tune it per workload with tolerationSeconds.

Nuances:

  • StatefulSet pods are not replaced while the old one is stuck Terminating on an unreachable node – Kubernetes can't prove it's dead, and running two db-0s would break the identity guarantee. Requires human action (confirm the node is gone, then delete the node or force-delete the pod).
  • RWO volumes may stay attached to the dead node, delaying the replacement pod.
  • DaemonSet pods are not rescheduled elsewhere (by design).

Diagnose the node itself: kubelet logs, container runtime, disk/memory pressure, network to the API server, expired certificates.

9. Security and Operations

Q46. How does RBAC work, and how do pods authenticate to the API and the cloud?

RBAC is allow-only: Role (namespaced) / ClusterRole (cluster-wide) list verbs on resources; RoleBinding / ClusterRoleBinding grant them to users, groups, or ServiceAccounts. There are no deny rules – least privilege means granting little, not revoking.

Pods run as a ServiceAccount and get a short-lived, auto-rotated projected token. Good practice: one ServiceAccount per app, automountServiceAccountToken: false for apps that never call the API, never bind cluster-admin to workloads, and remember that list secrets, create pods, and escalate/bind/impersonate are effectively privilege escalation.

For cloud access, use workload identity (IRSA / EKS Pod Identity, Azure Workload Identity, GKE Workload Identity): the ServiceAccount is federated to a cloud role, so there are no long-lived cloud keys stored in Secrets.

Q47. How do you prevent pods from running privileged or as root?

At the pod level, a securityContext: runAsNonRoot: true, allowPrivilegeEscalation: false, readOnlyRootFilesystem: true, capabilities: drop: ["ALL"], seccompProfile: RuntimeDefault.

At the cluster level, enforce it: PodSecurityPolicy was removed in 1.25; its replacement is Pod Security Admission, enforcing the Pod Security Standards (privileged, baseline, restricted) via namespace labels, with warn/audit modes for gradual rollout. For custom rules (allowed registries, required labels, signed images), use a policy engine – Kyverno, OPA Gatekeeper, or built-in ValidatingAdmissionPolicy (CEL).

Q48. Several teams share one cluster. How do you stop one team affecting another?

  • Namespaces per team/app as the boundary for RBAC and policy.
  • ResourceQuota – caps total CPU/memory/objects per namespace.
  • LimitRange – default and max requests/limits per container, so nobody deploys BestEffort pods by accident.
  • RBAC scoped to their namespaces only.
  • NetworkPolicies – default-deny between namespaces.
  • Priority classes so critical workloads preempt batch jobs, not the other way round.
  • Dedicated node pools (taints) for noisy or sensitive workloads.

Namespaces are soft multi-tenancy – they share the control plane and kernel. For untrusted tenants, use separate clusters, virtual clusters (vCluster), or sandboxed runtimes.

Q49. How do you deploy to Kubernetes in production? What is GitOps?

Not kubectl apply from a laptop. GitOps: the desired state of the cluster lives in git; an agent in the cluster (Argo CD or Flux) continuously pulls and reconciles the cluster to match. CI builds and pushes the image, then updates the image tag in the config repo (by PR or bot).

Benefits: every change is reviewed and audited in git, rollback is a revert, drift (manual changes) is detected and corrected, and CI doesn't need cluster-admin credentials because the cluster pulls instead of CI pushing. Packaging is usually Helm charts or Kustomize overlays per environment. Secrets don't go in git in plain form (Q23).

Q50. How do you upgrade a Kubernetes cluster safely?

  • Read the release notes and deprecation guide – removed APIs are the main breakage. Scan manifests and Helm releases for deprecated API versions (pluto, kubent) before upgrading.
  • One minor version at a time; control plane first, then nodes. Respect version skew (kubelet may lag the API server by a limited number of minors, never be newer).
  • Upgrade add-ons (CNI, CSI, ingress/gateway controllers, cert-manager) to versions that support the target.
  • Nodes: surge in new nodes or cordon and drain old ones; PDBs (Q29) keep apps available – and a broken PDB will block you.
  • Back up etcd (self-managed) and rehearse in a staging cluster first.

Current examples worth knowing: the dockershim removal (1.24), PSP removal (1.25), and cgroup v1 support removed in 1.35 – nodes on old OS images still using cgroup v1 must be migrated to cgroup v2 before upgrading. Kubernetes ships three minors a year with roughly 14 months of support each, so upgrading must be routine, not a project.
