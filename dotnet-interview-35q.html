.NET Senior Interview – 35 Questions

1. Runtime, Memory, and GC

This is the section that separates people who have run .NET in production from people who have written .NET. Almost no interview-prep content covers it, which is exactly why it gets asked.

Q1. Your API's memory climbs all day and drops on restart. Walk me through finding the leak.

First establish whether it is actually a leak or just a heap that has not been pressured yet. .NET does not return memory to the OS eagerly, so a working set that grows on a box with plenty of free RAM can be perfectly healthy. The question is whether live objects are growing, not whether committed memory is growing.

So: dotnet-counters monitor -n MyApi and watch dotnet.gc.last_collection.heap.size broken down by generation across a few hours. If gen 2 keeps climbing after collections, something is holding references. If only the working set climbs while gen 2 stays flat, it is fragmentation or native memory, not a managed leak.

Once you know it is managed, take two heap snapshots an hour apart with dotnet-gcdump collect -p <pid> and diff them. The diff tells you which type grew. Then the question is what is rooting it. Usual suspects:

  • a static collection
  • a long-lived event handler subscription that never unsubscribes
  • an IMemoryCache with no size limit or expiry
  • a captured closure inside something registered as a singleton

Q2. Is your API running Server GC or Workstation GC, and does it matter?

ASP.NET Core apps default to Server GC. The runtime's own default for a standalone app is Workstation, but for hosted apps the host chooses, and the web host picks Server. Server GC gives you a heap and a dedicated collection thread per logical CPU and collects them in parallel – faster on the same heap size but uses considerably more memory and CPU.

The key point: Workstation GC is always used on a machine with only one logical CPU, no matter what you configure. Set ServerGarbageCollection to true all you like; on a single-core container the runtime ignores you. So a service that behaved one way on a 4-core node can behave differently after someone tightens the CPU limit, and nothing in your config changed.

The other half is density. If you run many instances of a small service on one box, Server GC's per-core threads start fighting each other, and Workstation GC with concurrent collection disabled can genuinely be faster.

Q3. What is DATAS, and why should you care in .NET 10?

DATAS = Dynamic Adaptation To Application Sizes. It makes the GC size the heap roughly in proportion to the application's live data instead of holding a large heap because the machine happens to be large. Introduced in .NET 8 behind a switch, on by default since .NET 9, for Server GC only. Workstation GC is unaffected.

Why it comes up now: .NET 10 is LTS, so many teams meet DATAS for the first time while upgrading from .NET 8. Memory usage drops substantially; the trade is a small throughput cost (targets a 2% Throughput Cost Percentage by default). It also starts the process with a single heap and grows from there, so startup and the first minutes of a traffic ramp can look slower.

If a service regressed on throughput right after a .NET 9/10 upgrade, test DATAS first by setting System.GC.DynamicAdaptationMode to 0 and re-running the load test – not to leave it off, but to confirm the cause.

Note: DATAS is not a new collector and did not arrive in .NET 10 – it is an adaptation mode on Server GC, default since .NET 9.

Q4. What lands on the Large Object Heap, and why does that hurt you?

Anything 85,000 bytes or larger. In practice: big arrays and big strings – a 20,000-element int[], a buffer allocated per request, a serialised payload built in memory.

Two things make the LOH painful:

  • It is collected only with gen 2, so LOH pressure drags you into full collections.
  • It is not compacted by default, so differently sized large buffers fragment it – a heap that is mostly holes, committed memory you pay for and cannot use.

Caveat: in containers on .NET Core 3.0+, the LOH is compacted automatically. So in Kubernetes, fragmentation is much less likely to be your problem; the gen 2 pressure is the part that still bites.

The fix is almost never to tune the GC – it is to stop making the allocations: ArrayPool<T>.Shared for reusable buffers, streaming instead of materialising whole payloads, RecyclableMemoryStream instead of MemoryStream for large bodies. Raising System.GC.LOHThreshold can be right in narrow cases, but reaching for it first is a smell. GCSettings.LargeObjectHeapCompactionMode is an occasional emergency lever (it triggers a blocking full compacting collection), not a routine answer.

Q5. Gen 0 collections are supposed to be cheap. So why is your p99 spiking?

Because a cheap collection that happens constantly is not cheap, and a gen 0 collection is not the only thing that stops your threads.

The usual mechanism is promotion. Gen 0 is cheap when the objects in it are dead by the time it runs. If your handler allocates objects that stay alive until the response is written – which is normal – they survive gen 0, get promoted to gen 1, then gen 2, and now you pay for full collections you did not expect. Allocation rate turns into gen 2 pressure.

Look at dotnet.gc.pause.time against request latency, plus collection counts per generation. If gen 2 count climbs under load, p99 spikes almost certainly line up with those pauses. And near the memory limit, the GC gets more aggressive about full compacting collections once physical memory load crosses ~90% – in a container that means 90% of the container limit, not the host's.

Q6. Your process holds 8 GB but the heap snapshot only accounts for 2 GB. Where is the rest?

Managed heap size and process working set are different numbers. Short list of explanations:

  1. Fragmentation. Since .NET 7 the GC uses regions rather than segments on 64-bit Windows/Linux, but committed-but-unused space still shows up in the footprint; dotnet.gc.last_collection.heap.fragmentation.size tells you how much.
  2. Native memory – often the more common one in real services. Native DB drivers, image/PDF libraries, gRPC and HTTP/2 buffers, any SafeHandle-wrapped resource live outside the managed heap. A leak here is invisible to a gcdump.
  3. The GC has not been asked to give it back. Memory released to the heap but not decommitted to the OS still counts toward working set.

To split them apart, compare dotnet.process.memory.working_set against managed heap size over time. If managed is flat and working set climbs, stop looking at gcdumps and start looking at native handles and unmanaged libraries.

2. Concurrency and the Thread Pool

This section is about what happens when the pool itself is the bottleneck – a production problem, not a language one.

Q7. Your API times out under load but CPU sits at 15%. What's happening?

Slow responses + plenty of idle CPU = signature of thread pool starvation. Work items are queued and there are no free threads to run them.

The mechanism is almost always sync-over-async: something on the request path calls .Result, .Wait(), or .GetAwaiter().GetResult(). That blocks a pool thread instead of releasing it. Under load every concurrent request holds a thread, the pool runs dry, and the runtime injects more threads – slowly, roughly one or two per second after the initial burst.

To confirm: dotnet-counters monitor -n MyApi, watch dotnet.thread_pool.thread.count. Starvation looks like that number climbing to 2–3× the core count and then creeping upward while CPU stays low. Often dotnet.thread_pool.queue.length is large and dotnet.thread_pool.work_item.count is low at the same time: lots of pending work, little completing.

.NET 6 changed the pool heuristics to ramp up faster for certain blocking task APIs, so on modern .NET starvation often shows as a latency spike during ramp-up rather than a permanent stall. It did not remove the underlying problem. ThreadPool.SetMinThreads is only a stopgap while you fix the blocking call.

Q8. You've confirmed starvation. How do you find the blocking call?

Depends on whether the problem is constant or intermittent.

Constant: dotnet-stack report -n MyApi dumps every thread's stack to the console. Look for stacks ending in ThreadPoolWorkQueue.Dispatch() and PortableThreadPool+WorkerThread.WorkerThreadStart() (pool threads), then read the top of the stack. A blocked sync-over-async call shows Task.SpinThenBlockingWait and ManualResetEventSlim.Wait sitting above your own controller/handler method.

Intermittent: stacks are a lottery, so collect a trace:

dotnet trace collect -n MyApi --clrevents waithandle --clreventlevel verbose --duration 00:00:30

This captures the WaitHandleWait event (added in .NET 9 for exactly this). It fires whenever a thread blocks – on Task.Result, Task.Wait, lock, Monitor.Enter, SemaphoreSlim.Wait, etc. Open the .nettrace in PerfView or .NET Events Viewer, group by stack; the offending path is usually the top entry.

Q9. Pick between lock, SemaphoreSlim, and Interlocked for a shared counter, and defend it.

  • Interlocked.Increment – for a plain counter. A single atomic CPU instruction, no kernel transition, no blocking. Nothing else comes close for that shape.
  • lock – right default when several operations must stay consistent together (read, decide, write back). Cheap when uncontended, clearest to read. Hard limit: you cannot await inside it (the compiler rejects it).
  • SemaphoreSlim – when the critical section contains async work (WaitAsync yields the thread), or when you want N concurrent holders. Heavier than lock; release it in a finally.

The judgment tested: reach for the cheapest tool that fits. Guarding an int with a SemaphoreSlim is not wrong, just orders of magnitude more expensive than needed.

Q10. ConcurrentDictionary.GetOrAdd ran your factory twice. Why, and does it matter?

GetOrAdd is atomic about insertion, not about the factory. If two threads miss on the same key simultaneously, both run the value factory. One result wins and is stored; the other is discarded.

Whether that matters depends on the factory. If it computes a value, you wasted some CPU. If it opens a connection, starts a background task, or registers with an external system, you created an object nothing will ever dispose – a resource leak that only appears under concurrency and survives every test suite.

Fix: store Lazy<T> in the dictionary. GetOrAdd may still create two Lazy<T> wrappers, but only the winner's Value is ever accessed, so the expensive work happens once.

"Thread-safe" means the data structure will not corrupt – it does not mean your callback runs once.

Q11. You need to call a downstream API 500 times. How do you do it without taking it down?

Naive: Task.WhenAll over 500 tasks – fires all 500 at once; a fine way to get rate-limited or knock over the downstream. It runs them; it does not bound them.

Better: Parallel.ForEachAsync with an explicit MaxDegreeOfParallelism. Setting it explicitly is the point: the default is Environment.ProcessorCount, which is the wrong basis for I/O-bound work. The right value comes from what the downstream can take.

For more control: a SemaphoreSlim sized to the concurrency limit, acquired with WaitAsync inside each task – composes with retry policies more naturally.

Raise unprompted:

  • Pass a CancellationToken through – a batch of 500 that cannot be cancelled will outlive the request that started it.
  • Be careful combining bounded concurrency with retries – if every in-flight call retries when the downstream fails, you have built a load amplifier pointed at a struggling service.

3. Diagnosing Production

Nothing here is about writing code. It is about what you do at 3am with a service you cannot attach a debugger to.

Q12. Production is slow. You can't attach a debugger and you can't deploy. What do you reach for?

The .NET diagnostics CLI tools, escalating from cheapest to most invasive:

  1. dotnet-counters – always first. Nearly free, runs against a live process, answers the triage question: is this CPU, memory, GC pauses, thread pool, or lock contention?
  2. dotnet-stack report – if counters point at threads. Immediate console output; shows what every thread is doing.
  3. dotnet-trace – when the problem is intermittent and you need a window of history. Also where you get WaitHandleWait events.
  4. dotnet-gcdump – when it is memory; a heap graph you can diff against a later one.
  5. dotnet-dump – last. Most complete, most disruptive to collect, analysed offline.

Each step should be justified by what the previous one showed. Going straight to a full dump "because it has everything" is how you end up with 8 GB of file and no hypothesis.

Q13. You get four numbers on a dashboard for a .NET API. Which four?

Request rate, error rate, latency at p99, and saturation (RED/USE framing). Between them they detect nearly every incident shape, and each tells you something the others cannot.

  • Latency must be a percentile, never an average – a mean hides the 1% of users timing out.
  • Saturation is the .NET-specific one: thread pool queue length and GC pause time – the two resources that go into distress silently while CPU and memory look fine.

A fifth: dependency latency, split by dependency. Most "our API is slow" incidents are actually "something we call is slow".

CPU, memory, disk, network are host metrics – they describe the machine, not whether the service is doing its job; thread pool starvation is invisible in all four.

Q14. A bug appears in production once a week and never locally. How do you catch it?

Stop trying to reproduce it and start trying to capture it.

  • Correlation IDs flowing through every log line and downstream call, so a single failed request can be reassembled after the fact.
  • Error-biased sampling – trace 100% of failures even if you sample 1% of successes (tail-based sampling).
  • Targeted capture – if the failure has a detectable signature (specific exception, latency over threshold), collect a dump or trace automatically when it fires.

Narrow the space while waiting. "Once a week" is a clue: something periodic – a scheduled job, cache expiry, token refresh, certificate rotation, deployment window, a batch on a certain day. Line the failure timestamps up against every scheduled thing before assuming it is random.

Q15. Your logs are 40 GB a day and you still can't answer "why was this request slow?"

Volume is not signal. Three usual failures:

  1. Unstructured. You can grep but not aggregate – $"Order {id} took {ms}ms" is a string; you cannot ask it for p99 by endpoint. Structured logging with real properties makes it queryable.
  2. No correlation. A request's journey is scattered across services and instances with nothing tying it together.
  3. Wrong altitude. Entry/exit of every method (where most of the 40 GB comes from), but no timings around the boundaries that actually vary: DB call, HTTP call, cache lookup, lock acquisition.

Instead: distributed tracing for "where did the time go", logs carrying the trace ID so the two link up, and log levels you can raise for one tenant or endpoint without raising it for everyone.

Q16. A dependency upgrade broke production but every test passed. What was missing?

The tests were testing our code; the change was in the seam between our code and the world. Usual shapes:

  • Tests mocked the dependency, asserting our assumptions rather than the library's behaviour – and the assumptions are what changed.
  • A transitive dependency moved three levels down and nothing exercised that path.
  • The change is only visible under real conditions: connection pooling, timeout defaults, serialisation of an edge-case value, TLS negotiation, culture-sensitive parsing.

Afterwards: contract/integration tests against the real dependency for the behaviours you rely on (Testcontainers for infrastructure), plus a canary or staged rollout so first exposure is 1% of traffic, not 100%.

No test suite catches everything. The useful question is how fast you noticed and how fast you rolled back – if both are "hours", the gap is observability and deployment, not testing. "Better coverage" would not have moved here; the gap was the kind of test, not the quantity.

Q17. p50 is 40ms. p99 is 6 seconds. Where do you look first?

The common path is healthy; something occasionally stops otherwise-fine code. Candidates, roughly by frequency:

  • GC pauses – correlate dotnet.gc.pause.time with the latency spikes.
  • Thread pool queuing – the request was fine but waited to start.
  • Lock contention – dotnet.monitor.lock_contentions.
  • Connection pool exhaustion (DB or HTTP client) – work is fast, acquiring a connection is not.
  • Data skew – p99 is one tenant with 100× more rows.

Distinguishing move: are the slow requests random or a pattern? Clustered by endpoint, tenant, or payload size → data. Scattered uniformly → something process-wide (GC, pool, noisy neighbour). Optimising an endpoint that already runs in 40ms will not move a p99 caused by a stop-the-world pause.

4. Performance and Measurement

The most reliable senior signal: whether you distinguish between a change you believe is faster and a change you have measured.

Q18. You say your change made the endpoint three times faster. Prove it.

Method-level change: BenchmarkDotNet. It warms up (so you are not measuring JIT), runs enough iterations to get a distribution, reports variance so you can tell a real difference from noise, and with [MemoryDiagnoser] reports allocations – often where the real win is.

Endpoint-level change: a benchmark is the wrong instrument. Run a load test at realistic concurrency against both versions and compare percentile latency and throughput – the change might be faster in isolation and irrelevant under contention.

Comparison discipline: same hardware, same data volume, same warm state, one variable changed. A "3× faster" from a warm cache on the second run is not a result. A Stopwatch in a loop without warmup and iteration counts frequently measures JIT and GC timing rather than your code.

Q19. Why do microbenchmarks lie?

Because a benchmark removes exactly the conditions that make production slow:

  • The JIT optimises away work whose result you never use – you can measure nothing and get an impressive number.
  • Branch predictors and CPU caches get unrealistically warm; real traffic has cold caches and unpredictable branches.
  • No contention – no other threads, no GC pressure from the rest of the app, no lock queue.
  • Uniform input, where production data has outliers that are usually the whole problem.

Typical bite: make a method 40% faster, ship it, nothing moves – because it was 2% of request time and 98% is waiting on the DB (Amdahl's law). The benchmark was asked the wrong question.

Microbenchmarks are right for comparing two implementations of the same thing, wrong for deciding whether that thing is worth optimising. Profiling decides what to optimise; benchmarking decides how. More iterations fix noise, not measuring something that does not matter.

Q20. Where do you actually spend optimisation effort on a slow API? Give me the order.

Outside in, because that is the order the wins are usually sized in:

  1. Measure – find where the time actually goes. Nothing before this.
  2. Database – missing index, query returning far more rows than needed, N+1. Usually the largest and cheapest wins.
  3. Network shape – round trips, sequential calls that could run concurrently, oversized payloads.
  4. Caching – deliberately, once you know what is expensive and how stale it may be.
  5. Code – allocations, serialisation, hot-path work.
  6. Runtime – GC configuration, pooling, other knobs. Last: smallest lever, easiest to get wrong.

Don't start at the bottom. Tuning GC on a service whose real problem is a missing index is an expensive way to achieve nothing. Caching as a first move hides the problem, adds invalidation bugs, and makes the underlying query slower to find later.

Q21. When is "just add a cache" the wrong answer?

  • The operation is wrong, not slow. Caching wrong data serves it faster, and stale.
  • The data cannot tolerate staleness. Something the user just wrote, authorisation decisions, anything financial. Caching a permission check serves a revoked user their old access for the TTL.
  • Hit rate will be low. A long tail of unique keys costs a lookup, serialisation and memory, and returns misses. Know the access distribution first.
  • It hides a fixable problem. A 4-second query with no index stays 4 seconds for one unlucky user every TTL, forever, and nobody adds the index.
  • Invalidation is harder than the original problem. With several writers, caching converts a performance question into a correctness question.

A short TTL reduces staleness and destroys hit rate at the same time – if it must be short enough to be safe, the cache often buys nothing.

5. Data at Scale

What happens when the data outgrows the assumptions the code was written under.

Q22. Your read replica is four seconds behind and users see stale data right after saving. Fix it.

This is read-your-own-writes – a consistency problem created when reads were pointed at a replica without deciding what to do about lag.

  • Pragmatic fix: route reads to the primary for a short window after a write by that user – stamp the session with a timestamp or log position on write, read from primary until the replica has caught past it. Keeps the replica benefit for the ~95% of traffic not reading its own recent write.
  • Cheaper variant: route by operation – write-then-read flows read the primary; reporting, search, list views read the replica. Coarse but easy to reason about.
  • Stop lying to the user: if the write is genuinely async, show "saved, updating shortly". A product decision as much as a technical one.

Replication lag under load is a normal operating condition, not a bug you can buy your way out of with bigger hardware. Any design that assumes zero lag will break again.

Q23. A nightly batch job locks the Orders table and the API starts returning 500s. What do you change?

The batch is one enormous transaction, holding locks that escalate to the table for minutes. Everything else queues and times out.

  1. Batching: process chunks of a few thousand rows, commit each, pause briefly. One long lock becomes many short ones the API can interleave with. Also makes the job restartable.
  2. Narrow what is locked: operate on an indexed key range so the engine takes row/page locks instead of escalating; make sure the WHERE clause uses an index rather than scanning.
  3. Does it need the operational tables at all? Many nightly jobs are aggregations that could read a replica or a copy.

Set a lock timeout on the batch, not the API. If something has to lose, it should be the job that can retry at 4am, not the customer request. "Run it at a quieter time" is mitigation, not a fix – it breaks once you have customers in another timezone, and the job's runtime keeps growing with the data.

Q24. You need to add a NOT NULL column to a 200-million-row table with zero downtime. Walk me through it.

Not in one migration – a single ALTER adding a non-nullable column with a default rewrites the table and holds a lock the whole time. Use expand and contract, in separate deployments:

  1. Expand. Add the column as nullable, no default, no constraint. On a modern engine this is metadata-only and effectively instant.
  2. Backfill. Populate in batches, committing each chunk, throttled so it does not saturate IO live traffic needs. Can run for hours; nothing is blocked.
  3. Dual-write. Deploy code that writes the new column on every insert/update while still tolerating nulls on read.
  4. Contract. Once backfill is complete and verified, add the NOT NULL constraint, and only then deploy code that assumes the column is always present.

Rule underneath: schema changes and code changes must be independently deployable and backward compatible for one release, because during a rolling deploy old and new code run against the same database. Any step requiring them to change together requires downtime.

Q25. When do you leave the relational database, and what do you actually gain?

Rarely – most "we need NoSQL" conversations turn out to be "we need an index".

Cases where it earns its place:

  • Known key lookup at a scale where horizontal partitioning matters more than joins.
  • Genuinely schemaless data that varies per record (otherwise a sea of nullable columns).
  • Time-series or append-only at a volume where a purpose-built store is an order of magnitude cheaper.
  • Full-text and relevance search – a specialised index alongside the DB, not a replacement.

Gain: a data model shaped like your access pattern, and horizontal scaling without distributed joins.

Give up: transactions across entities, ad-hoc querying for anything unanticipated, and the huge body of operational knowledge for relational engines. And you rarely replace the relational DB – you add a second store, and now you own consistency between them.

6. Architecture and Judgment

No correct answer. They test whether your instinct is to make things better or to make things yours.

Q26. You've inherited a codebase with three competing patterns. What do you do in your first month?

Nothing structural, deliberately. The first month is for understanding why it looks like this – three patterns usually means three eras, each a reasonable decision under constraints you cannot see yet.

  • Ship small features across all three areas – teaches where the pain really is faster than reading.
  • Talk to whoever has been there longest; find which decisions were deliberate and which were accidents.
  • Watch which parts generate incidents and slow reviews – that is the real priority list, not what offends you aesthetically.

Then pick the one thing causing measurable pain and set a direction for new code rather than launching a migration. Old code gets converted when it is touched anyway. Improvement compounds without a big-bang rewrite that gets abandoned at 60%.

Three patterns is not automatically a problem. If separated by clear boundaries and each is internally consistent, unifying them can cost more than it returns.

Q27. Your team wants to adopt something new. How do you decide?

Three questions before the technical merits:

  1. What problem are we having? Not what the tool does – what is hurting now. No concrete pain → someone read a good blog post.
  2. What does it cost after the demo? Learning, CI changes, debugging at 2am, upgrade treadmill, one more hiring requirement. The demo is always the cheapest hour you'll spend with it.
  3. How do we get out? A library behind an interface is cheap to reverse; a messaging platform or database is not. Be more willing to say yes to things with a cheap exit.

Then prove it on something real but small – one service, one feature, with an agreed decision date – not a proof of concept that avoided every hard part. "Industry standard" for whom, at what scale? Tools standard at a thousand engineers are often overhead at ten.

Q28. Tell me about a technical decision you'd make differently today.

The interviewer checks three things: you have owned something long enough to see its consequences, you can criticise your own work without defensiveness or performative self-flagellation, and you updated on evidence rather than fashion.

Shape of a good answer:

  1. Name the decision and the context that made it reasonable at the time.
  2. Name the specific thing that revealed the problem – an incident, a cost line, a feature that took 3× longer.
  3. Name what you would do instead and why that is different, not just newer.

Failures: picking something with no stakes ("I'd have named that variable better"), or blaming the constraints ("it was the deadline's fault"). "I can't think of one" is the only genuinely wrong answer.

Q29. How do you decide which technical debt to pay down and which to leave?

By what it is costing, not by how much it bothers you. Ugly but stable, irrelevant code – rewriting it is a hobby, not engineering.

Worth paying (debt with interest): the module in every incident, the area where every estimate is off by 3×, the thing blocking a change the business wants, the pattern being copied into new code (most urgent – the only kind that compounds).

Worth leaving: stable, rarely-touched areas with no incidents; components with a known end date (cleaning code that will be deleted in six months is pure loss).

Argue it in business terms to get it funded. "This is badly written" gets nothing. "This module caused four of our last six incidents and every change takes 3× longer than estimated" gets a sprint. "20% of every sprint for tech debt" sounds disciplined and is the first thing cut under pressure; a named, justified piece of work survives.

Q30. The architecture you've inherited is wrong and a rewrite is off the table. What's your play?

Accept the constraint – it is almost always the right one. Rewrites fail at a rate that should make anyone cautious.

  1. Stop the bleeding: new code goes behind a boundary that does not depend on the bad design, so the problem stops growing.
  2. Strangle incrementally: route one capability at a time through the new path, keep both running until the old one has no traffic, delete it. Every step ships; any step can be the last.
  3. Prerequisite – a seam: if there are no boundaries, first introduce one (interface, facade, anti-corruption layer) so there is somewhere to put the new implementation.

Sometimes the correct answer is that it stays wrong: stable system, team delivering, wrongness aesthetic rather than operational. Saying that out loud is a senior signal. "Build a v2 alongside and switch when ready" is a rewrite with a different name – same failure mode, abandoned at 70%.

Q31. How would you scale this to ten times the traffic?

Refuse to answer in the abstract: 10× reads and 10× writes have almost nothing in common, and sustained 10× is different from a 10× spike. Ask the shape, then find the actual constraint.

Usually not the application tier (stateless services scale horizontally). The constraint is almost always the database, shared state someone added without noticing, or a downstream that is not scaling with you.

In order of cost:

  1. Cache the dominant reads that tolerate staleness.
  2. Scale reads horizontally with replicas.
  3. Move anything not needed in the request path out of it – notifications, exports.
  4. Only then partition writes – sharding makes the system harder to operate forever.

At 10×, failure modes change: harmless retries become an amplifier, a cache-miss storm takes out a DB that was fine, generous connection pools become the bottleneck. Capacity planning without failure-mode planning is half an answer. "More instances behind a load balancer" scales the tier that was never the problem.

7. Migration and the 2026 Reality

A currency check – cheap to ask, very revealing, because the answers change every couple of releases.

Q32. You have a .NET Framework 4.8 monolith and a mandate to modernise. What's the plan?

Inventory first. Which dependencies have modern equivalents, which have non-drop-in replacements, which have nothing – that last list decides whether this is a port or a rewrite of those pieces.

Order:

  1. Retarget projects to SDK-style project files (can be done while still on Framework).
  2. Move shared libraries, ideally to netstandard2.0 so both worlds can consume them.
  3. Move the leaf projects.
  4. Move the entry point last.

Delivery pattern: strangler fig – reverse proxy in front, move one route/capability at a time to the new app, run side by side. Every step shippable and reversible.

Tooling note: the .NET Upgrade Assistant is deprecated. Microsoft now points at the GitHub Copilot app modernization agent (Visual Studio 2026 and recent 2022 builds). A big-bang rewrite is cleaner and unshippable for eighteen months while the old system keeps changing.

Q33. What in .NET Framework has no .NET 10 equivalent?

  • ASP.NET Web Forms – nothing to port to; rewrite to MVC, Razor Pages, or Blazor depending on interactivity.
  • Server-side WCF – client side is supported, hosting is not in the box. CoreWCF (.NET Foundation, Microsoft-supported migration path) covers much of the surface, but it is a migration, not a recompile.
  • Windows Workflow Foundation – no equivalent; re-express as a durable workflow engine or explicit state machines.
  • AppDomains – not supported. Isolation = separate processes; plugin loading = AssemblyLoadContext (similar in spirit, different in practice).
  • BinaryFormatter – obsoleted in .NET 5, compile error in .NET 7, throws at runtime in .NET 8, in-box implementation removed in .NET 9 (not .NET 10). The APIs still exist and always throw. The unsupported System.Runtime.Serialization.Formatters package restores old behaviour with all its vulnerabilities – a deliberate, temporary decision with a date on it.

Q34. How do you keep a large codebase current across annual .NET releases?

Treat it as routine maintenance, not a project – once it becomes a project it stops happening and you end up doing four versions at once.

  • Centralise versions with Directory.Packages.props – a bump is one file, not forty.
  • Keep the TFM current even when nothing forces it; the cost of one version is small, four is not linear.
  • Read the breaking-changes list each release – short, and the highest-value hour of the upgrade.
  • LTS to LTS for large, slow-moving systems (stay on .NET 10 until .NET 12); upgrade smaller services every release to keep the muscle and find problems where they are cheap.

Safety net: upgrades pass tests and fail in production because runtime behaviour shifts – GC defaults, DATAS specifically on .NET 9/10. Canary the deploy and watch latency percentiles and memory for a full traffic cycle. "Upgrade only when a security patch forces it" turns a small recurring cost into a large unplanned one.

Q35. Your team uses AI coding tools. How do you keep quality from sliding?

The failure mode is not that generated code is bad – it is usually fine in isolation. It is that the volume of code goes up faster than the volume of understanding. Review capacity becomes the bottleneck, and the reviewer's willingness to actually read a large diff quietly gives way.

  • The author is accountable regardless of what wrote it – must be able to explain every line in review, or it does not ship.
  • Small diffs stay small – a 2,000-line generated PR gets rubber-stamped.
  • Tests written or at least verified by a human – generated tests tend to assert what the code does rather than what it should do.
  • Project conventions live somewhere the tool actually reads, so output fits the codebase instead of an average of the internet.

Real risk: architectural drift. These tools are excellent at producing more of what already exists and poor at noticing the existing pattern is wrong. Design decisions still need a human looking at the whole system. Banning them loses productivity for no quality gain (people use them anyway); letting them write everything and just reviewing output is where incidents come from.
