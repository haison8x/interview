Q27. What is a StatefulSet, and how does it differ from a Deployment?

Short answer

A StatefulSet runs pods that each have a stable identity: a fixed ordinal name (db-0, db-1), a stable DNS name through a headless Service, and their own PersistentVolumeClaim that follows them. Pods are created, updated and deleted in a predictable order. A Deployment treats pods as interchangeable cattle; a StatefulSet treats them as named members of a cluster.

1. Why Deployments are not enough for stateful systems

A Deployment assumes every replica is identical and disposable. When a pod dies, the replacement gets a random name (api-7d9f8c-x2kq4), a new IP, and – if the template mounts a PVC – the same shared volume as every other replica. That is fine for a stateless web API. It is wrong for a database cluster, where:

  • each member has its own data on its own disk (replica 1's data must not be mounted by replica 2);
  • members find each other by a stable address (the primary is configured as "db-0", replication peers are listed by name);
  • the order matters: the first member bootstraps the cluster, the others join it.

2. The three guarantees a StatefulSet gives

GuaranteeHow it works
Stable name Pods are named <statefulset>-<ordinal>: db-0, db-1, db-2. If db-1 is deleted, the replacement is again called db-1 – possibly on another node, with a new IP.
Stable DNS spec.serviceName points at a headless Service (clusterIP: None). Each pod gets a DNS record db-1.db.prod.svc.cluster.local that always resolves to whatever IP db-1 currently has.
Stable storage volumeClaimTemplates create one PVC per pod: data-db-0, data-db-1… When db-1 is rescheduled, it re-attaches data-db-1, so it comes back with its own data.

3. Ordering: creation, scaling and updates

With the default podManagementPolicy: OrderedReady:

  • Scale up / creation: db-0 first; db-1 is only created when db-0 is Running and Ready, and so on.
  • Scale down: in reverse – the highest ordinal is removed first.
  • Rolling update: also in reverse ordinal order, one pod at a time, waiting for each to become Ready before the next. A partition lets you update only ordinals ≥ N – a simple built-in canary.

podManagementPolicy: Parallel drops the ordering for creation and scaling (useful when members don't depend on each other starting in order); identity and storage guarantees remain. 

apiVersion: v1
kind: Service
metadata:
  name: db
spec:
  clusterIP: None          # headless: per-pod DNS records
  selector:
    app: db
  ports:
    - port: 5432
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  serviceName: db          # must match the headless Service
  replicas: 3
  selector:
    matchLabels:
      app: db
  template:
    metadata:
      labels:
        app: db
    spec:
      containers:
        - name: postgres
          image: postgres:17
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:      # one PVC per pod: data-db-0, data-db-1, ...
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 20Gi

4. What happens to the data on scale-down and delete

By default, PVCs created from volumeClaimTemplates are not deleted when you scale down or delete the StatefulSet. This is deliberate: losing a database disk because someone typed replicas: 1 would be catastrophic. Scale back up and db-2 re-attaches the old data-db-2. The persistentVolumeClaimRetentionPolicy field (whenDeleted, whenScaled: Retain or Delete) lets you opt into automatic cleanup.

Worked example

A 3-replica PostgreSQL StatefulSet, node 2 fails:

before:  db-0 (node1, data-db-0)  db-1 (node2, data-db-1)  db-2 (node3, data-db-2)
node2 dies, db-1 is eventually deleted (see Q59 for the force-delete caveat)
after:   db-0 (node1, data-db-0)  db-1 (node4, data-db-1)  db-2 (node3, data-db-2)
                                   ^ same name, same DNS, same disk, new node/IP

The replication config that says "replica connects to db-0.db" keeps working without change. With a Deployment, the new pod would have a random name and either no data or another replica's data.

Common pitfalls

  • Forgetting the headless Service or pointing serviceName at a normal ClusterIP Service – per-pod DNS names don't resolve.
  • Zonal disks: data-db-1 lives in zone A, so db-1 can only ever run in zone A. If zone A has no capacity, the pod stays Pending.
  • A broken rolling update with OrderedReady can get stuck on a pod that never becomes Ready; after reverting the template you may have to delete that pod manually so it is recreated with the old spec.
  • Believing the StatefulSet "makes the database HA". It only gives identity and storage; replication, failover, backups and upgrades are the database's (or an operator's – Q37) job.

In the interview

"A StatefulSet gives each replica a stable name, stable DNS via a headless Service, and its own PVC through volumeClaimTemplates, with ordered startup, scale-down and updates. I use it for clustered stateful systems – databases, Kafka, etcd – but for production databases I'd prefer an operator or a managed service, because the StatefulSet doesn't handle failover or backups." Likely follow-ups: what happens to PVCs on scale-down; how to do a canary with partition; why the pod isn't replaced when its node is unreachable.

Q28. What is a DaemonSet, and when would you use it?

Short answer

A DaemonSet ensures exactly one copy of a pod runs on every node (or every node matching a selector). New nodes get the pod automatically; removed nodes take it with them. It is for node-level agents: log collectors, metrics exporters, CNI/CSI plugins, security agents.

1. How it differs from a Deployment

A Deployment says "run N replicas somewhere". A DaemonSet says "run one per node" – there is no replicas field; the count is the number of eligible nodes. The DaemonSet controller creates one pod per node and pins it there with node affinity; the normal scheduler then places it. If you add 5 nodes, you get 5 more pods without touching anything.

2. Why node agents need this

  • Log collection – container logs are files on each node's disk (/var/log/pods), so a collector must run on every node and mount that host path.
  • Node metrics – node-exporter reads the node's own /proc and /sys.
  • Networking and storage – CNI agents (Calico, Cilium) program the node's network; CSI node plugins mount volumes on that node. kube-proxy itself usually runs as a DaemonSet.
  • Security – runtime detection (Falco, Tetragon) watches syscalls on each node.

3. Tolerations and which nodes it lands on

The controller automatically adds tolerations for common node conditions (not-ready, unreachable, disk/memory/PID pressure, unschedulable), so a log agent keeps running on a node under pressure or being drained. It does not automatically tolerate your custom taints, such as the control-plane taint or a dedicated=gpu taint – add them explicitly if the agent must run there. To target only some nodes, use nodeSelector or node affinity in the pod template. 

spec:
  template:
    spec:
      nodeSelector:
        accelerator: nvidia     # only GPU nodes
      tolerations:
        - key: dedicated
          operator: Equal
          value: gpu
          effect: NoSchedule
      priorityClassName: system-node-critical   # don't get preempted

4. Updating a DaemonSet

updateStrategy: RollingUpdate (default) replaces pods node by node; maxUnavailable (default 1) controls how many nodes are without the agent at once. Because there can only be one pod per node by default, an update briefly leaves that node without the agent; maxSurge lets the new pod start before the old one stops (needed when the agent must never be absent, e.g. a CNI). The alternative strategy OnDelete only updates a node's pod when you delete it manually – useful for agents you want to roll out very carefully.

CommandWhat it actually does
kubectl get ds -A DESIRED vs CURRENT vs READY – DESIRED is the number of eligible nodes. A gap means some nodes can't run the pod.
kubectl rollout status ds/fluent-bit -n logging Follows a DaemonSet rolling update node by node.
kubectl rollout undo ds/fluent-bit -n logging Rolls the DaemonSet back, same mechanism as Deployments.

Worked example

A cluster has 10 nodes: 2 control-plane (tainted node-role.kubernetes.io/control-plane:NoSchedule) and 8 workers. You deploy a Fluent Bit DaemonSet without tolerations: kubectl get ds shows DESIRED 8. Control-plane logs are not collected. Add a toleration for the control-plane taint (or operator: Exists to tolerate everything) and DESIRED becomes 10. Then the autoscaler adds 3 workers during a spike – DESIRED becomes 13 automatically, and logs from the new nodes are collected from their first minute.

Common pitfalls

  • No resource requests/limits on the agent: a leaky log shipper on every node can starve all nodes at once. Set them, and give critical agents a high priority class.
  • Requests that are too large: the DaemonSet pod is reserved on every node, so 500m CPU × 100 nodes = 50 CPUs of overhead.
  • Expecting a DaemonSet pod to move when its node dies – it won't; it belongs to that node.
  • Using a DaemonSet for an ordinary app "to spread it across nodes" – use a Deployment with topology spread constraints (Q31) instead.

In the interview

"A DaemonSet runs one pod per eligible node and follows the node lifecycle automatically. I use it for node agents – log collection, node metrics, CNI and CSI plugins, security sensors – usually with host-path mounts, explicit tolerations for tainted nodes, tight resource limits and a node-critical priority class." Follow-ups: how to run it only on some nodes; how updates work (maxUnavailable, maxSurge, OnDelete); why DESIRED is lower than the node count.

Q29. Jobs and CronJobs – what should you know?

Short answer

A Job runs pods until a given number complete successfully, retrying failures up to backoffLimit. A CronJob creates a Job on a cron schedule. In production you control overlap (concurrencyPolicy), timeouts (activeDeadlineSeconds), cleanup (ttlSecondsAfterFinished, history limits) and make the work idempotent because it may run more than once.

1. Job: run to completion

Deployments restart pods forever; a Job is done when its pods exit successfully. Key fields:

FieldMeaning
completions How many successful pods are needed (default 1).
parallelism How many pods may run at the same time.
completionMode: Indexed Each pod gets an index (JOB_COMPLETION_INDEX env) – e.g. 10 pods each process shard 0–9.
backoffLimit How many failed retries before the Job is marked Failed (default 6). Retries back off exponentially (10s, 20s, 40s… capped).
activeDeadlineSeconds Hard timeout for the whole Job; running pods are killed when it expires.
ttlSecondsAfterFinished Deletes the finished Job (and its pods) after N seconds.
podFailurePolicy Rules per exit code / condition: e.g. exit code 42 = "bad input, fail the Job now, don't retry"; pod disrupted by node drain = "don't count against backoffLimit".

The pod template's restartPolicy must be OnFailure (the kubelet restarts the container in the same pod) or Never (the Job controller creates a new pod for each retry – easier to read the logs of each failed attempt).

2. CronJob: Jobs on a schedule

apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-report
spec:
  schedule: "0 2 * * *"            # 02:00 every day
  timeZone: "Europe/Paris"         # explicit, don't depend on controller clock
  concurrencyPolicy: Forbid        # skip a run if the previous one is still going
  startingDeadlineSeconds: 600     # if missed by more than 10 min, skip it
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      backoffLimit: 2
      activeDeadlineSeconds: 3600  # never run longer than 1 hour
      ttlSecondsAfterFinished: 86400
      template:
        spec:
          restartPolicy: Never
          containers:
            - name: report
              image: my-reports:1.8
              args: ["--date", "yesterday"]

concurrencyPolicy options:

  • Allow (default) – runs may overlap.
  • Forbid – skip the new run while the old one runs.
  • Replace – kill the old run and start the new one.

3. "At least once", not "exactly once"

Kubernetes can run your Job's work more than once: a pod is retried after a crash, a node dies after the work finished but before the success was recorded, or (rarely) the CronJob controller creates a run twice. It can also miss a run (controller down, deadline passed). So the work must be idempotent – e.g. "upsert the report for date X", not "append a report row" – and important schedules need monitoring for "last successful run" rather than trusting that the schedule fired.

Worked example

A CronJob runs every 15 minutes with default concurrencyPolicy: Allow. One day the database is slow and a run takes 40 minutes: 

00:00 run A starts ............................ 00:40 A ends
00:15 run B starts ............................ (slower: competes with A)
00:30 run C starts ............................ (slower still)
00:45 run D starts ...

Overlapping runs make the database even slower – a feedback loop. With Forbid, runs B and C are simply skipped, and D starts on a quiet database. Add activeDeadlineSeconds: 840 so a single run can never exceed its 15-minute slot.

Common pitfalls

  • Finished Jobs and pods piling up (thousands of Completed pods) when no TTL or history limits are set.
  • A sidecar (e.g. mesh proxy) that never exits keeps the Job "running" forever – use native sidecars (Q33).
  • Omitting timeZone and getting runs at the wrong local hour, especially around daylight-saving changes.
  • A CronJob that missed too many schedules (e.g. it was suspended for days) without startingDeadlineSeconds can refuse to start and log an error – set a deadline.
  • Non-idempotent jobs (sending emails, charging cards) that run twice after a retry.

In the interview

"A Job runs pods to completion with retries via backoffLimit, timeouts via activeDeadlineSeconds, and cleanup via ttlSecondsAfterFinished; Indexed mode splits work into shards. A CronJob creates Jobs on a schedule – I set timeZone, concurrencyPolicy Forbid for jobs that must not overlap, a startingDeadlineSeconds, and I make the work idempotent because Kubernetes gives at-least-once semantics." Follow-ups: OnFailure vs Never; how to alert on a CronJob that silently stopped running; podFailurePolicy.

Q30. What is a service mesh, and why use one?

Short answer

A service mesh puts a proxy layer in the path of all service-to-service traffic and controls it centrally. That gives you mutual TLS and identity-based authorisation, retries/timeouts/traffic splitting, and uniform metrics and traces – without changing application code. The price is extra complexity, latency and resource usage.

1. Architecture: data plane and control plane

  • Data plane – proxies that every request passes through. Classic design: an Envoy (Istio) or linkerd2-proxy (Linkerd) sidecar in every pod, injected by a mutating admission webhook (Q34). iptables rules in the pod redirect all inbound and outbound traffic through it.
  • Control plane – watches Services, pods and mesh policies, issues certificates to each workload, and pushes routing configuration to the proxies. 
  pod A                                pod B
 ┌──────────────────┐   mTLS        ┌──────────────────┐
 │ app ──► proxy ───┼──────────────►│ proxy ──► app    │
 └──────────────────┘               └──────────────────┘
          ▲  config + certs              ▲
          └────────── control plane ─────┘

Sidecar-less designs reduce the per-pod cost: Istio's ambient mode uses a per-node proxy (ztunnel) for L4 mTLS and optional shared "waypoint" proxies for L7 features; Cilium implements mesh features with eBPF plus a per-node Envoy.

2. What you get

AreaFeatureWithout a mesh you'd need…
Security Automatic mTLS: every workload gets a certificate tied to its ServiceAccount identity; policies like "only orders may call payments". TLS code and certificate rotation in every service.
Traffic Per-request (L7) load balancing, retries, timeouts, circuit breaking, canary splits (90/10), fault injection. Client libraries in every language.
Observability Request rate, error rate and latency for every service pair; distributed tracing headers propagated by the proxy (the app still has to forward them). Instrumenting every service consistently.

It also fixes a real Kubernetes limitation: kube-proxy balances connections, so long-lived gRPC/HTTP2 connections stick to one pod (Q13). A mesh proxy balances individual requests.

3. The costs

  • Latency: two extra proxy hops per call (typically sub-millisecond to a few ms each).
  • Resources: a sidecar per pod – 1,000 pods × 50 MiB = 50 GiB of memory just for proxies.
  • Operational complexity: another control plane to upgrade, new CRDs, new failure modes ("is it the app or the mesh?"), certificate authority to manage.
  • Lifecycle issues with classic sidecars (startup order, Jobs that don't finish) – solved by native sidecars or ambient mode.

Worked example

A compliance audit requires all internal traffic to be encrypted and the payments service to accept calls only from the orders service. Without a mesh: 25 services in 3 languages each need TLS code, certificate distribution and caller checks. With Istio: 

apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: default
  namespace: istio-system
spec:
  mtls:
    mode: STRICT            # all workloads: mTLS only
---
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: payments-allow-orders
  namespace: payments
spec:
  selector:
    matchLabels:
      app: payments
  action: ALLOW
  rules:
    - from:
        - source:
            principals: ["cluster.local/ns/orders/sa/orders"]

Two manifests instead of 25 code changes; certificates rotate automatically.

Common pitfalls

  • Adopting a mesh "because everyone does" before having a concrete need – then spending months operating it.
  • Retries configured at several layers (client, mesh, gateway): one failure becomes 3 × 3 × 3 = 27 requests – a retry storm that turns a blip into an outage. Retry only idempotent calls, with budgets.
  • Switching to STRICT mTLS while some clients are still outside the mesh – their calls start failing. Use PERMISSIVE during migration.
  • Expecting tracing to work automatically – the app must propagate trace headers between inbound and outbound calls.

In the interview

"A service mesh adds a proxy data plane managed by a control plane, so mTLS, service-to-service authorisation, retries, timeouts, traffic splitting and golden-signal metrics come from infrastructure instead of code. Examples are Istio – sidecar or ambient – Linkerd and Cilium. I'd adopt one for a concrete need like zero-trust mTLS or fine-grained canaries, weighing the latency, memory and operational cost." Follow-ups: how sidecar injection works; sidecar vs ambient; retry storms; how mTLS identity maps to ServiceAccounts.

Q31. How do you control where pods run? Taints, tolerations, affinity, topology spread.

Short answer

Node selectors and node affinity attract pods to nodes with certain labels. Taints repel pods from nodes unless they carry a matching toleration. Pod affinity/anti-affinity places pods relative to other pods, and topology spread constraints spread replicas evenly across zones or nodes. Combine them carefully: every hard rule reduces the set of nodes a pod can use.

1. How the scheduler decides

For every unscheduled pod, kube-scheduler runs two phases:

  1. Filter – remove nodes that can't run the pod: not enough unreserved CPU/memory (requests), untolerated taints, failing required affinity rules, volume zone mismatch, hard spread constraints.
  2. Score – rank the remaining nodes using preferred rules, soft spread constraints, resource balance, image locality; bind the pod to the best one.

If the filter phase leaves zero nodes, the pod is Pending and its events list why each node was rejected (Q54). All these rules apply at scheduling time only ("IgnoredDuringExecution"): changing a node's labels later does not evict pods already running there (except NoExecute taints).

2. The four tools

ToolDirectionTypical use
nodeSelector / node affinity Pod → wants certain nodes GPU workloads on GPU nodes; arm64 images on arm64 nodes.
Taints + tolerations Node → rejects pods Dedicated pools (GPU, system, spot); keep apps off control plane.
Pod (anti-)affinity Pod ↔ other pods Cache next to app; never two replicas on one node.
Topology spread Replicas ↔ topology domains Even spread across zones and nodes for HA.

Taint effects: NoSchedule (new pods without a toleration are not scheduled), PreferNoSchedule (soft version), NoExecute (also evicts running pods that don't tolerate it – used by the node controller for unreachable nodes, Q59).

3. Dedicated node pool: taint + toleration + affinity

A toleration only says "I am allowed on tainted nodes" – it does not pull the pod there. To dedicate a GPU pool you need both: 

# 1. repel everyone else from the GPU nodes
kubectl taint nodes gpu-1 gpu-2 dedicated=gpu:NoSchedule
kubectl label nodes gpu-1 gpu-2 pool=gpu

# 2. in the GPU workload's pod spec
spec:
  tolerations:              # allowed on the tainted nodes
    - key: dedicated
      operator: Equal
      value: gpu
      effect: NoSchedule
  affinity:
    nodeAffinity:           # and required to go there
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: pool
                operator: In
                values: ["gpu"]

4. Topology spread constraints

spec:
  topologySpreadConstraints:
    - maxSkew: 1                               # max difference between domains
      topologyKey: topology.kubernetes.io/zone
      whenUnsatisfiable: DoNotSchedule         # hard rule
      labelSelector:
        matchLabels:
          app: api
    - maxSkew: 1
      topologyKey: kubernetes.io/hostname
      whenUnsatisfiable: ScheduleAnyway        # soft rule
      labelSelector:
        matchLabels:
          app: api

maxSkew: 1 across zones means the number of app=api pods in any zone may differ from the least-loaded zone by at most 1. This replaces most uses of pod anti-affinity, which only expresses "not together" and becomes expensive in large clusters.

Worked example

6 replicas, 3 zones (a, b, c), the zone constraint above. The scheduler places 2 + 2 + 2. Zone c goes down: 4 pods remain (2 + 2 + 0) and the Deployment creates 2 replacements. Placing them in a or b gives 3 + 2 + 0 – a skew of 3 against zone c. What happens next depends on whether zone c still "counts":

  • If zone c's Node objects are gone, the domain disappears from the calculation and the pods go to a and b (3 + 3).
  • If the nodes still exist but are NotReady (tainted), the default nodeTaintsPolicy: Ignore still counts zone c with 0 pods, so with DoNotSchedule the replacements stay Pending – exactly when you need capacity most. Setting nodeTaintsPolicy: Honor, or using ScheduleAnyway for the zone rule, avoids this.

Without any spread rule, the scheduler could have put 5 of the 6 replicas in zone a originally, and a single zone failure would have taken out most of the capacity.

Common pitfalls

  • Tolerations without affinity: the "dedicated" pod lands on ordinary nodes; or affinity without toleration: the pod is Pending forever.
  • Required anti-affinity per hostname with more replicas than nodes: replica 6 on a 5-node cluster stays Pending.
  • Spread rules with a labelSelector that doesn't match the pod's own labels – the constraint silently does nothing.
  • Stacking many hard rules (zone spread + node anti-affinity + node affinity + a zonal PVC) until no node satisfies them all.
  • Spread is evaluated only at scheduling; after a zone recovers, pods are not rebalanced automatically (that needs the Descheduler).

In the interview

"The scheduler filters then scores nodes. I attract pods with node affinity, repel them with taints – a toleration only permits, so dedicating a pool needs both a taint and affinity – place pods relative to each other with pod (anti-)affinity, and use topology spread constraints with maxSkew to spread replicas across zones and nodes. I prefer soft rules where possible because hard rules are the main cause of Pending pods." Follow-ups: NoSchedule vs NoExecute; why the spread is uneven after a zone outage; how the default 300s tolerations work.

Q32. What are sidecar containers, and how are they used?

Short answer

A sidecar is a helper container in the same pod as the main app. It shares the pod's network namespace (same IP, localhost) and can share volumes, so it can add capabilities – log shipping, proxying, config reloading, auth – without changing the app's code or image.

1. What containers in one pod share

  • Network namespace – one IP, one port space. The sidecar reaches the app on localhost:8080; two containers can't both listen on the same port.
  • Volumes – any volume declared in the pod can be mounted by several containers, typically an emptyDir.
  • Lifecycle and node – scheduled together, on the same node, deleted together. Their resource requests add up for scheduling.
  • Optionally the process namespace (shareProcessNamespace: true) so one container can see or signal the other's processes.

Each container still has its own image, filesystem, resource limits and restart behaviour.

2. Common patterns

PatternExample
Log shipper Legacy app writes to /var/log/app/*.log; Fluent Bit sidecar reads the shared volume and ships the logs.
Proxy (ambassador) Envoy mesh proxy; Cloud SQL Auth Proxy so the app connects to localhost:5432 and the proxy handles IAM and TLS.
Adapter Exporter that converts the app's custom stats into Prometheus metrics.
Config / secret reloader Watches a ConfigMap or Vault, writes files to a shared volume and signals the app to reload.
Auth proxy oauth2-proxy in front of an internal dashboard with no login.

3. When not to use a sidecar

  • If the helper is per node, not per pod (log collection from stdout, node metrics) – a DaemonSet (Q28) costs one pod per node instead of one container per pod.
  • If the two processes scale independently – separate Deployments. A sidecar always scales 1:1 with the app.
  • If the app can do it natively (log to stdout, expose /metrics) – one less moving part.

Worked example

An old Java app logs only to files. Instead of rewriting it, add a sidecar that tails the files from a shared emptyDir: 

apiVersion: v1
kind: Pod
metadata:
  name: legacy-app
spec:
  containers:
    - name: app
      image: legacy-app:3.2
      volumeMounts:
        - name: logs
          mountPath: /var/log/app        # app writes here
    - name: log-shipper
      image: fluent/fluent-bit:3.2
      resources:
        requests: { cpu: 20m, memory: 32Mi }
        limits: { memory: 64Mi }
      volumeMounts:
        - name: logs
          mountPath: /var/log/app        # sidecar reads here
          readOnly: true
  volumes:
    - name: logs
      emptyDir:
        sizeLimit: 1Gi                   # don't fill the node's disk

With 40 replicas, the shipper costs 40 × 32 MiB ≈ 1.3 GiB of reserved memory – compare with a DaemonSet if the app could log to stdout.

Common pitfalls

  • Startup race: the app starts before its proxy is ready and its first outbound calls fail.
  • Jobs never complete because the sidecar never exits; or the sidecar is killed before the app during shutdown and the last requests or log lines are lost. Both are solved by native sidecars (Q33).
  • No resource limits on the sidecar – it can OOM the pod or starve the app.
  • Port conflicts: both containers trying to listen on the same port in the shared network namespace.

In the interview

"A sidecar is a helper container in the same pod. Because it shares the pod's network and volumes, it can proxy traffic on localhost or read files the app writes – log shippers, mesh proxies, cloud auth proxies, config reloaders. I'd use it when the helper is genuinely per instance; per-node concerns go in a DaemonSet. Classic sidecars had ordering problems, which native sidecars fix." Follow-ups: what is shared and what isn't; how sidecar injection works; Jobs with sidecars.

Q33. What are native sidecars, and what problem do they solve?

Short answer

A native sidecar is an init container with restartPolicy: Always. Kubernetes then knows it is a helper: it starts before the app containers (and can block them until its startup probe passes), keeps running and is restarted if it dies, and is stopped after the app containers. This fixes the startup race, Jobs that never finish, and sidecars dying before the app during shutdown. GA since 1.33.

1. The problems with classic sidecars

Before native sidecars, all containers in spec.containers were equal – Kubernetes started them roughly in parallel and stopped them in parallel. Three recurring bugs followed:

  1. Startup race – the app starts and makes outbound calls before the mesh proxy is listening: "connection refused" on the first requests. Workarounds: sleep loops in the app's entrypoint, or the mesh's "hold application until proxy starts" hacks.
  2. Jobs that never complete – a Job is done when all its containers exit. The app finishes, but the proxy or log shipper runs forever, so the Job hangs. Workarounds: the app calls the proxy's "quit" endpoint at the end.
  3. Shutdown order – on pod deletion, every container gets SIGTERM at once. The proxy may exit first while the app is still finishing in-flight requests that need it; the log shipper may exit before the app writes its last lines.

2. How native sidecars work

pod start
  init container 1 (regular)      runs to completion
  sidecar (init, restartPolicy: Always) starts ──► startupProbe passes
  init container 2 (regular)      runs to completion (can already use the sidecar)
  app containers start            sidecar keeps running alongside
pod stop
  app containers get SIGTERM and exit
  sidecars get SIGTERM after the app containers have stopped (reverse order)
  • Init containers still run in the order listed; a sidecar listed first is available to all later init containers and to the app.
  • The kubelet moves on to the next init container as soon as the sidecar has started (or its startupProbe has passed) – it does not wait for it to complete.
  • Unlike regular init containers, sidecars may have liveness, readiness and startup probes, and are restarted when they crash, regardless of the pod's restartPolicy.
  • For Jobs, completion depends only on the regular containers – the sidecar is terminated once the app finishes.

3. Manifest

apiVersion: batch/v1
kind: Job
metadata:
  name: export
spec:
  template:
    spec:
      restartPolicy: Never
      initContainers:
        - name: proxy
          image: envoyproxy/envoy:v1.32
          restartPolicy: Always        # this makes it a native sidecar
          startupProbe:                # app waits until the proxy is ready
            httpGet:
              path: /ready
              port: 9901
            periodSeconds: 1
            failureThreshold: 30
      containers:
        - name: export
          image: my-exporter:2.0      # Job completes when this exits

Worked example

A nightly export Job running in a mesh:

SituationClassic sidecarNative sidecar
t=0s pod starts App and proxy start together; app's first DB call fails. Proxy starts; app waits until the startup probe passes (~1s).
t=20min export done App exits 0; proxy keeps running; Job shows Running forever. App exits 0; proxy gets SIGTERM; Job is Complete.
Pod deleted mid-run Proxy and app stop together; app's last DB writes fail. App stops first, then the proxy.

Common pitfalls

  • Putting restartPolicy: Always on a container in spec.containers – it only has this meaning on init containers.
  • No startup probe on the sidecar: the app is started as soon as the sidecar process starts, which may still be before it is listening.
  • Forgetting that the sidecar's resource requests are added for the pod's whole lifetime – unlike regular init containers, whose requests are only needed during initialisation.
  • terminationGracePeriodSeconds must cover the app's shutdown plus the sidecars' shutdown, since they now stop one after the other.

In the interview

"Native sidecars are init containers with restartPolicy Always. Kubernetes starts them before the app – optionally gated by a startup probe – keeps them running and restarted, and stops them after the app. That fixes the classic sidecar problems: proxies not ready at app startup, Jobs that never finish because the sidecar keeps running, and sidecars exiting before the app finishes draining. It's GA in 1.33, and meshes like Istio use it." Follow-ups: why it's an init container rather than a new field; how probes on sidecars behave; resource accounting.

Q34. What are admission webhooks and admission policies?

Short answer

Admission control is the last gate in the API server before an object is saved to etcd. Mutating admission may change the object (inject a sidecar, add defaults); validating admission may only accept or reject it (enforce policy). You extend it with webhooks – your own HTTPS service – or with in-process CEL rules (ValidatingAdmissionPolicy) that need no extra service.

1. Where admission sits in the request path

kubectl apply
   │
   ▼
authentication ──► authorization (RBAC) ──► mutating admission
                                              (built-in + webhooks, may modify)
                                                     │
                                         schema validation
                                                     │
                                          validating admission
                                     (built-in + webhooks + CEL policies)
                                                     │
                                                     ▼
                                                   etcd

Many core features are built-in admission plugins: ServiceAccount token mounting, LimitRanger defaults (Q48), ResourceQuota, Pod Security Admission (Q43). Webhooks and policies are how you add rules.

2. Mutating vs validating

MutatingValidating
Can modify the object Yes – returns a JSON patch No
Typical uses Sidecar injection (Istio, Vault agent), default labels, resources or securityContext, image digest pinning Block :latest tags, require labels, allowed registries only, require signed images, deny privileged pods
Runs First (may be re-invoked after other mutations) After all mutation, so it sees the final object

3. Webhooks vs CEL policies

A webhook is configured with a MutatingWebhookConfiguration or ValidatingWebhookConfiguration: which resources/operations to send, the HTTPS endpoint (usually a Service in the cluster), failurePolicy (Fail or Ignore), timeoutSeconds, and selectors to limit scope. Kyverno and OPA Gatekeeper are policy engines built on webhooks.

A ValidatingAdmissionPolicy (GA in 1.30) is evaluated inside the API server with CEL expressions – no service to run, no network hop, no outage if a pod is down: 

apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: no-latest-tag
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
      - apiGroups: ["apps"]
        apiVersions: ["v1"]
        operations: ["CREATE", "UPDATE"]
        resources: ["deployments"]
  validations:
    - expression: >-
        object.spec.template.spec.containers.all(c,
          !c.image.endsWith(':latest') && c.image.contains(':'))
      message: "Images must use an explicit, non-latest tag."
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: no-latest-tag-binding
spec:
  policyName: no-latest-tag
  validationActions: ["Deny"]      # or Warn / Audit while rolling out
  matchResources:
    namespaceSelector:
      matchLabels:
        env: prod

A newer CEL-based MutatingAdmissionPolicy does the same for simple mutations. Webhooks remain necessary when a rule needs external data (e.g. verifying an image signature against a registry).

Worked example

A team runs a validating webhook with failurePolicy: Fail matching all pods in all namespaces. The webhook Deployment has one replica. Its node is drained during an upgrade:

  1. The webhook pod is evicted; its replacement must be created.
  2. Creating that pod requires… calling the webhook, which is down. The API server rejects it.
  3. Now no pod can be created anywhere – including CoreDNS and the CNI pods on new nodes. The cluster slowly degrades.

Fix: exclude kube-system and the webhook's own namespace via namespaceSelector, run 2+ replicas with a PDB, set a short timeoutSeconds, and consider failurePolicy: Ignore for non-security webhooks. Recovery in the moment: delete the webhook configuration object.

Common pitfalls

  • Webhooks matching everything (* resources, all namespaces) – every API call pays their latency and depends on their availability.
  • Mutations that fight each other (two webhooks setting the same field), or a mutating webhook changing a field that a GitOps tool then reports as drift.
  • Expired TLS certificate on the webhook service – every matching request fails.
  • Admission only checks objects when they are created or updated; existing objects that violate a new policy keep running – audit them separately.

In the interview

"Admission runs in the API server after authn and RBAC and before etcd. Mutating admission can change objects – sidecar injection, defaults – and validating admission can only allow or deny – policy enforcement. You extend it with webhooks, which Kyverno and Gatekeeper use, or with in-process CEL ValidatingAdmissionPolicies for simple rules. The operational risk is a failing webhook with failurePolicy Fail blocking the cluster, so I scope them narrowly and exclude system namespaces." Follow-ups: ordering of mutating and validating; Warn and Audit modes; what happens to existing objects.

Q35. How do you achieve zero-downtime deployments? Why do users still get errors during a rolling update?

Short answer

Zero downtime needs four things: new pods only receive traffic once they are truly ready (readiness probes), capacity never drops (maxUnavailable: 0), old pods drain gracefully instead of dying mid-request (preStop delay + SIGTERM handling + enough grace period), and old and new versions can run side by side (backward compatible APIs and database schema). Errors during a rolling update usually come from the shutdown race: the pod stops before the load balancers have stopped sending it traffic.

1. Deployment strategies

StrategyHowTrade-off
Rolling update Built-in: replace pods gradually (Q18). Cheap; old and new versions serve traffic at the same time.
Blue/green Run the full new version (green) next to the old (blue), test it, then switch all traffic at once (Service selector or route). Instant switch and switch-back; double capacity during deploy.
Canary Send 5% → 25% → 100% of traffic to the new version, checking error rate and latency at each step (Argo Rollouts, Flagger, Gateway API weights). Smallest blast radius; needs good metrics and tooling.

2. The shutdown race, step by step

When a pod is deleted (rolling update, scale-down, drain):

t=0     pod marked Terminating
        ├─► kubelet: run preStop hook, then send SIGTERM to the container
        └─► endpoint controller: remove pod from EndpointSlices
                 └─► kube-proxy on every node updates iptables/nftables
                 └─► ingress controller / cloud LB updates its upstreams
t=0..~5s   routing updates are still propagating
           → NEW requests can still arrive at this pod

These two branches run in parallel; nothing waits for the routing update. If the app exits immediately on SIGTERM at t=0.1s, requests routed to it in the next few seconds get "connection refused" or 502. In-flight requests are cut off too if the app doesn't drain them.

3. The fix: delay, drain, then exit

spec:
  terminationGracePeriodSeconds: 45     # must cover preStop + drain
  containers:
    - name: api
      image: my-api:2.4
      lifecycle:
        preStop:
          sleep:
            seconds: 10                 # built-in sleep action; older clusters:
                                        # exec: { command: ["sleep", "10"] }
      readinessProbe:
        httpGet: { path: /ready, port: 8080 }
        periodSeconds: 5
---
# Deployment strategy
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1
  1. preStop sleep 10s – the container keeps serving normally while every load balancer removes the pod.
  2. SIGTERM arrives – the app stops accepting new connections, finishes in-flight requests, closes keep-alive connections, then exits. (.NET's host, Spring Boot and most frameworks support graceful shutdown; the process must actually receive the signal – see the Docker page, Q12.)
  3. The grace period clock started at t=0 and includes preStop: 45s = 10s preStop + up to 35s drain. When it runs out, SIGKILL.

4. Version compatibility – the part outside Kubernetes

During any rolling update or canary, v1 and v2 run at the same time and share the database. A v2 migration that renames a column breaks every v1 pod still running. Use expand/contract: release 1 adds the new column and writes both; release 2 reads the new column; release 3 drops the old one. The same applies to API contracts between services and to message formats on queues.

Worked example

A service handles 2,000 requests/s across 10 pods. During each deploy, monitoring shows a burst of ~300 HTTP 502s.

  • Each terminating pod gets ~200 req/s; routing takes ~1.5s to update everywhere → ~300 requests sent to a pod that already exited.
  • Adding preStop: sleep 10 removes those 502s – the pod is still serving while it disappears from the load balancers.
  • A few errors remain for long requests (file uploads up to 60s) cut off at the 30s default grace period. Raising terminationGracePeriodSeconds to 75 fixes those.
  • Result: deploys at 2 p.m. with zero errors in the dashboards.

Common pitfalls

  • preStop sleep longer than the grace period – the pod is SIGKILLed before it even receives SIGTERM.
  • Using exec: sleep in a distroless image that has no sleep binary – the hook fails; use the built-in sleep action.
  • Readiness probe that returns 200 before caches and connection pools are warm – new pods get traffic too early.
  • Long-lived connections (WebSockets, gRPC streams) that the app never closes – clients stay connected until SIGKILL.
  • Breaking database migrations run before the rollout completes.

In the interview

"Zero downtime needs readiness probes so new pods only get traffic when ready, maxUnavailable 0 so capacity never drops, graceful termination, and backward-compatible changes so two versions can coexist. The usual cause of errors during rolling updates is that SIGTERM and endpoint removal happen in parallel, so traffic still arrives after the app exits – I fix it with a preStop sleep, proper SIGTERM draining and a grace period that covers both. For risky changes I use canary with automated analysis." Follow-ups: blue/green vs canary; expand/contract migrations; long-lived connections.

Q36. What are Custom Resource Definitions (CRDs)?

Short answer

A CRD registers a new resource type with the Kubernetes API. After that, objects of that type can be created, listed, watched, RBAC-protected and stored in etcd exactly like built-in objects. A CRD only stores data; a controller or operator (Q37) has to watch those objects and act on them.

1. What happens when you install a CRD

  1. The API server adds new REST endpoints, e.g. /apis/example.com/v1/namespaces/{ns}/databases.
  2. kubectl discovers them: kubectl get databases, kubectl explain database.spec and kubectl apply just work.
  3. Objects are validated against the CRD's OpenAPI schema and stored in etcd; RBAC, admission, watches and audit logging apply to them like any other resource.

This is why Kubernetes became a platform: cert-manager's Certificate, Argo CD's Application, Prometheus Operator's ServiceMonitor, Gateway API's HTTPRoute are all CRDs.

2. Important parts of a CRD

FieldWhy it matters
scope Namespaced or Cluster.
versions[].schema Structural OpenAPI v3 schema: types, required fields, enums, min/max. Invalid objects are rejected at admission time.
x-kubernetes-validations CEL rules for cross-field checks, e.g. "replicas must be odd" or "field is immutable".
subresources.status Separates spec (desired, written by users) from status (observed, written by the controller).
additionalPrinterColumns Extra columns in kubectl get output.
Multiple versions v1beta1 and v1 served side by side; exactly one is the storage version; a conversion webhook translates between schemas when they differ.

Worked example

apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: databases.example.com      # <plural>.<group>
spec:
  group: example.com
  scope: Namespaced
  names:
    plural: databases
    singular: database
    kind: Database
    shortNames: ["db"]
  versions:
    - name: v1
      served: true
      storage: true
      subresources:
        status: {}
      additionalPrinterColumns:
        - name: Engine
          type: string
          jsonPath: .spec.engine
        - name: Phase
          type: string
          jsonPath: .status.phase
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              required: ["engine", "storageGB"]
              properties:
                engine:
                  type: string
                  enum: ["postgres", "mysql"]
                storageGB:
                  type: integer
                  minimum: 1
                  maximum: 1000
            status:
              type: object
              properties:
                phase:
                  type: string
kubectl apply -f - <<'EOF'
apiVersion: example.com/v1
kind: Database
metadata:
  name: orders
spec:
  engine: postgres
  storageGB: 5000            # rejected: maximum is 1000
EOF

kubectl get db               # NAME   ENGINE    PHASE
                             # orders postgres  (empty until a controller sets it)

Without a controller, the Database object exists but no database is created – the CRD is just a typed, validated API record.

Common pitfalls

  • Deleting a CRD deletes every object of that type in the cluster. Uninstalling a Helm chart that owns the CRDs can wipe out all Certificates or Applications.
  • Using a CRD as a general-purpose database – etcd is small (default quota of a few GiB) and every object is watched; large or high-churn data belongs elsewhere.
  • Schema changes without proper versioning: removing a field or changing its type breaks existing objects and clients.
  • Ordering in GitOps: custom resources applied before their CRD exists fail with "no matches for kind".

In the interview

"A CRD extends the Kubernetes API with a new resource type, with schema validation, RBAC, watches and kubectl support for free. It is only data; a controller reconciles it into real resources, and CRD plus controller is the operator pattern. Most of the ecosystem – cert-manager, Argo CD, Gateway API – is built this way." Follow-ups: spec vs status; CRD versioning and conversion; CRDs vs ConfigMaps; what happens when you delete a CRD.

Q37. What is an operator, and how does it work?

Short answer

An operator is a custom controller plus CRDs that encodes the operational knowledge of a human operator for one application: installing it, scaling it, backing it up, failing over, upgrading. It runs a reconciliation loop – watch the custom resources, compare desired with actual state, act to close the gap – just like the built-in Deployment controller.

1. The reconciliation loop

          ┌──────────── watch events (CR changed, owned pod died, timer) ───┐
          ▼                                                                 │
   Reconcile(name)                                                          │
     1. read the custom resource (desired state)                            │
     2. read what exists: StatefulSets, Services, Secrets, the app itself   │
     3. compute the difference                                              │
     4. act: create / update / delete objects, call the app's admin API    │
     5. write status (conditions, phase, observedGeneration)               │
     6. requeue if not finished ───────────────────────────────────────────┘

Key design principle: level-triggered, not edge-triggered. The reconcile function doesn't ask "what event happened?" but "what should the world look like, and what does it look like now?". If the operator crashes and misses events, the next reconcile still converges. Every step must be idempotent – running it twice is harmless.

2. Building blocks

  • CRDs (Q36) – the API the user talks to.
  • Owner references – objects the operator creates point to the custom resource; deleting the CR garbage-collects them.
  • Finalizers – block deletion of the CR until the operator has cleaned up external things (take a final backup, delete a cloud bucket).
  • Status conditions – Ready, Progressing, Degraded, with observedGeneration so users know whether the status reflects the latest spec.
  • Frameworks – Kubebuilder / controller-runtime and Operator SDK (Go), also Java (JOSDK), Python (Kopf) and others. They provide caching, watches, work queues and leader election.

3. What separates a good operator from a Helm chart

A Helm chart installs resources once. An operator keeps managing them: day-2 operations. The Operator Framework's capability levels describe this progression: basic install → seamless upgrades → full lifecycle (backup, restore, failover) → deep insights (metrics, alerts) → auto-pilot (auto-scaling, auto-tuning).

Worked example

A PostgreSQL cluster with the CloudNativePG operator:

apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: orders-db
spec:
  instances: 3
  storage:
    size: 20Gi
  1. You apply 8 lines. The operator creates 3 pods with their PVCs, Services for read-write and read-only traffic, certificates, and configures streaming replication: 1 primary, 2 replicas.
  2. The primary's node dies. The operator notices on its next reconcile, promotes the most up-to-date replica, repoints the read-write Service, and rebuilds the lost instance – in seconds, without a human.
  3. You change instances: 3 to 5: two new replicas are cloned and join replication.
  4. A minor version upgrade: replicas are updated first, then a switchover moves the primary role, then the old primary is updated.

A StatefulSet alone (Q27) would give you 3 pods with disks – but no replication setup, failover or safe upgrade order.

Common pitfalls

  • Installing an operator is installing privileged software – it often needs broad cluster RBAC. Check who maintains it and what it can do.
  • Writing an operator for something a Helm chart or a Deployment already handles – operators are worth it when there is real ongoing operational logic.
  • Edge-triggered logic ("on create, do X") that breaks when events are missed or replayed.
  • Stuck finalizers: the operator is uninstalled before its custom resources, and they can never be deleted (namespace stuck in Terminating).

In the interview

"An operator is CRDs plus a custom controller that automates the operational knowledge for an application. It runs a level-triggered, idempotent reconciliation loop: read the desired state from the custom resource, observe the actual state, act, and report status. It uses owner references for cleanup and finalizers for external resources. The value is day-2 operations – failover, backups, upgrades – e.g. CloudNativePG or Strimzi." Follow-ups: level vs edge triggering; operator vs Helm; how you'd test one; finalizers.

Q38. What is in-place pod resize?

Short answer

In-place pod resize (GA in 1.35) lets you change a running container's CPU and memory requests/limits through the pod's resize subresource, without deleting and recreating the pod. Each container's resizePolicy decides whether a resource changes live or requires a container restart. The node must have room for the new size, otherwise the resize stays pending.

1. Why it matters

Pod resources used to be immutable: to give a pod more memory you recreated it – new pod, new IP, cold caches, dropped connections, and for a StatefulSet member possibly a failover. That made vertical scaling disruptive, so most teams over-provisioned instead. In-place resize enables:

  • Rightsizing long-running pods without restarts.
  • "Startup boost": generous CPU while a JVM/.NET app warms up, then shrink it.
  • VPA's InPlaceOrRecreate update mode, which applies recommendations in place when possible.

2. How a resize flows

  1. You (or VPA) patch the pod's resize subresource with new resources. spec now holds the desired values.
  2. The kubelet checks whether the node's allocatable capacity can fit the new requests.
    • Fits → it updates the container's cgroup limits through the runtime (or restarts the container, per resizePolicy).
    • Doesn't fit now → the pod gets a PodResizePending condition (reason Deferred), retried later; can never fit on this node → reason Infeasible.
  3. While applying, the pod has a PodResizeInProgress condition. status.containerStatuses[].resources shows what is actually applied – compare it with spec. 
spec:
  containers:
    - name: app
      image: my-app:4.1
      resizePolicy:
        - resourceName: cpu
          restartPolicy: NotRequired       # change CPU live (default)
        - resourceName: memory
          restartPolicy: RestartContainer  # app sizes heap at startup
      resources:
        requests: { cpu: "500m", memory: "1Gi" }
        limits: { cpu: "1", memory: "1Gi" }

3. Commands

CommandWhat it actually does
kubectl patch pod web --subresource resize --patch '{"spec":{"containers":[{"name":"app","resources":{"requests":{"cpu":"2"},"limits":{"cpu":"2"}}}]}}' Requests a new CPU size for container app. Patching resources on the main pod object (without --subresource resize) is rejected.
kubectl get pod web -o jsonpath='{.status.containerStatuses[0].resources}' Shows the resources actually applied right now.
kubectl describe pod web Shows PodResizePending / PodResizeInProgress conditions and their reasons.

Worked example

A Java API pod is set to 2 CPU because startup (JIT compilation, cache loading) takes 90s at 0.5 CPU. In steady state it uses 0.3 CPU. 30 replicas × 1.5 wasted CPU = 45 CPUs reserved for nothing.

  1. Start pods with cpu: 2 – fast startup.
  2. Once Ready, an automation (or VPA) resizes CPU to 500m in place – NotRequired, so no restart, no dropped connections.
  3. The node now has 1.5 CPU free per pod for other workloads; the cluster needs fewer nodes.

Memory is different: the JVM sized its heap from the limit at startup, so it is set to RestartContainer – the container restarts (the pod, its IP and volumes stay) and picks up the new heap size.

Common pitfalls

  • Assuming a resize always happens: if the node lacks room it stays Deferred – the pod is not moved to another node.
  • Lowering a memory limit live below what the process already uses – risky (OOM); prefer RestartContainer for memory, or check usage first.
  • The QoS class (Q21) is fixed at creation; a resize that would change it (e.g. Guaranteed → Burstable) is rejected.
  • Editing the Deployment template still triggers a normal rolling update – in-place resize applies to existing pods, and the template decides what new pods get.

In the interview

"Since 1.35 in-place resize is GA: you patch the pod's resize subresource and the kubelet updates the container's cgroups without recreating the pod. resizePolicy decides per resource whether a container restart is needed – typically CPU live, memory with restart for runtimes that size their heap at startup. If the node can't fit it, the resize is deferred. It enables non-disruptive rightsizing, startup CPU boosts, and VPA's InPlaceOrRecreate mode." Follow-ups: how to see the applied vs desired size; why memory needs care; what happens if the node is full.
