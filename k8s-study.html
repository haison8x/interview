1. Basics

Q1. What are the components of a Kubernetes cluster?

Short answer

A cluster has a control plane (kube-apiserver, etcd, kube-scheduler, kube-controller-manager, optionally cloud-controller-manager) that stores and decides the desired state, and worker nodes (kubelet, a container runtime, kube-proxy and a CNI plugin) that actually run the containers. Every component talks only to the API server, and each one runs a reconciliation loop that moves actual state towards desired state.

1. The big picture

Think of Kubernetes as a database of "what should be running" plus a set of independent robots that keep reality in line with that database. The database is etcd, the only door into it is the API server, and the robots are controllers, the scheduler and the kubelets. 

                 +-------------------- control plane --------------------+
 kubectl  --->   |  kube-apiserver  <--->  etcd                            |
 CI / GitOps     |       ^    ^                                             |
                 |       |    +---- kube-scheduler                          |
                 |       +--------- kube-controller-manager                 |
                 |       +--------- cloud-controller-manager (cloud only)   |
                 +-------^-----------------------------------------------+
                         | watch / update (HTTPS)
          +--------------+---------------+
          |                              |
   +------ node 1 ------+         +------ node 2 ------+
   | kubelet            |         | kubelet            |
   | containerd (CRI)   |         | containerd (CRI)   |
   | kube-proxy         |         | kube-proxy         |
   | CNI plugin         |         | CNI plugin         |
   | [pods...]          |         | [pods...]          |
   +--------------------+         +--------------------+

2. Control plane components

ComponentWhat it really does
kube-apiserver Stateless REST front end. Authenticates the caller, authorises (RBAC), runs admission (mutation, validation, policy), validates the schema and writes to etcd. Also serves watches – the streaming change feed every other component depends on. It is the only component that talks to etcd. Scales horizontally behind a load balancer.
etcd Distributed, strongly consistent key-value store using the Raft consensus protocol. Holds every object: Deployments, Pods, Secrets, Nodes, leases. Needs a majority (quorum) of members to accept writes, which is why it runs as 3 or 5 members. Lose etcd without a backup and you lose the cluster (see Q39).
kube-scheduler Watches for pods with no nodeName. For each one it filters nodes that can fit it (resources, taints, affinity, volume topology) and scores the rest, then writes a binding. It does not start anything – it only fills in a field.
kube-controller-manager One binary running dozens of controllers: Deployment, ReplicaSet, StatefulSet, Job, Node (marks nodes NotReady), EndpointSlice, Namespace (cleans up deleted namespaces), ServiceAccount, garbage collector and more.
cloud-controller-manager Cloud-specific controllers: creates cloud load balancers for type: LoadBalancer Services, sets up routes, removes Node objects when the VM is deleted. Absent on bare metal.

The scheduler and the controller-manager run as several replicas for high availability, but only one replica of each is active at a time – they use leader election (a Lease object in the API) so two schedulers never place the same pod twice.

3. Node components

  • kubelet – the node agent. Watches the API server for pods bound to its node, tells the container runtime to pull images and start containers, mounts volumes, runs probes, and reports pod and node status back. It also sends heartbeats (Lease objects); if they stop, the node becomes NotReady (Q59).
  • Container runtime – containerd or CRI-O, spoken to over the Container Runtime Interface (CRI). It uses a low-level runtime such as runc to create the namespaces and cgroups. Docker Engine itself is no longer used on nodes (see the Docker page).
  • kube-proxy – programs iptables/IPVS/nftables rules so Service virtual IPs reach pods (Q13). Some CNIs (Cilium) replace it with eBPF.
  • CNI plugin – gives each pod an IP and makes pod-to-pod networking work across nodes (Calico, Cilium, cloud VPC CNIs).

Add-ons that almost every cluster runs as ordinary pods: CoreDNS (Q49), metrics-server (for kubectl top and HPA), an ingress or gateway controller.

4. The reconciliation loop – the key idea

No component tells another what to do. Each one watches the API server, compares the desired state stored there with what it observes, and acts to close the gap – then repeats forever. This is why Kubernetes self-heals: if a pod dies, nobody "handles the event" specially; the ReplicaSet controller simply sees 2 pods where 3 are desired and creates one more. 

loop:
  desired = read spec from API server
  actual  = observe the world
  if actual != desired:
      take one step towards desired
  update status

Worked example

A Deployment wants 3 replicas. A node crashes, taking one pod with it.

  1. The kubelet on that node stops sending heartbeats; after ~40s the Node controller marks it NotReady and taints it.
  2. After the default 300s toleration, the pod on it is marked for deletion. The ReplicaSet controller now counts 2 healthy pods vs 3 desired and creates a new Pod object.
  3. The scheduler binds the new pod to a healthy node.
  4. That node's kubelet starts it; readiness passes; traffic flows.

Four independent loops cooperated without ever calling each other.

Common pitfalls

  • Saying "the master node runs the pods" – control-plane nodes are usually tainted so ordinary workloads don't land there.
  • Thinking the scheduler starts containers – it only assigns a node; the kubelet starts them.
  • Running an even number of etcd members (2 or 4) – it adds no fault tolerance; a 4-member cluster still survives only 1 failure.
  • Forgetting that on managed services (EKS, AKS, GKE) you never see or manage the control plane – but you still own the nodes and add-ons.

In the interview

Name the components in two groups, give each a one-line job, then finish with the unifying idea: "everything goes through the API server, etcd is the source of truth, and every component is a reconciliation loop – that's what makes it self-healing." Likely follow-ups: what happens if etcd is lost, what happens if the API server is down (running pods keep running, but nothing changes), and why etcd needs an odd number of members.

Q2. What happens, end to end, when you run kubectl apply on a Deployment?

Short answer

kubectl sends the object to the API server, which authenticates, authorises, runs admission and stores it in etcd. Then a chain of controllers reacts: the Deployment controller creates a ReplicaSet, the ReplicaSet controller creates Pods, the scheduler assigns nodes, the kubelets start containers, and once readiness passes the pods are added to Service endpoints. Nobody calls anybody – each step is a watch reacting to the previous step's write.

1. On your machine: kubectl

kubectl reads your kubeconfig (cluster URL, credentials, namespace), parses the YAML, and discovers which API group/version serves apps/v1 Deployment. With classic (client-side) apply it computes a three-way merge between your file, the live object and the kubectl.kubernetes.io/last-applied-configuration annotation, then sends a PATCH. With kubectl apply --server-side the API server does the merge and tracks which manager owns which field (managedFields), which avoids conflicts between tools such as kubectl, Helm and an HPA.

2. Inside the API server: the request pipeline

HTTPS request
  -> Authentication      who are you? (client cert, OIDC token, SA token)
  -> Authorization       may you patch deployments in this namespace? (RBAC)
  -> Mutating admission  defaults, injected labels/sidecars, webhooks
  -> Schema validation   is this a valid Deployment?
  -> Validating admission policies, quotas, Pod Security, webhooks
  -> Persist to etcd     object gets a new resourceVersion
  -> Notify watchers     everyone watching Deployments sees the change

If any step rejects, kubectl prints the error and nothing is stored. A successful apply only means "the desired state is recorded" – not that anything is running yet.

3. The controller chain

  1. Deployment controller sees the new or changed Deployment. It hashes the pod template and looks for a ReplicaSet with that hash (label pod-template-hash). None exists, so it creates one – or, if the template changed, starts a rolling update between the old and new ReplicaSets (Q18).
  2. ReplicaSet controller sees a ReplicaSet wanting 3 pods and owning 0, so it creates 3 Pod objects with an ownerReference pointing to the ReplicaSet. The pods have no nodeName – status Pending.
  3. Scheduler picks up the unscheduled pods: filter nodes (enough allocatable CPU/memory for the requests, taints tolerated, affinity satisfied, volumes reachable), score the survivors (spread, image locality, balanced utilisation), write a Binding.
  4. Kubelet on the chosen node sees a pod bound to it: creates the pod sandbox, calls the CNI plugin to get an IP, mounts volumes (ConfigMaps, Secrets, PVCs), pulls images, runs init containers, then starts app containers.
  5. Probes start. When the readiness probe passes, the kubelet marks the pod Ready.
  6. EndpointSlice controller adds the ready pod's IP to the slices of every Service whose selector matches; kube-proxy on every node reprograms its rules; traffic starts flowing.

4. Watching it happen

CommandWhat it actually does
kubectl apply -f app.yaml --dry-run=server Runs the full pipeline (auth, admission, validation) without persisting – catches webhook and quota rejections before you apply for real.
kubectl diff -f app.yaml Shows what would change on the live object.
kubectl get deploy,rs,pods -l app=web -w Watches the chain: Deployment → ReplicaSet → Pods appear.
kubectl get events --sort-by=.lastTimestamp Shows each step's events: ScalingReplicaSet, SuccessfulCreate, Scheduled, Pulling, Pulled, Created, Started.
kubectl rollout status deploy/web Blocks until all new replicas are updated and available.

Worked example

You apply a Deployment web with 3 replicas. The event stream looks roughly like this (times are typical, not guaranteed): 

t=0.0s  Deployment web     ScalingReplicaSet  Scaled up replica set web-7c9d to 3
t=0.1s  ReplicaSet web-7c9d SuccessfulCreate  Created pod web-7c9d-abcde (x3)
t=0.2s  Pod web-7c9d-abcde  Scheduled         assigned default/web-7c9d-abcde to node-2
t=0.4s  Pod web-7c9d-abcde  Pulling           image "nginx:1.27"
t=3.1s  Pod web-7c9d-abcde  Started           container nginx
t=8.0s  readiness passes -> pod Ready -> added to EndpointSlice of Service web

If the pods never appear, the problem is between steps 1 and 2 – look at the ReplicaSet events (quota or admission rejection). If they stay Pending, it is the scheduler (Q54). If they start but never become Ready, it is the probe (Q56).

Common pitfalls

  • Treating "apply succeeded" as "deployment succeeded" – in CI, follow apply with kubectl rollout status (with a timeout) or let GitOps report health.
  • Mixing kubectl edit/scale with apply: the next apply can silently revert manual changes, or manual changes conflict with the last-applied annotation.
  • Looking only at the Deployment's events when pods are missing – pod-creation errors are recorded on the ReplicaSet.

In the interview

Walk the path in order – kubectl, API server pipeline (authn, authz, admission, etcd), Deployment controller, ReplicaSet controller, scheduler, kubelet/CNI/runtime, readiness, EndpointSlices – and end with "no component calls another; they all watch the API server." Follow-ups: where would a mutating webhook inject a sidecar (before etcd), what does the scheduler look at (requests, not usage), and how you'd find which step failed.

Q3. What is a Pod, and why does Kubernetes schedule pods, not containers?

Short answer

A Pod is the smallest deployable unit: one or more containers that share one network namespace (one IP, talk over localhost), can share volumes, and are always placed on the same node and started and stopped together. Kubernetes schedules pods because some processes must be co-located – an app and its proxy or log shipper – and the pod is the unit that guarantees that.

1. What the containers in a pod share

SharedConsequence
Network namespace One IP and one port space for the whole pod. Container A reaches B on localhost:9090; two containers cannot both listen on port 8080.
Volumes (if mounted) An emptyDir volume lets one container write files the other reads – the basis of log-shipping sidecars.
Node and lifecycle All containers land on the same node and the pod is deleted as a unit.
IPC; optionally PIDs With shareProcessNamespace: true containers can see (and signal) each other's processes – useful for debugging.

Each container still has its own filesystem (image), its own resource requests/limits and its own restart counter. Under the hood the runtime creates a tiny "pause" (sandbox) container that holds the network namespace; the app containers join it.

2. Why not schedule containers directly?

Because the scheduler would then have to guarantee co-location constraints between containers ("put the Envoy proxy on the same host as the app and give them the same IP"). By making the group the unit, all those guarantees come for free. The pattern is "one main process per container, tightly coupled helpers in the same pod". Loosely coupled services (API and database) belong in separate pods so they can scale and fail independently.

3. Pods are ephemeral – and that's by design

  • A pod is never "moved". If its node dies or it is evicted, the pod is gone; a controller creates a new pod with a new name and a new IP somewhere else.
  • Containers inside a pod are restarted in place by the kubelet according to restartPolicy (Always by default for Deployments; OnFailure/Never for Jobs). The pod keeps its IP across container restarts.
  • That's why you almost never create bare pods: nobody recreates a bare pod when its node dies. Use a Deployment, StatefulSet, DaemonSet or Job.

4. Pod lifecycle

Pending   -> accepted, but not all containers running (scheduling, image pull, init containers)
Running   -> bound to a node, at least one container running
Succeeded -> all containers exited 0 and won't restart (Jobs)
Failed    -> all containers terminated, at least one with an error
Unknown   -> node not reporting

"CrashLoopBackOff", "ImagePullBackOff" and "Terminating" are not phases; they are container states or reasons shown by kubectl get pods.

Worked example

An API container writes logs to files; a Fluent Bit sidecar ships them. Both share an emptyDir, and the API also exposes metrics that the sidecar could scrape on localhost: 

apiVersion: v1
kind: Pod
metadata:
  name: api
  labels:
    app: api
spec:
  containers:
    - name: api
      image: my-api:2.1
      ports:
        - containerPort: 8080     # whole pod has this port
      volumeMounts:
        - name: logs
          mountPath: /var/log/api
    - name: log-shipper
      image: fluent/fluent-bit:3.2
      volumeMounts:
        - name: logs
          mountPath: /var/log/api
          readOnly: true
  volumes:
    - name: logs
      emptyDir: {}                # lives as long as the pod

kubectl get pod api -o wide shows one IP, e.g. 10.244.2.17, for both containers; kubectl logs api -c log-shipper reads one container's logs. If the node dies, the pod and the emptyDir are gone – which is why this is a bare pod only for illustration.

Common pitfalls

  • Putting the app and its database in one pod "because they talk to each other" – now you can't scale the app without cloning the database.
  • Expecting a pod's IP to be stable – use a Service (Q6).
  • Writing important data inside the container filesystem or an emptyDir – it disappears with the pod; use a PVC (Q11).
  • Two containers in a pod both binding the same port – the second one crashes with "address already in use".

In the interview

"A pod is a group of containers sharing a network namespace and volumes, always co-scheduled; it's the unit of scheduling so tightly coupled helpers like sidecars are guaranteed to sit next to the app. Pods are disposable – controllers replace them, they don't heal them." Follow-ups: what is the pause container, what's the difference between a pod restart and a container restart, and when you'd use multiple containers in one pod (Q32).

Q4. What is kubectl, and which commands do you use daily?

Short answer

kubectl is a client for the Kubernetes REST API: every command becomes HTTP calls to the API server, using the cluster, user and namespace from your kubeconfig's current context. Day to day you use get, describe, logs, exec, apply, rollout and events – and you always check which context you're in before changing anything.

1. How kubectl knows where to talk

The kubeconfig file (~/.kube/config, or the KUBECONFIG variable) contains clusters (API URL + CA), users (certificate, token, or an exec plugin such as the cloud CLI that fetches a short-lived token) and contexts that combine a cluster, a user and a default namespace. 

kubectl config get-contexts             # list contexts, * marks current
kubectl config use-context prod-eu      # switch cluster
kubectl config set-context --current --namespace=payments
kubectl get pods -v=6                   # show the HTTP calls being made

2. The daily command set

CommandWhat it actually does
kubectl get pods -o wide Lists pods with status, restarts, age, pod IP and node. Add -A for all namespaces, -w to watch, -o yaml for the full object.
kubectl describe pod <pod> Human-readable spec + status + Events: scheduling failures, probe failures, image pull errors, OOM kills. First stop for any broken pod.
kubectl logs <pod> -c <c> -f --previous Reads container stdout/stderr from the node. --previous shows the crashed instance; -l app=web reads several pods; --since=10m limits output.
kubectl exec -it <pod> -- sh Runs a process inside an existing container (needs a shell in the image). For distroless images use kubectl debug (Q16).
kubectl apply -f file.yaml Declarative create-or-update: merges your file into the live object. Pair with kubectl diff -f first.
kubectl rollout status|history|undo deploy/x Follow, inspect and reverse Deployment rollouts (Q18).
kubectl get events --sort-by=.lastTimestamp Recent cluster events in time order. Events are kept only for a short time (about an hour by default).
kubectl port-forward svc/web 8080:80 Tunnels a local port to a pod/Service through the API server – test an app without exposing it.
kubectl top pods / nodes Current CPU/memory usage from metrics-server.
kubectl explain deploy.spec.strategy Built-in API documentation for any field.
kubectl auth can-i delete pods --as jane Checks RBAC permissions (Q14).

3. Imperative vs declarative

Imperative commands (kubectl create, run, scale, edit, set image) are quick for experiments and emergencies, but leave no record of intent. Declarative management keeps YAML in git and applies it, so the cluster state is reproducible and reviewable. In production, a GitOps agent does the applying (Q60) and humans mostly use kubectl read-only.

Handy trick: generate YAML instead of writing it by hand – kubectl create deployment web --image=nginx --dry-run=client -o yaml > web.yaml.

4. Output formatting worth knowing

# just the names
kubectl get pods -o name
# custom columns
kubectl get pods -o custom-columns=NAME:.metadata.name,NODE:.spec.nodeName
# one field with JSONPath
kubectl get pod web-0 -o jsonpath='{.status.podIP}'
# which image is every deployment running?
kubectl get deploy -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.template.spec.containers[0].image}{"\n"}{end}'

Worked example

A typical "something is wrong with checkout" session:

kubectl config current-context                  # prod-eu - good
kubectl get pods -n shop -l app=checkout        # 1 of 3 pods: CrashLoopBackOff, 7 restarts
kubectl describe pod checkout-5f7c-x2k9 -n shop # Last State: OOMKilled, exit 137
kubectl logs checkout-5f7c-x2k9 -n shop --previous | tail -50
kubectl top pod -n shop -l app=checkout         # others at 480Mi of a 512Mi limit

Five read-only commands, and you know it's a memory-limit problem (Q57) – without touching anything.

Common pitfalls

  • Running a destructive command against the wrong context – show the context in your shell prompt, or use separate kubeconfigs per environment.
  • Forgetting -n: kubectl get pods shows only the current namespace, so "the pod doesn't exist".
  • kubectl logs on a restarted container shows the new instance; the crash reason is in --previous.
  • kubectl edit in production – the change is not in git and the next deploy (or GitOps) reverts it.

In the interview

Explain that kubectl is just an API client configured by kubeconfig contexts, list the handful of commands you use and why (describe for events, logs --previous for crashes, port-forward for testing), and mention that in production you prefer declarative changes through git. Follow-ups: how kubectl authenticates to a managed cluster (exec plugin / short-lived tokens), and the difference between apply and create.

Q5. What is a Deployment?

Short answer

A Deployment is a controller for stateless, interchangeable pods. You declare the pod template and replica count; the Deployment manages ReplicaSets, which keep exactly that many pods alive. Changing the template triggers a rolling update to a new ReplicaSet, and old ReplicaSets are kept so you can roll back.

1. Three layers: Deployment → ReplicaSet → Pods

Deployment web            (desired: 3 replicas, image nginx:1.27, strategy)
  |
  +-- ReplicaSet web-7c9d6f  (pod-template-hash=7c9d6f, replicas: 3)
  |     +-- Pod web-7c9d6f-abcde
  |     +-- Pod web-7c9d6f-fghij
  |     +-- Pod web-7c9d6f-klmno
  |
  +-- ReplicaSet web-5b8f2a  (old template, replicas: 0, kept for rollback)
  • The ReplicaSet does one thing: keep N pods matching its selector alive. It knows nothing about versions or updates.
  • The Deployment adds versioning on top: every distinct pod template gets its own ReplicaSet (identified by a hash of the template), and the Deployment scales them up and down to move between versions.
  • Pod names are <deployment>-<template-hash>-<random> – random, because the pods are interchangeable.

2. What the Deployment gives you

FeatureHow it works
Self-healing A dead or deleted pod is replaced by the ReplicaSet controller.
Scaling kubectl scale deploy/web --replicas=5 or an HPA (Q15) changes spec.replicas.
Rolling update Template change → new ReplicaSet scaled up while the old one scales down, paced by maxSurge/maxUnavailable (defaults 25% each) (Q18).
Rollback Old ReplicaSets are kept at 0 replicas (revisionHistoryLimit, default 10); kubectl rollout undo scales one back up.
Pause / resume kubectl rollout pause lets you batch several changes into one rollout.
Progress tracking If a rollout makes no progress for progressDeadlineSeconds (default 600), the Deployment reports ProgressDeadlineExceeded (Q52).

3. What triggers a new rollout – and what doesn't

Only changes to spec.template (image, env, resources, labels, annotations on the pod template…) create a new ReplicaSet. Changing replicas just scales the current ReplicaSet. Updating a ConfigMap that the pods reference does not trigger a rollout either – the template didn't change. To roll pods after a config change, use kubectl rollout restart deploy/web (it adds a timestamp annotation to the template) or put a hash of the config in a template annotation (Helm's common checksum/config trick).

4. Strategies

  • RollingUpdate (default) – gradual replacement, zero downtime if readiness probes are meaningful.
  • Recreate – kill all old pods, then start new ones. Causes downtime, but needed when two versions must never run at once (e.g. an incompatible schema migration) or when a ReadWriteOnce volume can only be attached to one pod (Q11).

Worked example

kubectl create deployment web --image=nginx:1.26 --replicas=3
kubectl get rs                    # web-6d4f8 DESIRED 3 CURRENT 3 READY 3
kubectl set image deploy/web nginx=nginx:1.27
kubectl get rs                    # web-6d4f8 0/0/0 (old), web-8c2a1 3/3/3 (new)
kubectl delete pod web-8c2a1-xyz  # a new pod appears within seconds
kubectl rollout undo deploy/web   # web-6d4f8 scaled back to 3, web-8c2a1 to 0

Note the rollback didn't rebuild anything – it reused the old ReplicaSet, which is why it takes seconds.

Common pitfalls

  • Changing the selector after creation – it's immutable; you must delete and recreate the Deployment.
  • Selector that also matches pods from another Deployment – the two controllers fight over the pods. Keep labels unique per app.
  • Running a database in a Deployment with a shared PVC – use a StatefulSet (Q27).
  • Setting replicas in git and using an HPA – every apply resets the replica count. Omit replicas when an HPA owns it.
  • Editing the ReplicaSet directly – the Deployment controller overwrites it.

In the interview

Q6. What is a Service, and why is it needed?

Short answer

Pods are ephemeral and their IPs change every time they are recreated, so clients can't use pod IPs. A Service selects a set of pods by label and gives them one stable virtual IP and DNS name; it load-balances connections across the pods that are currently Ready. It's the stable address in front of a moving target.

1. The problem it solves

A Deployment with 3 replicas has 3 pod IPs today. Tomorrow a rollout replaces all three; a node failure replaces one; the HPA adds two more. If the frontend hard-coded pod IPs it would break constantly. A Service decouples "who I want to talk to" (all pods with app=orders) from "where they are right now".

2. The moving parts

  1. You create a Service with a selector. It gets a ClusterIP from the service CIDR (e.g. 10.96.14.20) that never changes for the Service's lifetime, and a DNS name orders.shop.svc.cluster.local served by CoreDNS.
  2. The EndpointSlice controller continuously lists pods matching the selector and writes their IPs into EndpointSlice objects – only ready pods count as serving endpoints.
  3. kube-proxy on every node watches Services and EndpointSlices and programs kernel rules: "packets to 10.96.14.20:80 → pick one of 10.244.1.5:8080, 10.244.2.9:8080, 10.244.3.4:8080" (details in Q13). 
client pod --> orders.shop.svc.cluster.local
                 | CoreDNS
                 v
             10.96.14.20:80   (virtual, nothing listens here)
                 | kube-proxy rules (DNAT)
     +-----------+-----------+
     v           v           v
 10.244.1.5  10.244.2.9  10.244.3.4   :8080   (ready pods only)

3. port, targetPort, and named ports

FieldMeaning
port The port clients use on the Service IP/name.
targetPort The port the container actually listens on. Can be a number or a name of a container port – with a name, different pods (or versions) can listen on different numbers.
nodePort Only for NodePort/LoadBalancer types (Q7). 
apiVersion: v1
kind: Service
metadata:
  name: orders
  namespace: shop
spec:
  selector:
    app: orders              # must match pod labels exactly
  ports:
    - name: http
      port: 80               # clients call orders:80
      targetPort: http       # named port in the pod spec
---
# in the Deployment's pod template:
#   ports:
#     - name: http
#       containerPort: 8080

4. How clients find it

  • DNS (preferred): orders from the same namespace, orders.shop from another, or the full orders.shop.svc.cluster.local.
  • Environment variables like ORDERS_SERVICE_HOST are injected into pods – but only for Services that existed when the pod started, so don't rely on them.

Worked example

kubectl get svc orders -n shop
# NAME     TYPE        CLUSTER-IP    PORT(S)
# orders   ClusterIP   10.96.14.20   80/TCP

kubectl get endpointslices -n shop -l kubernetes.io/service-name=orders
# ADDRESSTYPE  PORTS  ENDPOINTS
# IPv4         8080   10.244.1.5,10.244.2.9,10.244.3.4

kubectl run tmp -n shop --rm -it --image=busybox -- wget -qO- http://orders/health

Now break one pod's readiness probe: within seconds it disappears from the EndpointSlice, and the Service sends traffic only to the other two. Delete a pod: its replacement appears with a new IP and is added automatically. The client never noticed.

Common pitfalls

  • Selector typo (app: order vs app: orders) → Service with no endpoints → "connection refused". Always check the EndpointSlices first.
  • targetPort doesn't match the port the app listens on, or the app listens on 127.0.0.1 instead of 0.0.0.0.
  • Pinging a ClusterIP to test it – ICMP usually doesn't work because the IP is virtual; test the TCP port instead.
  • Expecting per-request load balancing for long-lived connections (gRPC, HTTP/2) – Services balance per connection.

In the interview

"Pods are disposable and change IPs; a Service gives a label-selected group of pods a stable virtual IP and DNS name, and only routes to ready pods. EndpointSlices track the pod IPs, kube-proxy programs the routing." Follow-ups: what happens when a pod fails readiness, how DNS names are built, why a Service might have no endpoints, and the Service types (Q7).

Q7. What Service types are there?

Short answer

ClusterIP (internal only, the default), NodePort (a port on every node), LoadBalancer (a cloud load balancer in front of the NodePorts), ExternalName (a DNS alias to an outside host) and the headless variant (clusterIP: None, DNS returns pod IPs directly). The first three build on each other.

1. They are layered

LoadBalancer = NodePort + an external cloud load balancer pointing at the node ports
NodePort     = ClusterIP + the same port opened on every node
ClusterIP    = virtual IP + DNS name inside the cluster

So a LoadBalancer Service also has a ClusterIP and (by default) a nodePort – which is useful to know when debugging.

2. Each type in detail

TypeReachable fromTypical use
ClusterIP Inside the cluster only. Service-to-service traffic: frontend → orders → payments. The vast majority of Services.
NodePort <any-node-IP>:<30000–32767> Bare-metal setups, an external load balancer you manage yourself, quick tests. Ugly ports, and clients need to know node IPs.
LoadBalancer A public or internal cloud LB IP/hostname. Exposing one entry point – typically the ingress/gateway controller – to the outside. One LB per Service, which costs money, so you don't use it for every app.
ExternalName Inside the cluster (it's just DNS). A stable in-cluster name for an external dependency: db → CNAME prod-db.abc.eu-west-1.rds.amazonaws.com. No proxying, no ports, no selector.
Headless (clusterIP: None) Inside the cluster. DNS returns the individual pod IPs (A records) instead of one virtual IP. Used by StatefulSets for per-pod names (db-0.db) and by clients that balance themselves (gRPC, Cassandra drivers).

3. Important knobs

  • externalTrafficPolicy: Local (NodePort/LoadBalancer) – only nodes with a local ready pod receive traffic; preserves the client source IP and avoids an extra hop. The default Cluster spreads evenly but SNATs the source IP.
  • Cloud-specific annotations decide internal vs internet-facing, NLB vs ALB, etc. – read your provider's docs.
  • loadBalancerSourceRanges restricts which client CIDRs may connect.
  • On bare metal, LoadBalancer Services stay <pending> until you install something like MetalLB or Cilium's LB IPAM.

Worked example

A typical production layout: 40 ClusterIP Services for internal apps, one LoadBalancer Service for the gateway controller, and HTTP routing by host/path to the 40 apps (Q19, Q20). 

apiVersion: v1
kind: Service
metadata:
  name: gateway
  namespace: gateway-system
spec:
  type: LoadBalancer
  externalTrafficPolicy: Local   # keep the client IP for logs and allow-lists
  selector:
    app: gateway-proxy
  ports:
    - name: https
      port: 443
      targetPort: 8443
kubectl get svc gateway -n gateway-system
# TYPE          CLUSTER-IP    EXTERNAL-IP     PORT(S)
# LoadBalancer  10.96.80.11   203.0.113.25    443:31544/TCP
#                                                  ^ the NodePort underneath

Common pitfalls

  • One LoadBalancer per microservice – expensive and hard to secure; consolidate behind an ingress/gateway.
  • EXTERNAL-IP <pending> forever – no cloud controller or LB implementation, or a quota/permission issue; check the Service events.
  • ExternalName for HTTPS: the client connects with the in-cluster name in the Host header/SNI, which the external server's certificate may not cover.
  • externalTrafficPolicy: Local with pods on only some nodes – the cloud LB health-checks nodes and only sends to those with local pods, so spread replicas well.

In the interview

List the types, explain that LoadBalancer ⊃ NodePort ⊃ ClusterIP, and give a use case per type – then add headless and why StatefulSets need it. Bonus points: "in practice we expose one LoadBalancer for the gateway and keep everything else ClusterIP". Follow-ups: how to keep the client IP (externalTrafficPolicy: Local), and what you do on bare metal.

Q8. ConfigMap vs Secret – and are Secrets actually secret?

Short answer

Both decouple configuration from the image and are injected as environment variables or mounted files. ConfigMaps hold non-sensitive settings; Secrets hold credentials. But a Secret is only base64-encoded: real protection comes from encryption at rest in etcd, tight RBAC, and preferably an external secret manager.

1. Why they exist

The same image should run in dev, staging and prod – only the configuration differs. Baking config into the image means a rebuild per environment; baking secrets in means anyone who can pull the image has your passwords. ConfigMaps and Secrets are API objects the kubelet delivers to the pod at runtime.

2. Two ways to consume them

spec:
  containers:
    - name: api
      image: my-api:2.1
      env:
        - name: DB_HOST
          valueFrom:
            configMapKeyRef: { name: api-config, key: DATABASE_HOST }
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef: { name: api-secret, key: DB_PASSWORD }
      volumeMounts:
        - name: config
          mountPath: /etc/api        # each key becomes a file
          readOnly: true
  volumes:
    - name: config
      configMap:
        name: api-config
MethodWhen values change
Environment variables Read once at container start. A change has no effect until the pod restarts (e.g. kubectl rollout restart).
Mounted volume The kubelet updates the files eventually (typically within a minute or so). The app must re-read or watch them. Exception: mounts using subPath are never updated.

3. How "secret" is a Secret?

kubectl get secret api-secret -o jsonpath='{.data.DB_PASSWORD}' | base64 -d
# s3cr3t     <- anyone with "get secrets" can do this

Differences from a ConfigMap are real but limited:

  • Secrets can be encrypted at rest in etcd (Q46); ConfigMaps aren't.
  • The kubelet keeps Secret volumes in memory (tmpfs), not on node disk.
  • Secrets are only sent to nodes running pods that use them.
  • You can write RBAC that allows ConfigMaps but not Secrets.

What actually protects them:

  1. Encryption at rest – ideally KMS-backed. Without it, an etcd backup file contains every password in plain base64.
  2. RBAC – get, list and watch on secrets all reveal values. Also, anyone who can create pods in a namespace can mount any Secret in it – that's effectively read access.
  3. External secret managers – Vault, AWS Secrets Manager, Azure Key Vault, GCP Secret Manager – with External Secrets Operator (syncs into Secrets) or the Secrets Store CSI driver (mounts directly). Rotation, audit and access policy live there.
  4. Git hygiene – never commit plain Secret YAML (base64 is not encryption); use Sealed Secrets or SOPS if they must live in git.

4. Useful details

  • Secret types: Opaque (generic), kubernetes.io/tls (tls.crt/tls.key), kubernetes.io/dockerconfigjson (image pull credentials).
  • stringData lets you write plain text; the API server stores it base64-encoded in data.
  • immutable: true prevents accidental changes and reduces load on the API server (kubelets stop watching it).
  • Each object is limited to about 1 MiB – not for large files.

Worked example

Rotating a database password safely:

  1. Create the new password in the database (old still valid).
  2. Update it in Vault; External Secrets Operator syncs the Kubernetes Secret within its refresh interval.
  3. If the app reads it from an env var: kubectl rollout restart deploy/api – a rolling restart picks up the new value without downtime. If it reads a mounted file and reloads on change, nothing to do.
  4. After all pods use the new password, revoke the old one.

Common pitfalls

  • Believing base64 is encryption.
  • Updating a ConfigMap and wondering why nothing changed – env vars need a restart; subPath mounts never update.
  • Logging the environment at startup – prints all secrets into your log system.
  • Giving developers list secrets "to debug" – it returns every value in the namespace.
  • Referencing a missing key – the pod fails with CreateContainerConfigError.

In the interview

Contrast the two, explain env vars vs mounted files (and the update behaviour), then say clearly "Secrets are base64, not encrypted" and list the real controls: encryption at rest, RBAC (including the create-pods loophole), an external secret store, no secrets in git. Follow-ups: how you rotate a secret, and how you'd get secrets into a GitOps setup.

Q9. What are Namespaces?

Short answer

A namespace is a logical partition inside one cluster: a scope for object names and the unit to which RBAC, ResourceQuotas, LimitRanges, NetworkPolicies and Pod Security levels are applied. It is an organisational and policy boundary, not a hard security or network boundary on its own.

1. What a namespace scopes

  • Names – two teams can both have a Deployment called api in different namespaces.
  • Policies – RoleBindings, ResourceQuotas, LimitRanges, NetworkPolicies and Pod Security Admission labels all apply per namespace.
  • DNS – Services get <svc>.<ns>.svc.cluster.local; the short name api resolves inside the same namespace only.
  • Deletion – deleting a namespace deletes everything in it.

Some resources are cluster-scoped and live outside any namespace: Nodes, PersistentVolumes, StorageClasses, ClusterRoles, CRDs, Namespaces themselves. kubectl api-resources --namespaced=false lists them.

2. Built-in namespaces

NamespacePurpose
defaultWhere objects go if you don't specify one. Avoid using it for real workloads.
kube-systemCluster components: CoreDNS, kube-proxy, CNI, metrics-server.
kube-publicReadable by everyone, rarely used.
kube-node-leaseNode heartbeat Lease objects.

3. What namespaces do NOT isolate

  • Network – a pod in team-a can call a Service in team-b unless a NetworkPolicy blocks it (Q26).
  • Nodes and the kernel – pods from different namespaces share nodes. A container escape crosses namespaces.
  • The control plane – one noisy namespace can overload the API server for everyone.

That's why namespaces are "soft" multi-tenancy (Q47).

4. How to split

Common patterns: per team (team-payments), per application (checkout), or per team-and-environment in a shared non-prod cluster (checkout-dev, checkout-staging). Production and non-production are usually separate clusters, not just namespaces – blast radius and upgrades are cluster-wide.

Worked example

Onboarding a new team gets a "namespace kit":

kubectl create namespace team-search
kubectl label namespace team-search \
  pod-security.kubernetes.io/enforce=restricted \
  team=search
# then apply (usually via GitOps):
#   RoleBinding    -> search-devs group gets "edit" in team-search only
#   ResourceQuota  -> 8 CPU / 16Gi requests, 40 pods
#   LimitRange     -> default requests for containers that omit them
#   NetworkPolicy  -> default deny ingress, allow from the gateway namespace

The namespace on its own isolated almost nothing; the policies attached to it are what make it a tenant boundary.

Common pitfalls

  • Treating namespaces as a security boundary without NetworkPolicies and RBAC.
  • A namespace stuck in Terminating – usually a resource with a finalizer whose controller is gone (e.g. an uninstalled operator's CRs). Find what's left with kubectl api-resources --verbs=list --namespaced -o name | xargs -n1 kubectl get -n <ns> --ignore-not-found.
  • Running everything in default.
  • Calling a Service in another namespace by its short name – use svc.namespace.

In the interview

"A namespace is a name scope and the attachment point for RBAC, quotas, network and pod-security policies. On its own it doesn't isolate network or nodes – you add policies to make it a tenant boundary, and for hard isolation you use separate clusters." Follow-ups: which resources are cluster-scoped, how cross-namespace DNS works, and why a namespace gets stuck terminating.

Q10. What are labels and selectors?

Short answer

Labels are key/value pairs attached to objects; selectors are queries over labels. They are the glue of Kubernetes: Deployments find their pods, Services find their endpoints, NetworkPolicies, PDBs and affinity rules find their targets – always by label selector, never by name. Annotations look similar but are for metadata, not selection.

1. Labels

metadata:
  labels:
    app.kubernetes.io/name: checkout      # recommended common labels
    app.kubernetes.io/version: "2.4.1"
    app.kubernetes.io/part-of: shop
    env: prod
    tier: backend
  • Keys can have a DNS prefix (app.kubernetes.io/); names and values are short (up to 63 characters) and limited to letters, digits, -, _, ..
  • Labels are indexed for selection – keep them small and meaningful. Free-form data (git commit message, owner email, tool config) goes in annotations.

2. Two kinds of selectors

KindExampleUsed by
Equality-based env=prod,tier!=frontend Services (spec.selector is a plain map – AND of equalities)
Set-based env in (prod,staging), !canary Deployments, ReplicaSets, Jobs, NetworkPolicies, PDBs, affinity – via matchLabels + matchExpressions (operators In, NotIn, Exists, DoesNotExist) 
selector:
  matchLabels:
    app: checkout
  matchExpressions:
    - key: env
      operator: In
      values: ["prod", "staging"]
    - key: canary
      operator: DoesNotExist

3. Where selectors wire things together

Deployment.spec.selector      --> which pods its ReplicaSets own
Service.spec.selector         --> which pods become endpoints
NetworkPolicy.podSelector     --> which pods the policy protects
PodDisruptionBudget.selector  --> which pods a drain must keep up
podAntiAffinity.labelSelector --> which pods to stay away from
nodeSelector                  --> which nodes (by node labels) a pod may use

This loose coupling is powerful: you can add a pod to a Service just by labelling it – and dangerous: a too-broad selector silently grabs pods it shouldn't.

Worked example

Debugging a misbehaving pod without killing it: remove the label the Service and ReplicaSet select on. 

kubectl get pods -l app=checkout --show-labels
kubectl label pod checkout-7c9d-abcde app=checkout-debug --overwrite

Now the Service stops sending it traffic (not selected any more) and the ReplicaSet sees only 2 of 3 pods, so it creates a fresh one. The broken pod keeps running in isolation for you to inspect – then delete it. 

kubectl get pods -l 'env in (prod,staging),tier!=frontend'
kubectl get pods -L app.kubernetes.io/version     # show label as a column

Common pitfalls

  • Two Deployments whose selectors overlap (both app: api) – their ReplicaSets fight over the same pods and a Service routes to both versions.
  • Changing a Deployment's selector – immutable; changing pod template labels so they no longer match the selector is rejected.
  • Putting the version label in a Service selector – during a rollout the Service matches only one version and loses half its endpoints.
  • Storing large or frequently changing data in labels instead of annotations.

In the interview

"Labels are identifying key/values; selectors query them; every relationship in Kubernetes – Deployment to pods, Service to endpoints, policies to targets – is a label selector." Mention equality vs set-based, and annotations as the non-selectable sibling. A nice practical touch is the "relabel a pod to quarantine it" trick. Q11. Explain PV, PVC and StorageClass. Why is my pod Pending on a volume?

Short answer

A PersistentVolumeClaim is the app's request for storage; a PersistentVolume is the actual disk bound to it; a StorageClass tells a CSI driver how to create PVs on demand. Pods mount PVCs, so data outlives pods. Pods stay Pending on volumes when the claim can't be bound or the disk can't be attached where the pod can run – usually a missing StorageClass, a zone mismatch, or a ReadWriteOnce disk still attached elsewhere.

1. Why three objects?

Separation of concerns. The developer says "I need 20 GiB of fast storage, mountable by one node" (PVC) without knowing whether that's an EBS volume, an Azure disk or a Ceph RBD image. The platform team defines what "fast" means (StorageClass). The CSI driver creates and attaches the real disk (PV). 

Pod --mounts--> PVC "data" --bound to--> PV "pvc-3f2a..." --backed by--> cloud disk vol-0abc
                   |
                   +-- storageClassName: fast-ssd --> StorageClass --> CSI driver (provisioner)

2. Dynamic provisioning, step by step

  1. You create a PVC with storageClassName: fast-ssd (or none, to use the default class).
  2. Depending on volumeBindingMode: with Immediate the disk is created now; with WaitForFirstConsumer it waits until a pod using the PVC is scheduled, so the disk is created in that pod's zone.
  3. The CSI provisioner creates the disk and a PV object; the PVC becomes Bound.
  4. When the pod lands on a node, the CSI driver attaches the disk to the node and mounts it into the pod.
  5. When the PVC is deleted, the reclaimPolicy decides: Delete (default for dynamic PVs – the disk is destroyed) or Retain (PV becomes Released; data kept for manual recovery). 
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-ssd
  annotations:
    storageclass.kubernetes.io/is-default-class: "true"
provisioner: ebs.csi.aws.com          # example CSI driver
parameters:
  type: gp3
reclaimPolicy: Retain                 # keep data if the PVC is deleted
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true            # PVCs can be resized later

3. Access modes – about nodes, not pods

ModeMeaningTypical backend
ReadWriteOnce (RWO)Mounted read-write by one node (several pods on that node can share it)Block disks: EBS, Azure Disk, PD
ReadWriteOncePod (RWOP)Exactly one podCSI block disks that support it
ReadOnlyMany (ROX)Read-only on many nodesFile storage, some block disks
ReadWriteMany (RWX)Read-write on many nodesNFS, EFS, Azure Files, CephFS

4. Why a pod is Pending on a volume

Symptom (events)Cause and fix
PVC Pending: "no persistent volumes available… and no storage class is set" No default StorageClass and none specified. Set one or mark a class as default.
PVC Pending: "waiting for first consumer" Normal with WaitForFirstConsumer – it binds when a pod is scheduled.
Pod: "volume node affinity conflict" Disk was created in zone A (Immediate binding), pod can only go to zone B. Use WaitForFirstConsumer; for an existing disk, schedule into its zone.
Pod ContainerCreating: "Multi-Attach error for volume" RWO disk still attached to the old node – e.g. a RollingUpdate starting the new pod before the old one released the disk, or a dead node. Use Recreate strategy or a StatefulSet; for dead nodes, wait for detach or remove the node.
Provisioning failed: quota / permissions Cloud quota exceeded or the CSI driver's identity lacks permission – read the CSI controller logs.

Worked example

A PostgreSQL pod on a 3-zone cluster is stuck Pending after a node pool change: 

kubectl describe pod pg-0
# Events: 0/6 nodes are available: 3 node(s) had volume node affinity conflict,
#         3 node(s) didn't match Pod's node affinity/selector.
kubectl get pv $(kubectl get pvc data-pg-0 -o jsonpath='{.spec.volumeName}') \
  -o jsonpath='{.spec.nodeAffinity}'
# ... topology.kubernetes.io/zone In [eu-west-1a]

The disk lives in eu-west-1a, but the only nodes allowed by the pod's selector are now in 1b and 1c. Block disks can't cross zones, so the fix is to add nodes in 1a (or restore the data into a new disk in another zone) – not to delete the PVC, which with reclaimPolicy: Delete would destroy the data.

Common pitfalls

  • Deleting a PVC with reclaimPolicy: Delete and losing the database.
  • Expecting RWX from a block-disk StorageClass – it will never bind.
  • Using hostPath for "persistence" – data is tied to one node and lost when the pod moves.
  • Treating PVs as backups – a PV is a single disk in one zone; you still need snapshots or application-level backups.
  • Forgetting allowVolumeExpansion – you can't grow the PVC later without migrating.

In the interview

Explain the three objects with the developer/platform/driver split, then dynamic provisioning and the two settings that cause the most incidents: volumeBindingMode: WaitForFirstConsumer (zone awareness) and reclaimPolicy (data loss). For "why Pending", say you'd read the events on both the pod and the PVC and list the classic causes. Follow-ups: RWO vs RWX, how StatefulSets create one PVC per replica (Q27), and how to resize a volume.

2. Networking, Config, Resources, Rollouts

Q12. How does Kubernetes networking work?

Short answer

Every pod gets its own IP address, and every pod can reach every other pod on any node without NAT – a flat network. Kubernetes only defines these rules; a CNI plugin (Calico, Cilium, a cloud VPC CNI…) implements them. On top of that flat network, Services give stable virtual IPs, CoreDNS gives names, Ingress/Gateway bring traffic in from outside, and NetworkPolicies restrict the default allow-all.

1. The four communication problems Kubernetes networking solves

ProblemHow it is solved
Container ↔ container in the same pod They share one network namespace, so they talk over localhost. They cannot both listen on the same port.
Pod ↔ pod (same or different node) Each pod has a routable IP; the CNI plugin wires pod network namespaces into the node and routes between nodes.
Pod → Service A virtual ClusterIP translated to a real pod IP by kube-proxy or eBPF (Q13), found by name via CoreDNS (Q49).
Outside world → Service NodePort / LoadBalancer Services, and L7 routing through Ingress (Q19) or Gateway API (Q20).

2. What happens when a pod gets its IP

  1. Each node is given a slice of the cluster's pod address range (its podCIDR, e.g. 10.244.1.0/24), or the CNI manages its own IP pools.
  2. When the kubelet creates a pod, the container runtime first creates a "sandbox" – a small pause container that owns the pod's network namespace. All app containers of the pod join that namespace.
  3. The runtime calls the CNI plugin. The plugin creates a virtual ethernet pair (veth): one end becomes eth0 inside the pod, the other stays on the node. It allocates an IP (IPAM) and adds routes.
  4. The pod IP is reported back to the API server and appears in kubectl get pod -o wide.

3. How traffic crosses nodes: overlay vs routed

  • Overlay (encapsulation) – e.g. VXLAN in Flannel, Calico or Cilium. The pod packet is wrapped in a UDP packet addressed node to node, so the underlying network never sees pod IPs. Works anywhere, costs some MTU and CPU.
  • Native routing – the underlying network knows how to reach pod ranges (BGP with Calico, cloud route tables). No encapsulation overhead.
  • Cloud VPC CNIs (AWS VPC CNI, Azure CNI) give pods real IPs from the VPC subnet. Pods are directly reachable from the VPC, but you can run out of subnet IPs – a classic cause of "too many pods" scheduling failures.

Traffic leaving the cluster (to the internet or a database outside) is normally SNATed to the node's IP, which is why external firewalls must allow node or NAT gateway IPs, not pod IPs (Q53).

4. The layers on top

  • Services – pod IPs change on every restart; a Service gives a stable virtual IP and DNS name (Q6, Q13).
  • CoreDNS – resolves my-svc.my-ns.svc.cluster.local (Q49).
  • Ingress / Gateway API – HTTP(S) entry points (Q19, Q20).
  • NetworkPolicy – the flat network is allow-all by default; policies, enforced by the CNI, restrict it (Q26).

Worked example

Pod A (10.244.1.5 on node-1) calls pod B (10.244.2.7 on node-2) with a VXLAN overlay: 

pod A eth0 (10.244.1.5)
   │  veth pair
node-1 root namespace: route "10.244.2.0/24 via vxlan device"
   │  encapsulate: outer src 192.168.0.11 → dst 192.168.0.12 (UDP 8472/4789)
physical network (only sees node IPs)
   │
node-2: decapsulate, route 10.244.2.7 → veth of pod B
   │
pod B eth0 (10.244.2.7) sees source IP 10.244.1.5 – no NAT

Pod B sees the real source IP of pod A. That "no NAT between pods" property is what lets NetworkPolicies and logs identify callers.

Common pitfalls

  • Assuming namespaces isolate network traffic – they don't; only NetworkPolicies do.
  • Pod CIDR overlapping a corporate or VPC range, so traffic to that range is routed into the cluster instead.
  • MTU mismatch with overlays: small requests work, large responses hang.
  • Hard-coding pod IPs in config – they change on every restart; use Service names.
  • Running out of IPs with VPC CNIs (pods stuck Pending).

In the interview

Q13. How does a ClusterIP actually route traffic? Nothing listens on that IP.

Short answer

The ClusterIP is virtual: no interface owns it and no process listens on it. kube-proxy on every node watches Services and EndpointSlices and programs kernel rules (iptables, IPVS or nftables) that rewrite the destination of any packet sent to ClusterIP:port to one ready pod's IP:targetPort (DNAT). The choice is made once per connection, not per request.

1. The pieces involved

  1. Service – you create it; the API server allocates a ClusterIP from the service CIDR (e.g. 10.96.0.0/12).
  2. EndpointSlice controller – finds pods matching the Service's selector and writes their IPs into EndpointSlices, marking each as ready or not ready based on the readiness probe.
  3. kube-proxy (a DaemonSet) – watches Services and EndpointSlices and translates them into kernel rules on its node.
  4. The kernel – does the actual work: matches the destination, picks a backend, rewrites the packet, and records the mapping in conntrack so all later packets of that connection go to the same pod and replies are translated back.

2. kube-proxy modes

ModeHow it worksNotes
iptables Chains per Service and per endpoint; a random-probability rule picks the backend. Long-time default; rule updates get slow with many thousands of Services.
IPVS Kernel load balancer with hash tables. Scales better, more balancing algorithms.
nftables Same idea with the newer nftables framework. GA since 1.33; faster updates than iptables.
eBPF (no kube-proxy) CNIs such as Cilium handle Service translation in eBPF, often at the socket level. kube-proxy is not installed at all.

3. Connection-level, not request-level, balancing

The backend is chosen when a TCP connection is opened. Every HTTP request on that connection goes to the same pod. With short-lived connections that averages out. With long-lived connections – gRPC, HTTP/2, database pools, keep-alive clients – one pod can receive most of the traffic while new pods (after a scale-up) receive almost none. Fixes: client-side load balancing over a headless Service, an L7 proxy (service mesh, gateway), or limiting connection lifetime.

Worked example

Service orders, ClusterIP 10.96.12.34:80, targetPort: 8080, three ready pods. 

$ kubectl get svc orders
NAME     TYPE        CLUSTER-IP    PORT(S)
orders   ClusterIP   10.96.12.34   80/TCP

$ kubectl get endpointslices -l kubernetes.io/service-name=orders
NAME           ADDRESSTYPE   PORTS   ENDPOINTS
orders-x7k2p   IPv4          8080    10.244.1.5,10.244.2.7,10.244.3.9

A client pod calls http://orders:

  1. DNS resolves orders to 10.96.12.34.
  2. The client sends SYN to 10.96.12.34:80. On the client's own node, the kernel rule matches and picks one of three endpoints (roughly 1/3 each) – say 10.244.2.7:8080.
  3. The packet is rewritten (DNAT) and routed to node-2 over the pod network. Conntrack remembers the mapping.
  4. The reply comes back, conntrack rewrites the source back to 10.96.12.34:80; the client never sees the pod IP.

If pod 10.244.2.7 fails readiness, it is marked not ready in the EndpointSlice, kube-proxy removes it from the rules, and new connections go only to the other two. Existing connections may continue until they close.

Common pitfalls

  • ping to a ClusterIP usually fails – only the Service's TCP/UDP ports are translated. Test with curl or nc instead.
  • Empty EndpointSlices (selector doesn't match labels, or no pod is ready) – the Service exists but connections are refused or time out.
  • port vs targetPort confusion: clients use port, the container must listen on targetPort.
  • gRPC/HTTP/2 traffic piling onto a few pods after scale-up.

In the interview

Say "it's virtual – kube-proxy turns Services plus EndpointSlices into DNAT rules on every node, the kernel picks a backend per connection and conntrack keeps it sticky." Mention the modes (iptables, IPVS, nftables, eBPF) and the long-lived connection consequence – that is the senior detail. Follow-ups: "what happens when a pod becomes not ready?", "how would you balance gRPC?", "what is a headless Service?" (Q7).

Q14. How does RBAC work, and how do pods authenticate to the API and the cloud?

Short answer

Every API request is first authenticated (who are you?), then authorised by RBAC (may you do this verb on this resource?), then passed through admission. RBAC is allow-only: Roles/ClusterRoles list permissions, RoleBindings/ClusterRoleBindings grant them to users, groups or ServiceAccounts. Pods authenticate as their ServiceAccount using a short-lived projected token, and reach cloud services through workload identity instead of stored keys.

1. The request pipeline

kubectl / pod / controller
   │  1. Authentication: client cert, OIDC token, ServiceAccount token
   │  2. Authorization:  RBAC (and Node authorizer for kubelets)
   │  3. Admission:      mutating → validating webhooks / policies
   ▼
etcd (object stored)

Kubernetes has no "user" objects. Human users come from outside – client certificates or, in practice, an OIDC identity provider (Entra ID, Google, Okta, AWS IAM on EKS). Workloads use ServiceAccounts, which are Kubernetes objects.

2. The four RBAC objects

ObjectScopePurpose
Role One namespace List of rules: apiGroups + resources + verbs.
ClusterRole Cluster-wide Same, but can cover cluster-scoped resources (nodes, PVs) or be reused in many namespaces.
RoleBinding One namespace Grants a Role or a ClusterRole to subjects, only inside that namespace.
ClusterRoleBinding Cluster-wide Grants a ClusterRole in every namespace. Use sparingly.

The trick worth knowing: define a ClusterRole once (e.g. the built-in view, edit, admin) and bind it with a RoleBinding per namespace – the permissions apply only to that namespace. Verbs are get, list, watch, create, update, patch, delete, plus special ones like escalate, bind, impersonate. Subresources are separate: pods/log, pods/exec, deployments/scale.

3. How pods authenticate to the API server

  1. Every pod runs as a ServiceAccount (default if none is set).
  2. The kubelet requests a bound, projected token for it via the TokenRequest API and mounts it at /var/run/secrets/kubernetes.io/serviceaccount/token, together with the cluster CA and namespace.
  3. The token is short-lived, tied to that specific pod (invalid once the pod is deleted), and rotated automatically by the kubelet. Client libraries re-read the file. Long-lived token Secrets are no longer created automatically.
  4. The API server validates the token and sees the identity system:serviceaccount:<namespace>:<name>; RBAC bindings decide what it may do.

4. How pods authenticate to the cloud: workload identity

The old way was to put cloud access keys in a Secret – long-lived, easy to leak, hard to rotate. Workload identity federates the ServiceAccount with a cloud identity instead:

  1. The pod gets a projected ServiceAccount token whose audience is the cloud provider (or the provider's agent on the node issues one).
  2. The cloud SDK exchanges it at the cloud's STS for short-lived cloud credentials of the mapped role (IRSA / EKS Pod Identity on AWS, Azure Workload Identity, GKE Workload Identity).
  3. No static secret exists anywhere; revoking is a role change.

Worked example

A CI deployer in namespace shop should update Deployments but not read Secrets: 

apiVersion: v1
kind: ServiceAccount
metadata:
  name: deployer
  namespace: shop
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: deploy-apps
  namespace: shop
rules:
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "watch", "patch", "update"]
  - apiGroups: ["apps"]
    resources: ["deployments/scale"]
    verbs: ["patch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: deployer-binding
  namespace: shop
subjects:
  - kind: ServiceAccount
    name: deployer
    namespace: shop
roleRef:
  kind: Role
  name: deploy-apps
  apiGroup: rbac.authorization.k8s.io
CommandWhat it actually does
kubectl auth can-i patch deployments -n shop --as=system:serviceaccount:shop:deployer Asks the API server's authoriser; prints yes.
kubectl auth can-i get secrets -n shop --as=system:serviceaccount:shop:deployer Prints no – nothing grants it.
kubectl auth can-i --list -n shop --as=... Lists everything the identity may do in the namespace.
kubectl auth whoami Shows how the API server sees your current credentials.

Common pitfalls

  • Binding cluster-admin to a workload "to make it work".
  • Granting list on Secrets while thinking it is harmless – list returns the secret values.
  • Granting create pods (or Deployments) in a namespace: the user can mount any Secret or ServiceAccount there, so it is effectively access to all of them.
  • Forgetting subresources: pods/exec and pods/log need their own rules.
  • Leaving automountServiceAccountToken on for apps that never call the API – a free credential for an attacker who gets in.
  • Cloud keys stored in Secrets instead of workload identity.

In the interview

Walk the pipeline: authentication, then RBAC, then admission. Explain Role vs ClusterRole and binding scope, emphasise "allow-only, least privilege", and show you know the escalation paths (secrets, create pods, bind/escalate/impersonate). Finish with projected tokens and workload identity. Follow-ups: "how do you audit who has access?" (kubectl auth can-i --list, tools like rbac-tool), "how do humans log in?" (OIDC).

Q15. HPA, VPA, Cluster Autoscaler – how do they fit together? Traffic doubled but HPA didn't scale – why?

Short answer

HPA changes the number of pods, VPA changes the size (requests) of pods, and the Cluster Autoscaler or Karpenter changes the number of nodes so those pods have somewhere to run. They form a chain: load rises → HPA adds pods → pods are Pending → nodes are added. HPA fails to scale mostly because of missing metrics, missing CPU requests, a hit maxReplicas, or the wrong metric.

1. How the HPA calculates replicas

Every 15 seconds (by default) the HPA controller reads the metric and applies: 

desiredReplicas = ceil( currentReplicas × currentValue / targetValue )

For CPU utilisation, currentValue is the average usage as a percentage of the pods' CPU requests. That is why an HPA on CPU is useless without requests. A tolerance (10% by default) avoids flapping on tiny changes.

Scaling up is fast; scaling down waits for a stabilisation window (300 seconds by default) and uses the highest recommendation in that window, so a short dip does not remove pods. Both can be tuned in spec.behavior.

2. The three autoscalers side by side

AutoscalerChangesTriggered by
HPA Replica count of a Deployment/StatefulSet CPU/memory utilisation (metrics-server), custom metrics (e.g. requests per second via Prometheus Adapter), external metrics.
KEDA Replica count, including to and from zero Event sources: queue length, Kafka lag, cron, etc. It drives an HPA under the hood.
VPA CPU/memory requests (and limits proportionally) Historical usage. Modes: Off (recommend only), Initial (only at pod creation), Recreate (evicts pods to apply), InPlaceOrRecreate (uses in-place resize, Q38).
Cluster Autoscaler / Karpenter Number (and with Karpenter, type) of nodes Pods Pending because they don't fit; scale-down of underused nodes whose pods fit elsewhere.

Do not let HPA and VPA both act on CPU/memory for the same workload: VPA raises requests, which lowers utilisation percentage, which makes HPA scale in, which raises per-pod usage… they fight. A common split: VPA in Off mode for recommendations, HPA for scaling.

3. Why the HPA didn't scale – a checklist

SymptomCauseFix
TARGETS <unknown>/50% No metrics: metrics-server missing or failing. Install/fix metrics-server; check kubectl top pods.
Event "missing request for cpu" Containers have no CPU requests. Set requests on every container in the pod (sidecars too).
REPLICAS = MAXPODS Already at maxReplicas. Raise the max; check cost and dependencies.
CPU low, latency high Bottleneck is I/O, a thread pool, connections or a downstream service. Scale on RPS, latency, queue depth, or fix the bottleneck.
Replicas went up but nothing improved New pods Pending (no nodes) or slow to become Ready. Check node autoscaler, startup time, readiness; keep headroom.

Worked example

Deployment api runs 4 pods, each requesting 500m CPU. HPA target: 50% CPU, min 2, max 10.

  1. Normal load: pods use 200m each = 40% of request → desired = ceil(4 × 40/50) = ceil(3.2) = 4. No change.
  2. Traffic doubles: pods use 400m = 80% → desired = ceil(4 × 80/50) = ceil(6.4) = 7. HPA sets replicas to 7.
  3. The 3 new pods need 1.5 CPU in total; the nodes only have 0.8 CPU unreserved. Two pods go Pending.
  4. The Cluster Autoscaler sees unschedulable pods, simulates that a new node would fit them, and adds a node (1–3 minutes on most clouds).
  5. Pods schedule, pull images, pass readiness, and join the Service. Utilisation drops back towards 50%.
  6. When traffic falls, HPA waits for the 5-minute stabilisation window before scaling down; the node autoscaler later removes the underused node. 
$ kubectl get hpa api
NAME   REFERENCE        TARGETS   MINPODS   MAXPODS   REPLICAS
api    Deployment/api   80%/50%   2         10        7

$ kubectl describe hpa api      # Events and Conditions explain decisions

Common pitfalls

  • Setting replicas: in the Deployment manifest while an HPA manages it – every kubectl apply or GitOps sync resets the count. Remove the field from the manifest.
  • Memory-based HPA on runtimes that never give memory back – it scales up and never down.
  • minReplicas: 1 for a service that needs HA.
  • Total scale-up time = metric delay + HPA + node provisioning + image pull + startup. For sudden spikes, keep headroom or scale proactively.
  • HPA and VPA both on CPU/memory for the same workload.

In the interview

Describe the chain (HPA → Pending → node autoscaler) and give the formula, stressing that CPU utilisation is relative to requests. For the "didn't scale" part, go through the checklist in order: metrics, requests, max, wrong signal, capacity. Follow-ups: "how would you scale a queue worker?" (KEDA on queue length), "how do you handle sudden spikes?" (headroom, scheduled scaling, faster startup).

Q16. How do you debug a failing pod?

Short answer

Work from the outside in: the pod status tells you which phase failed, kubectl describe shows the events and the last exit code, kubectl logs --previous shows what the crashed container printed, and kubectl exec or an ephemeral kubectl debug container lets you look inside – even in a distroless image with no shell.

1. Read the status first – it tells you where to look

StatusWhat failedLook at
Pending Scheduling, or volumes not yet attached. Events: insufficient resources, taints, PVC (Q54).
ContainerCreating (stuck) Volume mount, CNI, Secret/ConfigMap missing. Events: FailedMount, network setup errors.
ImagePullBackOff / ErrImagePull Getting the image. Registry, credentials, tag (Q58).
CrashLoopBackOff The app starts and exits repeatedly. Previous logs and exit code (Q55).
Running but 0/1 Ready Readiness probe failing. Probe events, app health endpoint (Q56).
OOMKilled / Evicted Memory limit, or node pressure. Q57.
CreateContainerConfigError Referenced ConfigMap/Secret or key doesn't exist. Events name the missing key.

2. The core commands and what they really show

CommandWhat it actually does
kubectl get pod <pod> -o wide Status, restart count, pod IP and node – is it one node only?
kubectl describe pod <pod> Full spec plus State / Last State (exit code, reason such as OOMKilled), probe config, and the Events list at the bottom. Usually the single most useful command.
kubectl logs <pod> -c <container> stdout/stderr of the current container instance.
kubectl logs <pod> --previous Logs of the previous instance – the one that crashed. In a crash loop the current one often has no output yet.
kubectl get events -n <ns> --sort-by=.lastTimestamp Namespace events in time order. Events are kept only for about an hour by default, so look early.
kubectl exec -it <pod> -- sh Runs a process inside the running container – only works if the container is up and has a shell.
kubectl get pod <pod> -o yaml Shows the effective spec after mutating webhooks (injected sidecars, defaults) and the full status.

3. Debugging images with no shell: ephemeral containers

Distroless and chiseled images have no shell or tools, so kubectl exec fails. kubectl debug adds an ephemeral container to the running pod. With --target it joins the target container's process namespace, so you can see its processes and its filesystem via /proc/<pid>/root; it always shares the pod's network. 

# attach a toolbox to a running pod
kubectl debug -it api-7d9f -c debugger --image=busybox:1.36 --target=api

# copy the pod, override the command so it doesn't crash, then explore
kubectl debug api-7d9f -it --copy-to=api-debug --container=api -- sh

# debug the node: a pod with the host filesystem mounted at /host
kubectl debug node/node-1 -it --image=busybox:1.36

The --copy-to form is the answer for crash loops: the copy runs sh instead of the app, so you can start the app by hand and watch it fail. Delete the copy afterwards.

127Command not found (wrong entrypoint or path).

Worked example

$ kubectl get pods
NAME        READY   STATUS             RESTARTS   AGE
api-7d9f    0/1     CrashLoopBackOff   5          4m

Common pitfalls

  • Reading kubectl logs without --previous during a crash loop and seeing nothing.
  • Multi-container pods: forgetting -c and reading the sidecar's logs instead of the app's.
  • Looking at events too late – they expire after about an hour.
  • Fixing a pod by editing it live – the controller will recreate it from the Deployment template; fix the template.
  • Leaving --copy-to debug pods running.

Q17. Liveness vs readiness vs startup probes – and how can a probe cause an outage?

Short answer

Readiness decides whether a pod gets traffic (failing removes it from the Service, no restart). Liveness decides whether the container is restarted. Startup protects slow starters by holding off the other two until the app is up. A liveness probe that checks a shared dependency can restart every pod at once when that dependency blips – turning a small incident into a full outage.

1. What each probe controls

ProbeQuestion it answersOn failure
Startup "Have I finished starting?" Keeps retrying; liveness and readiness don't run yet. If it never succeeds within failureThreshold × periodSeconds, the container is killed and restarted.
Readiness "Can I serve traffic right now?" Pod marked not ready, removed from Service EndpointSlices; container keeps running. Re-added when it passes again. Also blocks a rolling update (Q18).
Liveness "Am I stuck beyond recovery?" Kubelet kills the container (SIGTERM, then SIGKILL) and restarts it.

Probe mechanisms: httpGet (2xx/3xx = success), tcpSocket (port accepts a connection), exec (command exits 0), and grpc (gRPC health protocol). The kubelet runs them from the node, so the app must listen on the pod IP, not only on 127.0.0.1.

2. The timing parameters

FieldDefaultMeaning
initialDelaySeconds0Wait before the first probe.
periodSeconds10How often to probe.
timeoutSeconds1How long one probe may take – often too short.
failureThreshold3Consecutive failures before acting.
successThreshold1Consecutive successes to be considered passing (readiness only may be > 1).

Time to detect a failure ≈ periodSeconds × failureThreshold (30 seconds with defaults). A startup probe with periodSeconds: 5 and failureThreshold: 24 gives the app up to 120 seconds to start, then hands over to a fast liveness probe – better than a large initialDelaySeconds, which delays every start, even fast ones.

3. How a probe causes an outage

t=0s   database has a 40-second failover
t=0s   every pod's liveness probe calls /healthz → /healthz checks the DB → fails
t=30s  3 failures in a row on ALL pods → kubelet restarts ALL containers
t=30s  no pod is ready → Service has zero endpoints → 100% errors
t=40s  database is back; 20 pods cold-start at once, each opening a connection
       pool and warming caches → database overloaded → probes fail again
       → restart loop (CrashLoopBackOff), outage lasts far longer than 40s

Without the liveness check on the database, the pods would simply have returned errors for 40 seconds and recovered by themselves. Rules that prevent this:

  • Liveness checks only the process itself – "is my HTTP server responding / is the main loop alive". No database, no downstream calls.
  • Dependencies belong in readiness if anywhere, and even then carefully: if all pods fail readiness together, the Service has no endpoints either.
  • Give probes realistic timeoutSeconds – a 1-second timeout under GC pauses or CPU throttling fails healthy pods.
  • Use a startup probe for slow starters.

Worked example

A .NET API that takes 20–60 seconds to warm up and depends on a database: 

containers:
  - name: api
    image: shop/api:2.1
    ports:
      - containerPort: 8080
    startupProbe:              # up to 30 × 2s = 60s to start
      httpGet:
        path: /healthz/live
        port: 8080
      periodSeconds: 2
      failureThreshold: 30
    livenessProbe:             # process alive? no dependencies
      httpGet:
        path: /healthz/live
        port: 8080
      periodSeconds: 10
      timeoutSeconds: 3
      failureThreshold: 3
    readinessProbe:            # ready to serve? may check critical deps
      httpGet:
        path: /healthz/ready
        port: 8080
      periodSeconds: 5
      timeoutSeconds: 3
      failureThreshold: 2

/healthz/live returns 200 if the web server answers. /healthz/ready also checks that caches are warmed and the connection pool can get a connection. During a database blip, pods turn not ready (traffic stops) but are not restarted, and come back as soon as the database does.

Common pitfalls

  • Liveness probe checking the database or other services.
  • Same endpoint and thresholds for liveness and readiness – then liveness restarts pods that only needed to be taken out of rotation.
  • Default timeoutSeconds: 1 on a busy or throttled app.
  • No startup probe on a slow starter: liveness kills it before it finishes starting, which looks exactly like a crash loop.
  • Expensive health endpoints (full DB queries) multiplied by probe frequency and pod count.
  • No readiness probe at all – traffic hits pods that are still starting.

In the interview

Define each probe by its consequence: readiness → traffic, liveness → restart, startup → protection for slow starts. Then tell the outage story (dependency in liveness, fleet-wide restart, thundering herd) – it shows production experience. Follow-ups: "should readiness check the database?" (carefully, it's a trade-off), "how do probes interact with rolling updates?" (Q18), "what about graceful shutdown?" (Q35).

Q18. How does a rolling update work, and how do you roll back?

Short answer

When the pod template changes, the Deployment creates a new ReplicaSet and gradually scales it up while scaling the old one down. maxSurge and maxUnavailable control the pace, and only pods that pass readiness count as available, so a broken version stalls instead of replacing everything. Old ReplicaSets are kept at zero replicas, which is what makes kubectl rollout undo instant – or, in GitOps, you roll back with a git revert.

1. The mechanism: two ReplicaSets

Instead of stopping the whole old version and then starting the new one (which causes downtime), the Deployment moves between versions step by step through two ReplicaSets:

  • Old ReplicaSet – manages the pods running the current version (e.g. my-app:1.4.1).
  • New ReplicaSet – created by the Deployment as soon as you change anything in the pod template (image, env, resources, labels…), e.g. my-app:1.4.2. The ReplicaSet name contains a hash of the template (pod-template-hash).
  • The shift – the Deployment controller repeatedly scales the new ReplicaSet up and the old one down until all replicas run the new version and the old ReplicaSet is at 0.

Only changes to spec.template trigger a rollout. Changing replicas just scales the current ReplicaSet. 

Deployment my-app (replicas: 4)
 ├─ ReplicaSet my-app-6f8c9d (1.4.1)   4 → 3 → 2 → 1 → 0   (kept for rollback)
 └─ ReplicaSet my-app-7b4d2e (1.4.2)   0 → 1 → 2 → 3 → 4

2. The two parameters that control speed and capacity

To avoid overloading nodes or leaving too few pods to serve users, the RollingUpdate strategy uses two parameters (integer or percentage of replicas):

ParameterMeaningDefault
maxSurge How many pods may exist above the desired replica count during the update. Higher = faster, needs spare capacity. 25% (rounded up)
maxUnavailable How many pods may be unavailable (not ready) below the desired count during the update. Higher = faster, less capacity while updating. 25% (rounded down)

They can't both be 0. The other strategy, Recreate, kills all old pods first – downtime, but needed when two versions must never run together (e.g. an RWO volume or an incompatible schema migration). 

spec:
  replicas: 4
  minReadySeconds: 10
  revisionHistoryLimit: 10
  progressDeadlineSeconds: 600
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0

Worked example

replicas: 4 with the safest settings, maxUnavailable: 0 and maxSurge: 1. At most 4 + 1 = 5 pods may exist; at least 4 − 0 = 4 must be available at all times. 

Step  Old (1.4.1)  New (1.4.2)  Total  Available  What happens
0     4            0            4      4          start
1     4            1            5      4          surge: create 1 new pod (maxSurge: 1)
2     4            1 (ready)    5      5          new pod passes readiness (+ minReadySeconds)
3     3            1            4      4          now 1 old pod may be removed
4     3            2            5      4          create the next new pod
...   repeat until
8     0            4            4      4          old ReplicaSet scaled to 0, done
  1. No old pod may be stopped first (maxUnavailable: 0), so at least 4 pods always serve users.
  2. The Deployment creates 1 extra new pod (maxSurge: 1) → 5 pods (4 old + 1 new).
  3. Only when that new pod is running, ready and has stayed ready for minReadySeconds does the Deployment stop 1 old pod → 4 pods (3 old + 1 new).
  4. Repeat until all 4 pods run the new version.

Compare with the defaults (25%): for 4 replicas that is maxSurge: 1, maxUnavailable: 1 – faster, but capacity can drop to 3 pods during the update.

3. The safety brake when the new version is broken

The key sentence: "Only pods that pass readiness count as available, so a broken version stalls rather than replacing everything."

  • Readiness probe – Kubernetes doesn't just check that the container started; it uses the readinessProbe (e.g. GET /healthz/ready) to decide whether the app can really serve requests (Q17).
  • Automatic stall – if 1.4.2 has a bug, crashes, or never passes readiness, its pods never count as "available". Because of maxUnavailable: 0, the Deployment is not allowed to stop any more old pods. The rollout freezes at step 1: 4 old pods keep serving users, 1 broken new pod sits there. Nothing is fully replaced, nothing goes down.
  • minReadySeconds (soak time) – some apps pass the health check right after start and crash 5 seconds later (memory blow-up, a background job failing). minReadySeconds: 10 requires a new pod to stay ready continuously for 10 seconds before it counts as available and the rollout moves on.
  • progressDeadlineSeconds (default 600) – if the rollout makes no progress for that long, the Deployment gets the condition Progressing=False, reason ProgressDeadlineExceeded, and kubectl rollout status exits with an error. Kubernetes does not roll back by itself – your pipeline or a human must (Q52).

The brake only works if readiness is meaningful. With no readiness probe, a pod is "ready" as soon as its container starts, and a broken version can replace everything.

4. Commands for the rollout and the rollback

CommandWhat it actually does

kubectl rollout status deployment/my-app Follows the rollout live (how many new replicas are updated and available) and blocks until it finishes; exits non-zero if the progress deadline is exceeded – useful as a CI gate.
kubectl rollout history deployment/my-app Lists revisions (one per ReplicaSet kept) with the CHANGE-CAUSE annotation. --revision=3 shows that revision's pod template.

kubectl rollout undo deployment/my-app --to-revision=3 Rolls back to exactly revision 3 from the history.

5. How history is stored, and rollback with GitOps

  • revisionHistoryLimit (default 10) – after an update, the old ReplicaSet isn't deleted; it is kept with 0 replicas. Because its pod template is still in the cluster, rollout undo can bring the old version back in seconds without re-applying any manifest. Setting the limit to 0 disables rollback.
  • A rollback creates a new revision number: rolling back from revision 5 to 4 turns revision 4 into revision 6. The history moves forward, it never rewinds.
  • GitOps (Argo CD / Flux) – the cluster must match the YAML in git. If you run kubectl rollout undo by hand, the GitOps tool sees the cluster as drifted (OutOfSync); with automatic sync and self-heal enabled it re-applies what is in git – the broken version – on top of your rollback. So in a GitOps setup the correct rollback is a git revert of the release commit; the tool then syncs the cluster back to the old version, and the history in git stays truthful.
  • For canary or blue/green with automatic analysis and abort, the built-in Deployment isn't enough – use Argo Rollouts or Flagger (Q35).

Common pitfalls

  • No readiness probe – the safety brake doesn't exist, a broken version replaces everything.
  • maxUnavailable: 0 on a cluster with no spare capacity: the surge pod stays Pending and the rollout stalls.
  • Expecting Kubernetes to roll back automatically after ProgressDeadlineExceeded – it doesn't.
  • Using mutable tags (latest): the template doesn't change, so no rollout happens, and "rollback" can't restore the old code (see the Docker page).
  • Rolling back the Deployment but not the config or database migration the new version needed – make migrations backward-compatible.
  • Manual rollout undo under GitOps, which gets overwritten.
  • Errors during every rollout even when it "works" – that is the graceful-shutdown race (Q35).

Q19. What is an Ingress, and how does it work?

Short answer

An Ingress is a set of HTTP(S) routing rules – host and path → Service – plus TLS settings. The object itself does nothing; an Ingress controller (a reverse proxy running in the cluster, exposed through one LoadBalancer Service) watches Ingress objects and configures itself from them. It lets many services share one external IP and certificate setup.

1. Why Ingress exists

Without it, each externally reachable service needs its own LoadBalancer Service: one cloud load balancer and public IP per service, no path routing, TLS handled in every app. Ingress puts one L7 entry point in front of everything: 

                    DNS: shop.example.com, api.example.com → 203.0.113.10
client ──HTTPS──▶ cloud load balancer (203.0.113.10)
                    │  Service type LoadBalancer of the controller
                    ▼
              ingress controller pods (TLS termination, routing)
                    │  host/path rules from Ingress objects
        ┌───────────┼───────────────┐
        ▼           ▼               ▼
   web pods     api pods      static pods
 (shop.../)   (api.../v1)   (shop.../assets)

Most controllers send traffic directly to pod IPs read from EndpointSlices rather than through the ClusterIP, which enables per-request load balancing and sticky sessions.

2. The pieces

PieceRole
Ingress controller The actual proxy: Traefik, HAProxy, the F5 NGINX Ingress Controller, Envoy-based controllers, or a cloud controller (e.g. AWS Load Balancer Controller creates an ALB per Ingress group). Not installed by default.
IngressClass Names a controller. spec.ingressClassName on an Ingress picks which controller handles it; one class can be marked default.
Ingress Rules: host, path, pathType, backend Service and port; TLS hosts and Secret.
TLS Secret Type kubernetes.io/tls with certificate and key – usually created and renewed automatically by cert-manager.

3. Path matching rules

  • Exact – only that exact path. /api does not match /api/.
  • Prefix – matches by path elements: /api matches /api and /api/orders, but not /apiv2.
  • ImplementationSpecific – up to the controller (regex, etc.); not portable.

When several rules match, the longest matching path wins. Anything beyond host/path/TLS – rewrites, timeouts, body size, auth, canary weights, rate limits – is configured via controller-specific annotations, which is the main limitation that led to the Gateway API (Q20). Note: the community ingress-nginx controller was retired in March 2026; the Ingress API itself remains.

Worked example

One public IP serves the shop front end and the API, with TLS from cert-manager: 

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
  namespace: shop
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt   # cert-manager creates the Secret
spec:
  ingressClassName: traefik
  tls:
    - hosts: ["shop.example.com", "api.example.com"]
      secretName: shop-tls
  rules:
    - host: shop.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web
                port:
                  number: 80
    - host: api.example.com
      http:
        paths:
          - path: /v1
            pathType: Prefix
            backend:
              service:
                name: api
                port:
                  number: 8080

A request for https://api.example.com/v1/orders: DNS points to the load balancer → controller terminates TLS with the shop-tls certificate → host api.example.com, prefix /v1 matches → forwarded to a ready pod behind Service api on port 8080. A request for https://api.example.com/v2 matches no rule → 404 from the controller's default backend.

CommandWhat it actually does
kubectl get ingressclass Shows which controllers are installed and which class is default.
kubectl get ingress -n shop Shows hosts and the ADDRESS – empty means no controller has picked the Ingress up.
kubectl describe ingress shop -n shop Rules, resolved backends (endpoints) and controller events.
curl -v --resolve api.example.com:443:203.0.113.10 https://api.example.com/v1/health Tests routing through the load balancer before DNS is changed.

Common pitfalls

  • Creating an Ingress with no controller installed, or with the wrong ingressClassName – it is accepted and silently ignored (no ADDRESS).
  • Ingress and backend Service in different namespaces – an Ingress can only reference Services in its own namespace.
  • Prefix vs Exact surprises, and apps expecting the prefix stripped (needs a controller-specific rewrite).
  • Annotations copied from one controller to another – they're silently ignored.
  • TLS Secret missing or in another namespace → controller serves its default self-signed certificate.
  • Still running the retired ingress-nginx controller – no security fixes.

Q20. What is the Gateway API, how is it different from Ingress – and what happened to ingress-nginx?

Short answer

The Gateway API is the successor to Ingress: a family of resources (GatewayClass, Gateway, HTTPRoute, GRPCRoute…) that splits ownership between infrastructure, platform and application teams and puts advanced routing – header matching, weighted traffic splitting, cross-namespace routing – into the portable spec instead of vendor-specific annotations. The community ingress-nginx controller was retired in March 2026; the Ingress API still exists, but new work should target Gateway API.

1. Why Ingress was not enough

The Ingress resource only standardises the basics: host, path, a backend Service, and TLS. Everything real-world applications need – rewrites, timeouts, retries, canary weights, header-based routing, authentication, rate limiting – had to be added by each controller as annotations: 

metadata:
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "10"

Three consequences:

  • Not portable – switching controller (nginx → Traefik → a cloud load balancer) means rewriting every annotation.
  • Not validated – annotations are free-form strings; a typo is silently ignored.
  • One object, one owner – the same Ingress mixes infrastructure concerns (TLS certificates, which load balancer) with application concerns (paths, backends), so either developers get too much power or the platform team becomes a bottleneck.

2. The role-oriented resource model

ResourceOwned byWhat it describes
GatewayClass Infrastructure provider Which implementation handles gateways of this class (Envoy Gateway, Istio, Cilium, NGINX Gateway Fabric, a cloud load balancer…). Cluster-scoped, like an IngressClass.
Gateway Platform / cluster operator An actual entry point: listeners (port, protocol, hostname), TLS certificates, and which namespaces may attach routes (allowedRoutes).
HTTPRoute, GRPCRoute, TLSRoute, TCPRoute… Application team Matching rules (path, header, method, query param) and backends with weights, filters (redirects, header modification, URL rewrite, request mirroring), timeouts.
ReferenceGrant Owner of the target namespace Explicit permission for a route in another namespace to point at Services (or Secrets) in this namespace.

The flow: a Route declares parentRefs pointing at a Gateway; the Gateway's listener decides whether to accept it; the controller programs the data plane and writes the result back into status.parents[].conditions (Accepted, ResolvedRefs). Status conditions are a big operational improvement – with Ingress you often had no feedback at all. 

apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: public-gateway
  namespace: infra
spec:
  gatewayClassName: envoy
  listeners:
    - name: https
      protocol: HTTPS
      port: 443
      hostname: "*.example.com"
      tls:
        certificateRefs:
          - name: wildcard-example-com   # Secret in namespace infra
      allowedRoutes:
        namespaces:
          from: Selector
          selector:
            matchLabels:
              gateway-access: public     # only labelled namespaces may attach

3. What you get in the spec instead of annotations

  • Weighted backends – canary and blue/green directly in the route (see example below).
  • Rich matching – headers, query parameters, HTTP method, not only host and path.
  • Filters – request/response header modification, redirects, URL rewrites, request mirroring.
  • More protocols – gRPC, TLS passthrough, TCP/UDP, and the same API is used for service-mesh (east-west) routing.
  • Conformance tests – implementations publish which features they support, so "portable" is actually checked.

Note that Gateway API is delivered as CRDs, not built into the API server – you install the CRDs (often bundled with the implementation) and a controller.

Worked example

Canary release of my-app v2. The application team owns only this HTTPRoute in its own namespace; it attaches to the shared gateway in infra: 

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: my-app
  namespace: shop
spec:
  parentRefs:
    - name: public-gateway
      namespace: infra
  hostnames: ["app.example.com"]
  rules:
    - matches:
        - headers:
            - name: x-canary         # testers force v2 with a header
              value: "true"
      backendRefs:
        - name: my-app-v2
          port: 80
    - backendRefs:                   # everyone else: weighted split
        - name: my-app-v1
          port: 80
          weight: 90
        - name: my-app-v2
          port: 80
          weight: 10
  1. Deploy v2 next to v1 (two Deployments, two Services).
  2. Testers send x-canary: true and always hit v2.
  3. 10% of real traffic goes to v2. Watch error rate and latency.
  4. Edit weights 90/10 → 50/50 → 0/100 (in git, if you use GitOps).
  5. Delete v1 once v2 has run at 100% for a while.

Rollback at any step is changing one number back. With ingress-nginx, the same thing needed a second "canary" Ingress object plus controller-specific annotations.

4. The ingress-nginx retirement

The community ingress-nginx controller (kubernetes/ingress-nginx – not to be confused with F5's NGINX products) was retired in March 2026: no new releases, no security patches. Because it was the most widely deployed controller, this forced migrations. Key points:

  • The Ingress API (networking.k8s.io/v1) is not removed. Existing Ingress objects keep working with any maintained controller.
  • Options: migrate to Gateway API (recommended direction), or move to another maintained Ingress controller and translate the nginx-specific annotations.
  • The ingress2gateway tool converts Ingress resources to Gateway API resources as a starting point; annotation-heavy configs still need manual review.

Common pitfalls

  • Route created but nothing happens: check kubectl describe httproute – the parent status will say NotAllowedByListeners (namespace not permitted by allowedRoutes) or ResolvedRefs=False (backend Service missing, or cross-namespace reference without a ReferenceGrant).
  • Assuming every implementation supports every feature – check the conformance level (Core / Extended / Implementation-specific).
  • Forgetting the CRDs: no matches for kind "HTTPRoute" means the Gateway API CRDs are not installed.
  • Saying "Ingress is deprecated/removed" in an interview – it is not; only the ingress-nginx controller was retired.

In the interview

"Ingress standardised only host/path routing, so everything else lived in non-portable annotations. Gateway API splits the model by role – GatewayClass for the provider, Gateway for the platform team, HTTPRoute for app teams – and puts weights, header matching, rewrites and cross-namespace rules in the typed spec with status conditions. Since ingress-nginx was retired in March 2026, we'd migrate to a Gateway API implementation, using ingress2gateway as a starting point." Likely follow-ups: how do you do a canary with it? How do you stop team A attaching routes to the production gateway (allowedRoutes, ReferenceGrant)?

Q21. Requests vs limits – and what are QoS classes?

Short answer

Requests are a reservation used by the scheduler and a guaranteed share under contention; limits are a hard runtime ceiling (CPU is throttled, memory is OOM-killed). The combination of requests and limits puts each pod into a QoS class – Guaranteed, Burstable or BestEffort – which decides who is evicted first when a node runs out of memory.

1. Units

  • CPU in cores: 1 = one vCPU/core, 500m = half a core, 100m = a tenth. CPU is a rate (time per period), so it can be shared and throttled.
  • Memory in bytes: 256Mi (mebibytes, 220) vs 256M (megabytes, 106). Mixing them up is a classic small mistake; 256m (lowercase) would mean 0.256 bytes.

2. What requests do

  1. Scheduling: the scheduler adds up the requests of all pods on a node and only places a new pod if the sum still fits the node's allocatable (capacity minus what is reserved for the OS, kubelet and eviction thresholds). It looks at reservations, not actual usage.
  2. CPU share at runtime: CPU requests become cgroup CPU weights. When the node's CPU is contended, each container gets CPU time in proportion to its request. When the node is idle, a container can use more than its request (up to its limit, if any).
  3. Eviction ranking: under node memory pressure the kubelet prefers to evict pods using the most memory above their requests.

3. What limits do

  • CPU limit → a CFS quota: at most limit × 100ms of CPU time per 100ms period. Exceed it and the container is paused until the next period – throttling (Q23).
  • Memory limit → the cgroup memory maximum. Exceed it and the kernel OOM killer kills the container (Q22).

Defaulting rules worth knowing: if you set only a limit, the request defaults to the limit. A LimitRange in the namespace can also inject defaults (Q48).

4. QoS classes

ClassRuleEviction priority
Guaranteed Every container has CPU and memory requests and limits, and request = limit for both. Evicted last; lowest OOM score.
Burstable At least one container has a CPU or memory request or limit, but the pod does not meet the Guaranteed rule. In between; those furthest above their requests go first.
BestEffort No requests or limits on any container. Evicted first; first choice of the OOM killer.

The class is computed by Kubernetes and shown in kubectl get pod <pod> -o jsonpath='{.status.qosClass}'. It also sets the kernel oom_score_adj, so when the whole node runs out of memory the kernel kills BestEffort processes first and Guaranteed ones last.

Worked example

A node with 4 CPU / 16Gi allocatable runs three pods:

PodRequestsLimitsQoS
api1 CPU / 2Gi1 CPU / 2GiGuaranteed
worker1 CPU / 4Gi– / 6GiBurstable
debug-toolnonenoneBestEffort
  • Reserved: 2 CPU / 6Gi. A new pod requesting 2.5 CPU will not fit (only 2 CPU left unreserved), even if the node's actual CPU usage is 10%.
  • CPU contention: api and worker each get a share proportional to 1 CPU; debug-tool gets only a minimal share.
  • Memory pressure (say worker grows to 6Gi and debug-tool to 5Gi): the kubelet evicts debug-tool first (BestEffort), then worker (2Gi above its request). api is untouched.

5. How to choose the numbers

  • Start from observed usage (kubectl top, Prometheus, VPA in recommendation mode): request ≈ typical usage (e.g. p90-p95), memory limit = peak + headroom.
  • Memory: request = limit is a common choice (Guaranteed for memory, no surprise OOMs from overcommit).
  • CPU: accurate request; limit is a policy choice (Q23).
  • Revisit regularly – requests that are far too high waste nodes and money; far too low overpack nodes and cause noisy neighbours and evictions.

Common pitfalls

  • No requests at all → BestEffort pods, overpacked nodes, and the HPA cannot compute CPU utilisation (Q15).
  • Expecting a Guaranteed pod while one sidecar has no limits – the rule applies to every container, so the pod is Burstable.
  • Thinking "Pending: Insufficient cpu" means the node is busy – it means the requests don't fit (Q54).
  • m vs Mi typos in memory values.

In the interview

"Requests are a reservation: the scheduler packs nodes by requests, and under CPU contention each pod gets a share proportional to its request. Limits are the ceiling: CPU over the limit is throttled, memory over the limit is OOM-killed. From the combination Kubernetes derives the QoS class – Guaranteed, Burstable, BestEffort – which is the eviction order under node memory pressure. I size requests from real usage and usually set memory request equal to limit." Follow-ups: what happens when you exceed each limit? Do you set CPU limits?

Q22. What happens when a container exceeds its limits?

Short answer

Memory and CPU behave differently. Memory is not compressible: going over the memory limit gets the container killed by the kernel OOM killer (exit code 137, reason OOMKilled) and restarted. CPU is compressible: going over the CPU limit just throttles the container, which keeps running but slower. Node-level eviction is a third, separate mechanism.

1. Memory over the limit: OOM kill

  1. The memory limit is written to the container's cgroup as its memory maximum.
  2. When the processes in that cgroup try to allocate beyond it and the kernel cannot reclaim enough (e.g. page cache), the kernel's OOM killer kills a process in the cgroup – in practice the container's main process.
  3. The container exits with code 137 (128 + signal 9, SIGKILL). No graceful shutdown, no preStop, in-flight requests are lost.
  4. The kubelet records Last State: Terminated, Reason: OOMKilled and restarts the container according to restartPolicy (Always for Deployments). It is the same pod on the same node – not rescheduled.
  5. If it keeps happening, restarts back off exponentially (10s, 20s, 40s… capped at 5 minutes) and the pod shows CrashLoopBackOff (Q55).

2. CPU over the limit: throttling

The CPU limit is a quota per 100ms period. Once the container has used its quota in the current period, the kernel stops scheduling its threads until the next period starts. Nothing is killed and no event is recorded – the only symptom is latency. You see it in metrics: 

# fraction of periods in which the container was throttled
rate(container_cpu_cfs_throttled_periods_total[5m])
  / rate(container_cpu_cfs_periods_total[5m])

See Q23 for why this can hurt even at low average usage.

3. A third case: eviction (the node runs short)

Eviction is not about a container's own limit – it is the kubelet protecting the node when node-level memory, disk or PIDs drop below eviction thresholds. The kubelet terminates whole pods (by QoS and usage above requests), marks them Evicted/Failed, and their controller recreates them – possibly on another node. Also: exceeding an ephemeral-storage limit (container writable layer, logs, emptyDir) gets the pod evicted, not OOM-killed. Details in Q57.

SituationWho actsResult
Container memory > its limitKernel OOM killerContainer killed (137, OOMKilled), restarted in place
Container CPU > its limitKernel CFS schedulerThrottled; slower, not killed
Node memory/disk/PIDs lowkubeletPod evicted, recreated elsewhere by its controller
ephemeral-storage > limitkubeletPod evicted
Whole node out of memory before kubelet reactsKernel OOM killerKills processes by OOM score – BestEffort first

Worked example

An API pod with limits.memory: 512Mi restarts a few times an hour during traffic peaks. 

$ kubectl get pod api-7d9c-xk2lp
NAME             READY   STATUS    RESTARTS      AGE
api-7d9c-xk2lp   1/1     Running   4 (12m ago)   3h

$ kubectl describe pod api-7d9c-xk2lp
    Last State:     Terminated
      Reason:       OOMKilled
      Exit Code:    137
  1. Confirm: OOMKilled + 137 → own memory limit, not eviction.
  2. Look at the memory graph (working set) before each restart: a steady climb to 512Mi suggests a leak; sudden jumps during peaks suggest load-dependent memory (large uploads, big result sets, unbounded caches, too many concurrent requests).
  3. Check the runtime respects the cgroup limit (modern .NET and JVM do; hard-coded heap flags like -Xmx2g in a 512Mi container guarantee OOM kills).
  4. Fix: bound the memory use in code, or raise the limit to measured peak + headroom (and the request with it).

Common pitfalls

  • Confusing OOMKilled (container limit) with Evicted (node pressure) – they have different fixes.
  • Looking only at kubectl top averages: an OOM spike can happen between scrapes.
  • Expecting graceful shutdown on OOM – SIGKILL skips handlers and preStop.
  • Treating CPU throttling as harmless because "nothing crashes" – it shows up as timeouts and failing probes, which can then cause restarts.
  • /tmp or emptyDir with medium: Memory (tmpfs) counts against the memory limit.

In the interview

"Memory isn't compressible, so exceeding the memory limit gets the container OOM-killed by the kernel – exit 137, OOMKilled – and the kubelet restarts it in place; repeated OOMs become CrashLoopBackOff. CPU is compressible, so exceeding the CPU limit only throttles it, which shows up as latency. Separately, if the node itself runs short, the kubelet evicts pods, starting with BestEffort." Q23. Should you set CPU limits?

Short answer

It depends, and the strong answer explains why. CPU limits are enforced per 100ms period, so multi-threaded apps can be throttled and suffer latency spikes even when average usage is low and the node has idle CPU. A common stance: always set memory requests and limits, set accurate CPU requests, and omit or generously size CPU limits for latency-sensitive services – but keep CPU limits where you need hard isolation or cost control.

1. How the CPU limit is enforced (CFS quota)

Linux enforces a CPU limit with a quota per period. The default period is 100ms; the quota is limit × period:

CPU limitQuota per 100ms period
500m50ms of CPU time
1100ms of CPU time
2200ms of CPU time

The quota is shared by all threads of the container. Four threads running in parallel consume CPU time four times as fast as wall-clock time. When the quota is gone, every thread is paused until the next period begins.

Worked example

A service with limits.cpu: 1 (100ms quota per 100ms) receives a request that needs 200ms of CPU, and the runtime spreads the work over 8 threads: 

period 1 (0-100ms):   8 threads x 12.5ms = 100ms quota used at t=12.5ms
                      -> throttled for the remaining 87.5ms
period 2 (100-200ms): another 100ms of work done by t=112.5ms
                      -> request finishes at ~112ms instead of ~25ms

Without the limit, on a node with spare cores, the request would finish in about 25ms. With it, ~112ms – a 4–5× latency hit – while the dashboard shows the pod's average CPU usage at maybe 20% of its limit, because the bursts are tiny compared to a 1-minute average. This is why throttling surprises people: it is invisible in usage graphs and visible only in the throttling metric and in tail latency (p99).

2. Why you might not need CPU limits

  • CPU requests already protect neighbours under contention: each container gets CPU time in proportion to its request. A pod without a limit can only use idle CPU beyond its request.
  • CPU is compressible – a greedy pod slows others down to their fair share, it cannot crash them (unlike memory).
  • Using idle CPU is free performance: faster startup (JIT, warm-up), absorbing short bursts.

3. Why you might still want them

  • Multi-tenant clusters – hard isolation between teams or customers, predictable performance.
  • Predictability / benchmarking – an app that "works in staging" only because it borrowed idle CPU will be slow in a busy production node; limits expose that early.
  • Batch and cost control – stop a runaway job from consuming the whole node.
  • Guaranteed QoS requires CPU limit = request (Q21), which you may want for critical pods (it is also a prerequisite for exclusive CPU pinning with the static CPU manager policy).
  • Policy – some organisations require limits (LimitRange or admission policies).

4. A practical decision table

WorkloadCPU requestCPU limit
Latency-sensitive web/API serviceAccurate (p90–p95 usage)None, or 2–4× the request
Critical, must be Guaranteed= limit= request
Batch jobs, CI runnersModerateYes, to cap runaway usage
Untrusted / multi-tenant workloadsAccurateYes

Memory is different in every row: always set memory requests and limits, because memory cannot be reclaimed from a process the way CPU time can.

5. How to detect throttling

# throttled ratio per container (alert if consistently > ~25%)
sum by (namespace, pod, container) (
  rate(container_cpu_cfs_throttled_periods_total[5m])
) / sum by (namespace, pod, container) (
  rate(container_cpu_cfs_periods_total[5m])
)

Also check runtime settings: many runtimes size their thread pools from the CPU limit (e.g. .NET and the JVM detect the container's CPU quota), so removing or changing limits can change concurrency behaviour.

Common pitfalls

  • Judging CPU limits by average usage – throttling happens in sub-second bursts.
  • Removing CPU limits but also having no (or tiny) CPU requests – then nothing protects anyone under contention.
  • Setting a CPU limit below what startup needs, so the app starts slowly and fails its startup/liveness probe – looks like a crash loop.
  • Applying "never set CPU limits" dogmatically in a shared or multi-tenant cluster.

In the interview

"It's a trade-off. CPU limits are enforced as a CFS quota per 100ms, so a multi-threaded service can burn its quota in a few milliseconds and get paused for the rest of the period – p99 latency spikes while average usage looks low. Requests already guarantee each pod its share under contention, so for latency-sensitive services I set accurate CPU requests and no or generous CPU limits, and I watch the throttling metric. I keep CPU limits for multi-tenant, batch, or Guaranteed-QoS workloads. Memory always gets requests and limits." Follow-up: how do you measure throttling?

Q24. What are init containers, and when should you use them?

Short answer

Init containers are containers in the pod spec that run to completion one after another before any app container starts; if one fails, the pod does not proceed. Use them for preparation that must finish first – waiting for a dependency, rendering config, fetching certificates, fixing volume permissions – using tools you don't want in the app image.

1. Lifecycle step by step

Pod scheduled
  -> volumes mounted
  -> init container 1 runs ... exits 0
  -> init container 2 runs ... exits 0
  -> app containers (and probes) start together
     (native sidecars, Q33, are started in order among the init containers
      and keep running)
  • Sequential: init container n+1 only starts after n exits successfully.
  • Failure: a non-zero exit is retried according to the pod's restartPolicy (with back-off); the pod status shows Init:Error or Init:CrashLoopBackOff. With restartPolicy: Never the whole pod fails.
  • Re-runs: if the pod restarts (or is recreated), all init containers run again, so they must be idempotent.
  • No probes: regular init containers don't support liveness, readiness or startup probes – they are expected to finish.
  • Shared with the app: same volumes and same network namespace, so they can write files into an emptyDir that the app later reads.

2. Good use cases

Use caseHow
Wait for a dependencyLoop until a TCP port or DNS name answers
Render configurationTemplate a config file into a shared emptyDir
Fetch secrets/certificatesDownload from a vault into a memory-backed volume
Prepare volumeschown a data directory so a non-root app can write to it
Keep the app image smallUse git, curl, tooling in the init image only

Worked example

The app needs Postgres to be reachable and a config file rendered from environment variables before it starts: 

apiVersion: v1
kind: Pod
metadata:
  name: shop-api
spec:
  initContainers:
    - name: wait-for-db
      image: busybox:1.36
      command: ["sh", "-c", "until nc -z postgres 5432; do echo waiting; sleep 2; done"]
    - name: render-config
      image: busybox:1.36
      command: ["sh", "-c", "echo \"db_host=$DB_HOST\" > /config/app.conf"]
      env:
        - name: DB_HOST
          value: postgres
      volumeMounts:
        - name: config
          mountPath: /config
  containers:
    - name: api
      image: shop-api:2.3
      volumeMounts:
        - name: config
          mountPath: /etc/shop     # reads /etc/shop/app.conf
  volumes:
    - name: config
      emptyDir: {}

What you observe while Postgres is still starting:

$ kubectl get pod shop-api
NAME       READY   STATUS     RESTARTS   AGE
shop-api   0/1     Init:0/2   0          20s

$ kubectl logs shop-api -c wait-for-db
waiting
waiting

Once Postgres answers, the status moves to Init:1/2, then PodInitializing, then Running.

3. Resource accounting

Because init containers run one at a time, the scheduler uses the largest init container request, not the sum: the pod's effective request is the higher of (largest init container request) and (sum of app container requests, plus native sidecars). A heavy init container (e.g. a 4Gi data download) can therefore make the whole pod hard to schedule even if the app itself is small.

4. When not to use an init container

  • Database migrations with many replicas – each replica's init container runs the migration, concurrently, on every restart. Prefer a dedicated Job (or deploy pipeline step / Helm hook) that runs once per release, or a migration tool with locking.
  • Things that must keep running – that is a sidecar (Q32, Q33).
  • Replacing resilience – "wait for DB" only helps at startup; the app must still retry when the DB disappears later.

Common pitfalls

  • Pod stuck at Init:0/1 forever – the dependency name or port is wrong; check kubectl logs <pod> -c <init>.
  • Forgetting -c – kubectl logs <pod> shows the app container, which hasn't started.
  • Non-idempotent init steps that break on the second run.
  • Waiting on a dependency inside the same Deployment rollout that is waiting on you – circular startup dependencies deadlock.

In the interview

"Init containers run sequentially to completion before the app containers start; a failure blocks the pod and is retried. They share volumes with the app, so they're good for preparation – waiting for a dependency, rendering config, fetching certificates, fixing permissions – with tooling that stays out of the app image. They re-run on every pod restart, so they must be idempotent, and I wouldn't run DB migrations in them with multiple replicas – that's a Job." Follow-up: what's the difference from a sidecar?

Q25. What is a PodDisruptionBudget, and how do you keep apps highly available?

Short answer

A PodDisruptionBudget (PDB) limits how many pods of an app can be taken down at the same time by voluntary disruptions – node drains, cluster upgrades, autoscaler scale-down – which go through the Eviction API. It does nothing against crashes or node failures, and a badly configured PDB can block drains forever. App HA needs several replicas spread across nodes/zones, a PDB, and good readiness probes.

1. Voluntary vs involuntary disruptions

Voluntary (PDB applies)Involuntary (PDB cannot help)
kubectl drain for maintenance or upgrades; Cluster Autoscaler / Karpenter removing a node; anything calling the Eviction API Node hardware failure or kernel panic; cloud VM terminated; OOM kill; kubelet node-pressure eviction

Also not covered: directly deleting pods (kubectl delete pod) and a Deployment's own rolling update – that is governed by maxUnavailable/maxSurge (Q18).

2. How the Eviction API enforces a PDB

  1. kubectl drain node-1 cordons the node (no new pods) and sends an eviction request for each pod on it.
  2. The API server finds PDBs whose selector matches the pod and checks: after this eviction, would the number of healthy (Ready) pods still satisfy minAvailable / maxUnavailable?
  3. Yes → the pod is evicted (graceful termination). No → the API returns 429 Too Many Requests; drain waits and retries.
  4. The evicted pod's controller creates a replacement elsewhere; once it becomes Ready, the budget frees up and the next eviction is allowed. 
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: api-pdb
spec:
  maxUnavailable: 1          # or minAvailable: 2 / "75%" (use one, not both)
  selector:
    matchLabels:
      app: api
  unhealthyPodEvictionPolicy: AlwaysAllow   # don't let already-broken pods block drains

maxUnavailable is usually the better choice: it keeps working when you scale the Deployment up or down, whereas a fixed minAvailable can become equal to the replica count.

Worked example

api has 3 replicas, one on each of nodes A, B, C, with maxUnavailable: 1. The platform team drains A and B for an upgrade at the same time: 

t0  drain A: evict api-a      -> allowed (3 healthy, 1 may go)
    drain B: evict api-b      -> 429, budget used up (only 2 healthy)
t1  api-a2 starts on node C or D, becomes Ready (3 healthy again)
t2  drain B retries: evict api-b -> allowed
t3  api-b2 becomes Ready      -> both drains complete

The app never drops below 2 serving replicas. Now the broken version: minAvailable: 3 with 3 replicas → every eviction returns 429, drain hangs forever, and the cluster upgrade stalls until someone edits the PDB.

3. The full HA checklist for an application

  • Replicas ≥ 2 (3+ for anything important) – a PDB on a single replica can only either block drains or allow downtime.
  • Spread replicas across nodes and zones with topologySpreadConstraints or pod anti-affinity (Q31) – three replicas on one node is one failure away from zero.
  • PDB for voluntary disruptions.
  • Readiness probes so replacements receive traffic only when ready (Q17), and graceful shutdown (Q35).
  • Capacity headroom – evicted pods need somewhere to go; with full nodes, drains stall waiting for replacements to schedule.
  • PriorityClass for critical workloads so they win when capacity is short.
CommandWhat it actually does
kubectl get pdb -AShows ALLOWED DISRUPTIONS per PDB – 0 means drains of those pods will block right now.
kubectl drain <node> --ignore-daemonsets --delete-emptydir-dataCordons the node and evicts pods via the Eviction API, honouring PDBs; DaemonSet pods are skipped.
kubectl cordon / uncordon <node>Marks the node unschedulable / schedulable again without evicting anything.

Common pitfalls

  • minAvailable = replica count, or a PDB on a 1-replica app → drains and node upgrades blocked forever.
  • Pods that are already unhealthy (CrashLoopBackOff) consuming the budget – set unhealthyPodEvictionPolicy: AlwaysAllow.
  • Selector that matches no pods (typo) → the PDB protects nothing.
  • Believing a PDB protects against node crashes – only replicas and spreading do.
  • Two PDBs selecting the same pods – eviction of those pods fails.

In the interview

"A PDB caps how many pods of an app can be voluntarily disrupted at once. Drains and autoscaler scale-down use the Eviction API, which returns 429 if the eviction would break the budget, so they wait for replacements to become Ready. It doesn't help with node crashes or OOM kills, and it doesn't govern rolling updates. I use maxUnavailable: 1 rather than a fixed minAvailable, and combine it with 3 replicas spread across zones and proper readiness probes." Follow-up: why is your cluster upgrade stuck on draining a node?

Q26. What is a NetworkPolicy, and why might yours do nothing?

Short answer

By default every pod can reach every other pod. A NetworkPolicy selects pods by label and allow-lists their ingress and/or egress traffic; once a pod is selected for a direction, everything not explicitly allowed in that direction is denied. Policies are enforced by the CNI plugin – if it doesn't support NetworkPolicy, the objects are accepted and silently ignored.

1. The semantics, precisely

  • Default: a pod not selected by any policy allows all traffic.
  • Isolation: a pod becomes isolated for ingress (or egress) as soon as any policy with that policyType selects it.
  • Additive: policies are allow-lists and their rules are combined (union). There is no "deny" rule and no ordering in the standard API – you deny by isolating and not allowing.
  • Stateful: reply traffic for an allowed connection is allowed automatically; you don't write rules for responses.
  • Both ends count: for A → B to work, A's egress (if isolated) must allow it and B's ingress (if isolated) must allow it.
  • Ports refer to the pod's port (targetPort), not the Service port, because policies apply after Service translation.

2. Selectors: the AND vs OR trap

# ONE element with both selectors = AND:
# pods labelled app=frontend IN namespaces labelled team=web
ingress:
  - from:
      - namespaceSelector:
          matchLabels:
            team: web
        podSelector:
          matchLabels:
            app: frontend

# TWO elements = OR:
# ANY pod in namespaces labelled team=web, OR pods app=frontend in THIS namespace
ingress:
  - from:
      - namespaceSelector:
          matchLabels:
            team: web
      - podSelector:
          matchLabels:
            app: frontend

One dash makes the difference between a tight rule and a wide-open one. Namespaces automatically carry the label kubernetes.io/metadata.name: <name>, which is handy for selecting a namespace by name.

CauseHow to check

4. Beyond the standard API

The built-in API is namespaced and allow-only. The upstream network-policy working group is also developing cluster-scoped admin policies. Common pitfalls

  • Egress default-deny without allowing DNS → every connection fails with name-resolution errors.
  • Using the Service port instead of the container port in ports.
  • Allowing egress on the client but forgetting ingress on the server (or vice versa) when both sides are isolated.
  • Expecting ipBlock to match pod IPs reliably – it is meant for traffic to/from outside the cluster; pod IPs change.
  • Assuming policies exist because the YAML is in git – verify with a real connection test.

In the interview

Q27. What is a StatefulSet, and how does it differ from a Deployment?

Short answer

A StatefulSet runs pods that each have a stable identity: a fixed ordinal name (db-0, db-1), a stable DNS name through a headless Service, and their own PersistentVolumeClaim that follows them. Pods are created, updated and deleted in a predictable order. A Deployment treats pods as interchangeable cattle; a StatefulSet treats them as named members of a cluster.

1. Why Deployments are not enough for stateful systems

A Deployment assumes every replica is identical and disposable. When a pod dies, the replacement gets a random name (api-7d9f8c-x2kq4), a new IP, and – if the template mounts a PVC – the same shared volume as every other replica. That is fine for a stateless web API. It is wrong for a database cluster, where:

  • each member has its own data on its own disk (replica 1's data must not be mounted by replica 2);
  • members find each other by a stable address (the primary is configured as "db-0", replication peers are listed by name);
  • the order matters: the first member bootstraps the cluster, the others join it.

2. The three guarantees a StatefulSet gives

GuaranteeHow it works
Stable name Pods are named <statefulset>-<ordinal>: db-0, db-1, db-2. If db-1 is deleted, the replacement is again called db-1 – possibly on another node, with a new IP.
Stable DNS spec.serviceName points at a headless Service (clusterIP: None). Each pod gets a DNS record db-1.db.prod.svc.cluster.local that always resolves to whatever IP db-1 currently has.
Stable storage volumeClaimTemplates create one PVC per pod: data-db-0, data-db-1… When db-1 is rescheduled, it re-attaches data-db-1, so it comes back with its own data.

3. Ordering: creation, scaling and updates

With the default podManagementPolicy: OrderedReady:

  • Scale up / creation: db-0 first; db-1 is only created when db-0 is Running and Ready, and so on.
  • Scale down: in reverse – the highest ordinal is removed first.
  • Rolling update: also in reverse ordinal order, one pod at a time, waiting for each to become Ready before the next. A partition lets you update only ordinals ≥ N – a simple built-in canary.

podManagementPolicy: Parallel drops the ordering for creation and scaling (useful when members don't depend on each other starting in order); identity and storage guarantees remain. 

apiVersion: v1
kind: Service
metadata:
  name: db
spec:
  clusterIP: None          # headless: per-pod DNS records
  selector:
    app: db
  ports:
    - port: 5432
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  serviceName: db          # must match the headless Service
  replicas: 3
  selector:
    matchLabels:
      app: db
  template:
    metadata:
      labels:
        app: db
    spec:
      containers:
        - name: postgres
          image: postgres:17
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
  volumeClaimTemplates:      # one PVC per pod: data-db-0, data-db-1, ...
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 20Gi

4. What happens to the data on scale-down and delete

By default, PVCs created from volumeClaimTemplates are not deleted when you scale down or delete the StatefulSet. This is deliberate: losing a database disk because someone typed replicas: 1 would be catastrophic. Scale back up and db-2 re-attaches the old data-db-2. The persistentVolumeClaimRetentionPolicy field (whenDeleted, whenScaled: Retain or Delete) lets you opt into automatic cleanup.

Worked example

A 3-replica PostgreSQL StatefulSet, node 2 fails:

before:  db-0 (node1, data-db-0)  db-1 (node2, data-db-1)  db-2 (node3, data-db-2)
node2 dies, db-1 is eventually deleted (see Q59 for the force-delete caveat)
after:   db-0 (node1, data-db-0)  db-1 (node4, data-db-1)  db-2 (node3, data-db-2)
                                   ^ same name, same DNS, same disk, new node/IP

The replication config that says "replica connects to db-0.db" keeps working without change. With a Deployment, the new pod would have a random name and either no data or another replica's data.

Common pitfalls

  • Forgetting the headless Service or pointing serviceName at a normal ClusterIP Service – per-pod DNS names don't resolve.
  • Zonal disks: data-db-1 lives in zone A, so db-1 can only ever run in zone A. If zone A has no capacity, the pod stays Pending.
  • A broken rolling update with OrderedReady can get stuck on a pod that never becomes Ready; after reverting the template you may have to delete that pod manually so it is recreated with the old spec.
  • Believing the StatefulSet "makes the database HA". It only gives identity and storage; replication, failover, backups and upgrades are the database's (or an operator's – Q37) job.

In the interview

"A StatefulSet gives each replica a stable name, stable DNS via a headless Service, and its own PVC through volumeClaimTemplates, with ordered startup, scale-down and updates. I use it for clustered stateful systems – databases, Kafka, etcd – but for production databases I'd prefer an operator or a managed service, because the StatefulSet doesn't handle failover or backups." Likely follow-ups: what happens to PVCs on scale-down; how to do a canary with partition; why the pod isn't replaced when its node is unreachable.

Q28. What is a DaemonSet, and when would you use it?

Short answer

A DaemonSet ensures exactly one copy of a pod runs on every node (or every node matching a selector). New nodes get the pod automatically; removed nodes take it with them. It is for node-level agents: log collectors, metrics exporters, CNI/CSI plugins, security agents.

1. How it differs from a Deployment

A Deployment says "run N replicas somewhere". A DaemonSet says "run one per node" – there is no replicas field; the count is the number of eligible nodes. The DaemonSet controller creates one pod per node and pins it there with node affinity; the normal scheduler then places it. If you add 5 nodes, you get 5 more pods without touching anything.

2. Why node agents need this

  • Log collection – container logs are files on each node's disk (/var/log/pods), so a collector must run on every node and mount that host path.
  • Node metrics – node-exporter reads the node's own /proc and /sys.
  • Networking and storage – CNI agents (Calico, Cilium) program the node's network; CSI node plugins mount volumes on that node. kube-proxy itself usually runs as a DaemonSet.
  • Security – runtime detection (Falco, Tetragon) watches syscalls on each node.

3. Tolerations and which nodes it lands on

The controller automatically adds tolerations for common node conditions (not-ready, unreachable, disk/memory/PID pressure, unschedulable), so a log agent keeps running on a node under pressure or being drained. It does not automatically tolerate your custom taints, such as the control-plane taint or a dedicated=gpu taint – add them explicitly if the agent must run there. To target only some nodes, use nodeSelector or node affinity in the pod template. 

spec:
  template:
    spec:
      nodeSelector:
        accelerator: nvidia     # only GPU nodes
      tolerations:
        - key: dedicated
          operator: Equal
          value: gpu
          effect: NoSchedule
      priorityClassName: system-node-critical   # don't get preempted

4. Updating a DaemonSet

updateStrategy: RollingUpdate (default) replaces pods node by node; maxUnavailable (default 1) controls how many nodes are without the agent at once. Because there can only be one pod per node by default, an update briefly leaves that node without the agent; maxSurge lets the new pod start before the old one stops (needed when the agent must never be absent, e.g. a CNI). The alternative strategy OnDelete only updates a node's pod when you delete it manually – useful for agents you want to roll out very carefully.

CommandWhat it actually does
kubectl get ds -A DESIRED vs CURRENT vs READY – DESIRED is the number of eligible nodes. A gap means some nodes can't run the pod.
kubectl rollout status ds/fluent-bit -n logging Follows a DaemonSet rolling update node by node.
kubectl rollout undo ds/fluent-bit -n logging Rolls the DaemonSet back, same mechanism as Deployments.

Worked example

A cluster has 10 nodes: 2 control-plane (tainted node-role.kubernetes.io/control-plane:NoSchedule) and 8 workers. You deploy a Fluent Bit DaemonSet without tolerations: kubectl get ds shows DESIRED 8. Control-plane logs are not collected. Add a toleration for the control-plane taint (or operator: Exists to tolerate everything) and DESIRED becomes 10. Then the autoscaler adds 3 workers during a spike – DESIRED becomes 13 automatically, and logs from the new nodes are collected from their first minute.

Common pitfalls

  • No resource requests/limits on the agent: a leaky log shipper on every node can starve all nodes at once. Set them, and give critical agents a high priority class.
  • Requests that are too large: the DaemonSet pod is reserved on every node, so 500m CPU × 100 nodes = 50 CPUs of overhead.
  • Expecting a DaemonSet pod to move when its node dies – it won't; it belongs to that node.
  • Using a DaemonSet for an ordinary app "to spread it across nodes" – use a Deployment with topology spread constraints (Q31) instead.

In the interview

"A DaemonSet runs one pod per eligible node and follows the node lifecycle automatically. I use it for node agents – log collection, node metrics, CNI and CSI plugins, security sensors – usually with host-path mounts, explicit tolerations for tainted nodes, tight resource limits and a node-critical priority class." Follow-ups: how to run it only on some nodes; how updates work (maxUnavailable, maxSurge, OnDelete); why DESIRED is lower than the node count.

Q29. Jobs and CronJobs – what should you know?

Short answer

A Job runs pods until a given number complete successfully, retrying failures up to backoffLimit. A CronJob creates a Job on a cron schedule. In production you control overlap (concurrencyPolicy), timeouts (activeDeadlineSeconds), cleanup (ttlSecondsAfterFinished, history limits) and make the work idempotent because it may run more than once.

1. Job: run to completion

Deployments restart pods forever; a Job is done when its pods exit successfully. Key fields:

FieldMeaning
completions How many successful pods are needed (default 1).
parallelism How many pods may run at the same time.
completionMode: Indexed Each pod gets an index (JOB_COMPLETION_INDEX env) – e.g. 10 pods each process shard 0–9.
backoffLimit How many failed retries before the Job is marked Failed (default 6). Retries back off exponentially (10s, 20s, 40s… capped).
activeDeadlineSeconds Hard timeout for the whole Job; running pods are killed when it expires.
ttlSecondsAfterFinished Deletes the finished Job (and its pods) after N seconds.
podFailurePolicy Rules per exit code / condition: e.g. exit code 42 = "bad input, fail the Job now, don't retry"; pod disrupted by node drain = "don't count against backoffLimit".

The pod template's restartPolicy must be OnFailure (the kubelet restarts the container in the same pod) or Never (the Job controller creates a new pod for each retry – easier to read the logs of each failed attempt).

2. CronJob: Jobs on a schedule

apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-report
spec:
  schedule: "0 2 * * *"            # 02:00 every day
  timeZone: "Europe/Paris"         # explicit, don't depend on controller clock
  concurrencyPolicy: Forbid        # skip a run if the previous one is still going
  startingDeadlineSeconds: 600     # if missed by more than 10 min, skip it
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      backoffLimit: 2
      activeDeadlineSeconds: 3600  # never run longer than 1 hour
      ttlSecondsAfterFinished: 86400
      template:
        spec:
          restartPolicy: Never
          containers:
            - name: report
              image: my-reports:1.8
              args: ["--date", "yesterday"]

concurrencyPolicy options:

  • Allow (default) – runs may overlap.
  • Forbid – skip the new run while the old one runs.
  • Replace – kill the old run and start the new one.

3. "At least once", not "exactly once"

Kubernetes can run your Job's work more than once: a pod is retried after a crash, a node dies after the work finished but before the success was recorded, or (rarely) the CronJob controller creates a run twice. It can also miss a run (controller down, deadline passed). So the work must be idempotent – e.g. "upsert the report for date X", not "append a report row" – and important schedules need monitoring for "last successful run" rather than trusting that the schedule fired.

Worked example

A CronJob runs every 15 minutes with default concurrencyPolicy: Allow. One day the database is slow and a run takes 40 minutes: 

00:00 run A starts ............................ 00:40 A ends
00:15 run B starts ............................ (slower: competes with A)
00:30 run C starts ............................ (slower still)
00:45 run D starts ...

Overlapping runs make the database even slower – a feedback loop. With Forbid, runs B and C are simply skipped, and D starts on a quiet database. Add activeDeadlineSeconds: 840 so a single run can never exceed its 15-minute slot.

Common pitfalls

  • Finished Jobs and pods piling up (thousands of Completed pods) when no TTL or history limits are set.
  • A sidecar (e.g. mesh proxy) that never exits keeps the Job "running" forever – use native sidecars (Q33).
  • Omitting timeZone and getting runs at the wrong local hour, especially around daylight-saving changes.
  • A CronJob that missed too many schedules (e.g. it was suspended for days) without startingDeadlineSeconds can refuse to start and log an error – set a deadline.
  • Non-idempotent jobs (sending emails, charging cards) that run twice after a retry.

In the interview

"A Job runs pods to completion with retries via backoffLimit, timeouts via activeDeadlineSeconds, and cleanup via ttlSecondsAfterFinished; Indexed mode splits work into shards. A CronJob creates Jobs on a schedule – I set timeZone, concurrencyPolicy Forbid for jobs that must not overlap, a startingDeadlineSeconds, and I make the work idempotent because Kubernetes gives at-least-once semantics." Follow-ups: OnFailure vs Never; how to alert on a CronJob that silently stopped running; podFailurePolicy.

Q30. What is a service mesh, and why use one?

Short answer

A service mesh puts a proxy layer in the path of all service-to-service traffic and controls it centrally. That gives you mutual TLS and identity-based authorisation, retries/timeouts/traffic splitting, and uniform metrics and traces – without changing application code. The price is extra complexity, latency and resource usage.

1. Architecture: data plane and control plane

  • Data plane – proxies that every request passes through. Classic design: an Envoy (Istio) or linkerd2-proxy (Linkerd) sidecar in every pod, injected by a mutating admission webhook (Q34). iptables rules in the pod redirect all inbound and outbound traffic through it.
  • Control plane – watches Services, pods and mesh policies, issues certificates to each workload, and pushes routing configuration to the proxies. 
  pod A                                pod B
 ┌──────────────────┐   mTLS        ┌──────────────────┐
 │ app ──► proxy ───┼──────────────►│ proxy ──► app    │
 └──────────────────┘               └──────────────────┘
          ▲  config + certs              ▲
          └────────── control plane ─────┘

Sidecar-less designs reduce the per-pod cost: Istio's ambient mode uses a per-node proxy (ztunnel) for L4 mTLS and optional shared "waypoint" proxies for L7 features; Cilium implements mesh features with eBPF plus a per-node Envoy.

2. What you get

AreaFeatureWithout a mesh you'd need…
Security Automatic mTLS: every workload gets a certificate tied to its ServiceAccount identity; policies like "only orders may call payments". TLS code and certificate rotation in every service.
Traffic Per-request (L7) load balancing, retries, timeouts, circuit breaking, canary splits (90/10), fault injection. Client libraries in every language.
Observability Request rate, error rate and latency for every service pair; distributed tracing headers propagated by the proxy (the app still has to forward them). Instrumenting every service consistently.

It also fixes a real Kubernetes limitation: kube-proxy balances connections, so long-lived gRPC/HTTP2 connections stick to one pod (Q13). A mesh proxy balances individual requests.

3. The costs

  • Latency: two extra proxy hops per call (typically sub-millisecond to a few ms each).
  • Resources: a sidecar per pod – 1,000 pods × 50 MiB = 50 GiB of memory just for proxies.
  • Operational complexity: another control plane to upgrade, new CRDs, new failure modes ("is it the app or the mesh?"), certificate authority to manage.
  • Lifecycle issues with classic sidecars (startup order, Jobs that don't finish) – solved by native sidecars or ambient mode.

Worked example

A compliance audit requires all internal traffic to be encrypted and the payments service to accept calls only from the orders service. Without a mesh: 25 services in 3 languages each need TLS code, certificate distribution and caller checks. With Istio: 

apiVersion: security.istio.io/v1
kind: PeerAuthentication
metadata:
  name: default
  namespace: istio-system
spec:
  mtls:
    mode: STRICT            # all workloads: mTLS only
---
apiVersion: security.istio.io/v1
kind: AuthorizationPolicy
metadata:
  name: payments-allow-orders
  namespace: payments
spec:
  selector:
    matchLabels:
      app: payments
  action: ALLOW
  rules:
    - from:
        - source:
            principals: ["cluster.local/ns/orders/sa/orders"]

Two manifests instead of 25 code changes; certificates rotate automatically.

Common pitfalls

  • Adopting a mesh "because everyone does" before having a concrete need – then spending months operating it.
  • Retries configured at several layers (client, mesh, gateway): one failure becomes 3 × 3 × 3 = 27 requests – a retry storm that turns a blip into an outage. Retry only idempotent calls, with budgets.
  • Switching to STRICT mTLS while some clients are still outside the mesh – their calls start failing. Use PERMISSIVE during migration.
  • Expecting tracing to work automatically – the app must propagate trace headers between inbound and outbound calls.

In the interview

"A service mesh adds a proxy data plane managed by a control plane, so mTLS, service-to-service authorisation, retries, timeouts, traffic splitting and golden-signal metrics come from infrastructure instead of code. Examples are Istio – sidecar or ambient – Linkerd and Cilium. I'd adopt one for a concrete need like zero-trust mTLS or fine-grained canaries, weighing the latency, memory and operational cost." Follow-ups: how sidecar injection works; sidecar vs ambient; retry storms; how mTLS identity maps to ServiceAccounts.

Q31. How do you control where pods run? Taints, tolerations, affinity, topology spread.

Short answer

Node selectors and node affinity attract pods to nodes with certain labels. Taints repel pods from nodes unless they carry a matching toleration. Pod affinity/anti-affinity places pods relative to other pods, and topology spread constraints spread replicas evenly across zones or nodes. Combine them carefully: every hard rule reduces the set of nodes a pod can use.

1. How the scheduler decides

For every unscheduled pod, kube-scheduler runs two phases:

  1. Filter – remove nodes that can't run the pod: not enough unreserved CPU/memory (requests), untolerated taints, failing required affinity rules, volume zone mismatch, hard spread constraints.
  2. Score – rank the remaining nodes using preferred rules, soft spread constraints, resource balance, image locality; bind the pod to the best one.

If the filter phase leaves zero nodes, the pod is Pending and its events list why each node was rejected (Q54). All these rules apply at scheduling time only ("IgnoredDuringExecution"): changing a node's labels later does not evict pods already running there (except NoExecute taints).

2. The four tools

ToolDirectionTypical use
nodeSelector / node affinity Pod → wants certain nodes GPU workloads on GPU nodes; arm64 images on arm64 nodes.
Taints + tolerations Node → rejects pods Dedicated pools (GPU, system, spot); keep apps off control plane.
Pod (anti-)affinity Pod ↔ other pods Cache next to app; never two replicas on one node.
Topology spread Replicas ↔ topology domains Even spread across zones and nodes for HA.

Taint effects: NoSchedule (new pods without a toleration are not scheduled), PreferNoSchedule (soft version), NoExecute (also evicts running pods that don't tolerate it – used by the node controller for unreachable nodes, Q59).

3. Dedicated node pool: taint + toleration + affinity

A toleration only says "I am allowed on tainted nodes" – it does not pull the pod there. To dedicate a GPU pool you need both: 

# 1. repel everyone else from the GPU nodes
kubectl taint nodes gpu-1 gpu-2 dedicated=gpu:NoSchedule
kubectl label nodes gpu-1 gpu-2 pool=gpu

# 2. in the GPU workload's pod spec
spec:
  tolerations:              # allowed on the tainted nodes
    - key: dedicated
      operator: Equal
      value: gpu
      effect: NoSchedule
  affinity:
    nodeAffinity:           # and required to go there
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: pool
                operator: In
                values: ["gpu"]

4. Topology spread constraints

spec:
  topologySpreadConstraints:
    - maxSkew: 1                               # max difference between domains
      topologyKey: topology.kubernetes.io/zone
      whenUnsatisfiable: DoNotSchedule         # hard rule
      labelSelector:
        matchLabels:
          app: api
    - maxSkew: 1
      topologyKey: kubernetes.io/hostname
      whenUnsatisfiable: ScheduleAnyway        # soft rule
      labelSelector:
        matchLabels:
          app: api

maxSkew: 1 across zones means the number of app=api pods in any zone may differ from the least-loaded zone by at most 1. This replaces most uses of pod anti-affinity, which only expresses "not together" and becomes expensive in large clusters.

Worked example

6 replicas, 3 zones (a, b, c), the zone constraint above. The scheduler places 2 + 2 + 2. Zone c goes down: 4 pods remain (2 + 2 + 0) and the Deployment creates 2 replacements. Placing them in a or b gives 3 + 2 + 0 – a skew of 3 against zone c. What happens next depends on whether zone c still "counts":

  • If zone c's Node objects are gone, the domain disappears from the calculation and the pods go to a and b (3 + 3).
  • If the nodes still exist but are NotReady (tainted), the default nodeTaintsPolicy: Ignore still counts zone c with 0 pods, so with DoNotSchedule the replacements stay Pending – exactly when you need capacity most. Setting nodeTaintsPolicy: Honor, or using ScheduleAnyway for the zone rule, avoids this.

Without any spread rule, the scheduler could have put 5 of the 6 replicas in zone a originally, and a single zone failure would have taken out most of the capacity.

Common pitfalls

  • Tolerations without affinity: the "dedicated" pod lands on ordinary nodes; or affinity without toleration: the pod is Pending forever.
  • Required anti-affinity per hostname with more replicas than nodes: replica 6 on a 5-node cluster stays Pending.
  • Spread rules with a labelSelector that doesn't match the pod's own labels – the constraint silently does nothing.
  • Stacking many hard rules (zone spread + node anti-affinity + node affinity + a zonal PVC) until no node satisfies them all.
  • Spread is evaluated only at scheduling; after a zone recovers, pods are not rebalanced automatically (that needs the Descheduler).

In the interview

"The scheduler filters then scores nodes. I attract pods with node affinity, repel them with taints – a toleration only permits, so dedicating a pool needs both a taint and affinity – place pods relative to each other with pod (anti-)affinity, and use topology spread constraints with maxSkew to spread replicas across zones and nodes. I prefer soft rules where possible because hard rules are the main cause of Pending pods." Follow-ups: NoSchedule vs NoExecute; why the spread is uneven after a zone outage; how the default 300s tolerations work.

Q32. What are sidecar containers, and how are they used?

Short answer

A sidecar is a helper container in the same pod as the main app. It shares the pod's network namespace (same IP, localhost) and can share volumes, so it can add capabilities – log shipping, proxying, config reloading, auth – without changing the app's code or image.

1. What containers in one pod share

  • Network namespace – one IP, one port space. The sidecar reaches the app on localhost:8080; two containers can't both listen on the same port.
  • Volumes – any volume declared in the pod can be mounted by several containers, typically an emptyDir.
  • Lifecycle and node – scheduled together, on the same node, deleted together. Their resource requests add up for scheduling.
  • Optionally the process namespace (shareProcessNamespace: true) so one container can see or signal the other's processes.

Each container still has its own image, filesystem, resource limits and restart behaviour.

2. Common patterns

PatternExample
Log shipper Legacy app writes to /var/log/app/*.log; Fluent Bit sidecar reads the shared volume and ships the logs.
Proxy (ambassador) Envoy mesh proxy; Cloud SQL Auth Proxy so the app connects to localhost:5432 and the proxy handles IAM and TLS.
Adapter Exporter that converts the app's custom stats into Prometheus metrics.
Config / secret reloader Watches a ConfigMap or Vault, writes files to a shared volume and signals the app to reload.
Auth proxy oauth2-proxy in front of an internal dashboard with no login.

3. When not to use a sidecar

  • If the helper is per node, not per pod (log collection from stdout, node metrics) – a DaemonSet (Q28) costs one pod per node instead of one container per pod.
  • If the two processes scale independently – separate Deployments. A sidecar always scales 1:1 with the app.
  • If the app can do it natively (log to stdout, expose /metrics) – one less moving part.

Worked example

An old Java app logs only to files. Instead of rewriting it, add a sidecar that tails the files from a shared emptyDir: 

apiVersion: v1
kind: Pod
metadata:
  name: legacy-app
spec:
  containers:
    - name: app
      image: legacy-app:3.2
      volumeMounts:
        - name: logs
          mountPath: /var/log/app        # app writes here
    - name: log-shipper
      image: fluent/fluent-bit:3.2
      resources:
        requests: { cpu: 20m, memory: 32Mi }
        limits: { memory: 64Mi }
      volumeMounts:
        - name: logs
          mountPath: /var/log/app        # sidecar reads here
          readOnly: true
  volumes:
    - name: logs
      emptyDir:
        sizeLimit: 1Gi                   # don't fill the node's disk

With 40 replicas, the shipper costs 40 × 32 MiB ≈ 1.3 GiB of reserved memory – compare with a DaemonSet if the app could log to stdout.

Common pitfalls

  • Startup race: the app starts before its proxy is ready and its first outbound calls fail.
  • Jobs never complete because the sidecar never exits; or the sidecar is killed before the app during shutdown and the last requests or log lines are lost. Both are solved by native sidecars (Q33).
  • No resource limits on the sidecar – it can OOM the pod or starve the app.
  • Port conflicts: both containers trying to listen on the same port in the shared network namespace.

In the interview

"A sidecar is a helper container in the same pod. Because it shares the pod's network and volumes, it can proxy traffic on localhost or read files the app writes – log shippers, mesh proxies, cloud auth proxies, config reloaders. I'd use it when the helper is genuinely per instance; per-node concerns go in a DaemonSet. Classic sidecars had ordering problems, which native sidecars fix." Follow-ups: what is shared and what isn't; how sidecar injection works; Jobs with sidecars.

Q33. What are native sidecars, and what problem do they solve?

Short answer

A native sidecar is an init container with restartPolicy: Always. Kubernetes then knows it is a helper: it starts before the app containers (and can block them until its startup probe passes), keeps running and is restarted if it dies, and is stopped after the app containers. This fixes the startup race, Jobs that never finish, and sidecars dying before the app during shutdown. GA since 1.33.

1. The problems with classic sidecars

Before native sidecars, all containers in spec.containers were equal – Kubernetes started them roughly in parallel and stopped them in parallel. Three recurring bugs followed:

  1. Startup race – the app starts and makes outbound calls before the mesh proxy is listening: "connection refused" on the first requests. Workarounds: sleep loops in the app's entrypoint, or the mesh's "hold application until proxy starts" hacks.
  2. Jobs that never complete – a Job is done when all its containers exit. The app finishes, but the proxy or log shipper runs forever, so the Job hangs. Workarounds: the app calls the proxy's "quit" endpoint at the end.
  3. Shutdown order – on pod deletion, every container gets SIGTERM at once. The proxy may exit first while the app is still finishing in-flight requests that need it; the log shipper may exit before the app writes its last lines.

2. How native sidecars work

pod start
  init container 1 (regular)      runs to completion
  sidecar (init, restartPolicy: Always) starts ──► startupProbe passes
  init container 2 (regular)      runs to completion (can already use the sidecar)
  app containers start            sidecar keeps running alongside
pod stop
  app containers get SIGTERM and exit
  sidecars get SIGTERM after the app containers have stopped (reverse order)
  • Init containers still run in the order listed; a sidecar listed first is available to all later init containers and to the app.
  • The kubelet moves on to the next init container as soon as the sidecar has started (or its startupProbe has passed) – it does not wait for it to complete.
  • Unlike regular init containers, sidecars may have liveness, readiness and startup probes, and are restarted when they crash, regardless of the pod's restartPolicy.
  • For Jobs, completion depends only on the regular containers – the sidecar is terminated once the app finishes.

3. Manifest

apiVersion: batch/v1
kind: Job
metadata:
  name: export
spec:
  template:
    spec:
      restartPolicy: Never
      initContainers:
        - name: proxy
          image: envoyproxy/envoy:v1.32
          restartPolicy: Always        # this makes it a native sidecar
          startupProbe:                # app waits until the proxy is ready
            httpGet:
              path: /ready
              port: 9901
            periodSeconds: 1
            failureThreshold: 30
      containers:
        - name: export
          image: my-exporter:2.0      # Job completes when this exits

Worked example

A nightly export Job running in a mesh:

SituationClassic sidecarNative sidecar
t=0s pod starts App and proxy start together; app's first DB call fails. Proxy starts; app waits until the startup probe passes (~1s).
t=20min export done App exits 0; proxy keeps running; Job shows Running forever. App exits 0; proxy gets SIGTERM; Job is Complete.
Pod deleted mid-run Proxy and app stop together; app's last DB writes fail. App stops first, then the proxy.

Common pitfalls

  • Putting restartPolicy: Always on a container in spec.containers – it only has this meaning on init containers.
  • No startup probe on the sidecar: the app is started as soon as the sidecar process starts, which may still be before it is listening.
  • Forgetting that the sidecar's resource requests are added for the pod's whole lifetime – unlike regular init containers, whose requests are only needed during initialisation.
  • terminationGracePeriodSeconds must cover the app's shutdown plus the sidecars' shutdown, since they now stop one after the other.

In the interview

"Native sidecars are init containers with restartPolicy Always. Kubernetes starts them before the app – optionally gated by a startup probe – keeps them running and restarted, and stops them after the app. That fixes the classic sidecar problems: proxies not ready at app startup, Jobs that never finish because the sidecar keeps running, and sidecars exiting before the app finishes draining. It's GA in 1.33, and meshes like Istio use it." Follow-ups: why it's an init container rather than a new field; how probes on sidecars behave; resource accounting.

Q34. What are admission webhooks and admission policies?

Short answer

Admission control is the last gate in the API server before an object is saved to etcd. Mutating admission may change the object (inject a sidecar, add defaults); validating admission may only accept or reject it (enforce policy). You extend it with webhooks – your own HTTPS service – or with in-process CEL rules (ValidatingAdmissionPolicy) that need no extra service.

1. Where admission sits in the request path

kubectl apply
   │
   ▼
authentication ──► authorization (RBAC) ──► mutating admission
                                              (built-in + webhooks, may modify)
                                                     │
                                         schema validation
                                                     │
                                          validating admission
                                     (built-in + webhooks + CEL policies)
                                                     │
                                                     ▼
                                                   etcd

Many core features are built-in admission plugins: ServiceAccount token mounting, LimitRanger defaults (Q48), ResourceQuota, Pod Security Admission (Q43). Webhooks and policies are how you add rules.

2. Mutating vs validating

MutatingValidating
Can modify the object Yes – returns a JSON patch No
Typical uses Sidecar injection (Istio, Vault agent), default labels, resources or securityContext, image digest pinning Block :latest tags, require labels, allowed registries only, require signed images, deny privileged pods
Runs First (may be re-invoked after other mutations) After all mutation, so it sees the final object

3. Webhooks vs CEL policies

A webhook is configured with a MutatingWebhookConfiguration or ValidatingWebhookConfiguration: which resources/operations to send, the HTTPS endpoint (usually a Service in the cluster), failurePolicy (Fail or Ignore), timeoutSeconds, and selectors to limit scope. Kyverno and OPA Gatekeeper are policy engines built on webhooks.

A ValidatingAdmissionPolicy (GA in 1.30) is evaluated inside the API server with CEL expressions – no service to run, no network hop, no outage if a pod is down: 

apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicy
metadata:
  name: no-latest-tag
spec:
  failurePolicy: Fail
  matchConstraints:
    resourceRules:
      - apiGroups: ["apps"]
        apiVersions: ["v1"]
        operations: ["CREATE", "UPDATE"]
        resources: ["deployments"]
  validations:
    - expression: >-
        object.spec.template.spec.containers.all(c,
          !c.image.endsWith(':latest') && c.image.contains(':'))
      message: "Images must use an explicit, non-latest tag."
---
apiVersion: admissionregistration.k8s.io/v1
kind: ValidatingAdmissionPolicyBinding
metadata:
  name: no-latest-tag-binding
spec:
  policyName: no-latest-tag
  validationActions: ["Deny"]      # or Warn / Audit while rolling out
  matchResources:
    namespaceSelector:
      matchLabels:
        env: prod

A newer CEL-based MutatingAdmissionPolicy does the same for simple mutations. Webhooks remain necessary when a rule needs external data (e.g. verifying an image signature against a registry).

Worked example

A team runs a validating webhook with failurePolicy: Fail matching all pods in all namespaces. The webhook Deployment has one replica. Its node is drained during an upgrade:

  1. The webhook pod is evicted; its replacement must be created.
  2. Creating that pod requires… calling the webhook, which is down. The API server rejects it.
  3. Now no pod can be created anywhere – including CoreDNS and the CNI pods on new nodes. The cluster slowly degrades.

Fix: exclude kube-system and the webhook's own namespace via namespaceSelector, run 2+ replicas with a PDB, set a short timeoutSeconds, and consider failurePolicy: Ignore for non-security webhooks. Recovery in the moment: delete the webhook configuration object.

Common pitfalls

  • Webhooks matching everything (* resources, all namespaces) – every API call pays their latency and depends on their availability.
  • Mutations that fight each other (two webhooks setting the same field), or a mutating webhook changing a field that a GitOps tool then reports as drift.
  • Expired TLS certificate on the webhook service – every matching request fails.
  • Admission only checks objects when they are created or updated; existing objects that violate a new policy keep running – audit them separately.

In the interview

"Admission runs in the API server after authn and RBAC and before etcd. Mutating admission can change objects – sidecar injection, defaults – and validating admission can only allow or deny – policy enforcement. You extend it with webhooks, which Kyverno and Gatekeeper use, or with in-process CEL ValidatingAdmissionPolicies for simple rules. The operational risk is a failing webhook with failurePolicy Fail blocking the cluster, so I scope them narrowly and exclude system namespaces." Follow-ups: ordering of mutating and validating; Warn and Audit modes; what happens to existing objects.

Q35. How do you achieve zero-downtime deployments? Why do users still get errors during a rolling update?

Short answer

Zero downtime needs four things: new pods only receive traffic once they are truly ready (readiness probes), capacity never drops (maxUnavailable: 0), old pods drain gracefully instead of dying mid-request (preStop delay + SIGTERM handling + enough grace period), and old and new versions can run side by side (backward compatible APIs and database schema). Errors during a rolling update usually come from the shutdown race: the pod stops before the load balancers have stopped sending it traffic.

1. Deployment strategies

StrategyHowTrade-off
Rolling update Built-in: replace pods gradually (Q18). Cheap; old and new versions serve traffic at the same time.
Blue/green Run the full new version (green) next to the old (blue), test it, then switch all traffic at once (Service selector or route). Instant switch and switch-back; double capacity during deploy.
Canary Send 5% → 25% → 100% of traffic to the new version, checking error rate and latency at each step (Argo Rollouts, Flagger, Gateway API weights). Smallest blast radius; needs good metrics and tooling.

2. The shutdown race, step by step

When a pod is deleted (rolling update, scale-down, drain):

t=0     pod marked Terminating
        ├─► kubelet: run preStop hook, then send SIGTERM to the container
        └─► endpoint controller: remove pod from EndpointSlices
                 └─► kube-proxy on every node updates iptables/nftables
                 └─► ingress controller / cloud LB updates its upstreams
t=0..~5s   routing updates are still propagating
           → NEW requests can still arrive at this pod

These two branches run in parallel; nothing waits for the routing update. If the app exits immediately on SIGTERM at t=0.1s, requests routed to it in the next few seconds get "connection refused" or 502. In-flight requests are cut off too if the app doesn't drain them.

3. The fix: delay, drain, then exit

spec:
  terminationGracePeriodSeconds: 45     # must cover preStop + drain
  containers:
    - name: api
      image: my-api:2.4
      lifecycle:
        preStop:
          sleep:
            seconds: 10                 # built-in sleep action; older clusters:
                                        # exec: { command: ["sleep", "10"] }
      readinessProbe:
        httpGet: { path: /ready, port: 8080 }
        periodSeconds: 5
---
# Deployment strategy
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1
  1. preStop sleep 10s – the container keeps serving normally while every load balancer removes the pod.
  2. SIGTERM arrives – the app stops accepting new connections, finishes in-flight requests, closes keep-alive connections, then exits. (.NET's host, Spring Boot and most frameworks support graceful shutdown; the process must actually receive the signal – see the Docker page, Q12.)
  3. The grace period clock started at t=0 and includes preStop: 45s = 10s preStop + up to 35s drain. When it runs out, SIGKILL.

4. Version compatibility – the part outside Kubernetes

During any rolling update or canary, v1 and v2 run at the same time and share the database. A v2 migration that renames a column breaks every v1 pod still running. Use expand/contract: release 1 adds the new column and writes both; release 2 reads the new column; release 3 drops the old one. The same applies to API contracts between services and to message formats on queues.

Worked example

A service handles 2,000 requests/s across 10 pods. During each deploy, monitoring shows a burst of ~300 HTTP 502s.

  • Each terminating pod gets ~200 req/s; routing takes ~1.5s to update everywhere → ~300 requests sent to a pod that already exited.
  • Adding preStop: sleep 10 removes those 502s – the pod is still serving while it disappears from the load balancers.
  • A few errors remain for long requests (file uploads up to 60s) cut off at the 30s default grace period. Raising terminationGracePeriodSeconds to 75 fixes those.
  • Result: deploys at 2 p.m. with zero errors in the dashboards.

Common pitfalls

  • preStop sleep longer than the grace period – the pod is SIGKILLed before it even receives SIGTERM.
  • Using exec: sleep in a distroless image that has no sleep binary – the hook fails; use the built-in sleep action.
  • Readiness probe that returns 200 before caches and connection pools are warm – new pods get traffic too early.
  • Long-lived connections (WebSockets, gRPC streams) that the app never closes – clients stay connected until SIGKILL.
  • Breaking database migrations run before the rollout completes.

In the interview

"Zero downtime needs readiness probes so new pods only get traffic when ready, maxUnavailable 0 so capacity never drops, graceful termination, and backward-compatible changes so two versions can coexist. The usual cause of errors during rolling updates is that SIGTERM and endpoint removal happen in parallel, so traffic still arrives after the app exits – I fix it with a preStop sleep, proper SIGTERM draining and a grace period that covers both. For risky changes I use canary with automated analysis." Follow-ups: blue/green vs canary; expand/contract migrations; long-lived connections.

Q36. What are Custom Resource Definitions (CRDs)?

Short answer

A CRD registers a new resource type with the Kubernetes API. After that, objects of that type can be created, listed, watched, RBAC-protected and stored in etcd exactly like built-in objects. A CRD only stores data; a controller or operator (Q37) has to watch those objects and act on them.

1. What happens when you install a CRD

  1. The API server adds new REST endpoints, e.g. /apis/example.com/v1/namespaces/{ns}/databases.
  2. kubectl discovers them: kubectl get databases, kubectl explain database.spec and kubectl apply just work.
  3. Objects are validated against the CRD's OpenAPI schema and stored in etcd; RBAC, admission, watches and audit logging apply to them like any other resource.

This is why Kubernetes became a platform: cert-manager's Certificate, Argo CD's Application, Prometheus Operator's ServiceMonitor, Gateway API's HTTPRoute are all CRDs.

2. Important parts of a CRD

FieldWhy it matters
scope Namespaced or Cluster.
versions[].schema Structural OpenAPI v3 schema: types, required fields, enums, min/max. Invalid objects are rejected at admission time.
x-kubernetes-validations CEL rules for cross-field checks, e.g. "replicas must be odd" or "field is immutable".
subresources.status Separates spec (desired, written by users) from status (observed, written by the controller).

Multiple versions v1beta1 and v1 served side by side; exactly one is the storage version; a conversion webhook translates between schemas when they differ.

Worked example

      storage: true

          type: string

Common pitfalls

  • Deleting a CRD deletes every object of that type in the cluster. Uninstalling a Helm chart that owns the CRDs can wipe out all Certificates or Applications.
  • Using a CRD as a general-purpose database – etcd is small (default quota of a few GiB) and every object is watched; large or high-churn data belongs elsewhere.
  • Schema changes without proper versioning: removing a field or changing its type breaks existing objects and clients.
  • Ordering in GitOps: custom resources applied before their CRD exists fail with "no matches for kind".

Q37. What is an operator, and how does it work?

Short answer

An operator is a custom controller plus CRDs that encodes the operational knowledge of a human operator for one application: installing it, scaling it, backing it up, failing over, upgrading. It runs a reconciliation loop – watch the custom resources, compare desired with actual state, act to close the gap – just like the built-in Deployment controller.

1. The reconciliation loop

          ┌──────────── watch events (CR changed, owned pod died, timer) ───┐
          ▼                                                                 │
   Reconcile(name)                                                          │
     1. read the custom resource (desired state)                            │
     2. read what exists: StatefulSets, Services, Secrets, the app itself   │
     3. compute the difference                                              │
     4. act: create / update / delete objects, call the app's admin API    │
     5. write status (conditions, phase, observedGeneration)               │
     6. requeue if not finished ───────────────────────────────────────────┘

Key design principle: level-triggered, not edge-triggered. The reconcile function doesn't ask "what event happened?" but "what should the world look like, and what does it look like now?". If the operator crashes and misses events, the next reconcile still converges. Every step must be idempotent – running it twice is harmless.

2. Building blocks

  • CRDs (Q36) – the API the user talks to.
  • Owner references – objects the operator creates point to the custom resource; deleting the CR garbage-collects them.
  • Finalizers – block deletion of the CR until the operator has cleaned up external things (take a final backup, delete a cloud bucket).
  • Status conditions – Ready, Progressing, Degraded, with observedGeneration so users know whether the status reflects the latest spec.
  • Frameworks – Kubebuilder / controller-runtime and Operator SDK (Go), also Java (JOSDK), Python (Kopf) and others. They provide caching, watches, work queues and leader election.

3. What separates a good operator from a Helm chart

A Helm chart installs resources once. An operator keeps managing them: day-2 operations. The Operator Framework's capability levels describe this progression: basic install → seamless upgrades → full lifecycle (backup, restore, failover) → deep insights (metrics, alerts) → auto-pilot (auto-scaling, auto-tuning).

Worked example

A PostgreSQL cluster with the CloudNativePG operator:

apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: orders-db
spec:
  instances: 3
  storage:
    size: 20Gi
  1. You apply 8 lines. The operator creates 3 pods with their PVCs, Services for read-write and read-only traffic, certificates, and configures streaming replication: 1 primary, 2 replicas.
  2. The primary's node dies. The operator notices on its next reconcile, promotes the most up-to-date replica, repoints the read-write Service, and rebuilds the lost instance – in seconds, without a human.
  3. You change instances: 3 to 5: two new replicas are cloned and join replication.
  4. A minor version upgrade: replicas are updated first, then a switchover moves the primary role, then the old primary is updated.

A StatefulSet alone (Q27) would give you 3 pods with disks – but no replication setup, failover or safe upgrade order.

Common pitfalls

  • Installing an operator is installing privileged software – it often needs broad cluster RBAC. Check who maintains it and what it can do.
  • Writing an operator for something a Helm chart or a Deployment already handles – operators are worth it when there is real ongoing operational logic.
  • Edge-triggered logic ("on create, do X") that breaks when events are missed or replayed.
  • Stuck finalizers: the operator is uninstalled before its custom resources, and they can never be deleted (namespace stuck in Terminating).

In the interview

"An operator is CRDs plus a custom controller that automates the operational knowledge for an application. It runs a level-triggered, idempotent reconciliation loop: read the desired state from the custom resource, observe the actual state, act, and report status. It uses owner references for cleanup and finalizers for external resources. The value is day-2 operations – failover, backups, upgrades – e.g. CloudNativePG or Strimzi." Follow-ups: level vs edge triggering; operator vs Helm; how you'd test one; finalizers.

Q38. What is in-place pod resize?

Short answer

In-place pod resize (GA in 1.35) lets you change a running container's CPU and memory requests/limits through the pod's resize subresource, without deleting and recreating the pod. Each container's resizePolicy decides whether a resource changes live or requires a container restart. The node must have room for the new size, otherwise the resize stays pending.

1. Why it matters

Pod resources used to be immutable: to give a pod more memory you recreated it – new pod, new IP, cold caches, dropped connections, and for a StatefulSet member possibly a failover. That made vertical scaling disruptive, so most teams over-provisioned instead. In-place resize enables:

  • Rightsizing long-running pods without restarts.
  • "Startup boost": generous CPU while a JVM/.NET app warms up, then shrink it.
  • VPA's InPlaceOrRecreate update mode, which applies recommendations in place when possible.

2. How a resize flows

  1. You (or VPA) patch the pod's resize subresource with new resources. spec now holds the desired values.
  2. The kubelet checks whether the node's allocatable capacity can fit the new requests.
    • Fits → it updates the container's cgroup limits through the runtime (or restarts the container, per resizePolicy).
    • Doesn't fit now → the pod gets a PodResizePending condition (reason Deferred), retried later; can never fit on this node → reason Infeasible.
  3. While applying, the pod has a PodResizeInProgress condition. status.containerStatuses[].resources shows what is actually applied – compare it with spec. 
spec:
  containers:
    - name: app
      image: my-app:4.1
      resizePolicy:
        - resourceName: cpu
          restartPolicy: NotRequired       # change CPU live (default)
        - resourceName: memory
          restartPolicy: RestartContainer  # app sizes heap at startup
      resources:
        requests: { cpu: "500m", memory: "1Gi" }
        limits: { cpu: "1", memory: "1Gi" }

3. Commands

CommandWhat it actually does
kubectl patch pod web --subresource resize --patch '{"spec":{"containers":[{"name":"app","resources":{"requests":{"cpu":"2"},"limits":{"cpu":"2"}}}]}}' Requests a new CPU size for container app. Patching resources on the main pod object (without --subresource resize) is rejected.
kubectl get pod web -o jsonpath='{.status.containerStatuses[0].resources}' Shows the resources actually applied right now.
kubectl describe pod web Shows PodResizePending / PodResizeInProgress conditions and their reasons.

Worked example

A Java API pod is set to 2 CPU because startup (JIT compilation, cache loading) takes 90s at 0.5 CPU. In steady state it uses 0.3 CPU. 30 replicas × 1.5 wasted CPU = 45 CPUs reserved for nothing.

  1. Start pods with cpu: 2 – fast startup.
  2. Once Ready, an automation (or VPA) resizes CPU to 500m in place – NotRequired, so no restart, no dropped connections.
  3. The node now has 1.5 CPU free per pod for other workloads; the cluster needs fewer nodes.

Memory is different: the JVM sized its heap from the limit at startup, so it is set to RestartContainer – the container restarts (the pod, its IP and volumes stay) and picks up the new heap size.

Common pitfalls

  • Assuming a resize always happens: if the node lacks room it stays Deferred – the pod is not moved to another node.
  • Lowering a memory limit live below what the process already uses – risky (OOM); prefer RestartContainer for memory, or check usage first.
  • The QoS class (Q21) is fixed at creation; a resize that would change it (e.g. Guaranteed → Burstable) is rejected.
  • Editing the Deployment template still triggers a normal rolling update – in-place resize applies to existing pods, and the template decides what new pods get.

In the interview

"Since 1.35 in-place resize is GA: you patch the pod's resize subresource and the kubelet updates the container's cgroups without recreating the pod. resizePolicy decides per resource whether a container restart is needed – typically CPU live, memory with restart for runtimes that size their heap at startup. If the node can't fit it, the resize is deferred. It enables non-disruptive rightsizing, startup CPU boosts, and VPA's InPlaceOrRecreate mode." Follow-ups: how to see the applied vs desired size; why memory needs care; what happens if the node is full.

Q39. How do you back up and restore etcd?

Short answer

On a self-managed cluster, take regular etcdctl snapshot save snapshots, store them encrypted off the node, and restore with etcdutl snapshot restore into a new data directory while the API servers are stopped. On managed clusters (EKS, AKS, GKE) the provider owns etcd, so you back up workloads and volumes instead (Velero, GitOps repo, volume snapshots). An untested backup is not a backup – rehearse the restore.

1. Why etcd is the one thing you must not lose

Every object in the cluster – Deployments, Services, Secrets, RBAC rules, CRDs and custom resources, node registrations, leases – lives as a key under /registry/... in etcd. The API server is stateless; controllers, the scheduler and kubelets are stateless too. They all reconstruct their view from etcd via the API server. So:

  • Lose a worker node → controllers recreate its pods elsewhere. Annoying, not fatal.
  • Lose the API server → restart it, nothing is lost.
  • Lose etcd (all members, or quorum with corrupted data) → the cluster forgets everything it was supposed to run. Containers already running keep running for a while, but nothing can be managed or healed.

What an etcd snapshot does not contain: the data inside PersistentVolumes (database files, uploads), container images, and anything outside the cluster (DNS records, cloud load balancers). Those need their own backup strategy.

2. Taking a snapshot

etcdctl snapshot save connects to one healthy member over TLS and streams a consistent point-in-time copy of its keyspace into a single file. It does not stop the cluster. On a kubeadm cluster with "stacked" etcd (etcd runs as a static pod on each control-plane node), the certificates live in /etc/kubernetes/pki/etcd/: 

# run on a control-plane node
export ETCDCTL_API=3   # default since etcd 3.4, harmless to set
etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /backup/etcd-$(date +%F-%H%M).db

# verify the file: hash, revision, number of keys, size
etcdutl snapshot status /backup/etcd-2026-11-15-0200.db -w table

In practice this runs as a CronJob or systemd timer on a control-plane node, then uploads the file to object storage (S3, Azure Blob, GCS) with encryption and a retention policy. Remember that the snapshot contains every Secret – if etcd encryption at rest is not enabled (Q46), it contains them in plain base64.

3. Restoring – the actual procedure

A restore does not "load data into" a running etcd. It builds a brand new data directory from the snapshot, with a new cluster ID, and you start etcd on top of that directory. Steps for a kubeadm single control-plane cluster: 

1. Stop the API server and etcd
   (kubelet stops static pods whose manifests disappear)
   mkdir /root/manifests-off
   mv /etc/kubernetes/manifests/kube-apiserver.yaml /root/manifests-off/
   mv /etc/kubernetes/manifests/etcd.yaml           /root/manifests-off/

2. Restore the snapshot into a NEW directory
   etcdutl snapshot restore /backup/etcd-2026-11-15-0200.db \
     --data-dir /var/lib/etcd-restored

3. Point etcd at the new directory
   edit /root/manifests-off/etcd.yaml:
     volumes -> etcd-data -> hostPath.path: /var/lib/etcd-restored

4. Start etcd, then the API server
   mv /root/manifests-off/etcd.yaml           /etc/kubernetes/manifests/
   mv /root/manifests-off/kube-apiserver.yaml /etc/kubernetes/manifests/

5. Check
   kubectl get nodes
   kubectl get pods -A

For a multi-member etcd cluster you restore the same snapshot on every member, each with its own --name, --initial-cluster and --initial-advertise-peer-urls, so they form a new cluster together. You never restore only one member of a running cluster.

etcdutl is the offline tool for working with data files; etcdctl snapshot restore still exists in older guides but is deprecated in favour of etcdutl.

4. What happens after the restore

The cluster's state jumps back to the moment of the snapshot. Everything then reconciles towards that old desired state: Deployments created after the snapshot no longer exist, so their pods are cleaned up; objects deleted after the snapshot come back. Nodes re-register, and kubelets compare what they run with what the API says they should run. This is why you want frequent snapshots (often every hour or less) and why GitOps (Q60) is a great complement: after a restore, Argo CD or Flux re-applies anything that changed since the snapshot.

CommandWhat it actually does
etcdctl snapshot save f.db Streams a consistent copy of one live member's keyspace into a file, over the network, without downtime.
etcdutl snapshot status f.db Reads the file offline and prints hash, revision, key count and size – a cheap integrity check after every backup.
etcdutl snapshot restore f.db --data-dir d Creates a fresh data directory (new cluster ID and member ID) from the snapshot. Does not touch any running etcd.
etcdctl endpoint health / endpoint status -w table Shows which members are healthy, who is leader, DB size and raft index – use before and after a restore.

Worked example

Snapshots run every hour at :00 and are uploaded to S3 with 7 days of retention (168 files, each about 80 MB). At 14:20 an engineer runs a script that deletes a namespace containing 40 Deployments and their Secrets. Options:

  • GitOps-managed namespace: recreate the namespace and let Argo CD re-sync – no etcd restore needed. Secrets come back from the external secret store. Minutes of work, no impact on other teams.
  • Not in git: an etcd restore to 14:00 would bring the namespace back, but it would also roll back every other team's changes from the last 20 minutes. A restore is a whole-cluster time machine, not a per-namespace undo. Velero (namespace-level backups) is the better tool for this case.

Conclusion: etcd snapshots are for disaster recovery (all members lost, data corrupted); namespace mistakes are better fixed from git or Velero.

Common pitfalls

  • Never testing the restore. The first restore attempt should not be during an outage.
  • Keeping snapshots only on the control-plane node – if the node dies, so does the backup.
  • Restoring into the existing data directory, or restoring only one member of a multi-member cluster – leads to a split or corrupt cluster.
  • Forgetting that snapshots contain all Secrets: store them encrypted and restrict who can read the bucket.
  • Assuming the snapshot covers PersistentVolume data. It does not.

In the interview

"etcd is the only stateful part of the control plane, so on self-managed clusters I take scheduled etcdctl snapshot save backups, verify them with etcdutl snapshot status, and ship them encrypted to object storage. Restore means stopping the API servers, etcdutl snapshot restore into a new data dir on every member, pointing etcd at it and starting again – and we rehearse it. On managed Kubernetes the provider handles etcd, so I rely on GitOps plus Velero for workloads and volumes." Likely follow-ups: what is not in the snapshot (PV data), how often you back up, how restore interacts with GitOps.

Q40. How do you upgrade a cluster safely?

Short answer

Prepare first (release notes, deprecated APIs, add-on compatibility, etcd backup, staging rehearsal), then upgrade one minor version at a time: control plane first, then nodes one by one (or by surging new nodes), letting PodDisruptionBudgets keep applications available. Upgrading should be a routine process every few months, not a yearly project.

1. Why upgrades are unavoidable

Kubernetes releases three minor versions per year, and each one gets about 14 months of patch support. Managed providers follow a similar calendar and eventually force-upgrade clusters that fall off support (or charge extra for extended support). If you skip upgrades for a year, you are suddenly two or three minors behind and must do several upgrades in a row under time pressure. Teams that upgrade every release find each step small and boring – which is the goal.

2. Preparation: where breakages actually come from

  • Removed API versions. The classic breakage: a manifest or Helm chart still uses an API version that the new release no longer serves (for example policy/v1beta1 PodDisruptionBudget was removed in 1.25). The API server simply rejects it. Scan before upgrading: 
    pluto detect-helm -o wide          # Helm releases
pluto detect-files -d ./manifests  # files in git
kubent                              # live cluster objects
    The API server also exposes the metric apiserver_requested_deprecated_apis, which tells you who is still calling old versions.
  • Behaviour changes and removed features in the release notes – for example dockershim removal (1.24), PodSecurityPolicy removal (1.25), and cgroup v1 support removal in 1.35, which means nodes still on an OS image with cgroup v1 must be moved to cgroup v2 first.
  • Add-ons: CNI, CSI drivers, ingress/gateway controllers, cert-manager, service mesh, monitoring agents. Each has its own compatibility matrix; upgrade them to a version that supports both the old and new Kubernetes version before the cluster upgrade.
  • Backup and rehearsal: etcd snapshot (Q39) on self-managed clusters, then run the exact same upgrade on a staging cluster first.

3. Order of operations and version skew

Components are allowed to run at slightly different versions during the upgrade – this is the version skew policy, and it dictates the order:

  • The kube-apiserver is upgraded first. In an HA control plane, API servers may differ by at most one minor version from each other.
  • kube-controller-manager and kube-scheduler must not be newer than the API server – so they follow it.
  • kubelet must never be newer than the API server, and may be a few minor versions older (up to three in current releases). That is why nodes come after the control plane and why you can upgrade nodes gradually.
  • kubectl is supported within one minor version of the API server.

You must go one minor version at a time: 1.33 → 1.34 → 1.35. Skipping (1.33 → 1.35) is not supported, because storage migrations and API conversions are only guaranteed between adjacent versions.

4. Upgrading nodes without dropping traffic

Two strategies:

  • In place (cordon + drain + upgrade): kubectl cordon marks the node unschedulable, kubectl drain evicts its pods through the eviction API (which respects PodDisruptionBudgets – Q25), controllers recreate those pods on other nodes, you upgrade the kubelet, then uncordon.
  • Surge / replace: add new nodes already on the new version, drain old nodes, delete them. This is what managed node groups and Karpenter do. It is safer (rollback = keep old nodes) and needs spare capacity or quota. 
# kubeadm example: 1.34 -> 1.35
# 0. switch the package repo to the new minor (pkgs.k8s.io is per-minor)

# first control-plane node
apt-get install -y kubeadm=1.35.x-*
kubeadm upgrade plan              # shows what will change, checks health
kubeadm upgrade apply v1.35.x     # upgrades static pods: apiserver, etcd, ...

# other control-plane nodes
kubeadm upgrade node

# each node (control plane too), one at a time
kubectl drain node-1 --ignore-daemonsets --delete-emptydir-data
apt-get install -y kubelet=1.35.x-* kubectl=1.35.x-*
systemctl daemon-reload && systemctl restart kubelet
kubectl uncordon node-1
CommandWhat it actually does
kubeadm upgrade plan Checks cluster health and prints the versions you can upgrade to, plus any component config changes. Changes nothing.
kubeadm upgrade apply v1.35.x Rewrites the static pod manifests of the control plane on this node, renews certificates, updates cluster-wide config (kubeadm/kubelet ConfigMaps, CoreDNS, kube-proxy).
kubeadm upgrade node On other nodes: upgrades local control-plane components (if any) and the local kubelet configuration.
kubectl drain node-1 --ignore-daemonsets Cordons the node, then evicts every pod via the eviction API, honouring PDBs. DaemonSet pods are skipped (they would be recreated on the same node anyway). Hangs if a PDB cannot be satisfied.
kubectl uncordon node-1 Makes the node schedulable again.

Worked example

Cluster: 3 control-plane nodes, 6 workers, version 1.34. Payment API has 3 replicas with a PDB maxUnavailable: 1.

  1. Week before: pluto finds one Helm chart using a removed API version → chart updated. CNI upgraded to a version supporting 1.34 and 1.35. Staging cluster upgraded first; smoke tests pass.
  2. Upgrade day: etcd snapshot taken. Control-plane node 1: kubeadm upgrade apply. Nodes 2 and 3: kubeadm upgrade node. During this time the API server is served by the other two nodes through the load balancer – clients see no downtime.
  3. Workers one by one: drain worker-1. It hosts 2 payment pods; the eviction API evicts the first, refuses the second until the replacement is Ready elsewhere (PDB allows only 1 unavailable), then evicts it. Payment always has at least 2 of 3 replicas serving.
  4. After all 6 workers: kubectl get nodes shows v1.35 on all nine nodes. Total: a few hours, zero customer impact.

Common pitfalls

  • A PDB with minAvailable equal to the replica count, or a PDB on a single-replica app → drain waits forever.
  • Pods with emptyDir or not owned by a controller block drain unless you pass --delete-emptydir-data / --force – and bare pods are then gone for good.
  • Skipping minor versions, or upgrading kubelets before the control plane (kubelet newer than API server is not supported).
  • Forgetting add-ons: a CNI or CSI driver that doesn't support the new version can take down networking or storage cluster-wide.
  • Not enough spare capacity: when you drain a node, its pods must fit somewhere else, otherwise they stay Pending.

In the interview

Structure the answer as prepare → control plane → nodes → verify: "I read the release notes, scan for removed APIs with pluto or kubent, upgrade add-ons to compatible versions, back up etcd, and rehearse in staging. Then one minor at a time: control plane first because of the version skew policy, then nodes by drain or surge, with PDBs protecting availability." Follow-ups: what is version skew, why can't you skip versions, what blocks a drain, how managed clusters differ (the provider upgrades the control plane; you still handle node pools and add-ons).

Q41. How do you monitor a cluster?

Short answer

Collect metrics with Prometheus from several sources – node-exporter (machines), kubelet/cAdvisor (containers), kube-state-metrics (object state) and the applications themselves – visualise them in Grafana and alert through Alertmanager. Add traces with OpenTelemetry and central logs (Q42). Alert on user-facing symptoms first, then on cluster health signals.

1. The metric sources and what each one answers

SourceWhat it measuresExample question
node-exporter (DaemonSet) Machine-level: CPU, memory, disk space and IO, network, load. Is node-4's disk 95% full?
kubelet / cAdvisor Per-container resource usage: CPU seconds, memory working set, CPU throttling, network per pod. Is the API pod being CPU-throttled?
kube-state-metrics The state of objects from the API: desired vs available replicas, pod phase, restarts, Job failures, PVC status, node conditions. Which Deployments have fewer available replicas than desired?
Control plane API server request latency/errors, etcd latency and DB size, scheduler queue (self-managed clusters). Is the API server slow because etcd disks are slow?
Applications Request rate, errors, latency, business metrics. Did checkout errors rise after the deploy?

metrics-server is a different, much smaller component: it keeps only the latest CPU/memory value per pod and node in memory, and serves the Metrics API used by kubectl top, HPA and VPA. It is not a monitoring system – no history, no alerts.

2. How it usually fits together

  apps (/metrics) ─┐
  node-exporter ───┤
  kubelet/cAdvisor ┼──> Prometheus ──> Grafana (dashboards)
  kube-state-metr. ┤        │
  control plane ───┘        └──> Alertmanager ──> Slack / PagerDuty / email

  apps ──(OTel SDK)──> OpenTelemetry Collector ──> Tempo / Jaeger (traces)

The common way to install this is the kube-prometheus-stack Helm chart, which uses the Prometheus Operator. Applications declare what to scrape with a ServiceMonitor or PodMonitor custom resource instead of editing Prometheus config: 

apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: orders-api
  namespace: shop
spec:
  selector:
    matchLabels:
      app: orders-api      # the Service to scrape
  endpoints:
    - port: http-metrics   # named port on the Service
      path: /metrics
      interval: 30s

For long retention or many clusters, Prometheus data is shipped to a scalable backend (Thanos, Mimir, a managed Prometheus service).

3. What to alert on

Alert on symptoms that users feel, and use cluster metrics to diagnose. A good split:

  • Paging alerts (wake someone up): error rate and latency SLOs of user-facing services (the RED method: Rate, Errors, Duration), Deployments with zero available replicas, API server down.
  • Ticket alerts (fix during working hours): nodes NotReady, pods crash-looping or Pending for over 15 minutes, PVC above 85% full, certificates expiring within 14 days, failed CronJobs, sustained CPU throttling, etcd DB size growing, nodes with memory/disk pressure.

For infrastructure, the USE method (Utilisation, Saturation, Errors) per resource is a good checklist.

Worked example

Latency of the orders API rises from 80 ms to 900 ms (p99). Average CPU usage on the dashboard is only 40% of the limit. Investigation with the metrics above: 

# fraction of CPU periods in which the container was throttled
sum(rate(container_cpu_cfs_throttled_periods_total{pod=~"orders-api.*"}[5m]))
/
sum(rate(container_cpu_cfs_periods_total{pod=~"orders-api.*"}[5m]))
# result: 0.62  -> 62% of periods throttled

The average hides bursts: each request spikes CPU on many threads and hits the CFS quota (Q23). Raising/removing the CPU limit brings p99 back to 90 ms. Without cAdvisor's throttling metric, this would look like a mystery "slow app".

Common pitfalls

  • Confusing metrics-server with monitoring – it has no history and no alerts.
  • Alerting on causes instead of symptoms ("CPU > 80%") → alert fatigue, people start ignoring pages.
  • High-cardinality labels (user IDs, request IDs, full URLs) in application metrics – Prometheus memory explodes.
  • Monitoring stack running inside the same cluster only: when the cluster is down, so is the alerting. Have at least an external heartbeat / dead-man's-switch alert.
  • Looking at average CPU and missing throttling or p99 latency.

In the interview

Mention that metrics-server only feeds kubectl top and HPA. Follow-ups: how do you monitor multiple clusters (remote write to Thanos/Mimir), how do you avoid alert fatigue, what is cardinality.

Q42. How do you set up logging?

Short answer

Apps write structured logs to stdout/stderr; the container runtime stores them as files on the node; a DaemonSet agent (Fluent Bit, Grafana Alloy, OpenTelemetry Collector) tails those files, adds pod metadata and ships them to a central backend such as Loki or Elasticsearch/OpenSearch. Node-local logs disappear with the pod or node, so central shipping is mandatory in production.

1. Where container logs actually live

When a container writes to stdout/stderr, the container runtime (containerd) captures the stream and writes it to a file on the node: 

/var/log/pods/<namespace>_<pod>_<pod-uid>/<container>/0.log
/var/log/containers/<pod>_<namespace>_<container>-<id>.log   (symlinks)

kubectl logs asks the API server, which asks the kubelet on that node to read this file. Consequences:

  • The kubelet rotates these files (by default around 10 MiB and a handful of files per container), so kubectl logs only shows recent output.
  • When the pod is deleted, its log directory is removed. When the node is gone, its logs are gone.
  • kubectl logs --previous works only for the immediately previous container instance, and only while the pod still exists.

So for anything older than a few minutes – or any incident investigation – you need logs shipped elsewhere.

2. The node-agent pattern

node 1                         node 2
┌──────────────────────────┐   ┌──────────────────────────┐
│ app pods -> stdout       │   │ app pods -> stdout       │
│   -> /var/log/pods/...   │   │   -> /var/log/pods/...   │
│ log agent (DaemonSet)    │   │ log agent (DaemonSet)    │
│   tail + add metadata ───┼─┐ │   tail + add metadata ───┼─┐
└──────────────────────────┘ │ └──────────────────────────┘ │
                             └──────────────┬───────────────┘
                                            ▼
                         Loki  or  Elasticsearch / OpenSearch
                                            ▼
                                 Grafana  or  Kibana / Dashboards

The agent runs as a DaemonSet (Q28), mounts the node's /var/log read-only, and enriches every line with Kubernetes metadata from the API (namespace, pod, container, labels, node) so you can filter by app=orders-api later. Common agents: Fluent Bit (very light), Grafana Alloy (the successor of Promtail, which is deprecated), and the OpenTelemetry Collector (one agent for logs, metrics and traces).

A sidecar log shipper (Q32) is only needed when an app can't write to stdout (it insists on writing files) – it costs one extra container per pod, so the DaemonSet is the default.

3. Choosing a backend

BackendHow it indexesTrade-off
Loki + Grafana Indexes only labels (namespace, app, pod); log text is compressed in object storage and scanned at query time. Cheap and simple; full-text search over huge ranges is slower. Keep label cardinality low.
Elasticsearch / OpenSearch + Kibana Full-text inverted index over every field. Powerful search and analytics; much more CPU, RAM and disk to run.
Cloud logging (CloudWatch, Azure Monitor, Cloud Logging) Managed. No operations, but cost grows with volume.

4. What the application should do

  • Log to stdout/stderr, never to files inside the container.
  • Log structured JSON: level, message, timestamp, trace ID, and request fields as separate keys, so the backend can filter on them.
  • Include the trace ID so you can jump from a log line to the distributed trace (Q41).
  • Never log secrets, tokens or personal data.

Separately, enable API server audit logs (who did what through the API) – they are configured with an audit policy on the API server on self-managed clusters, or switched on in the provider's settings on managed ones. They answer "who deleted this namespace?".

Worked example

A pod of orders-api crashed at 03:12 and was replaced; by the morning the pod (and its local logs) no longer exists. With Loki you query: 

{namespace="shop", app="orders-api"} | json | level="error"

You find {"level":"error","msg":"connection pool exhausted","traceId":"4bf9..."} at 03:11:58 from that pod, follow the trace ID to the trace showing a slow database call, and correlate with a database maintenance window at 03:10. None of this would be possible with kubectl logs.

Common pitfalls

  • Apps writing logs to files inside the container: the agent never sees them, and the writable layer fills up (can cause eviction for ephemeral storage – Q57).
  • Multi-line stack traces split into many log entries – configure multiline parsing or, better, log JSON.
  • Using high-cardinality values (pod UID, request ID) as Loki labels.
  • No retention policy → the logging cluster becomes the most expensive system you run.
  • Logging tokens, passwords or personal data.

In the interview

"Containers log to stdout; the runtime writes files on the node that rotate and vanish with the pod, so we run a DaemonSet agent – Fluent Bit or Alloy – that adds Kubernetes metadata and ships to Loki, or to OpenSearch when we need full-text analytics. Apps log JSON with trace IDs, and API audit logging is enabled separately." Follow-ups: sidecar vs DaemonSet, Loki vs Elasticsearch, how to control log cost.

Q43. How do you prevent pods from running privileged or as root?

Short answer

At the pod level, set a securityContext (runAsNonRoot, allowPrivilegeEscalation: false, drop all capabilities, seccompProfile: RuntimeDefault, read-only root filesystem). At the cluster level, enforce it with Pod Security Admission labels on namespaces (the restricted profile), and use a policy engine (Kyverno, Gatekeeper, ValidatingAdmissionPolicy) for rules beyond that.

1. Why root in a container matters

A container is just a process on the host kernel (see the Docker page). If it runs as UID 0 and an attacker finds a way out – a kernel bug, a mounted host path, a dangerous capability – they are root on the node, and from the node they can read every Secret mounted into every pod there. Privileged containers (privileged: true) are worse: they get all capabilities and access to host devices, which is practically the same as root on the host. So the goal is defence in depth: even if the app is compromised, the attacker is an unprivileged user with no capabilities.

2. The securityContext, field by field

apiVersion: v1
kind: Pod
metadata:
  name: api
spec:
  securityContext:                  # pod level: applies to all containers
    runAsNonRoot: true
    runAsUser: 10001                # numeric UID (see pitfalls)
    runAsGroup: 10001
    fsGroup: 10001                  # group ownership for mounted volumes
    seccompProfile:
      type: RuntimeDefault
  containers:
    - name: api
      image: registry.example.com/api:1.8.0
      securityContext:              # container level
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
      volumeMounts:
        - name: tmp
          mountPath: /tmp           # writable scratch space
  volumes:
    - name: tmp
      emptyDir: {}
FieldWhat it actually does
runAsNonRoot: true The kubelet refuses to start the container if it would run as UID 0. It is a check, not a change of user.
runAsUser Overrides the image's USER with this UID.
allowPrivilegeEscalation: false Sets the Linux no_new_privs flag: setuid binaries (like sudo) can't raise privileges.
capabilities.drop: ["ALL"] Removes all Linux capabilities (fine-grained root powers such as NET_ADMIN, SYS_ADMIN). Add back only what is needed, e.g. NET_BIND_SERVICE to bind port 80.
seccompProfile: RuntimeDefault Applies the runtime's default syscall filter, blocking rarely used dangerous syscalls.
readOnlyRootFilesystem: true Attackers can't drop tools or modify binaries; the app writes only to explicit volumes such as an emptyDir on /tmp.

3. Enforcing it: Pod Security Admission

Setting good defaults in your own manifests is not enough – you need the cluster to reject bad pods from anyone. PodSecurityPolicy was removed in 1.25; its built-in replacement is Pod Security Admission (PSA). It implements three predefined Pod Security Standards:

  • privileged – no restrictions (for system namespaces such as CNI or storage agents).
  • baseline – blocks known privilege escalations: privileged containers, host namespaces (hostNetwork, hostPID), hostPath volumes, dangerous capabilities.
  • restricted – baseline plus hardening: must run as non-root, allowPrivilegeEscalation: false, drop ALL capabilities, seccomp RuntimeDefault, limited volume types.

You choose a level per namespace and a mode: enforce (reject), audit (record in audit log), warn (return a warning to the user). 

kubectl label namespace shop \
  pod-security.kubernetes.io/enforce=baseline \
  pod-security.kubernetes.io/warn=restricted \
  pod-security.kubernetes.io/audit=restricted

# dry run: which existing pods would violate "restricted"?
kubectl label --dry-run=server --overwrite namespace shop \
  pod-security.kubernetes.io/enforce=restricted

PSA is deliberately simple: it cannot express "images must come from our registry" or "every pod needs a team label". For custom rules use a policy engine – Kyverno, OPA Gatekeeper, or the built-in CEL-based ValidatingAdmissionPolicy (Q34).

Worked example

Rolling out restricted to an existing namespace safely:

  1. Add warn=restricted and audit=restricted, keep enforce=baseline. Developers see warnings on every kubectl apply; nothing breaks.
  2. The server-side dry run lists 3 of 20 workloads failing: two lack seccompProfile, one runs as root because its image has no USER.
  3. Fix the manifests and rebuild the image with a numeric non-root user.
  4. Switch to enforce=restricted. A later attempt to deploy a pod with privileged: true is rejected immediately: violates PodSecurity "restricted:latest": privileged ...

Common pitfalls

  • runAsNonRoot: true with an image whose USER is a name (e.g. USER app): the kubelet can't verify the name isn't root and refuses to start the container. Use a numeric UID in the image or set runAsUser.
  • PSA enforce checks pods, not Deployments: the Deployment is accepted, but the ReplicaSet can't create pods. Look at the ReplicaSet events (warn mode also checks workload objects).
  • Read-only root filesystem without a writable /tmp → the app crashes when it writes temp files.
  • Non-root app trying to listen on port 80 – use a port above 1024 or add only NET_BIND_SERVICE.
  • Labelling kube-system restricted and breaking CNI/CSI agents that legitimately need privileges.

In the interview

Two layers: "Workloads set a hardened securityContext – non-root numeric UID, no privilege escalation, drop ALL, seccomp RuntimeDefault, read-only root FS. The cluster enforces it with Pod Security Admission namespace labels, rolled out via warn and audit before enforce, plus Kyverno or ValidatingAdmissionPolicy for custom rules." Mention PSP was removed in 1.25. Follow-ups: difference between baseline and restricted, what capabilities are, how you handle system namespaces that need privileges.

Q44. How do you secure a Kubernetes cluster overall?

Short answer

Use layered defence – the "4C" model: Cloud (network and IAM around the cluster), Cluster (API access, RBAC, admission policies, network policies, secrets encryption, audit, upgrades), Container (trusted minimal images, non-root, no privileges) and Code (secrets handling, dependencies, mTLS). Add runtime detection for what prevention misses. Each outer layer protects the inner ones; none is enough alone.

1. The 4C model

┌─────────────────────────────── Cloud / infrastructure ─┐
│  ┌────────────────────────────────────── Cluster ───┐  │
│  │  ┌─────────────────────────── Container ──────┐  │  │
│  │  │  ┌──────────── Code ──────────┐            │  │  │
│  │  │  │  app, dependencies, secrets│            │  │  │
│  │  │  └────────────────────────────┘            │  │  │
│  │  └────────────────────────────────────────────┘  │  │
│  └──────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────┘

You can't secure the code if anyone on the internet can reach the API server with a stolen token, and a perfect cluster config does not help if the image contains a critical vulnerability. Think about each layer.

2. Cloud / infrastructure

  • API server endpoint private, or restricted to known IP ranges / VPN.
  • Nodes in private subnets, no public IPs, no SSH from the internet.
  • Least-privilege cloud IAM for node roles – a node role that can modify IAM or read all S3 buckets turns any pod escape into an account compromise.
  • Block pod access to the cloud metadata endpoint (or require IMDSv2 with a hop limit) so pods can't steal the node's credentials.
  • Encrypted disks and etcd volumes.

3. Cluster

  • Authentication: SSO/OIDC for humans, short-lived credentials, no shared admin kubeconfigs; anonymous auth disabled; kubelet API (port 10250) requires authentication.
  • Authorization: RBAC with least privilege (Q14); review who has cluster-admin, list secrets, create pods, escalate/bind/impersonate.
  • Admission: Pod Security Admission (Q43) plus policies: allowed registries, signed images, required labels, no latest tag (Q34).
  • Network: default-deny NetworkPolicies per namespace (Q26), egress control.
  • Data: etcd encryption at rest (Q46), external secret stores, etcd reachable only from the API servers.
  • Visibility and hygiene: API audit logs, regular upgrades (Q40), certificate rotation, CIS benchmark checks (kube-bench).

4. Container and Code

  • Minimal base images (distroless, chiseled), scanned in CI and in the registry (Trivy, Grype), rebuilt regularly for patches.
  • Images signed in the pipeline (cosign) and signatures verified at admission, so only your pipeline's images run.
  • Non-root, read-only filesystem, no capabilities – the securityContext of Q43.
  • Secrets from a secrets manager, never in images, env files in git or logs; dependency scanning; mTLS between services where needed (Q30).

5. Detection: assume something gets through

Prevention can fail, so watch behaviour at runtime: Falco or Tetragon observe syscalls and alert on suspicious activity – a shell spawned in a production container, a read of /etc/shadow, an unexpected outbound connection. Combined with audit logs, this tells you what happened and when.

Worked example

Attack path: a web app has a remote code execution bug. Watch how each layer stops or limits it:

  1. Code: the vulnerable dependency would have been flagged by the scanner – but suppose it was a zero-day.
  2. Container: the attacker gets a shell as UID 10001, with no capabilities and a read-only filesystem – they can't install tools or escalate with setuid binaries. Distroless image: there isn't even a shell, so they must work with only the app's runtime.
  3. Cluster: the pod's ServiceAccount token is not mounted (automountServiceAccountToken: false), so no API access. NetworkPolicy allows the pod to reach only its database, so lateral movement to other services fails.
  4. Cloud: the metadata endpoint is blocked, so the node's IAM role can't be stolen.
  5. Detection: Falco alerts "unexpected process spawned in container" within seconds; the pod is isolated and investigated.

One bug in the code did not become a cluster or cloud compromise.

Common pitfalls

  • Public API endpoint with long-lived admin kubeconfigs shared over chat.
  • Granting cluster-admin to CI pipelines or operators "because it was easier".
  • Thinking namespaces isolate network traffic – they don't without NetworkPolicies.
  • Treating Secrets as encrypted – they are base64 unless encryption at rest is configured.
  • Never upgrading, so known CVEs stay open for years.

In the interview

Use the 4C model as a structure and give two or three concrete controls per layer, then mention runtime detection. Interviewers like the "attack path" framing: "even if the app is compromised, non-root plus no SA token plus NetworkPolicy plus blocked metadata endpoint keeps the blast radius to that pod". Follow-ups: how do you secure CI access to the cluster (GitOps pull model, Q60), how do you verify image signatures, what does kube-bench check.

Q45. How do you make the cluster itself highly available?

Short answer

Run 3 (or 5) control-plane nodes across availability zones behind a load balancer, with an etcd cluster of an odd number of members so it keeps quorum when one fails. Spread worker nodes across zones with an autoscaler and spare capacity, and make the workloads themselves HA (replicas spread across zones, PDBs, several CoreDNS replicas). For losing a whole region you need more than one cluster.

1. What "the cluster is down" can mean

  • Control plane down: running pods keep serving traffic (kubelets and the dataplane keep working), but nothing can change – no deploys, no scaling, no rescheduling of failed pods, no self-healing.
  • Nodes / zone down: the pods on them are gone; whether users notice depends on whether replicas exist elsewhere and there is capacity to replace them.

So HA has to cover both: the control plane and the data plane.

2. Control plane HA: each component behaves differently

ComponentHow it is made HA
kube-apiserver Stateless, so all instances are active at once behind a load balancer (cloud LB, or kube-vip / HAProxy + keepalived on bare metal). Clients and kubelets use the LB address – in kubeadm, --control-plane-endpoint.
kube-scheduler, kube-controller-manager Active/standby via leader election: every instance runs, but only the one holding a Lease object in kube-system acts. If the leader dies, its lease expires and another instance takes over within seconds. Two active schedulers would make conflicting decisions – hence one leader.
etcd A Raft cluster that needs a quorum (majority) to accept writes. Either "stacked" on the control-plane nodes or on separate "external" etcd nodes.

3. etcd quorum arithmetic

Quorum = floor(n / 2) + 1. A write is committed only when a majority of members has persisted it, which prevents two halves of a split cluster from both accepting writes.

MembersQuorumFailures tolerated
110
220 (worse than 1: two things that can fail)
321
431 (no gain over 3)
532

That's why etcd clusters are 3 or 5 members. More than 5 slows writes (every write waits for more acknowledgements) without real benefit. etcd is also very sensitive to disk and network latency: use fast SSDs and keep members in zones of one region, not across continents.

4. Data plane and workload HA

  • Worker node pools in at least 3 zones, with Cluster Autoscaler or Karpenter to replace capacity.
  • Spare capacity (headroom) so that losing a zone still leaves room for the evicted pods – running at 95% utilisation means a zone failure leaves pods Pending.
  • Workloads: several replicas spread with topology spread constraints (Q31), PDBs (Q25), readiness probes, and HA for cluster add-ons that everything depends on: CoreDNS, ingress/gateway controllers, cert-manager webhooks.

Managed services (EKS, AKS, GKE) give you an HA control plane by default; you are still responsible for nodes, zones and workloads. Against a whole region failing, the answer is multiple clusters in different regions with global traffic routing – one cluster is never multi-region.

Worked example

Setup: 3 control-plane nodes (one per zone a/b/c) with stacked etcd, 9 workers (3 per zone), app with 6 replicas spread maxSkew: 1 across zones. Zone b goes down:

  • etcd: 2 of 3 members left = quorum of 2 kept → writes continue. One more failure would make etcd read-only and the API unusable for changes.
  • API server: LB health checks drop the zone-b instance; clients continue via a and c.
  • Scheduler: if the leader was in zone b, its lease expires and an instance in a or c takes over in seconds.
  • App: 2 of 6 replicas lost, 4 keep serving. After the unreachable taint timeout (~5 minutes, Q59) replacements are scheduled in a and c – which works only because the workers had ~35% headroom.

Common pitfalls

  • 2 or 4 etcd members – more failure points, no extra tolerance.
  • Three control-plane nodes, but all in one zone or on one hypervisor host.
  • Kubelets pointing at one API server's IP instead of the load balancer – that node becomes a single point of failure.
  • Single-replica CoreDNS or ingress controller: the cluster is "HA" but DNS or all external traffic is not.
  • Spreading etcd across regions → high latency, unstable leader.

In the interview

Separate control plane from data plane, then explain per component: API servers active-active behind an LB, scheduler and controller manager leader-elected, etcd 3 or 5 members with quorum math. Then zones, headroom, and workload spreading. End with "managed control planes are HA already; multi-region needs multiple clusters". Follow-ups: what happens when etcd loses quorum (the API stops accepting writes; running pods keep running), stacked vs external etcd.

Q46. How do you encrypt Secrets at rest in etcd?

Short answer

Give the API server an EncryptionConfiguration file via --encryption-provider-config. The API server then encrypts Secrets before writing them to etcd and decrypts them on read. Prefer the kms v2 provider (key in an external KMS) over a local key. Existing Secrets stay unencrypted until rewritten, and keys must be rotated with a specific ordering.

1. What problem this solves (and what it doesn't)

Without encryption at rest, a Secret is stored in etcd as plain protobuf with base64 values. Anyone who gets an etcd backup file, a disk snapshot of a control-plane node, or direct etcd access can read every password in the cluster.

Encryption at rest protects data on disk and in backups. It does not protect against someone who can call the API with get secrets permission – the API server decrypts for them. That is RBAC's job (Q14).

2. How it works: the providers list

apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources: ["secrets"]       # can also include configmaps, custom resources
    providers:
      - kms:                     # 1st provider: used to ENCRYPT new writes
          apiVersion: v2
          name: cloud-kms
          endpoint: unix:///var/run/kms-plugin.sock
      - aescbc:                  # later providers: only used to DECRYPT
          keys:
            - name: key1
              secret: <BASE64_32_BYTE_KEY>
      - identity: {}             # = "no encryption": reads old plain data
  • Write: the API server always encrypts with the first provider in the list, and stores a prefix telling which provider and key was used, e.g. k8s:enc:aescbc:v1:key1:.
  • Read: it looks at the prefix and tries the matching provider. If there is no prefix, the data is plain and only identity can read it.
ProviderWhere the key livesNotes
identity – No encryption. The default if nothing is configured.
aescbc, aesgcm, secretbox In the config file on the control-plane node Simple, but the key sits on the same disk as etcd backups' source; rotation is manual. aesgcm needs frequent key rotation.
kms (v2) External KMS (cloud KMS, Vault, HSM) Envelope encryption: a data encryption key (DEK) encrypts the data; the KMS key encrypts the DEK. The master key never leaves the KMS, access is audited, rotation is easier. Recommended.

3. Enabling it on a kubeadm cluster

  1. Create the file on every control-plane node, e.g. /etc/kubernetes/enc/enc.yaml (for aescbc, generate a key with head -c 32 /dev/urandom | base64).
  2. Edit /etc/kubernetes/manifests/kube-apiserver.yaml: add --encryption-provider-config=/etc/kubernetes/enc/enc.yaml and a hostPath volume + volumeMount for that directory. The kubelet restarts the API server pod automatically.
  3. Rewrite existing Secrets so they are stored encrypted: 
    kubectl get secrets -A -o json | kubectl replace -f -
  4. Verify directly in etcd (next section).

4. Verifying and rotating keys

ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  get /registry/secrets/default/db-password | hexdump -C | head
# encrypted: starts with  k8s:enc:aescbc:v1:key1:  followed by random bytes
# NOT encrypted: you can read the password in the dump

Rotation with several API servers must be done in steps, because during the change some API servers may write with a key that others can't yet read:

  1. Add key2 as the second key on all API servers; restart all.
  2. Move key2 to the first position on all API servers; restart all.
  3. Rewrite all Secrets (kubectl replace as above).
  4. Remove key1; restart all.

Managed clusters encrypt etcd storage by default, and most let you add envelope encryption with your own KMS key as a setting.

Worked example

A team enabled aescbc on Monday. On Wednesday a security review takes an etcd snapshot and greps it: 140 of 150 Secrets are still readable in plain text. Reason: only Secrets created or updated after Monday were encrypted; the old ones were never rewritten. After running kubectl get secrets -A -o json | kubectl replace -f -, all 150 entries in etcd start with k8s:enc:aescbc:v1:key1:. The review also points out that the aescbc key is stored on the same node disk as the etcd data, so a full disk image still exposes everything – the team plans a move to KMS v2.

Common pitfalls

  • Forgetting to rewrite existing Secrets after enabling encryption.
  • Putting identity first – then nothing new is encrypted, although the config "has" a key.
  • Different config files on different API servers in HA – some instances can't read what others wrote.
  • Losing the encryption key (or KMS access): the Secrets in etcd and in every backup become unreadable. Back up the key separately from the etcd snapshots.
  • Believing encryption at rest protects against users with get secrets RBAC permission – it doesn't.

In the interview

"Secrets are only base64 in etcd by default. I configure an EncryptionConfiguration on the API servers – ideally KMS v2 envelope encryption so the master key stays in the KMS – then rewrite existing Secrets and verify in etcd that values carry the k8s:enc: prefix. The first provider encrypts; the rest only decrypt, which is also how key rotation works." Follow-ups: what is envelope encryption, how to rotate, does this protect against RBAC misconfigurations (no).

Q47. Several teams share one cluster. How do you stop one team affecting another?

Short answer

Give each team its own namespaces and wrap every namespace in the same set of guardrails: RBAC limited to that namespace, ResourceQuota and LimitRange for capacity, NetworkPolicies for traffic, Pod Security for privileges, and priority classes for who wins under pressure. This is "soft" multi-tenancy for teams that trust each other; untrusted tenants need separate clusters, virtual clusters or sandboxed runtimes.

1. The ways one team can hurt another

ProblemGuardrail
Deletes or edits another team's Deployment RBAC: RoleBindings only in the team's own namespaces (Q14)
Deploys 200 replicas and eats all cluster capacity ResourceQuota per namespace (Q48)
Pods without requests overpack nodes, then get everyone evicted LimitRange defaults (Q48), quota requiring requests
A compromised pod scans and calls other teams' services Default-deny NetworkPolicies (Q26)
A privileged pod escapes to the node and reads others' Secrets Pod Security Admission restricted/baseline (Q43)
A batch job starves a critical service when the cluster is full PriorityClasses + preemption
A noisy or GPU workload disturbs others on the same node Dedicated node pools with taints/tolerations (Q31)

2. Make it a template, not a manual setup

The guardrails only work if every namespace gets them. Platform teams typically create namespaces through a template (a Helm chart, a GitOps "tenant" folder, or tools like Capsule or Kyverno generate rules) that always produces the same bundle: 

tenants/team-a/
  namespace.yaml        # labels: team=a, pod-security enforce=restricted
  rbac.yaml             # RoleBinding: group team-a -> ClusterRole "edit"
  quota.yaml            # ResourceQuota: cpu, memory, pods, PVC storage
  limitrange.yaml       # default requests/limits per container
  netpol-default.yaml   # default-deny + allow DNS + allow from ingress ns

Binding the built-in edit ClusterRole with a RoleBinding (not a ClusterRoleBinding) gives the team edit rights only inside that namespace.

3. Priority classes: who wins when the cluster is full

apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: batch-low
value: 1000
preemptionPolicy: Never      # never kicks out other pods

When a high-priority pod can't be scheduled, the scheduler may preempt (evict) lower-priority pods to make room. Restrict who can use high priority classes – otherwise every team marks everything critical. A ResourceQuota with a scopeSelector on priorityClassName can limit that.

4. Soft vs hard multi-tenancy

All namespaces still share one control plane, one API server, one set of CRDs (cluster-scoped – teams can't each have a different version of an operator), and the same node kernels. That is fine for teams of the same company. For untrusted tenants (customers running their own code), add stronger isolation:

  • Separate clusters per tenant – strongest, most expensive.
  • Virtual clusters (vCluster) – each tenant gets its own API server and CRDs running inside a namespace of the host cluster.
  • Sandboxed runtimes (gVisor, Kata Containers) via RuntimeClass, so a kernel exploit doesn't reach the host.

Worked example

A 24-CPU cluster shared by teams A and B, each with a quota of requests.cpu: 10. Team B runs a load test and scales to 50 replicas of 500m each (25 CPU). What happens:

  • The first 20 pods are admitted (20 × 0.5 = 10 CPU). Pod 21 is rejected by the quota: the ReplicaSet events say exceeded quota: team-b-quota, requested: requests.cpu=500m, used: requests.cpu=10, limited: requests.cpu=10.
  • Team A's services still have their 10 CPU available and are not affected.
  • Without the quota: team B's pods would fill the cluster, team A's next rollout would leave new pods Pending, and the autoscaler would add nodes that the platform team pays for.

Common pitfalls

  • Using ClusterRoleBindings for team access – that grants the role in all namespaces.
  • NetworkPolicies on some namespaces only, or a CNI that ignores them.
  • Quota without LimitRange: pods without requests are rejected and teams get confusing errors.
  • Letting tenants create cluster-scoped resources (CRDs, webhooks, ClusterRoles) – one tenant's broken webhook can block everyone.
  • Treating namespaces as a hard security boundary for untrusted code.

In the interview

List the failure modes (access, capacity, network, privileges, priority) and the guardrail for each, and say they are applied by a namespace template through GitOps so no namespace is forgotten. Close with soft vs hard multi-tenancy. Follow-ups: how does preemption work, how do you handle CRDs that different teams need, when would you choose vCluster or separate clusters.

Q48. ResourceQuota vs LimitRange?

Short answer

ResourceQuota caps the total a namespace may consume (sum of CPU and memory requests/limits, number of pods, PVC storage, object counts). LimitRange works per container/pod/PVC: it fills in default requests/limits and enforces min/max values. They are used together, because a quota on CPU/memory makes requests mandatory and the LimitRange supplies them.

1. ResourceQuota: a budget for the namespace

The ResourceQuota admission controller keeps a running total of what is used in the namespace. Every create request is checked: if adding the new object would exceed a hard value, the request is rejected with 403 Forbidden: exceeded quota. 

apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-a-quota
  namespace: team-a
spec:
  hard:
    requests.cpu: "8"            # sum of CPU requests of all pods
    requests.memory: 16Gi
    limits.memory: 24Gi
    pods: "40"
    requests.storage: 500Gi      # sum of PVC requests
    persistentvolumeclaims: "20"
    services.loadbalancers: "2"  # each one costs money
    count/deployments.apps: "30" # object count for any resource

Important rule: once a quota tracks requests.cpu (or memory, or limits), every new pod must specify that value, otherwise it is rejected – the quota can't count something that is not declared.

2. LimitRange: rules and defaults per object

apiVersion: v1
kind: LimitRange
metadata:
  name: container-defaults
  namespace: team-a
spec:
  limits:
    - type: Container
      defaultRequest:            # used when a container sets no request
        cpu: 100m
        memory: 128Mi
      default:                   # used when a container sets no limit
        memory: 256Mi
      max:                       # anything bigger is rejected
        cpu: "2"
        memory: 4Gi
      min:
        memory: 64Mi
    - type: PersistentVolumeClaim
      max:
        storage: 50Gi

The LimitRanger admission plugin mutates new pods (injects the defaults) and validates them against min/max. It only acts at creation time; existing pods are not changed when you edit the LimitRange.

3. How they work together, in order

kubectl apply (Deployment)
  └─ ReplicaSet controller creates Pod
       └─ API server admission:
            1. LimitRanger: container has no requests?
                 -> inject defaultRequest 100m / 128Mi, default limit 256Mi
               exceeds max 2 CPU? -> reject
            2. ResourceQuota: used + new pod > hard?
                 -> reject "exceeded quota"
            3. stored in etcd -> scheduled
ResourceQuotaLimitRange
Scope Whole namespace (sum) Each container / pod / PVC
Sets defaults? No Yes (default, defaultRequest)
Typical question it answers "Team A may use at most 8 CPUs in total." "No single container may ask for more than 2 CPUs; unspecified means 100m."
Counts objects? Yes (pods, services, PVCs, any count/...) No

4. Useful commands

CommandWhat it actually does
kubectl describe resourcequota -n team-a Shows Used vs Hard for every tracked resource.
kubectl describe limitrange -n team-a Shows defaults, min and max per type.
kubectl describe rs <replicaset> -n team-a The place where quota rejections appear as FailedCreate events – not on the Deployment.
kubectl get pod p -o yaml | grep -A6 resources Shows the requests/limits the LimitRange injected.

Worked example

Quota requests.cpu: "4", no LimitRange. A developer deploys a chart whose containers have no resources section. kubectl get deploy shows 0/3 READY, and kubectl get pods shows nothing at all. The answer is in the ReplicaSet: 

Warning  FailedCreate  replicaset-controller  Error creating: pods "web-7d9c-x2" is
forbidden: failed quota: team-a-quota: must specify requests.cpu

Adding the LimitRange above fixes it without changing the chart: each container gets 100m CPU injected. Three replicas use 300m of the 4 CPU budget. Later the team scales to 50 replicas: 40 pods are created (4000m / 100m), the remaining 10 fail with exceeded quota.

Common pitfalls

  • Looking for quota errors on the Deployment or in kubectl get pods – they are on the ReplicaSet events.
  • A LimitRange with only default (limit) and no defaultRequest: the request then defaults to the limit, which can make every pod reserve far more than it uses.
  • Expecting a changed LimitRange to update running pods – it applies only at creation.
  • Quotas tighter than what a rolling update needs: with maxSurge, old and new pods exist at the same time and both count against the quota, so the rollout gets stuck.

In the interview

"ResourceQuota is the namespace budget – totals and object counts. LimitRange is per container – defaults plus min/max. A CPU or memory quota makes requests mandatory, so we always pair it with a LimitRange that injects defaults. Quota failures show up as FailedCreate on the ReplicaSet." Q49. How does DNS (CoreDNS) work, and why might lookups be slow?

Short answer

CoreDNS runs as a Deployment in kube-system behind the kube-dns Service; it answers names like my-svc.my-ns.svc.cluster.local from the Kubernetes API and forwards everything else upstream. Pods get a resolv.conf with search domains and ndots:5, which makes most external names go through several failing lookups first – the main cause of extra DNS load and latency, along with UDP conntrack races and too few CoreDNS replicas.

1. The pieces

  • CoreDNS pods (usually 2+) watch Services and EndpointSlices through the API and keep the records in memory.
  • The kube-dns Service in kube-system has a fixed ClusterIP (often 10.96.0.10).
  • The kubelet writes each pod's /etc/resolv.conf pointing at that IP: 
# /etc/resolv.conf inside a pod in namespace "shop"
nameserver 10.96.0.10
search shop.svc.cluster.local svc.cluster.local cluster.local
options ndots:5

Records CoreDNS serves:

NameAnswer
orders.shop.svc.cluster.local (normal Service) A record with the Service's ClusterIP
db.shop.svc.cluster.local (headless Service) A records of all ready pod IPs
db-0.db.shop.svc.cluster.local (StatefulSet pod) That pod's IP (Q27)
_http._tcp.orders.shop.svc.cluster.local SRV record with the named port

2. The Corefile

CoreDNS is configured by the coredns ConfigMap:

.:53 {
    errors
    health
    ready
    kubernetes cluster.local in-addr.arpa ip6.arpa {   # answer cluster names
        pods insecure
        fallthrough in-addr.arpa ip6.arpa
    }
    prometheus :9153                                  # metrics
    forward . /etc/resolv.conf                        # everything else upstream
    cache 30                                          # cache answers 30s
    loop
    reload
    loadbalance
}
corp.example.com:53 {                                 # added: stub domain
    forward . 10.0.0.53 10.0.0.54                     # corporate DNS servers
}

kubectl -n kube-system edit configmap coredns; the reload plugin picks up changes automatically after a short delay. Adding a block like corp.example.com is how pods resolve internal company names.

3. Why lookups get slow: ndots and the search list

ndots:5 means: "if the name has fewer than 5 dots, try it with each search domain appended before trying it as-is". This is what lets orders resolve to orders.shop.svc.cluster.local. But it also applies to external names: 

lookup "api.stripe.com"  (2 dots < 5)
  1. api.stripe.com.shop.svc.cluster.local   -> NXDOMAIN
  2. api.stripe.com.svc.cluster.local        -> NXDOMAIN
  3. api.stripe.com.cluster.local            -> NXDOMAIN
  4. api.stripe.com.                          -> answer
  x 2  (A and AAAA queries for each)
= 8 queries, 6 of them wasted, for one connection

On cloud nodes the host may add more search domains (e.g. a cloud internal domain), making it worse. Multiply by thousands of requests per second and CoreDNS becomes a bottleneck.

4. The 5-second timeouts and other causes

  • conntrack race: glibc sends the A and AAAA queries in parallel from the same UDP socket. Under load, a race in the kernel's connection tracking (when queries are DNATed to the CoreDNS ClusterIP) can drop one packet. The resolver then waits its full timeout – 5 seconds – before retrying. Symptom: occasional requests taking exactly 5 s longer.
  • Too few CoreDNS replicas or CPU-limited CoreDNS pods.
  • Slow upstream DNS for external names.
  • Egress NetworkPolicy that forgot port 53, so lookups time out instead of failing fast (Q26).

Fixes:

FixWhat it actually does
Trailing dot: api.stripe.com. Marks the name as fully qualified – search domains are skipped, 1 lookup.
dnsConfig: options: [{name: ndots, value: "2"}] Per pod: names with 2+ dots are tried as-is first. Short names like orders still work.
NodeLocal DNSCache A DNS cache DaemonSet on every node, on a link-local IP; pods query it locally, avoiding the conntrack race and most network hops.
Scale CoreDNS (more replicas, autoscaler) More capacity; spread replicas across nodes and zones.
App-side caching / connection reuse Fewer lookups in the first place. 
# per-pod DNS tuning
spec:
  dnsConfig:
    options:
      - name: ndots
        value: "2"
      - name: single-request-reopen   # glibc: separate sockets for A/AAAA

Worked example

A payment service calls api.stripe.com 2,000 times per second without connection reuse. CoreDNS dashboards show 16,000 queries/s, 75% of them NXDOMAIN, and 2 CoreDNS pods at their CPU limit; p99 latency of the service has occasional 5-second spikes.

  1. Debug from a pod: 
    kubectl run dnsutils --rm -it --image=registry.k8s.io/e2e-test-images/agnhost:2.39 -- sh
nslookup -debug api.stripe.com    # shows each search-domain attempt
  2. Set ndots: 2 on the payment Deployment → 2 queries per lookup instead of 8: about 4,000 queries/s.
  3. Enable connection keep-alive in the HTTP client → lookups drop by another order of magnitude.
  4. Deploy NodeLocal DNSCache → the 5-second spikes disappear.

Common pitfalls

  • Lowering ndots cluster-wide and breaking apps that rely on short names like orders.shop (one dot) resolving via search domains – test first.
  • dnsPolicy confusion: ClusterFirst is the default; Default actually means "use the node's DNS" (no cluster names); pods with hostNetwork: true need ClusterFirstWithHostNet to resolve Services.
  • Single CoreDNS replica, or replicas on one node – a node failure breaks DNS for the whole cluster.
  • Debugging DNS from an image without tools – use a debug image or kubectl debug (Q16).

In the interview

"CoreDNS watches Services through the API and serves svc.ns.svc.cluster.local; pods point at the kube-dns ClusterIP with search domains and ndots:5. That ndots setting makes external names try every search domain first – several NXDOMAINs times A and AAAA – and under load the UDP conntrack race causes 5-second timeouts. Fixes: FQDNs with a trailing dot, lower ndots per workload, NodeLocal DNSCache, scale CoreDNS." Follow-ups: how to add a corporate DNS zone (stub domain in the Corefile), what a headless Service returns, dnsPolicy options.

Q50. An application in Kubernetes has become slow. How do you investigate?

Short answer

First narrow the scope: is it every pod or one, every endpoint or one, and when did it start (deploy, traffic spike, node change)? Then check, in order: pod resources (including CPU throttling, not just usage), restarts and probe failures, logs for timeouts, dependencies and DNS, the nodes the pods run on, and whether autoscaling is keeping up. Traces and per-pod latency dashboards usually find the slow hop faster than kubectl.

1. Why "slow" is harder than "down"

A crashed pod leaves evidence: an exit code, an event, a restart count. A slow pod usually looks healthy to Kubernetes – it is Running, Ready, and passing probes. Kubernetes only knows about container lifecycle and resources; it has no idea that p99 latency went from 80 ms to 2 s. So the investigation is a process of elimination across layers: 

user ──► ingress/gateway ──► Service ──► pod (app) ──► dependencies
                                          │                (DB, cache, APIs, DNS)
                                          ▼
                                     node (CPU, memory, disk, network)

Every arrow is a place where time can be lost. The goal is to find which hop got slower, not to guess.

2. Scope it before touching kubectl

  • All pods or one? If only one replica is slow, suspect that pod's node (noisy neighbour, disk pressure) or that pod's state (memory leak, stuck thread pool). If all replicas are slow, suspect a shared cause: a dependency, a deploy, or traffic volume.
  • All endpoints or one? One slow endpoint points at a specific query or downstream call; everything slow points at resources or infrastructure.
  • Since when? Correlate with kubectl rollout history, the GitOps commit log, HPA events and node changes. "It got slow at 14:02, the deploy finished at 14:01" solves half the incidents.

3. The diagnostic flow

  • Looking only at average CPU usage and concluding "CPU is fine" while the pod is throttled.
  • Restarting pods "to fix it" – destroys the evidence (heap state, thread dumps) and often only helps for a few minutes.
  • Blaming Kubernetes when the logs show the database is the slow hop. Kubernetes is often just the messenger.
  • Forgetting that kubectl top needs metrics-server and only shows the last short window – use Prometheus/Grafana for history and comparison with "before".
  • Several replicas scheduled on the same overloaded node because there is no topology spread or anti-affinity.

Q51. Nginx pods are Running, but the application is unreachable via its URL. What do you check?

Short answer

Follow the traffic path from the pod outward (or from the user inward) and test each hop separately: the pod itself, the Service (selector, targetPort, endpoints), NetworkPolicies, the Ingress/Gateway route, and finally the outside world – load balancer IP, DNS, firewalls and TLS. kubectl port-forward lets you test each layer in isolation.

1. The path a request takes

browser
  │  DNS: app.example.com → 203.0.113.10
  ▼
cloud load balancer (Service type LoadBalancer, external IP 203.0.113.10)
  │
  ▼
ingress / gateway controller pods
  │  matches host + path → backend Service "nginx", port 80
  ▼
Service "nginx" (ClusterIP 10.96.12.34:80)
  │  EndpointSlice: ready pod IPs, targetPort 8080
  ▼
pod 10.244.1.17:8080  ── container listening on 0.0.0.0:8080

"Pod is Running" only proves the last box is alive. Any box in between can break the chain, and each one fails with a characteristic symptom. The trick is to bisect: test the middle, then decide which half is broken.

2. Test each hop

Hop / CommandWhat it actually does
kubectl get pods -l app=nginx -o wide Are pods Ready (1/1), not just Running? Not Ready pods are never added to the Service.
kubectl port-forward pod/<pod> 8080:8080 Tunnels through the API server directly to the pod, bypassing Service, policies and ingress. If curl localhost:8080 fails here, the problem is the app (wrong port, listening on 127.0.0.1).

kubectl get svc -n ingress Does the controller's LoadBalancer Service have an EXTERNAL-IP, or is it stuck at <pending>?

      targetPort: 8080  # what the container actually listens on
---
# pod template in the Deployment

    app: web            # ← mismatch: Service selects app=nginx → no endpoints

      image: nginxinc/nginx-unprivileged:1.27   # listens on 8080, not 80
      ports:
        - containerPort: 8080

Pods are Ready but the EndpointSlice is empty: the Service selector requires tier=frontend, which the pods don't have. A 503 (not 404) already hinted at this – the controller found the route but had no backends. Adding the label to the pod template fixes it within seconds.

  • Testing only with port-forward and declaring the Service fine – port-forward bypasses kube-proxy and NetworkPolicy.
  • The app binds 127.0.0.1: works with kubectl exec ... curl localhost, fails from anywhere else.
  • Missing or wrong ingressClassName – the Ingress is accepted by the API server but no controller picks it up.
  • A default-deny NetworkPolicy in the app namespace that does not allow traffic from the ingress controller's namespace.
  • LoadBalancer stuck in <pending> on bare metal or when the cloud quota for IPs is exhausted.

Q52. A new version was deployed and fails to start, or the rollout is stuck. How do you investigate and recover?

Short answer

Restore service first, investigate second: kubectl rollout undo (or git revert under GitOps). Then look at the new ReplicaSet's pods to see why they never became available – crash, image pull, readiness, capacity, quota or an admission webhook. After progressDeadlineSeconds the Deployment reports ProgressDeadlineExceeded, but Kubernetes never rolls back by itself.

1. What "stuck" means mechanically

During a rolling update (Q18) the Deployment controller scales the new ReplicaSet up and the old one down, but only as fast as new pods become available (Ready for minReadySeconds). If new pods never become available, the controller simply stops: maxUnavailable forbids removing more old pods. That is the safety brake – most users keep being served by the old version – but the rollout hangs forever unless someone acts. 

replicas: 4, maxSurge: 1, maxUnavailable: 0

old RS (v1.4.1): ████  4 ready
new RS (v1.4.2): ▒     1 created → CrashLoopBackOff → never available
                 ↑ controller waits here; old pods untouched
after 600s: condition Progressing=False, reason=ProgressDeadlineExceeded

progressDeadlineSeconds (default 600) only reports failure: kubectl rollout status exits non-zero and the condition is set – useful for CI pipelines and alerts. It does not undo anything.

2. Recover first

CommandWhat it actually does
kubectl rollout status deploy/my-app --timeout=5m Blocks until the rollout completes or fails; non-zero exit on failure. Use it as the last CI deploy step.
kubectl rollout undo deploy/my-app Copies the previous ReplicaSet's pod template back into the Deployment. The old ReplicaSet still exists (scaled to 0), so it scales back up in seconds – no image rebuild needed.
kubectl rollout history deploy/my-app Lists revisions (one per ReplicaSet kept, up to revisionHistoryLimit, default 10).
kubectl rollout history deploy/my-app --revision=7 Shows the full pod template of revision 7 – diff it against the current one.
kubectl rollout pause / resume Freezes the rollout where it is (for example to investigate one canary pod) without rolling back.

Under GitOps (Q60), rollout undo is fought by the GitOps agent: the cluster no longer matches git, so Argo CD or Flux re-applies the broken version. Revert the commit instead.

 │
 ├─ kubectl get rs -l app=my-app        → which RS is new; DESIRED vs READY
 ├─ kubectl get pods -l app=my-app      → status of the NEW pods:
 │     ├─ CrashLoopBackOff        → Q55 (logs --previous, exit code)
 │     ├─ ImagePullBackOff        → Q58 (tag, registry, credentials)
 │     ├─ Running, 0/1 Ready      → Q56 (readiness probe)
 │     └─ Pending                 → Q54 (no room for the surge pod)
 └─ no new pods at all?
       └─ kubectl describe rs <new-rs> → quota exceeded / webhook denied

That last branch catches people out: if the new pod is rejected at admission (ResourceQuota exceeded, a policy forbids :latest), there is no pod to describe. The error is only in the ReplicaSet's events: 

$ kubectl describe rs my-app-5f7c9d8b6d | tail -3
Events:
  Warning  FailedCreate  replicaset-controller  Error creating: pods "my-app-5f7c9d8b6d-" is
  forbidden: exceeded quota: team-a-quota, requested: requests.memory=1Gi,
  used: requests.memory=7680Mi, limited: requests.memory=8Gi

Worked example

Version 2.3.0 of an API adds a required env variable PAYMENT_URL. The ConfigMap change was forgotten. 

$ kubectl rollout status deploy/api --timeout=3m
Waiting for deployment "api" rollout to finish: 1 out of 4 new replicas have been updated...
error: timed out waiting for the condition

$ kubectl get pods -l app=api
NAME                   READY   STATUS             RESTARTS     AGE
api-7b6d5c4f9-6gk2x    1/1     Running            0            2d

Common pitfalls

  • Expecting progressDeadlineSeconds to roll back automatically. It doesn't – use Argo Rollouts/Flagger for automatic abort.
  • maxUnavailable > 0 with a broken version: some old pods are removed before the new ones prove themselves, so capacity drops during the incident.
  • A readiness probe that always passes (or none at all): a broken version becomes "available" and replaces everything.
  • Looking at Deployment events only – quota and webhook rejections are on the ReplicaSet.
  • kubectl rollout undo under GitOps, then wondering why the broken version comes back.
  • Database migrations that are not backward compatible – rolling back the code doesn't roll back the schema.

In the interview

"First mitigate: roll back – rollout undo, or a git revert if we use GitOps. Then investigate: compare the revisions, look at the new ReplicaSet's pods – crash, image pull, readiness, Pending – and the ReplicaSet events for quota or webhook rejections. Note that Kubernetes only marks ProgressDeadlineExceeded; it never rolls back on its own, so I'd make CI fail on rollout status and consider progressive delivery." Follow-ups: "Why weren't users affected?" (readiness + maxUnavailable), "What about the database schema?" (expand/contract migrations).

Q53. A microservice can't connect to an external database outside the cluster. How do you fix it?

Short answer

Separate the layers and test each from inside the pod: DNS resolution, then TCP connectivity, then the application layer (credentials, TLS, connection limits). In between sit egress NetworkPolicies inside the cluster and firewalls/security groups outside it – which see the node or NAT gateway IP, not the pod IP.

1. What happens when a pod calls an external host

pod (10.244.3.9)
  │ 1. resolve db.example.com  → CoreDNS → upstream DNS (corporate / cloud)
  │ 2. TCP SYN to 192.0.2.50:5432
  ▼
egress NetworkPolicy check (CNI)            ← can drop DNS or the DB port
  ▼
node: SNAT 10.244.3.9 → node IP 10.0.1.12   ← most CNIs masquerade pod IPs
  ▼
NAT gateway (private clusters) → 198.51.100.7
  ▼
database firewall / security group           ← must allow 10.0.1.0/24 or 198.51.100.7
  ▼
database: TLS handshake, authentication, max_connections

The error message usually tells you the layer: "could not translate host name" (DNS), "connection timed out" (packets dropped – policy, firewall, routing), "connection refused" (reached the host, nothing listening on that port), "password authentication failed" / "SSL required" / "too many connections" (application layer).

2. Test each layer from inside the pod

CommandWhat it actually does
kubectl exec -it <pod> -- nslookup db.example.com Resolves through the pod's resolv.conf (CoreDNS, search domains). Failure → CoreDNS forwarding or blocked port 53.
kubectl exec -it <pod> -- nc -zv db.example.com 5432 Pure TCP connect, no protocol. Success means network and firewalls are fine; the problem is in the app layer.
kubectl debug -it <pod> --image=nicolaka/netshoot --target=app Adds an ephemeral container with network tools sharing the pod's network namespace – for distroless images without nc/nslookup.
kubectl get networkpolicy -n <ns> -o yaml Look for policies with policyTypes: [Egress] that select the pod. Anything not allowed is dropped silently (timeout).
kubectl run tmp --rm -it --image=busybox --overrides='{"spec":{"hostNetwork":true}}' -- nc -zv 192.0.2.50 5432 Same test from the node's network namespace. Works from node but not from pod → it's NetworkPolicy/CNI; fails from both → it's outside the cluster.

3. Fixes by layer

Egress NetworkPolicy – allow DNS and the database explicitly:

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: orders-egress
  namespace: shop
spec:
  podSelector:
    matchLabels:
      app: orders
  policyTypes: ["Egress"]
  egress:
    - to:                       # DNS to CoreDNS
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system
          podSelector:
            matchLabels:
              k8s-app: kube-dns
      ports:
        - { protocol: UDP, port: 53 }
        - { protocol: TCP, port: 53 }
    - to:                       # the external database
        - ipBlock:
            cidr: 192.0.2.50/32
      ports:
        - { protocol: TCP, port: 5432 }

Outside the cluster – the database firewall must allow the source IP it actually sees: node subnet, or the NAT gateway's public IP. Allowing the pod CIDR does nothing when pods are SNATed. With cloud VPC CNIs (pods get VPC IPs) the pod subnet may be the right thing to allow – know your CNI.

A stable in-cluster name – so apps don't hard-code external hosts: 

apiVersion: v1
kind: Service
metadata:
  name: orders-db
  namespace: shop
spec:
  type: ExternalName
  externalName: db.example.com   # DNS CNAME; no proxying, no port mapping

If the database only has an IP, use a Service without a selector plus a manually created EndpointSlice (labelled kubernetes.io/service-name: orders-db).

Worked example

After a security hardening sprint, the orders service logs timeout expired connecting to PostgreSQL on a VM. 

$ kubectl exec -it orders-5d8c7b9f6-kq2lp -- nslookup pg.internal.example.com
;; connection timed out; no servers could be reached

$ kubectl get networkpolicy -n shop
NAME                  POD-SELECTOR   AGE
default-deny-egress   <none>         2h

DNS itself times out – the new default-deny-egress policy blocks port 53 too. After adding the DNS rule, nslookup works, but nc -zv pg.internal.example.com 5432 still times out. Adding the ipBlock rule for the database fixes it. Two separate problems with the same symptom – which is why you test layer by layer instead of stopping at the first fix.

Common pitfalls

  • Using curl http://db:5432 to test a database – it's not HTTP; use nc -zv (or the database client).
  • Allowing the pod CIDR on the database firewall when traffic is SNATed to the node/NAT IP.
  • Egress default-deny without a DNS exception.
  • New nodes from autoscaling come up in a different subnet that the database firewall doesn't allow – works on some pods, fails on others.
  • Treating "too many connections" as a network issue: 30 replicas × a pool of 20 = 600 connections against a database allowing 200. Scale-out made it worse.

In the interview

"I'd test from inside the pod, layer by layer: DNS with nslookup, TCP with nc, then the app layer – credentials, TLS, connection limits. The error type tells me where to look: name resolution, timeout, refused or auth. Inside the cluster I'd check egress NetworkPolicies, including DNS; outside, that the database firewall allows the node or NAT gateway IP, since pods are usually SNATed." Follow-ups: "Works from the node but not from the pod?" (NetworkPolicy/CNI), "How do you give it a cluster DNS name?" (ExternalName).

Q54. New pods stay Pending with "0/3 nodes are available: Insufficient cpu, Insufficient memory". Walk me through it.

Short answer

The scheduler could not find a node whose unreserved allocatable capacity fits the pod's requests. Scheduling is based on requests, not on actual usage, so nodes can look idle in kubectl top and still be "full". Fix by right-sizing requests, freeing capacity, or adding nodes – and if an autoscaler exists, find out why it didn't add them.

1. How the scheduler decides

For each pending pod, the scheduler runs a filter phase (which nodes are feasible?) and a score phase (which feasible node is best?). The resource filter is plain arithmetic: 

node allocatable  = capacity − kube-reserved − system-reserved − eviction threshold
free for scheduling = allocatable − Σ requests of pods already on the node

pod fits  ⇔  pod.requests.cpu ≤ free cpu  AND  pod.requests.memory ≤ free memory

Every node that fails a filter is counted in the message, grouped by reason. 0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 Insufficient cpu means: of 3 nodes, 1 was excluded by a taint and 2 lacked CPU. Read the whole line – it is a complete explanation. The message often ends with a preemption: part saying whether evicting lower-priority pods would help.

2. Requests vs usage – why "the cluster looks empty"

$ kubectl top nodes
NAME     CPU(cores)   CPU%   MEMORY(bytes)   MEMORY%
node-1   820m         21%    5100Mi          34%
node-2   760m         19%    4900Mi          33%

$ kubectl describe node node-1 | grep -A6 "Allocated resources"
Allocated resources:
  Resource           Requests       Limits
  --------           --------       ------
  cpu                3800m (97%)    6 (153%)
  memory             13Gi (88%)     18Gi (122%)

Actual usage is 21% but 97% of CPU is reserved by requests. To the scheduler, this node is full. That is by design: requests are a promise that the pod can use that much when it needs to. The usual root cause is inflated requests – teams copy cpu: 1 into every Deployment "to be safe".

3. Diagnostic flow

Pod Pending

 ├─ kubectl describe pod → Events → FailedScheduling message
 │     ├─ Insufficient cpu/memory ─► compare pod requests vs node "Allocated resources"
 │     │      ├─ pod request bigger than ANY node's allocatable?
 │     │      │      └─ it can never fit → reduce request or add a bigger node type
 │     │      └─ nodes full of reservations?
 │     │             ├─ right-size requests (kubectl top pods -A vs requests)
 │     │             ├─ scale down non-essential workloads
 │     │             └─ add nodes / check autoscaler events
 │     ├─ untolerated taint        ─► toleration missing (Q31)
 │     ├─ node affinity/selector   ─► labels or rules too strict
 │     ├─ unbound PVC              ─► storage (Q11)
 │     └─ Too many pods            ─► max pods per node / CNI IP exhaustion
 │
 └─ no pod at all? ─► ReplicaSet events: quota / admission rejection (Q52)

Worked example

3 worker nodes, each 4 vCPU / 16 GiB with allocatable 3.8 CPU / 14.5 GiB. A new report-worker Deployment requests cpu: 2, memory: 4Gi per pod.

Common pitfalls

  • Using kubectl top to judge free capacity – the scheduler uses requests.
  • Comparing with node capacity instead of allocatable (system reservations and DaemonSets eat into it).
  • Ignoring fragmentation – aggregate free capacity doesn't help if no single node has room.
  • Autoscaler "not working" when it is at its max node count, or when no node group has an instance type big enough for the pod.
  • Fixing it by removing requests entirely – pods become BestEffort, nodes get overpacked, and you trade Pending for evictions (Q57).

In the interview

Long term: right-size requests from real usage and use priority classes so critical pods can preempt." Follow-ups: "Nodes are at 20% CPU – how can pods be Pending?", "What is preemption?"

Q55. A pod is in CrashLoopBackOff. What do you do?

Short answer

CrashLoopBackOff is a symptom: the container keeps exiting and the kubelet waits longer and longer between restarts. Get the logs of the previous (crashed) instance, read the last exit code and reason in kubectl describe, check for liveness-probe kills and missing config, and if needed get inside with kubectl debug.

1. What the kubelet is doing

With restartPolicy: Always (the only option for Deployment pods), the kubelet restarts a container every time it exits – even with exit code 0. To avoid hammering the node, it backs off exponentially: 

crash → wait 10s → restart → crash → wait 20s → 40s → 80s → 160s → 300s (cap) …
the back-off resets once the container has run successfully for 10 minutes

While waiting, the pod's status shows CrashLoopBackOff. Between restarts the container briefly shows Running or Error, which is why the status seems to flicker. The pod object stays on the same node – this is a container restart, not a reschedule.

2. Read the exit code

$ kubectl describe pod api-84c9f7d6b-tq5zr
    State:          Waiting
      Reason:       CrashLoopBackOff
    Last State:     Terminated
      Reason:       Error
      Exit Code:    1
      Started:      Sat, 14 Nov 2026 10:02:11 +0000
      Finished:     Sat, 14 Nov 2026 10:02:13 +0000
    Restart Count:  6
Exit code / reasonWhat it usually means
1 (or other app code)The application threw/exited on an error – the logs say why.
0 / CompletedThe process finished. A web server shouldn't "finish": wrong command, or it daemonised into the background.
137 + OOMKilledExceeded the memory limit (Q57).
137 without OOMKilledSIGKILL from outside – very often a failed liveness probe after the grace period.
143Exited on SIGTERM (stopped by the kubelet, e.g. liveness probe, and handled it).
126Command found but not executable (permissions, non-root user can't run it).
127Command not found – wrong command/entrypoint, missing binary in a slim image.

"Started" and "Finished" two seconds apart = a crash on startup (config, dependency). Minutes apart = a runtime crash or a liveness kill.

3. Commands

CommandWhat it actually does
kubectl logs <pod> --previous Logs of the last terminated instance. Without --previous you get the new instance, which may have printed nothing yet.
kubectl describe pod <pod> Last State (exit code, reason, timestamps) and events such as Liveness probe failed.
kubectl get events --field-selector involvedObject.name=<pod> Only that pod's events, in order.
kubectl debug <pod> -it --copy-to=dbg --container=app -- sh Creates a copy of the pod with the container's command replaced by a shell, so you can inspect files and env and run the real command by hand.
kubectl debug -it <pod> --image=busybox --target=app Ephemeral debug container sharing the process namespace – useful when the container stays up long enough between crashes.

4. The usual root causes

  • Configuration: missing ConfigMap/Secret key, wrong env value, bad connection string. The app throws on startup – exit 1 within seconds.
  • A dependency treated as fatal: the app exits if the database isn't reachable at startup. Better: retry with backoff and report not-Ready.
  • Liveness probe too aggressive: a slow starter is killed before it is up – it looks exactly like a crash. Use a startup probe (Q17).
  • Permissions: running as non-root with a file or directory owned by root, or a read-only root filesystem the app tries to write to.
  • Wrong architecture: amd64 image on arm64 nodes – exec format error in the logs.

Worked example

$ kubectl get pods -l app=search
NAME                      READY   STATUS             RESTARTS        AGE
search-6f9c8d7b5-hv2qk    0/1     CrashLoopBackOff   7 (2m10s ago)   14m

$ kubectl logs search-6f9c8d7b5-hv2qk --previous | tail -2
Started search service, warming index cache…
Loading 2.1 GB index into memory

$ kubectl describe pod search-6f9c8d7b5-hv2qk | grep -E "Reason|Exit|Liveness"
      Reason:       Error
      Exit Code:    137
  Warning  Unhealthy  Liveness probe failed: Get "http://10.244.2.8:8080/healthz": context deadline exceeded

Exit 137 but no OOMKilled, and liveness failures in the events: the app needs ~90 s to load its index, but the liveness probe (initialDelaySeconds: 15, failureThreshold: 3, periodSeconds: 10) kills it after ~45 s. Every restart starts the load again – an endless loop. Adding a startupProbe with failureThreshold: 30 and periodSeconds: 5 (up to 150 s to start) fixes it without weakening the liveness probe for normal operation.

Common pitfalls

  • Reading the current logs instead of --previous and seeing nothing.
  • Assuming every 137 is OOM – check the Reason field; a liveness kill also ends with SIGKILL.
  • "Fixing" it by deleting the pod – the replacement crashes the same way.
  • Removing the liveness probe entirely instead of adding a startup probe.
  • Logs that go to a file inside the container instead of stdout – kubectl logs shows nothing useful.

In the interview

"CrashLoopBackOff just means the container keeps exiting and the kubelet is backing off restarts, up to five minutes. I'd get logs --previous, then the Last State in describe – the exit code and reason tell me whether it's an app error, OOM, a liveness kill, or a missing binary. Then config, dependencies and probes. If I need to look inside, kubectl debug with a copy of the pod and a shell." Follow-ups: "Exit code 137 but not OOMKilled?", "Why does it restart even with exit code 0?"

Q56. Pods are Running but not Ready, or the Service returns intermittent 503s.

Short answer

Running but not Ready means the readiness probe is failing, so the pod is kept out of the Service's endpoints – describe the pod to see the probe error. Intermittent 503s mean that, at some moments, a request hits no healthy backend: pods flapping between Ready and NotReady, pods shutting down during deploys, one bad replica, or proxy timeouts and limits.

1. Running vs Ready

StateMeaningGets traffic?
RunningAt least one container process is up.Not necessarily
Ready (1/1)All containers pass readiness; the pod condition Ready=True.Yes – IP is in the EndpointSlice as ready
Running, 0/1Process alive, readiness failing.No

A failing readiness probe never restarts the container – that is liveness. The pod just waits, out of rotation, until the probe passes. So "Running 0/1 for an hour" is readiness, not a crash. 

$ kubectl describe pod web-7c9d8f6b5-m2x8k | grep -A2 Readiness
    Readiness:  http-get http://:8080/ready delay=0s timeout=1s period=5s #success=1 #failure=3
  Warning  Unhealthy  kubelet  Readiness probe failed: Get "http://10.244.1.23:8080/ready":
  dial tcp 10.244.1.23:8080: connect: connection refused

Interpreting the probe error:

  • connection refused – nothing listens on that port/IP: wrong port, or the app binds 127.0.0.1 (the kubelet probes the pod IP).
  • context deadline exceeded – the endpoint is too slow for timeoutSeconds (default 1 s!), often under load or during GC.
  • HTTP probe failed with statuscode: 503 – the app answers "not ready", typically because its readiness checks a dependency that is down.

2. Where intermittent 503s come from

Intermittent 503s
 │
 ├─ only during deploys / scale-down?
 │     └─ graceful-shutdown race: pod gets SIGTERM before routing is updated (Q35)
 │
 ├─ kubectl get pods -w: pods toggling 1/1 ↔ 0/1 under load?
 │     └─ readiness probe on the edge of its 1s timeout → capacity collapses
 │
 ├─ errors concentrated on one pod?  (per-pod metrics / access logs)
 │     └─ one bad replica: bad node, stuck thread pool, stale cache → delete it, investigate
 │
 ├─ RESTARTS increasing?
 │     └─ OOM / liveness kills (Q57, Q55)
 │
 └─ none of the above?
       └─ ingress/gateway: upstream timeout, max connections, keep-alive mismatch

The flapping case is a nasty feedback loop: under load, one pod's /ready takes longer than 1 s → it's removed → the remaining pods get more load → their probes time out too → for a few seconds there are zero endpoints and the proxy returns 503.

3. Commands

CommandWhat it actually does
kubectl get pods -l app=web -w Watches READY changes live – flapping is obvious within a minute under load.
kubectl get endpointslices -l kubernetes.io/service-name=web -o yaml Per-endpoint conditions.ready, serving, terminating – what the proxies actually see.
kubectl describe pod <pod> Probe definition and failure messages.
kubectl get events --field-selector reason=Unhealthy All probe failures in the namespace – reveals whether it's one pod or all.
kubectl logs -n <ingress-ns> <controller-pod> Proxy-side reason: "no healthy upstream", "upstream timed out", connection reset.

Worked example

An API with 6 replicas returns ~2% 503s at peak traffic, never at night. Readiness probe: /ready, timeoutSeconds: 1, failureThreshold: 1; and /ready runs a SELECT 1 against the database. 

$ kubectl get pods -l app=api -w
api-5c7d9-2kq8p   1/1   Running   0   3h
api-5c7d9-2kq8p   0/1   Running   0   3h     ← probe timed out at peak
api-5c7d9-9vt4x   0/1   Running   0   3h
api-5c7d9-2kq8p   1/1   Running   0   3h
api-5c7d9-9vt4x   1/1   Running   0   3h

At peak, the DB connection pool is busy, SELECT 1 waits for a connection, the probe exceeds 1 s, and a single failure removes the pod. Fixes: readiness checks only the process's own ability to serve (no DB round-trip), timeoutSeconds: 3, failureThreshold: 3. The 503s disappear and – as a bonus – the database receives fewer probe queries.

Common pitfalls

  • Leaving timeoutSeconds at its default of 1 s for an endpoint that does real work.
  • failureThreshold: 1 – a single slow GC pause takes a pod out of rotation.
  • Readiness that checks shared dependencies: when the dependency blips, all pods go NotReady at once and the Service has zero endpoints.
  • App listening on localhost – the probe (and the Service) uses the pod IP.
  • Blaming Kubernetes for 503s that only happen during deploys – that's the app's shutdown handling.

In the interview

"Running but not Ready is always the readiness probe – describe shows why: connection refused, timeout or a non-2xx status. For intermittent 503s I'd ask when they happen: only during deploys points to the shutdown race; under load points to probes timing out and pods flapping; one pod points to a bad replica; otherwise the proxy's timeouts and limits. I'd watch READY live and look at the EndpointSlice conditions." Follow-ups: "Does a failing readiness probe restart the container?" (no), "Should readiness check the database?"

Q57. Pods restart during traffic spikes with OOMKilled. Or they get Evicted. What's the difference?

Short answer

OOMKilled is about the container: it used more memory than its own limit, the kernel killed it, and the kubelet restarts it in the same pod on the same node. Evicted is about the node: it ran short of memory, disk or PIDs, so the kubelet removed whole pods – ranked by QoS and usage above requests – and their controllers recreate them elsewhere.

1. Side by side

OOMKilledEvicted
Who actsLinux kernel OOM killer (cgroup limit)kubelet (node-pressure eviction)
TriggerContainer memory ≥ its limits.memoryNode below an eviction threshold (e.g. memory.available<100Mi, nodefs.available<10%)

What happens nextContainer restarted in place; RESTARTS +1Pod phase Failed, reason Evicted; a new pod is created (possibly elsewhere)
Can happen within limits?No – by definition over the limitYes – a pod well within its limit can be evicted
Main fixRight-size the limit or fix the leak/spikeRealistic requests, ephemeral-storage limits, node sizing

2. How each looks

$ kubectl get pods
NAME                     READY   STATUS      RESTARTS      AGE
api-7f8c9d6b4-x2kq9      1/1     Running     5 (3m ago)    2h      ← OOMKilled, restarted in place
worker-5d6c7b8f9-n4r7t   0/1     Evicted     0             41m     ← evicted pod object left behind
worker-5d6c7b8f9-q9z2m   1/1     Running     0             40m     ← its replacement

$ kubectl describe pod api-7f8c9d6b4-x2kq9 | grep -A3 "Last State"
    Last State:     Terminated
      Reason:       OOMKilled
      Exit Code:    137

$ kubectl describe pod worker-5d6c7b8f9-n4r7t | grep -E "Status|Reason|Message"
Status:   Failed
Reason:   Evicted
Message:  The node was low on resource: memory. Threshold quantity: 100Mi, available: 87Mi.
          Container worker was using 2.9Gi, request is 512Mi, has larger consumption of memory.

The eviction message is gold: it names the resource, the threshold, and how far the evicted container was above its request.

3. Eviction order

When a node is under memory pressure, the kubelet ranks pods by:

  1. Whether usage exceeds requests (pods above their requests go first).
  2. Pod priority (lower priority first).
  3. How far usage is above requests.

In practice: BestEffort pods (no requests – any usage is "above") go first, then Burstable pods using far more than they requested. Guaranteed pods (requests = limits) using no more than their requests are the last to go. That is why accurate memory requests are the best protection against eviction (Q21).

Disk pressure works the same way: logs, emptyDir volumes and the writable container layer count as ephemeral storage. A pod writing large temp files can get the node into DiskPressure and get evicted – or other pods evicted with it. Set requests/limits.ephemeral-storage.

4. Why OOMs happen "only during spikes"

  • Per-request memory: large request bodies, file uploads buffered in memory, big query results – 10× traffic = 10× in-flight memory.
  • Unbounded caches or queues that grow with traffic and never shrink.
  • The runtime not sizing itself to the container: modern .NET and JVM read the cgroup limit, but hard-coded heap flags (e.g. -Xmx larger than the limit) or old runtimes don't. Native memory, thread stacks and tmpfs-backed emptyDir (medium: Memory) also count against the limit.
  • The limit was set from average usage, with no headroom for peaks.

Worked example

A node has 16 GiB, allocatable 14.5 GiB. It runs an API (Guaranteed, 2 Gi request = limit), and 6 report workers, each Burstable with requests.memory: 512Mi, limits.memory: 4Gi. The scheduler sees 2 + 6 × 0.5 = 5 Gi reserved – plenty of room.

At month-end all workers process large reports at once and each grows to 2.5 Gi: 2 + 6 × 2.5 = 17 Gi. None exceeds its own 4 Gi limit, so there is no OOMKill – but the node runs out of memory. The kubelet hits memory.available<100Mi and evicts the workers that are furthest above their 512 Mi request. The API, using exactly its request, survives.

Fix: set the workers' requests to their real peak (2.5 Gi) so the scheduler spreads them across nodes, and lower the limit to ~3 Gi. Overcommit (limit ≫ request) is exactly what makes eviction possible.

Common pitfalls

  • Treating both as "out of memory, raise the limit". For eviction, raising the limit makes it worse – the fix is requests.
  • Leaving thousands of Evicted pod objects around – they are kept for inspection until garbage-collected; clean up with kubectl delete pods --field-selector=status.phase=Failed.
  • Memory request far below limit for memory-hungry apps – the common advice is memory request = limit.
  • Forgetting ephemeral storage: DiskPressure evictions caused by logs or temp files.
  • Monitoring only kubectl top: it shows working-set memory at one point in time and misses the spike that triggered the kill.

In the interview

"OOMKilled is the container exceeding its own memory limit – the kernel kills it, exit 137, the kubelet restarts it in place. Eviction is the node running low on memory, disk or PIDs – the kubelet removes pods, BestEffort first, then those furthest above their requests, and they're recreated elsewhere. So OOMs are fixed with the limit or the app; evictions with accurate requests so the scheduler doesn't overpack nodes." Follow-ups: "Can a pod be evicted while under its limit?" (yes), "Which QoS class is safest?" (Guaranteed).

Q58. ImagePullBackOff / ErrImagePull – what's wrong?

Short answer

The kubelet on the node could not pull the image. The exact registry error is in kubectl describe pod and tells you which case it is: wrong name or tag, missing credentials or permissions, registry rate limiting, no network path to the registry, or no image for the node's CPU architecture.

1. ErrImagePull vs ImagePullBackOff

They are the same problem at two moments. ErrImagePull is shown right after a pull attempt fails. The kubelet then retries with an exponential back-off (up to 5 minutes), and while it waits the status is ImagePullBackOff. The pod is scheduled – this is entirely between the node (kubelet + container runtime) and the registry. The API server and your kubectl credentials play no part, which is why "I can pull it on my laptop" proves little. 

kubelet on node-3
  │ resolve registry.example.com      ← node DNS
  │ HTTPS to registry                 ← node network: NAT, proxy, private endpoint
  │ authenticate                      ← imagePullSecrets or node identity (IAM)
  │ fetch manifest for tag 2.3.1      ← does the tag exist?
  │ pick the entry for linux/arm64    ← multi-arch index must include node's arch
  ▼ pull layers → containerd unpacks → container can start

2. Read the error message

Message in Events (abridged)Cause
failed to resolve reference "…/api:2.3.1": not found Typo in repository or tag, or the CI never pushed that tag.
pull access denied, repository does not exist or may require authorization / 401 Unauthorized / 403 Forbidden Private registry without valid credentials: no imagePullSecrets, secret in the wrong namespace, expired token, or the node's cloud identity lacks pull permission.
429 Too Many Requests / toomanyrequests Registry rate limit – typically anonymous Docker Hub pulls from many nodes behind one NAT IP.
dial tcp …:443: i/o timeout / no such host Node can't reach the registry: private cluster without NAT/private endpoint, proxy, firewall, DNS.
no match for platform in manifest The image has no variant for the node's OS/architecture (amd64-only image on arm64 nodes).
x509: certificate signed by unknown authority Private registry with an internal CA that the node's container runtime doesn't trust.

3. Commands and fixes

CommandWhat it actually does
kubectl describe pod <pod> | grep -A10 Events Shows the exact image reference used and the registry error.
kubectl get pod <pod> -o jsonpath='{.spec.imagePullSecrets}' Which pull secrets the pod actually has (they can also come from its ServiceAccount).
kubectl create secret docker-registry regcred --docker-server=registry.example.com --docker-username=… --docker-password=… -n shop Creates a pull secret – it must be in the same namespace as the pod.
kubectl patch sa default -n shop -p '{"imagePullSecrets":[{"name":"regcred"}]}' Attaches the secret to a ServiceAccount, so every pod using it gets the secret automatically.
docker manifest inspect registry.example.com/shop/api:2.3.1 From your machine: does the tag exist, and which platforms does it contain?
kubectl debug node/<node> -it --image=busybox then chroot /host crictl pull … Reproduces the pull from the node itself, with the node's network and runtime.

kind: Pod

  name: api
  namespace: shop
spec:
  imagePullSecrets:
    - name: regcred                  # docker-registry Secret in namespace "shop"
  containers:
    - name: api

On managed clouds, prefer node or workload identity over static pull secrets: grant the node role pull rights on ECR/ACR/Artifact Registry and the kubelet's credential provider fetches short-lived tokens automatically.

Worked example

The team adds a cheaper arm64 node pool. Pods of one service land there and never start; the same pods on amd64 nodes are fine. 

$ kubectl get pods -o wide -l app=pdf
NAME                   READY   STATUS             NODE

The image was built for amd64 only. Short term: add a nodeSelector kubernetes.io/arch: amd64 to the Deployment. Real fix: build a multi-arch image (docker buildx build --platform linux/amd64,linux/arm64 --push).

Common pitfalls

  • The pull secret exists – in another namespace. Secrets are namespaced.
  • Testing the pull on a laptop that is logged in to the registry, then concluding "the image is fine" – the node has different credentials and network.
  • Relying on anonymous Docker Hub pulls in production; a scale-out event across many nodes hits the rate limit. Mirror critical images or use a pull-through cache.
  • Mutable tags with IfNotPresent: some nodes run a cached old image under the same tag (pin by digest – see the Docker page).
  • Expired registry tokens stored as static Secrets (e.g. short-lived cloud registry tokens).

In the interview

"ErrImagePull is the failure, ImagePullBackOff is the kubelet waiting before it retries. It's always between the node and the registry, so I read the exact error in describe: not found means name or tag; unauthorized means pull secrets or node IAM; 429 means rate limiting; timeouts mean network; 'no match for platform' means architecture. To prevent it: multi-arch images, a mirror or pull-through cache, and node identity instead of static secrets." Follow-ups: "Where must the pull secret live?", "Why does it work on some nodes but not others?"

Q59. A node becomes NotReady. What happens to its pods?

Short answer

When the kubelet stops reporting, the node controller marks the node NotReady/Unknown and taints it with a NoExecute taint. Pods tolerate that taint for 300 seconds by default; after that they are deleted and their controllers create replacements on healthy nodes. StatefulSet pods and RWO volumes need extra care, and DaemonSet pods are not moved at all.

1. The timeline

t = 0      kubelet on node-2 stops renewing its Lease (crash, network cut, power loss)
             (healthy kubelets renew a Lease in kube-node-lease about every 10s)
t ≈ 40-50s node-monitor-grace-period expires
             → node condition Ready = Unknown (or False if the kubelet reports NotReady)
             → taint node.kubernetes.io/unreachable:NoExecute (or not-ready:NoExecute)
             → pods on the node get condition Ready=False → removed from Service endpoints
t ≈ 5m     default tolerationSeconds: 300 expires for each pod
             → pods are marked for deletion (Terminating)
             → ReplicaSet sees too few pods → creates replacements → scheduled elsewhere
node never comes back?  pods stay "Terminating" until the node object is deleted
                        or the node returns and the kubelet confirms they're gone

Two important consequences. First, traffic stops quickly (within the grace period) because the pods go NotReady and leave the EndpointSlices. Second, capacity is reduced for about 5 minutes, because replacements are created only after the toleration expires – so you need enough replicas on other nodes to cover that window.

The 300 s comes from a default toleration added to every pod by the DefaultTolerationSeconds admission plugin. You can override it per workload: 

tolerations:
  - key: node.kubernetes.io/unreachable
    operator: Exists
    effect: NoExecute
    tolerationSeconds: 60     # move this stateless app after 1 minute
  - key: node.kubernetes.io/not-ready
    operator: Exists
    effect: NoExecute
    tolerationSeconds: 60

Shorter means faster recovery but more churn during brief network blips; don't go to near zero.

2. Why StatefulSets behave differently

Kubernetes cannot tell whether an unreachable node is dead or just partitioned – the pod may still be running and writing to its disk. A Deployment doesn't care: two copies of a stateless pod are harmless. A StatefulSet guarantees at most one db-0; starting a second one while the first might still write to the same volume risks data corruption. So the StatefulSet controller waits until the old pod is really gone – which never happens on its own if the node never returns.

A human (or automation that knows the node is dead) must break the tie:

CommandWhat it actually does
kubectl get nodes / kubectl describe node node-2 Node conditions, taints, last heartbeat time, and which pods are on it.
kubectl taint nodes node-2 node.kubernetes.io/out-of-service=nodeshutdown:NoExecute Non-graceful node shutdown: you declare the node is really off. Pods are force-deleted and their volumes detached, so StatefulSet pods and RWO volumes can move.
kubectl delete node node-2 Removes the node object; its pods are garbage-collected and controllers replace them.
kubectl delete pod db-0 --grace-period=0 --force Removes the pod object without waiting for the kubelet. Only safe if you are sure the node is powered off or isolated.
kubectl drain node-2 --ignore-daemonsets --delete-emptydir-data For planned maintenance (node still reachable): evicts pods respecting PDBs.

3. Volumes and DaemonSets

  • RWO volumes (block disks) can only be attached to one node. The cloud may still consider the disk attached to the dead node, so the replacement pod waits with a Multi-Attach error until the attachment is released – the out-of-service taint speeds this up.
  • DaemonSet pods tolerate the unreachable/not-ready taints without a time limit and are never moved – there is one per node by design.

4. Diagnosing the node

kubectl describe node shows conditions and the last heartbeat. On the node (SSH or kubectl debug node/... if the API can still reach it): systemctl status kubelet, journalctl -u kubelet, container runtime status, disk full, memory exhaustion, expired kubelet client certificates, and network connectivity to the API server.

Worked example

A 3-node cluster loses node-2 (hardware failure) at 09:00. It runs 2 of 6 web replicas and postgres-0 (StatefulSet, RWO disk). 

$ kubectl get nodes
NAME     STATUS     ROLES    AGE
node-1   Ready      <none>   90d
node-2   NotReady   <none>   90d
node-3   Ready      <none>   90d

$ kubectl get pods -o wide        # at 09:06
NAME                  READY   STATUS        NODE
web-5f7c8-2kd9q       1/1     Terminating   node-2
web-5f7c8-8xq3m       1/1     Running       node-1   ← replacement
web-5f7c8-vt6p2       1/1     Running       node-3   ← replacement
postgres-0            1/1     Terminating   node-2   ← no replacement
  • 09:00:45 – node NotReady; web pods on node-2 leave the endpoints. 4 of 6 replicas serve traffic.
  • 09:05:45 – tolerations expire; 2 new web pods start on node-1/node-3. Back to 6.
  • postgres-0 stays Terminating. After confirming in the cloud console that node-2 is off, the operator applies the out-of-service taint; the disk is detached, and postgres-0 starts on node-3 about a minute later.

Common pitfalls

  • Expecting pods to move immediately – the default is about 5 minutes.
  • Running only 2 replicas on 2 nodes and losing half the capacity for the whole window; spread replicas and keep headroom.
  • Force-deleting a StatefulSet pod while the node might still be alive – split brain on the database.
  • Single-replica databases on node-local or RWO storage with no plan for node loss.
  • Setting tolerationSeconds: 0 so a short network blip reschedules everything.

In the interview

"The node controller marks the node NotReady after the grace period and adds a NoExecute taint. Pods go NotReady, so traffic stops, but they are only deleted after the default 300-second toleration; then ReplicaSets create replacements elsewhere. StatefulSet pods aren't replaced automatically because Kubernetes can't prove the old one is dead – I'd confirm the node is off and use the out-of-service taint or delete the node. DaemonSet pods don't move." Follow-ups: "How can you make stateless pods move faster?" (tolerationSeconds), "Why not force-delete right away?"

Q60. How do you deploy to Kubernetes in production? What is GitOps?

Short answer

Not with kubectl apply from a laptop. With GitOps, the desired state of each cluster lives in git, and an agent inside the cluster (Argo CD or Flux) continuously pulls it and reconciles the cluster to match. CI only builds, tests and pushes images, then updates the image tag in git. Every change is reviewed and auditable, rollback is a git revert, and drift is detected and corrected.

1. Push vs pull deployment

CI pushes (kubectl/helm in pipeline)GitOps pull (agent in cluster)
Who talks to the API serverThe CI runner, with cluster credentialsAn agent inside the cluster
Source of truthWhatever the last pipeline appliedThe git repository
Manual change in the clusterStays until the next deploy (drift)Detected; reverted if self-heal is on
RollbackRe-run an old pipeline / rollout undogit revert
AuditPipeline logsGit history + pull-request reviews

The security point matters: with push, every CI system that deploys needs powerful credentials for every cluster. With pull, the cluster only needs read access to git and the registry; nothing outside holds cluster-admin.

2. The end-to-end flow

developer ── PR ──► app repo (code + Dockerfile)
                        │ CI: build, test, scan, sign
                        ▼
                  registry: shop/api:2.3.1 (immutable tag or digest)
                        │ CI or an image-updater bot opens a PR:
                        ▼
                  config repo:  envs/staging/api/values.yaml  tag: 2.3.1
                        │ merge
                        ▼
      Argo CD / Flux in the staging cluster
        1. polls git (or gets a webhook)
        2. renders Helm / Kustomize
        3. diffs rendered manifests vs live objects
        4. applies the difference → Deployment rolls out (Q18)
        5. reports Synced + Healthy
                        │ promotion = another PR: envs/prod/api/values.yaml  tag: 2.3.1
                        ▼
      prod cluster syncs the same way

Environments are usually directories (or overlays) in the config repo: a Helm chart with per-environment values files, or a Kustomize base with per-environment overlays. Promotion is just a PR that changes the tag in the next environment's directory.

3. What it looks like in Argo CD

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: api-prod
  namespace: argocd
spec:
  project: shop
  source:
    repoURL: https://git.example.com/platform/config.git
    targetRevision: main
    path: envs/prod/api          # Helm chart or Kustomize overlay
  destination:
    server: https://kubernetes.default.svc
    namespace: shop
  syncPolicy:
    automated:
      prune: true                # delete objects removed from git
      selfHeal: true             # revert manual changes (drift)
    syncOptions:
      - CreateNamespace=true
ConceptWhat it actually does
SyncApply git's rendered manifests to the cluster.
OutOfSyncLive objects differ from git – a new commit, or someone changed the cluster by hand.
selfHealAutomatically re-applies git when the live state drifts.
pruneDeletes resources that were removed from git; without it they linger.
HealthArgo CD's view of whether resources are working (Deployment rolled out, pods Ready).

Flux expresses the same ideas with a GitRepository (where to pull from) and a Kustomization or HelmRelease (what to apply and how often).

4. Secrets and progressive delivery

  • Secrets never go to git in plain text (base64 is not encryption, Q8). Options: SOPS-encrypted files that Flux/Argo decrypt, Sealed Secrets (encrypted for one cluster's key), or External Secrets Operator where git holds only a reference to the secret in Vault or a cloud secret manager.
  • Progressive delivery: GitOps decides what should run; Argo Rollouts or Flagger decide how to shift traffic – canary steps, metric analysis, automatic abort (Q35).

Worked example

Version 2.3.1 of the API reaches production at 10:00 through a merged PR. At 10:07 error rates climb.

  1. An engineer runs kubectl rollout undo deploy/api. The cluster now runs 2.3.0 – but Argo CD sees the live Deployment differs from git (which says 2.3.1), marks it OutOfSync, and because selfHeal is on, re-applies 2.3.1 within minutes. The errors come back.
  2. Correct fix: git revert the promotion commit (or merge a PR setting the tag back to 2.3.0). Argo CD syncs, the Deployment rolls back, and the history shows who rolled back, when, and why.
  3. Some teams allow an emergency path: temporarily disable auto-sync for that Application, roll back by hand, then fix git – but the fix must end up in git, or the next sync undoes it.

Common pitfalls

  • Rolling back or "hot-fixing" with kubectl while self-heal is on – GitOps reverts it.
  • Using :latest or other mutable tags in git – the config repo no longer describes what runs; use immutable tags or digests.
  • Plain Secrets committed to the config repo.
  • prune disabled forever: renamed or deleted resources keep running in the cluster.
  • Mixing code and environment config in one repo, so every app commit triggers syncs and promotion history is buried in code history.
  • Treating "Synced" as "working" – sync only means applied; check Health and the rollout status.

In the interview

"CI builds, tests, scans and pushes an immutable image, then updates the tag in a config repo through a PR. An agent in the cluster – Argo CD or Flux – pulls that repo and reconciles the cluster to it. So git is the source of truth, every change is reviewed, rollback is a revert, drift is corrected automatically, and CI doesn't need cluster credentials. Packaging is Helm or Kustomize per environment, secrets via SOPS or External Secrets, and canaries via Argo Rollouts." Likely follow-ups: "How do you roll back?" (git revert, not rollout undo), "How do you promote between environments?", "How do you handle secrets?"
