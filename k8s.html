Kubernetes Interview – 60 Questions

From basics to cluster administration and production troubleshooting scenarios. Container fundamentals (images, Dockerfiles, PID 1, signals) are on the Docker page.

1. Basics

Q1. What are the components of a Kubernetes cluster?

Control plane:

  • kube-apiserver – the only component that talks to etcd; every client and component goes through it (authn, authz, admission, validation).
  • etcd – consistent key-value store holding the entire cluster state. Back it up (Q39).
  • kube-scheduler – assigns unscheduled pods to nodes.
  • kube-controller-manager – runs the controllers (Deployment, ReplicaSet, Node, Job, EndpointSlice…).
  • cloud-controller-manager – cloud integrations (load balancers, node lifecycle, routes).

Every node: kubelet (makes the pods assigned to its node actually run, reports status), the container runtime (containerd/CRI-O), and usually kube-proxy (Service networking) plus a CNI plugin for pod networking.

The core idea: everything is a reconciliation loop – controllers continuously compare desired state (in etcd) with actual state and act to close the gap.

Q2. What happens, end to end, when you run kubectl apply on a Deployment?

  1. kubectl sends the manifest to the API server, which authenticates, authorises (RBAC), runs admission controllers/webhooks (mutation, validation, policy), and stores the Deployment in etcd.
  2. The Deployment controller notices it and creates a ReplicaSet.
  3. The ReplicaSet controller creates Pod objects – with no node assigned yet.
  4. The scheduler sees unscheduled pods, filters nodes that fit (resources, taints, affinity, volumes), scores them, and binds each pod to a node.
  5. The kubelet on that node sees the pod, asks the runtime to pull the image and start containers, the CNI plugin sets up networking, volumes are mounted.
  6. Probes run; when readiness passes, the pod's IP is added to the matching Service's EndpointSlices, and kube-proxy/the dataplane starts routing traffic to it.

No component calls another directly – they all watch the API server and react. That's why the system self-heals.

Q3. What is a Pod, and why does Kubernetes schedule pods, not containers?

A Pod is the smallest deployable unit: one or more containers that share a network namespace (same IP, talk over localhost), can share volumes, and are always scheduled together on the same node. It is the unit for things that must live together – an app plus a log shipper, proxy, or config reloader. 

apiVersion: v1
kind: Pod
metadata:
  name: my-pod
spec:
  containers:
    - name: nginx
      image: nginx:1.27
      ports:
        - containerPort: 80

Pods are ephemeral and get a new IP each time they are created. You almost never create bare pods in production – a controller (Deployment, StatefulSet, Job…) creates and replaces them for you.

Q4. What is kubectl, and which commands do you use daily?

kubectl is the CLI for the Kubernetes API. Everything it does is a REST call to the API server, authenticated with the credentials in your kubeconfig (kubectl config get-contexts shows which cluster you are pointed at – check it before destructive commands). 

kubectl get pods -o wide                 # list pods with node and IP
kubectl describe pod <pod>              # spec, status and Events
kubectl logs <pod> [-c container] [-f]  # container logs
kubectl exec -it <pod> -- sh            # shell inside a container
kubectl apply -f manifest.yaml           # declarative create/update
kubectl get events --sort-by=.lastTimestamp
kubectl explain deployment.spec.strategy # built-in API docs

Prefer declarative apply of files kept in git over imperative create/edit – and in production, let GitOps do the applying (Q60).

Q5. What is a Deployment?

A Deployment manages stateless, interchangeable replicas. You declare the desired state (image, replica count, pod template); the Deployment creates a ReplicaSet, which keeps exactly that many pods running. It gives you self-healing (a dead pod is replaced), scaling, rolling updates and rollbacks (Q18). 

apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
          ports:
            - containerPort: 80

The selector must match the template's labels, and it is immutable after creation.

Q6. What is a Service, and why is it needed?

Pods come and go and their IPs change, so clients cannot talk to pod IPs directly. A Service gives a group of pods – selected by labels – a stable virtual IP and DNS name, and load-balances connections across the pods that are currently Ready. 

apiVersion: v1
kind: Service
metadata:
  name: my-service
spec:
  type: ClusterIP
  selector:
    app: my-app
  ports:
    - protocol: TCP
      port: 80          # port of the Service
      targetPort: 8080  # port the container listens on

A selector that matches no pods is the classic "service has no endpoints" bug; check with kubectl get endpointslices -l kubernetes.io/service-name=my-service.

Q7. What Service types are there?

  • ClusterIP (default) – stable virtual IP and DNS name reachable only inside the cluster.
  • NodePort – opens the same port (30000–32767) on every node, forwarding to the service.
  • LoadBalancer – asks the cloud provider for an external load balancer pointing at the service.
  • ExternalName – DNS CNAME to an external host; no proxying.
  • Headless (clusterIP: None) – no virtual IP; DNS returns the individual pod IPs. Used by StatefulSets and clients that do their own load balancing.

For HTTP traffic from outside, you normally use one LoadBalancer in front of an Ingress or Gateway controller (Q19–Q20) instead of one load balancer per service.

Q8. ConfigMap vs Secret – and are Secrets actually secret?

Both inject configuration as env variables or mounted files, keeping config out of the image. ConfigMap is for non-sensitive data; Secret is for credentials. 

apiVersion: v1
kind: ConfigMap
metadata:
  name: my-config
data:
  DATABASE_HOST: "db.example.com"
---
apiVersion: v1
kind: Secret
metadata:
  name: my-secret
type: Opaque
stringData:            # plain text in; stored base64-encoded
  DB_PASSWORD: "s3cr3t"

But a Secret is only base64-encoded, not encrypted – anyone who can read it via the API, or read etcd, has the value. What actually protects secrets:

  • Encryption at rest for etcd (Q46) – on by default on most managed clusters, verify it.
  • RBAC – tightly restrict get/list/watch on secrets; list returns the values too.
  • An external secret store (Vault, AWS Secrets Manager, Azure Key Vault) synced via External Secrets Operator or the Secrets Store CSI driver.
  • Never commit raw Secret manifests to git – use Sealed Secrets/SOPS or the external store.

Also: env-variable values are read once at start; mounted files are updated (eventually) when the Secret/ConfigMap changes, but the app still has to re-read them.

Q9. What are Namespaces?

A namespace is a logical partition of one cluster: a scope for names, and the boundary to which RBAC, ResourceQuotas, LimitRanges and NetworkPolicies are applied. Typical split: per team, per app, or per environment. 

kubectl create namespace dev
kubectl run nginx --image=nginx -n dev
kubectl get pods -n dev
kubectl config set-context --current --namespace=dev   # change default

Namespaces are not a security boundary by themselves: pods in different namespaces can still talk to each other unless a NetworkPolicy blocks it, and they share nodes and the kernel. Some objects are cluster-scoped (Nodes, PersistentVolumes, ClusterRoles, StorageClasses).

Q10. What are labels and selectors?

Labels are key/value pairs on objects (app: nginx, env: prod). Selectors filter objects by labels. They are how Kubernetes wires things together: a Deployment finds its pods, a Service finds its endpoints, a NetworkPolicy or PDB finds the pods it applies to – all by label selector, never by name. 

kubectl get pods -l env=prod
kubectl get pods -l 'env in (prod,staging),tier!=frontend'

Annotations look similar but are not selectable – they hold non-identifying metadata for tools (build info, ingress controller settings).

Q11. Explain PV, PVC and StorageClass. Why is my pod Pending on a volume?

  • PersistentVolumeClaim – the app's request: "10 GiB, ReadWriteOnce, class fast-ssd".
  • PersistentVolume – the actual piece of storage bound to that claim, outliving any pod.
  • StorageClass – how to provision PVs dynamically via a CSI driver (disk type, reclaim policy, binding mode). With dynamic provisioning you only write the PVC. 
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data
spec:
  accessModes: ["ReadWriteOnce"]
  storageClassName: fast-ssd
  resources:
    requests:
      storage: 10Gi

Access modes: RWO (one node), ROX, RWX (many nodes – needs NFS/file storage, most block disks can't do it), RWOP (one pod).

Common Pending causes: no default StorageClass; a zonal disk in zone A while the pod can only schedule in zone B (fix with volumeBindingMode: WaitForFirstConsumer, so the disk is created where the pod lands); RWO volume still attached to the old node during a rollout (multi-attach error – use Recreate strategy or a StatefulSet). Check events on the PVC and pod, and the CSI driver's logs. Also check reclaimPolicy: Delete means deleting the PVC deletes the data.

2. Networking, Config, Resources, Rollouts

Q12. How does Kubernetes networking work?

The Kubernetes network model has a few simple rules:

  • Every pod gets its own IP; containers in a pod share it.
  • Every pod can reach every other pod on any node without NAT (a flat network). The CNI plugin (Calico, Cilium, cloud VPC CNIs…) implements this.
  • Services provide stable virtual IPs and DNS names in front of changing pod IPs (Q13); CoreDNS resolves them (Q49).
  • Ingress / Gateway API bring external HTTP(S) traffic in (Q19–Q20).
  • NetworkPolicies restrict the default allow-all (Q26).

Q13. How does a ClusterIP actually route traffic? Nothing listens on that IP.

Correct – the ClusterIP is virtual. The endpoint controller maintains EndpointSlices listing the IPs of ready pods behind each Service. kube-proxy on every node watches Services and EndpointSlices and programs the kernel – iptables, IPVS, or nftables rules (nftables mode is GA since 1.33) – to DNAT packets addressed to the ClusterIP:port to one of the backing pod IPs.

Some CNIs (e.g. Cilium) replace kube-proxy entirely with eBPF. Either way, the load balancing is per connection, not per request – which is why long-lived connections (gRPC, HTTP/2, keep-alive) can pile onto one pod and need client-side or L7 (mesh/gateway) balancing.

Q14. How does RBAC work, and how do pods authenticate to the API and the cloud?

RBAC is allow-only: Role (namespaced) / ClusterRole (cluster-wide) list verbs on resources; RoleBinding / ClusterRoleBinding grant them to users, groups, or ServiceAccounts. There are no deny rules – least privilege means granting little, not revoking. 

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader-binding
  namespace: dev
subjects:
  - kind: User
    name: jane
    apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io

Test with kubectl auth can-i list pods -n dev --as jane.

Pods run as a ServiceAccount and get a short-lived, auto-rotated projected token. Good practice: one ServiceAccount per app, automountServiceAccountToken: false for apps that never call the API, never bind cluster-admin to workloads, and remember that list secrets, create pods, and escalate/bind/impersonate are effectively privilege escalation.

For cloud access, use workload identity (IRSA / EKS Pod Identity, Azure Workload Identity, GKE Workload Identity): the ServiceAccount is federated to a cloud role, so there are no long-lived cloud keys stored in Secrets.

Q15. HPA, VPA, Cluster Autoscaler – how do they fit together? Traffic doubled but HPA didn't scale – why?

  • HPA – changes the number of replicas based on metrics (CPU/memory utilisation, custom or external metrics). KEDA extends this with event sources like queue length and scale-to-zero.
  • VPA – recommends or sets requests/limits per pod (size, not count).
  • Cluster Autoscaler / Karpenter – adds nodes when pods are Pending for lack of capacity, removes underused nodes. 
kubectl autoscale deployment nginx --cpu-percent=50 --min=2 --max=10

# equivalent manifest
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: nginx
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: nginx
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50

Don't let HPA and VPA both act on CPU/memory for the same workload – they fight.

HPA didn't scale – usual reasons:

  • No metrics: metrics-server not installed, or kubectl get hpa shows <unknown>.
  • No CPU requests set – utilisation is a percentage of requests, so it can't be computed.
  • Already at maxReplicas.
  • Wrong signal: the service is I/O-bound or thread-pool-starved, so CPU stays low while latency explodes – scale on RPS, latency or queue depth instead.
  • It did scale, but new pods are Pending (no node capacity) or slow to become Ready.

Q16. How do you debug a failing pod?

Work from the outside in:

kubectl get pod <pod> -o wide          # status, restarts, node
kubectl describe pod <pod>              # Events, Last State, exit code
kubectl logs <pod> --previous           # logs of the crashed instance
kubectl exec -it <pod> -- sh            # look around inside
kubectl get events -n <ns> --sort-by=.lastTimestamp
kubectl get pods -A --field-selector=status.phase=Failed

If the image has no shell (distroless), attach an ephemeral debug container that shares the target's process namespace: 

kubectl debug -it <pod> --image=busybox --target=<container>
kubectl debug node/<node> -it --image=busybox   # debug the node itself

The status tells you where to look: Pending → scheduling (Q54), CrashLoopBackOff → the app (Q55), ImagePullBackOff → the registry (Q58), Running but not Ready → readiness probe (Q56).

Q17. Liveness vs readiness vs startup probes – and how can a probe cause an outage?

  • Readiness – "can I receive traffic now?" Failing removes the pod from Service endpoints; the container is not restarted.
  • Liveness – "am I stuck beyond recovery?" Failing restarts the container. For deadlocks and hung processes.
  • Startup – "have I finished starting?" Disables the other probes until it passes; for slow-starting apps. 
containers:
  - name: api
    image: my-api:2.1
    startupProbe:
      httpGet: { path: /healthz, port: 8080 }
      failureThreshold: 30
      periodSeconds: 2       # up to 60s to start
    livenessProbe:
      httpGet: { path: /healthz, port: 8080 }
      periodSeconds: 10
    readinessProbe:
      httpGet: { path: /ready, port: 8080 }
      periodSeconds: 5

The outage pattern: a liveness probe that checks a dependency (the database). The database blips, every pod fails liveness at once, Kubernetes restarts the whole fleet, the cold-starting pods hammer the recovering database – a self-inflicted outage. Rules: liveness checks only the process itself (cheap, local, no dependencies); dependencies belong in readiness if anywhere; give probes realistic timeouts and thresholds; use a startup probe instead of a huge initialDelaySeconds. A too-aggressive liveness probe on a slow starter produces a restart loop that looks exactly like an application crash.

Q18. How does a rolling update work, and how do you roll back?

The Deployment creates a new ReplicaSet and shifts pods across gradually, controlled by:

  • maxSurge – how many extra pods above the desired count during the update.
  • maxUnavailable – how many may be unavailable. maxUnavailable: 0 + maxSurge: 1 = never drop below capacity. 
kubectl set image deployment/my-app app=my-app:1.4.2
kubectl rollout status deployment/my-app
kubectl rollout history deployment/my-app
kubectl rollout undo deployment/my-app                 # previous revision
kubectl rollout undo deployment/my-app --to-revision=3

Only pods that pass readiness count as available, so a broken version stalls rather than replacing everything – if readiness is meaningful. minReadySeconds adds a soak time. Old ReplicaSets are kept for rollback, per revisionHistoryLimit; in a GitOps setup, rollback is a git revert instead.

Q19. What is an Ingress, and how does it work?

An Ingress is an API object for L7 HTTP(S) routing from outside the cluster to Services, by host and path, with TLS termination. The Ingress resource does nothing on its own – an Ingress controller (a reverse proxy running in the cluster, usually behind one LoadBalancer Service) watches Ingress objects and configures itself. 

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-ingress
spec:
  ingressClassName: nginx
  tls:
    - hosts: ["app.example.com"]
      secretName: app-tls
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: my-service
                port:
                  number: 80

Its weakness: the spec is minimal, so anything advanced (rewrites, timeouts, canary, auth) lives in controller-specific annotations and configs aren't portable between controllers.

Q20. What is the Gateway API, how is it different from Ingress – and what happened to ingress-nginx?

Gateway API is the successor to Ingress: role-oriented resources (GatewayClass for the infra provider, Gateway for the platform team, HTTPRoute/GRPCRoute for app teams), with header matching, traffic splitting (canary, A/B), and cross-namespace routing in the spec instead of annotations. It also covers TCP/UDP/TLS routes and service-mesh traffic. 

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: my-app
spec:
  parentRefs:
    - name: public-gateway
  hostnames: ["app.example.com"]
  rules:
    - backendRefs:
        - name: my-app-v1
          port: 80
          weight: 90
        - name: my-app-v2
          port: 80
          weight: 10

2026 currency point: the community ingress-nginx controller was retired in March 2026 – no further releases or security fixes. The Kubernetes project recommends migrating to Gateway API or another controller. Note the distinction: the Ingress API itself is not removed, only that popular controller.

Q21. Requests vs limits – and what are QoS classes?

Requests are what the scheduler reserves: a pod only lands on a node with enough unreserved allocatable capacity, and under contention the pod is guaranteed that share. Limits are the hard ceiling enforced at runtime. 

resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    memory: "256Mi"

QoS classes come from how you set them, and decide eviction order under node memory pressure:

  • Guaranteed – every container has CPU and memory requests = limits. Evicted last.
  • Burstable – some requests/limits set but not equal.
  • BestEffort – nothing set. Evicted first.

Requests that are too low cause overcommitted nodes and noisy neighbours; too high wastes money. Base them on observed usage.

Q22. What happens when a container exceeds its limits?

The two resources behave differently because memory is not compressible and CPU is:

  • Memory over the limit → the kernel OOM killer kills the container (exit code 137, reason OOMKilled); the kubelet restarts it according to the pod's restartPolicy. Repeated OOMs show up as CrashLoopBackOff.
  • CPU over the limit → the container is throttled, not killed. The app keeps running but slower – often visible only as latency spikes.

Different from both: eviction, where the node runs short and the kubelet removes pods even if they are within their limits (Q57).

Q23. Should you set CPU limits?

It is a real debate, and the senior answer explains the mechanism. CPU limits are enforced by CFS quota per time period: a multi-threaded app can burn its whole quota in the first part of the 100ms period and then be throttled for the rest – causing latency spikes even when the node has idle CPU and average usage looks well under the limit.

A common production stance: always set memory requests and limits (memory is not compressible – usually request = limit), set CPU requests accurately, and omit or set generous CPU limits for latency-sensitive services, since requests already guarantee each pod its share under contention. Keep CPU limits where you need hard isolation (multi-tenant, batch, cost control). Watch the container_cpu_cfs_throttled_periods_total metric either way.

Q24. What are init containers, and when should you use them?

Init containers run to completion, one after another, before the app containers start. If one fails, the pod restarts it (per restartPolicy) and the app never starts until all succeed. Use them for preparation that must finish first: database migrations, waiting for a dependency, fetching config or certificates, fixing volume permissions – using tools you don't want in the app image. 

spec:
  initContainers:
    - name: wait-for-db
      image: busybox:1.36
      command: ["sh", "-c", "until nc -z db 5432; do sleep 2; done"]
  containers:
    - name: app
      image: my-app:1.0

Caveat: "wait for dependency" init containers only help at startup; the app must still tolerate the dependency disappearing later.

Q25. What is a PodDisruptionBudget, and how do you keep apps highly available?

A PDB limits how many pods of an application may be down at once due to voluntary disruptions – node drains, cluster upgrades, autoscaler scale-down. kubectl drain uses the eviction API, which refuses to evict if it would violate the PDB (minAvailable or maxUnavailable). 

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: my-app-pdb
spec:
  maxUnavailable: 1
  selector:
    matchLabels:
      app: my-app

It does not protect against involuntary disruptions (node crash, OOM). And misconfigured PDBs can block operations: minAvailable equal to the replica count, or a PDB on a single-replica deployment, means a drain hangs forever and cluster upgrades stall.

Application HA as a whole: at least 2–3 replicas, spread across nodes and zones (topology spread constraints / anti-affinity, Q31), a PDB, and meaningful readiness probes.

Q26. What is a NetworkPolicy, and why might yours do nothing?

By default every pod can talk to every other pod in the cluster. A NetworkPolicy selects pods by label and whitelists allowed ingress and/or egress (by pod selector, namespace selector, or IP block). Once any policy selects a pod for a direction, everything not explicitly allowed in that direction is denied. 

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: team-a
spec:
  podSelector: {}        # all pods in the namespace
  policyTypes: ["Ingress"]

Why it might do nothing: NetworkPolicy is enforced by the CNI plugin; if your CNI doesn't support it (e.g. plain flannel), the objects are accepted and silently ignored.

Common pattern: a default-deny policy per namespace, then explicit allows. And the classic mistake with egress default-deny: forgetting to allow DNS (UDP/TCP 53 to CoreDNS), so everything breaks with name-resolution errors.

3. Advanced Workloads and Extensibility

Q27. What is a StatefulSet, and how does it differ from a Deployment?

  • Deployment – stateless, interchangeable replicas; pods have random names, can be replaced anywhere, and share any volume they mount.
  • StatefulSet – stable identity: ordered, predictable names (db-0, db-1), stable DNS per pod via a headless Service (db-0.db.ns.svc.cluster.local), and a dedicated PersistentVolumeClaim per replica (from volumeClaimTemplates) that follows the pod across rescheduling. Pods are created, updated and deleted in order.

Use it for databases, Kafka, ZooKeeper-style clustered systems. But the hard part of running a database is not Kubernetes – it is backups, failover, and upgrades. That is why operators (Q37) or managed databases are usually the better answer.

Q28. What is a DaemonSet, and when would you use it?

A DaemonSet runs exactly one pod per (matching) node. When a node joins, the pod is added automatically; when the node leaves, the pod goes with it. Typical uses: log collectors (Fluent Bit), monitoring agents (node-exporter), CNI and CSI node plugins, security agents. 

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: log-collector
spec:
  selector:
    matchLabels:
      app: log-collector
  template:
    metadata:
      labels:
        app: log-collector
    spec:
      tolerations:
        - operator: Exists      # also run on tainted (e.g. control plane) nodes
      containers:
        - name: fluent-bit
          image: fluent/fluent-bit:3.2
          resources:
            limits:
              memory: 200Mi

Use a nodeSelector or affinity to target a subset of nodes (e.g. only GPU nodes for a GPU driver plugin).

Q29. Jobs and CronJobs – what should you know?

A Job runs pods to completion: completions, parallelism, backoffLimit for retries, activeDeadlineSeconds as a timeout, and ttlSecondsAfterFinished to clean up. A CronJob creates Jobs on a schedule.

Production details interviewers like:

  • concurrencyPolicy: Forbid so a slow run doesn't overlap the next one; startingDeadlineSeconds for missed schedules.
  • Jobs can run more than once (retries, node failure) – make them idempotent.
  • Set timeZone on the CronJob explicitly instead of relying on the controller's clock.

Q30. What is a service mesh, and why use one?

A service mesh moves service-to-service concerns from application code into the infrastructure layer:

  • Security – automatic mTLS between services, identity-based authorisation.
  • Traffic management – retries, timeouts, circuit breaking, per-request (L7) load balancing, canary splits.
  • Observability – uniform metrics, traces and access logs for every call.

Examples: Istio (sidecar or sidecar-less "ambient" mode), Linkerd, Cilium. The cost is operational complexity and some latency/resource overhead – adopt it when you actually need mTLS everywhere or fine-grained traffic control, not by default.

Q31. How do you control where pods run? Taints, tolerations, affinity, topology spread.

  • nodeSelector / node affinity – the pod is attracted to nodes with certain labels (GPU, zone, instance type); required or preferred.
  • Taints and tolerations – the node repels pods unless they tolerate the taint. Used to dedicate nodes (GPU pool, system pool). A toleration only allows; to force pods onto those nodes you also need affinity.
  • Pod (anti-)affinity – place pods near or away from other pods (e.g. not two replicas on one node).
  • Topology spread constraints – spread replicas evenly across zones/nodes with a max skew. The modern, more flexible way to get high availability across zones. 
kubectl taint nodes gpu-node-1 dedicated=gpu:NoSchedule

# in the pod spec
tolerations:
  - key: "dedicated"
    operator: "Equal"
    value: "gpu"
    effect: "NoSchedule"

Taint effects: NoSchedule, PreferNoSchedule, and NoExecute (also evicts running pods that don't tolerate it). Too many hard (required) rules is the classic source of mysteriously Pending pods.

Q32. What are sidecar containers, and how are they used?

A sidecar is a helper container in the same pod as the app, sharing its network and volumes. Typical uses: log shipping, a service-mesh proxy (Envoy), config/secret reloaders, auth proxies. 

spec:
  containers:
    - name: app
      image: my-app
      volumeMounts:
        - name: logs
          mountPath: /var/log/app
    - name: log-shipper
      image: fluent/fluent-bit:3.2
      volumeMounts:
        - name: logs
          mountPath: /var/log/app
          readOnly: true
  volumes:
    - name: logs
      emptyDir: {}

Before native sidecars, these were just regular containers – which caused the lifecycle problems in Q33.

Q33. What are native sidecars, and what problem do they solve?

With plain containers, Kubernetes had no idea which container was the helper: the app could start before its proxy was ready (and fail its first requests), a Job never finished because its proxy sidecar kept running, and a sidecar could die before the app finished shutting down.

Native sidecars are init containers with restartPolicy: Always (GA in 1.33): they start before the app containers (and can gate them with a startup probe), keep running alongside them, and are stopped after them. 

spec:
  initContainers:
    - name: proxy
      image: envoyproxy/envoy:v1.32
      restartPolicy: Always    # this makes it a sidecar
  containers:
    - name: app
      image: my-app

Q34. What are admission webhooks and admission policies?

Admission control runs inside the API server after authentication and authorisation, before an object is persisted to etcd:

  • Mutating admission – can change the object: inject sidecars, add default labels, resources or security settings.
  • Validating admission – can only accept or reject: enforce policies (no latest tag, required labels, allowed registries, signed images).

Webhooks call an external HTTPS service; Kyverno and OPA Gatekeeper are built on them. For simple rules, the in-process, CEL-based ValidatingAdmissionPolicy (GA in 1.30) avoids running a webhook server at all.

Operational risk: a webhook with failurePolicy: Fail whose backend is down blocks every matching API request – including the pods that would fix it. Scope webhooks narrowly, exclude kube-system, and monitor their latency.

Q35. How do you achieve zero-downtime deployments? Why do users still get errors during a rolling update?

Strategies: rolling update (default), blue/green (run the full new version alongside the old one and switch traffic at once, with instant switch-back), and canary (send a small percentage of traffic to the new version and widen it if metrics stay healthy – Argo Rollouts, Flagger, or Gateway API weights).

Even with a rolling update, users often see errors because graceful shutdown is a race. When a pod is deleted, two things happen in parallel: the kubelet sends SIGTERM to the container, and the endpoint controller removes the pod from EndpointSlices, which then has to propagate to every node's kube-proxy and to ingress controllers/load balancers. If the app exits immediately on SIGTERM, traffic is still being routed to it for a few seconds → connection refused / 502s.

Fixes:

  • Meaningful readiness probes so new pods only get traffic when ready.
  • A preStop hook that sleeps a few seconds (newer versions have a built-in sleep action) so routing updates before shutdown starts.
  • The app handles SIGTERM: stop accepting new connections, finish in-flight requests, then exit.
  • terminationGracePeriodSeconds (default 30s) must cover preStop + drain time, or the pod is SIGKILLed.
  • Make sure the process actually receives SIGTERM (exec form, see the Docker page, Q12).

Q36. What are Custom Resource Definitions (CRDs)?

A CRD adds a new resource type to the Kubernetes API. Once installed, you can kubectl get, RBAC-protect, watch and store custom objects exactly like built-in ones. On its own a CRD is just data – it needs a controller (Q37) to make it do something. 

apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: databases.example.com
spec:
  group: example.com
  scope: Namespaced
  names:
    plural: databases
    singular: database
    kind: Database
  versions:
    - name: v1
      served: true
      storage: true
      schema:
        openAPIV3Schema:
          type: object
          properties:
            spec:
              type: object
              properties:
                engine: { type: string }
                storageGB: { type: integer }

Then kubectl get databases. Real examples: cert-manager's Certificate, Argo CD's Application, Prometheus Operator's ServiceMonitor.

Q37. What is an operator, and how does it work?

An operator = CRDs + a custom controller that encodes operational knowledge for one piece of software. Like built-in controllers, it runs a reconciliation loop: watch the custom resources (and the objects it owns), compare desired with actual state, and act – create StatefulSets, take backups, perform failover, run version upgrades in the right order.

Examples: CloudNativePG and other database operators, Strimzi (Kafka), Prometheus Operator, cert-manager. Built with Kubebuilder / Operator SDK (Go) or other frameworks. Good operators are idempotent and level-based – they react to current state, not to individual events.

Q38. What is in-place pod resize?

Historically, changing a pod's CPU or memory meant deleting and recreating it. Since Kubernetes 1.35 in-place pod resize is GA: you can change a running container's resources via the pod's resize subresource without recreating the pod. Each container's resizePolicy says whether a given resource can change live (NotRequired) or needs a container restart (RestartContainer) – memory changes often need a restart because the app sized itself at startup.

Why it matters: rightsizing without restarts, giving extra CPU during startup then shrinking it, and VPA's InPlaceOrRecreate mode, which uses it. The scheduler still has to fit the new size on the current node – if it doesn't fit, the resize stays pending.

4. Cluster Administration

Q39. How do you back up and restore etcd?

etcd holds the entire cluster state, so on self-managed clusters it must be backed up regularly and the restore rehearsed. (On managed services – EKS, AKS, GKE – the provider owns etcd; you back up workloads and volumes with tools like Velero instead.) 

# snapshot
etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /backup/etcd-$(date +%F).db

# restore into a new data directory
etcdutl snapshot restore /backup/etcd-2026-11-14.db \
  --data-dir /var/lib/etcd-restored

Then point the etcd static pod manifest at the new data directory. Store snapshots off the node and encrypted – they contain every Secret.

Q40. How do you upgrade a cluster safely?

  • Read the release notes and deprecation guide – removed APIs are the main breakage. Scan manifests and Helm releases for deprecated API versions (pluto, kubent) before upgrading.
  • Back up etcd (self-managed) and rehearse in a staging cluster first.
  • One minor version at a time; control plane first, then nodes. Respect version skew (kubelet may lag the API server by a limited number of minors, never be newer).
  • Upgrade add-ons (CNI, CSI, ingress/gateway controllers, cert-manager) to versions that support the target.
  • Nodes: surge in new nodes, or cordon and drain old ones one at a time; PDBs (Q25) keep apps available – and a broken PDB will block you. 
# kubeadm, on the first control-plane node
kubeadm upgrade plan
kubeadm upgrade apply v1.35.x
# then on each node: drain, upgrade kubeadm/kubelet, uncordon
kubectl drain node-1 --ignore-daemonsets --delete-emptydir-data
kubeadm upgrade node
systemctl restart kubelet
kubectl uncordon node-1

Current examples worth knowing: the dockershim removal (1.24), PSP removal (1.25), and cgroup v1 support removed in 1.35 – nodes on old OS images still using cgroup v1 must be migrated to cgroup v2 before upgrading. Kubernetes ships three minors a year with roughly 14 months of support each, so upgrading must be routine, not a project.

Q41. How do you monitor a cluster?

  • Metrics: Prometheus (often via kube-prometheus-stack) scraping node-exporter, kube-state-metrics, cAdvisor/kubelet and app metrics; Grafana dashboards; Alertmanager for alerts. metrics-server is separate – it only feeds kubectl top and HPA.
  • Traces: OpenTelemetry instrumentation with Jaeger or Tempo.
  • Logs: see Q42.

What to alert on: symptoms users feel (error rate, latency, saturation), plus cluster health – nodes NotReady, pods crash-looping or Pending, PVCs filling up, certificate expiry, failed Jobs, CPU throttling, and control-plane/etcd latency on self-managed clusters.

Q42. How do you set up logging?

Containers log to stdout/stderr; the runtime writes those to files on the node, and kubectl logs reads them – but they are lost when the pod is deleted or the node goes away. So you ship them centrally:

  • A DaemonSet agent on every node (Fluent Bit, Grafana Alloy, OpenTelemetry Collector) tails container log files and adds Kubernetes metadata (namespace, pod, labels).
  • A backend: Loki + Grafana (lightweight, label-indexed, cheap) or Elasticsearch/OpenSearch + Kibana (full-text indexing, heavier).

Apps should log structured JSON to stdout, not to files inside the container. Enable API server audit logs separately for security investigations.

Q43. How do you prevent pods from running privileged or as root?

At the pod level, a securityContext:

securityContext:
  runAsNonRoot: true
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  capabilities:
    drop: ["ALL"]
  seccompProfile:
    type: RuntimeDefault

At the cluster level, enforce it: PodSecurityPolicy was removed in 1.25; its replacement is Pod Security Admission, enforcing the Pod Security Standards (privileged, baseline, restricted) via namespace labels, with warn/audit modes for gradual rollout: 

kubectl label namespace team-a \
  pod-security.kubernetes.io/enforce=restricted \
  pod-security.kubernetes.io/warn=restricted

For custom rules (allowed registries, required labels, signed images), use a policy engine – Kyverno, OPA Gatekeeper, or built-in ValidatingAdmissionPolicy (Q34).

Q44. How do you secure a Kubernetes cluster overall?

Think in layers – the "4C" model: Cloud, Cluster, Container, Code.

  • Cloud / infrastructure – private API endpoint or restricted IP ranges, least-privilege IAM, encrypted disks, nodes not reachable from the internet.
  • Cluster – RBAC with least privilege (Q14), Pod Security Admission (Q43), NetworkPolicies default-deny (Q26), etcd encryption (Q46), audit logs, regular upgrades (Q40), rotated certificates and tokens.
  • Container – minimal, scanned, signed images from trusted registries; non-root, read-only filesystem, no privileged pods.
  • Code – secrets from a secrets manager, never in images or git; dependency scanning; mTLS between services where needed (Q30).

Add runtime detection (Falco, Tetragon) to catch what prevention misses, e.g. a shell spawned in a production container.

Q45. How do you make the cluster itself highly available?

  • Control plane: 3 (or 5) control-plane nodes across zones behind a load balancer for the API server. The API server is stateless; the scheduler and controller-manager run active/standby via leader election.
  • etcd: odd number of members; it needs a quorum (majority), so 3 members tolerate 1 failure, 5 tolerate 2. Even numbers add no fault tolerance.
  • Nodes: worker pools across multiple zones, Cluster Autoscaler or Karpenter, spare capacity for losing a zone.
  • Workloads: replicas spread across zones (Q31), PDBs (Q25), multiple CoreDNS replicas.

Managed services give you an HA control plane; you still own node and workload HA. For region-level failure, you need multiple clusters.

Q46. How do you encrypt Secrets at rest in etcd?

By default Secrets are stored in etcd unencrypted (just base64). On self-managed clusters, give the API server an EncryptionConfiguration: 

apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources: ["secrets"]
    providers:
      - kms:                 # preferred: key held in an external KMS
          apiVersion: v2
          name: my-kms
          endpoint: unix:///var/run/kms-plugin.sock
      - aescbc:              # or a local key (key lives on the node)
          keys:
            - name: key1
              secret: <BASE64_32_BYTE_KEY>
      - identity: {}         # read old unencrypted data

Pass it with --encryption-provider-config in the kube-apiserver manifest. The first provider encrypts new writes; the others are only used to read. Existing Secrets stay unencrypted until rewritten: 

kubectl get secrets -A -o json | kubectl replace -f -

Managed clusters encrypt etcd by default; many also support envelope encryption with your own KMS key.

Q47. Several teams share one cluster. How do you stop one team affecting another?

  • Namespaces per team/app as the boundary for RBAC and policy.
  • ResourceQuota – caps total CPU/memory/objects per namespace (Q48).
  • LimitRange – default and max requests/limits per container, so nobody deploys BestEffort pods by accident.
  • RBAC scoped to their namespaces only.
  • NetworkPolicies – default-deny between namespaces.
  • Priority classes so critical workloads preempt batch jobs, not the other way round.
  • Dedicated node pools (taints) for noisy or sensitive workloads.

Namespaces are soft multi-tenancy – they share the control plane and kernel. For untrusted tenants (hard multi-tenancy), use separate clusters, virtual clusters (vCluster), or sandboxed runtimes (gVisor, Kata).

Q48. ResourceQuota vs LimitRange?

ResourceQuota limits the total a namespace may consume; LimitRange sets defaults and min/max per container/pod. They work together: once a quota covers CPU/memory, every new pod must declare requests/limits or it is rejected – a LimitRange fills in defaults so that doesn't break deployments. 

apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-a-quota
  namespace: team-a
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.memory: 16Gi
    pods: "20"
---
apiVersion: v1
kind: LimitRange
metadata:
  name: defaults
  namespace: team-a
spec:
  limits:
    - type: Container
      defaultRequest: { cpu: 100m, memory: 128Mi }
      default: { memory: 256Mi }

Check usage with kubectl describe resourcequota -n team-a. Quota rejections show up on the ReplicaSet's events, not the Deployment's – a common "why are no pods created?" trap.

Q49. How does DNS (CoreDNS) work, and why might lookups be slow?

CoreDNS runs as a Deployment in kube-system and serves records like my-svc.my-namespace.svc.cluster.local. Pods get a resolv.conf pointing at it, with search domains so you can just use my-svc within a namespace. Its configuration (the Corefile) is a ConfigMap: kubectl -n kube-system get configmap coredns -o yaml – e.g. to add stub domains or forwarders for corporate DNS.

Gotcha: the default ndots:5. Any name with fewer than five dots (e.g. api.example.com) is first tried with every search domain appended – several failing lookups (times A and AAAA) before the real one. Under load that multiplies DNS traffic and adds latency, and conntrack races on UDP can cause occasional 5-second timeouts. Mitigations: use FQDNs with a trailing dot for external names, lower ndots in dnsConfig, NodeLocal DNSCache, and scale CoreDNS.

5. Production Scenarios

Q50. An application in Kubernetes has become slow. How do you investigate?

  1. Scope it: all pods or one? all endpoints or one? since when – a deploy, a traffic spike, a node change?
  2. Resources: kubectl top pods --sort-by=cpu / --sort-by=memory. Check CPU throttling metrics, not just usage (Q23), and restarts/OOMs.
  3. Pod details: kubectl describe pod – restarts, probe failures, recent events; kubectl logs for timeouts and connection errors.
  4. Dependencies and network: test latency from inside a pod to the database and downstream services; check DNS latency (Q49).
  5. Nodes: kubectl top nodes, kubectl describe node – memory/disk pressure, noisy neighbours, an overloaded node hosting several replicas.
  6. Scaling: is the HPA at max or not scaling (Q15)?

Traces and per-pod latency dashboards usually answer this faster than kubectl – they show which hop is slow.

Q51. Nginx pods are Running, but the application is unreachable via its URL. What do you check?

Follow the traffic path inward and test each hop:

  1. Pod: Ready? Listening on the expected port, on 0.0.0.0? Test with kubectl port-forward pod/<pod> 8080:80.
  2. Service: does the selector match the pod labels, and does targetPort match the container port? kubectl get endpointslices -l kubernetes.io/service-name=nginx – empty means selector/readiness problem. Test with kubectl port-forward svc/nginx 8080:80.
  3. NetworkPolicy: is ingress from the ingress controller's namespace allowed?
  4. Ingress/Gateway: correct ingressClassName/parent gateway, host and path; the controller's logs and the route's status conditions.
  5. Outside the cluster: does the LoadBalancer have an external IP (not <pending>)? Does DNS point at it? Do firewalls / security groups allow the port? Is the TLS certificate valid?

Q52. A new version was deployed and fails to start, or the rollout is stuck. How do you investigate and recover?

kubectl rollout status hangs; after progressDeadlineSeconds (default 600s) the Deployment gets the condition ProgressDeadlineExceeded – but Kubernetes does not roll back automatically.

  1. Restore service first: kubectl rollout undo deployment/my-app (or a git revert in GitOps).
  2. kubectl rollout history and a diff of the manifests – what actually changed (image, config, env, resources)?
  3. Look at the new ReplicaSet's pods: CrashLoopBackOff (Q55), ImagePullBackOff (Q58), failing readiness (Q56), Pending for capacity (with maxUnavailable: 0 you need room for surge pods).
  4. A quota or admission webhook rejecting the new pods (shown on the ReplicaSet events).

Long term: alert on ProgressDeadlineExceeded, or use progressive delivery (Argo Rollouts/Flagger) that aborts automatically on bad metrics.

Q53. A microservice can't connect to an external database outside the cluster. How do you fix it?

  1. DNS: kubectl exec -it <pod> -- nslookup db.example.com. Failing → CoreDNS forwarding/upstream config, or an egress NetworkPolicy blocking port 53.
  2. TCP connectivity: kubectl exec -it <pod> -- nc -zv db.example.com 5432 (or from a kubectl debug container if the image has no tools).
  3. Egress NetworkPolicies in the namespace – a default-deny egress policy blocks everything not explicitly allowed.
  4. Outside the cluster: the database's firewall / security group must allow the cluster's egress IPs (node IPs or the NAT gateway), not the pod IPs; routing/peering for private networks.
  5. Application level: credentials from the Secret, TLS requirements, connection-pool exhaustion or max-connections on the database.

Tip: an ExternalName Service (or a Service with manual EndpointSlices) gives the external database a stable in-cluster name.

Q54. New pods stay Pending with "0/3 nodes are available: Insufficient cpu, Insufficient memory". Walk me through it.

Pending = not scheduled yet (or, after scheduling, waiting on volumes/images). kubectl describe pod – the Events section almost always states the reason:

  • Insufficient cpu/memory – requests don't fit any node's allocatable (not raw capacity). Note that scheduling uses requests, not actual usage: kubectl top nodes may look idle while every node is fully reserved – compare with kubectl describe node → "Allocated resources".
  • node(s) had untolerated taint – missing toleration.
  • didn't match Pod's node affinity/selector or topology spread – rules too strict.
  • unbound immediate PersistentVolumeClaims – storage problem (Q11).
  • Too many pods per node (max pods / IP exhaustion in the CNI).

Fixes for capacity: right-size over-inflated requests (biggest consumers via kubectl top pods -A vs their requests), scale down non-essential workloads, add nodes or check why the autoscaler isn't adding them (max size reached, no instance type fits the pod). If the pod doesn't exist at all, it's not a scheduling problem – look at the ReplicaSet events (often a ResourceQuota or admission webhook rejection).

Q55. A pod is in CrashLoopBackOff. What do you do?

CrashLoopBackOff means the container keeps starting and exiting, and the kubelet is backing off restarts (exponentially, up to 5 minutes). It's a symptom, not a cause.

  1. kubectl logs pod --previous – logs of the crashed instance, not the new one that's backing off.
  2. kubectl describe pod – Last State: exit code and reason. 1 = app error; 137 + OOMKilled = memory limit; 137 without OOM = killed (often failed liveness probe); 127 = command not found; 126 = permission.
  3. Check events for liveness probe failures – a too-aggressive liveness probe on a slow starter looks exactly like a crash loop.
  4. Check config: missing ConfigMap/Secret keys, wrong env, unreachable dependency the app treats as fatal at startup.
  5. To get inside: kubectl debug with an ephemeral container, or a copy of the pod with the command overridden to sleep.

Q56. Pods are Running but not Ready, or the Service returns intermittent 503s.

Running but not Ready: the readiness probe is failing. kubectl describe pod shows the probe failure messages. Typical causes: wrong port/path, probe timeout too short, readiness checking a dependency that is down, app listening on 127.0.0.1 instead of 0.0.0.0.

Intermittent 503s:

  • Some pods flapping between Ready and NotReady (probe on the edge of its timeout under load).
  • Errors only during deploys/scale-down → graceful shutdown race (Q35).
  • One bad pod behind the Service – check per-pod error rates; kubectl get endpointslices to see what's actually behind it.
  • Ingress/gateway timeouts or upstream connection limits.
  • Pods being CPU-throttled or OOM-restarting under load.

Q57. Pods restart during traffic spikes with OOMKilled. Or they get Evicted. What's the difference?

OOMKilled (exit 137): the container exceeded its own memory limit; the kernel kills it and the kubelet restarts it in place. Fix: right-size the limit, or find the leak/spike (large request bodies, unbounded caches, runtime not respecting the cgroup limit).

Evicted: the node is under pressure (memory, disk/ephemeral storage, PIDs). The kubelet evicts pods to protect the node – BestEffort first, then Burstable pods using the most above their requests. The pod is terminated and (if owned by a controller) recreated elsewhere. Fix: set realistic requests so the scheduler doesn't overpack nodes, set ephemeral-storage requests/limits, clean up log/temp file growth.

Q58. ImagePullBackOff / ErrImagePull – what's wrong?

  • Typo in image name or tag, or the tag was never pushed.
  • Private registry without credentials: missing imagePullSecrets, or the node identity lacks pull permission (ECR/ACR/GAR IAM).
  • Registry rate limiting (e.g. anonymous Docker Hub pulls) – use a pull-through cache or mirror.
  • Network: nodes can't reach the registry (private cluster without NAT or private endpoint).
  • Architecture mismatch: arm64 nodes with an amd64-only image – no matching manifest.

kubectl describe pod shows the exact registry error. Pre-building multi-arch images and mirroring critical images into your own registry removes most of these.

Q59. A node becomes NotReady. What happens to its pods?

The kubelet stops reporting; the node controller marks the node NotReady/Unknown and adds a NoExecute taint (node.kubernetes.io/unreachable or not-ready). Pods have a default toleration of 300 seconds for these taints, so after ~5 minutes they are marked for deletion and controllers create replacements on healthy nodes. Tune it per workload with tolerationSeconds.

Nuances:

  • StatefulSet pods are not replaced while the old one is stuck Terminating on an unreachable node – Kubernetes can't prove it's dead, and running two db-0s would break the identity guarantee. Requires human action (confirm the node is gone, then delete the node or force-delete the pod).
  • RWO volumes may stay attached to the dead node, delaying the replacement pod.
  • DaemonSet pods are not rescheduled elsewhere (by design).

Diagnose the node itself: kubelet logs, container runtime, disk/memory pressure, network to the API server, expired certificates.

Q60. How do you deploy to Kubernetes in production? What is GitOps?

Not kubectl apply from a laptop. GitOps: the desired state of the cluster lives in git; an agent in the cluster (Argo CD or Flux) continuously pulls and reconciles the cluster to match. CI builds and pushes the image, then updates the image tag in the config repo (by PR or bot).

Benefits: every change is reviewed and audited in git, rollback is a revert, drift (manual changes) is detected and corrected, and CI doesn't need cluster-admin credentials because the cluster pulls instead of CI pushing. Packaging is usually Helm charts or Kustomize overlays per environment. Secrets don't go in git in plain form (Q8).
